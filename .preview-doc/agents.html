The base roster · four agents in the box

Four base agents ship by default — the rest is a sub-agent layer + packs

There's one user: you. The roster (see blueprint / delegation) is base agents vs a sub-agent layer of workers. Four base agents ship in the box — chat targets, with their own connection, heartbeat and durable memory. Max is retired from base: automation is now a platform surface (Automations), available as an optional pack. Specialists and the Maker/creative set arrive via marketplace agent packs.

⭐ Mia · the Assistant

Default. Your memory-rich personal front door — bound to My Workspace, runs your tasks · email · calendar, knows you across workspaces. owner = you.

🧭 Jim · the Orchestrator

Planner / PM. Supervises work across the tasks · blocked_by DAG and the delegation graph — Max-parallel fan-out, worktrees.

🔭 Ray · Scout

Research & summarize. Fans out reads, distils findings; the canonical delegation target for "go find out".

🛠️ Ava · the Builder

Agent & skill authoring (unchanged). Shapes new custom agents and skills from templates.

Beyond the base four: sub-agent workers (the tier below) do the labour, and marketplace agent packs — Maker/creative · ops · smart-home · domain specialists — extend the roster on demand. The split is base agents vs sub-agent workers; there is no fixed "5 cores".
Mia · your Assistant

The Assistant is yours — auto-provisioned, the ⭐ default

Mia is a base agent auto-provisioned for you at onboarding ("meet your Assistant" in My Workspace), seeded from a built-in template, then named and shaped by you. She's the ⭐ default chat target.

🤝 Yours, by ownership

  • A base agent you own (owner = you, attribution) — auto-provisioned at onboarding
  • Seeded from a built-in Assistant template, then fully yours — name · tone · model · tools
  • The ⭐ default agent on a fresh install

🏠 Bound to My Workspace

  • Bound to your My Workspace; runs your email · calendar · tasks
  • The assistant binding = this agent owns your My Workspace (a pre-seeded workspace)
  • Wired to your delegated connections

🧠 Cross-workspace recall

  • Its agent-global private room spans your workspaces — it knows you for free
  • It also reads the shared rooms of the workspaces it works in
  • No special store: the two-room spec already gives this
The sub-agent layer · executors

Below the base agents: sub-agent workers

Workers do the labour. They're not chat targets (the test-run button is the exception) — they're spawned by delegation and carry an executor.

⚙️ Worker characteristics

  • The seeded general-purpose worker + your custom workers
  • No heartbeat · no own connection · ephemeral memory · depth-limited · leaner model · not chat targets (test-run button excepted)
  • Ephemeral, task-driven; no user-facing persona
  • Soul is optional (may be left empty). At invocation the worker's effective prompt = soul.md (if any) + the task prompt submitted by the caller — composed the same way for every executor (native · external-cli · future remote-a2a).
  • Narrow recall: the current workspace's shared room (+ its own private room)

🔌 executor

  • native — runs in-process on the agent loop
  • external-cli — Claude Code · opencode · Codex driven as a child process
  • future: remote-a2a — a remote agent over agent-to-agent
Deferred to v0.2.0 — observable sub-agent sessions. A delegated worker run should be a first-class, inspectable entry in the session history, with delegation lineage (parent_id · depth · owner) so the call-tree renders — including external-CLI child runs as their own session rather than text merged into the caller's transcript. In v0.1.0 a worker run is folded into its caller's session (only task_create yields a discrete session); first-class sub-agent session visibility + lineage lands in v0.2.0.

Safety

High blast-radius — handled by existing gates

Delegated access

An agent acting with the user's Google creds is powerful. Calendar/email write actions sit behind the existing allow / ask / deny per-agent policy; reads (free/busy, triage) are low-risk.

Untrusted inbound

Inbound email is a command surface → sender allowlist + DMARC/SPF (not raw From). Same Rule-2 ownership gating already in place.

Isolation

The present gate is owner ownership — canAccess (#406, rest_projects.go:75) — so an agent only reaches data in workspaces it owns. Per-workspace kernel isolation is the target (the sandbox-redesign design, unimplemented); today isolation is per-agent-workspace, not per-workspace.
