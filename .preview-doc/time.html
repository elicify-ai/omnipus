Calendar & Automations

The Calendar is a workspace tab (alongside Chat · Board · List · Graph · Team · Settings) showing the workspace's scheduled and recurring tasks. It was previously an orphan route — it is now a first-class view in the workspace task UI. Tasks are the unified model: Board/List/Graph/Calendar are four views over one task store. Time triggers (once / every / recurring / manual) fire in v0.1.0 via the existing cron scheduler engine. The separate Automations screen is removed — scheduling is now scheduled tasks with triggers, surfaced on the Calendar view.

The friendly view

Calendar — workspace task tab + import

All (default) + 4 category filters · the sidebar workspace switcher · imported & delegated calendars overlay read-only.

① iCal subscribe v0.2

Paste a .ics URL → read-only overlay, server-refreshed. Zero credentials. Pure-Go: golang-ical + rrule-go. Deferred to v0.2.

② Provider OAuth two-way

Google (then MS Graph): free/busy for agents + write-back. syncToken + watch webhooks (7-day renewal).

③ CalDAV self-host

Nextcloud / Fastmail / iCloud. Lower priority — vendor quirks, poll-based.

The unified task model carries a trigger field ({kind: once|every|cron}) and a due deadline. A recurring task = a task with an every or cron trigger — each fire spawns a fresh run. The Calendar is the view for these scheduled/recurring tasks; Board is for one-shot work. The existing cron scheduler engine already fires these triggers today. Expand RRULE against the IANA tz database — DST is the #1 calendar bug. iCal subscribe deferred to v0.2; provider OAuth (CalDAV/Google) to v1.0.
Decision: Automations screen removed

Scheduling dissolves into Tasks

The separate Automations screen is removed. Scheduling is now tasks with triggers — a task carries a trigger field (once / every / recurring / manual) and the cron scheduler engine fires it. The Calendar view is the home for scheduled/recurring tasks. Heartbeat = a recurring-trigger task per Main agent (surface: heartbeat, hidden from the board, shown in the agent profile). The Trigger → Action concepts below describe the underlying engine that powers tasks and heartbeats — not a separate Automations UI.

Triggers — "when…"

  • ⏰ Time — every Mon 9am · cron · interval engine exists
  • ⚡ Event — task done · run failed · milestone due bus exists
  • 📥 Connection received — email · webhook · message seam exists
  • 🗓️ Calendar — event starts / nears new

Actions — "…do this"

  • 🤖 Run an agent exists
  • 📋 Run / create a task new link
  • 🛠️ Invoke a tool / MCP MCP today
  • 📤 Send via a connection · 📡 webhook-out · 🔔 notify
The lowest-friction first event: task_status_changed is already defined in the contract with no producer — a ready slot. schedule_failed is already a live event. Heartbeat = a surface: heartbeat recurring task per Main agent — hidden from board/calendar general views, shown only in the agent profile. v0.1.0 time triggers only (once/every/cron/manual); event triggers (on_task, webhook, on_condition) are v0.3.

Scheduled tasks and heartbeats are created by the user or by agents (Mia) from chat ("want me to do this every morning?") and run by the platform's cron scheduler engine — there is no separate automation agent (no Forge / Max persona). The Automations sidebar entry is removed; the Task Board + Calendar is the home.

Working memory · v0.3

The agent scratchpad is also a task

If scheduling dissolves into tasks, so does the agent's in-session planning. There is no separate "scratchpad" store — the agent's working todo list rides on the same task substrate, behind a one-tool facade.

One tool: plan

  • The agent sets its full current todo list [{text, status}] in one call — replace, not append (it rewrites the list, so no todo IDs are needed).
  • Agent-unaware task creation: the first call auto-creates a scratchpad-flagged task for that agent and reuses it. The agent never sees a task_id, never calls task_create for its own planning — it just "sets its plan."
  • Read-on-write: returns the updated list, so the agent always sees its plan (no separate read tool).
  • Replaces the append-only task_add_todo dead-end (you could add a todo but never tick it off, edit, or remove it).

Promotion, not a second path

  • A scratchpad task is hidden (not on the board), session-scoped, agent-owned.
  • When the work is delegated or committed, the same record is promoted to a real board task — the flag flips, no copy, no re-creation. It is then delegatable, schedulable (trigger), and visible.
  • Fleeting plans stay hidden and clean up at session end; durable work persists.
  • Jim plans (scratchpad) → delegates (promote + assign to Ava) → Ava works it with her own scratchpad for sub-steps.
One record type (a task with todos), one store, one lifecycle. The agent's scratchpad, the board task, and the scheduled task are the same thing with different flags — not three parallel systems. Retires task_add_todo (→ plan), task_add_dependency (→ folded into task_update), and cron (→ scheduled tasks via task.Trigger + heartbeat).

Substrate: Todo {Text, Status} (pending/in_progress/completed); SetTodos(taskID, []Todo) full-replace; a scratchpad task flag. Open for the ADR: promotion trigger (implicit-on-delegate vs explicit commit vs operator) and scratchpad retention (clean up vs retain-as-audit). See docs/internal/design/tasks-system-refactor-2026-06.md + the Tool Catalog tasks section.
