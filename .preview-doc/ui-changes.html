Screen 1 · the frame

Global shell & navigation

The top-level surface map binds context to the existing sidebar workspace switcher, adds a few renames that reflect the new model, and two new shells.

As-is exists

Top-level screens: Chat, Agents, Channels, Skills, Tools, Monitor (with Schedules + Token Usage), Tasks/Projects, Command Center, Settings.

To-be

Context comes from the existing sidebar workspace switcher — My Workspace (default) vs a named workspace — not a new mode. Channels → Connectors. Monitor/Schedules reframed as Automations. A new Calendar surface. Settings gains tabs.

When: workspace-switcher context + renames + Calendar/Automations shells = v0.1.0

Screen 1b · first run

Onboarding

A single-user first-run flow that ends by introducing the agent that's yours.

As-is exists

Technical bring-up: a bearer-token / admin-bypass path (--allow-empty, dev_mode_bypass) — no guided setup, no password, no first agent.

To-be

A 3-step guided flow: 1. "What should I call you?" (your name) → 2. set one password → 3. add a model key. Then it auto-provisions your Assistant in My Workspace — "meet your Assistant". Single user, one password throughout.

Screen 2 · the home surface

Chat

Chat-first stays. The fragmented run indicators collapse into one timeline.

As-is exists

Chat-first. A handoff agent-switch indicator; spawned subagents render as a collapsible SubagentBlock; tool calls visible & collapsible.

To-be

A unified call-tree activity view — handover + delegation + tasks in one timeline. The current workspace in context. Plus multimodal: a mic (voice-in), a ▶ play per agent message (its own voice), and inline generated images.

When: basic activity view (surfacing what exists) v0.1.0  ·  richer v1.0.0

Screen 3 · the roster

Agents

The roster splits into base agents vs sub-agent workers — and, for the first time, a place to see and edit who delegates to whom.

As-is exists

Agent list, create, profile, ★ default. No delegation UI at all.

To-be

Two roster sections. Base agents — the 4 cores (Mia·Assistant⭐ · Jim·Orchestrator · Ray·Scout · Ava·Builder) + your custom agents (chat targets, own connection, heartbeat, durable memory); specialists / Maker arrive via marketplace packs. Sub agents — the seeded general-purpose worker + your custom workers, in a separate section: no heartbeat · no own connection · ephemeral memory · depth-limited · leaner model · not chat targets (the test-run button is the exception). Plus a Delegation tab in the profile (who I can delegate to + modes + accept-from) and a read-only trust-graph matrix.

Screen 4 · the renamed surface

Channels → Connectors

From a singleton config per channel type to a list of named connections, each with its own identity and binding.

As-is exists

One config panel per channel type (system-wide singleton). Secrets are credential-routed.

To-be

An instance list ("Connections") with Add connection. Each connection carries an identity (agent or user) + an agent binding. One instance per type initially; multi later.

  Slack      —                + add
────────────────────────────────────────────────────────
  one per type (v0.1.0) · identity = agent│you · binding v

When: instance-list UI (one per type) + basic IMAP/SMTP email = v0.1.0  ·  multi-instance + provider-OAuth email + Webhook channels = v0.3.0  ·  user-identity connections = v0.4.0

Screen 8 · the config surface

Settings

Two halves: a top-right Profile menu for personal settings, and Settings for the app's config (sensitive sections re-type the password). User management collapses — single user.

As-is exists

Tabs include providers, credential vault, user management (add/remove users + roles) — personal and system settings mixed together.

To-be

Settings = the app's config (sensitive sections re-type the password): Providers · Integrations (tool providers — search / voice / image) · Connectors · Performance → Max parallel agents · Security · Data. Personal settings move to a top-right Profile menu — your name, change password, appearance, devices, log out. User management is gone (single user) — the only account action is password reset, in Profile.

Screen 9 · new surface

Memory greenfield

The backend-only memory system finally gets a two-room view — and a place to review what the agent learned overnight.

Memory already spans 4 artifacts (MEMORY.md · daily notes · last-session · retros) with an idle-time LLM recap (pkg/agent/memory.go) — but it's backend-only, no dedicated UI.

The point

What ships in v0.1.0 is real, not placeholder

Every v0.1.0 row above sits on actual data — because v0.1.0 lands the structural shapes first, the UI is never thrown away later.

v0.1.0 lands the data shapes the rest builds on:
  • The Workspace scoping key threaded through tasks, memory, calendar and connections.
  • The Connection-as-instance model — capped at one per type, but the instance shape is real.
  • The agent tier field (base / sub) — the two-section roster.
  • The delegation-policy contract type (to · modes · accept_from).
  • The additive task fields (start / due / repeat / blocked_by).

Because the shapes are correct on day one, the v0.1.0 UI sits on real data and is not reshaped later — later releases add behavior (functional recurrence, OAuth, rule engines, multi-instance), not new structure. See the roadmap for the release sequence and the blueprint for the underlying data model.
