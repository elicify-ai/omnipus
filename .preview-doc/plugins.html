Plugins & Marketplaces

Two distinct concepts — do not conflate them: Skill marketplaces (ClawHub · GitHub · future Omnipus Market) are registries you search and install skills from; Plugin bundles (omnipus-plugin.json) are packages of skills + agents + MCP + channels + providers installed by the bundle installer. v0.1.0 ships the structural SHAPES (the registry list + the bundle manifest — both already built). The plugin installer + Marketplaces UI + Omnipus Marketplace are v0.2. Skills are installable in v0.1.0; plugins/agent-packs are v0.2. Everything compiled-in (4 base agents + Worker + Planner/Explorer/Researcher + 4 embedded skills + 3 runner drivers) is seeded, not installed via a plugin.

Part 1 · the provider model, a third time — SKILL registries only

Skill marketplaces = swappable providers (not plugin bundles)

A "marketplace" here is a SKILL registry — the same swappable-provider pattern used for per-tool providers and multi-instance Connections. Configure several skill registries; search fans out across all of them. Plugin bundles are separate (see Part 2 below) — a GitHub repo can host either a bare skill or a bundle; the installer detects omnipus-plugin.json to decide which it is.

  • SearchAll fans out across every registry, tolerates partial failure, sorts by score
  • ClawHubRegistry wired (default clawhub.ai); InstallFromGitHub installs from any repo, SSRF-guarded + hash-verified
  • Each result already carries verified / malware / suspicious flags

Part 1b · default skills & the self-improving authoring loop

Ship few, scope per agent, let them improve

Ship a tiny embedded default set — the bloat lesson is loud: Hermes ships ~70 skills and OpenClaw auto-loads 53, and users end up hand-whitelisting down to ~9. The authoring loop: today only install / remove / search / list exist — and as stubs. The missing piece is system.skill.create + system.skill.edit — the skill_manage equivalent that turns a one-shot generator into a self-improving loop: an agent codifies a repeated workflow as a skill, then refines it after each use via the edit verb. skill-authoring is the full lifecycle (create · edit/refine · validate · version · deprecate) and replaces the one-shot skill-creator. Writes are consent-gated + versioned (rollback / review). This is the editable arm of Learning (procedural memory).

Two v0.1.0 work items: (a) WIRE the 4 stub tools (install / remove / search / list) to the real pkg/skills engine; (b) ADD system.skill.create / .edit. The engine (SkillInstaller · RegistryManager · ClawHubRegistry · loader) is built; the agent-facing tool surface is hollow + missing the authoring verbs.

Part 2 · plugins as bundles

A plugin = composition over what we already ship

Your definition — a package of skills + provider config + MCPs + channels + agents — is the convergent industry model (OpenClaw's WhatsApp plugin bundles a tool + skill + provider + channel; Claude Code plugins bundle skills + agents + hooks + MCP). Omnipus's twist: the bundle is declarative, and its installer just fans each component out to the subsystem that already owns it.

omnipus-plugin.json  — component-level hybrid manifest
  {
    "name": "support-desk",  "version": "1.2.0",  "signature": "...",
    "skills":    "./skills/",         // SKILL.md verbatim — ecosystem-portable
    "mcpServers": "./.mcp.json",         // .mcp.json verbatim — ecosystem-portable
    "agents":    "./agents/",         // native AGENT.md + SOUL.md + HEARTBEAT.md
    "channels":  "./channels.json",   // native — binds a compiled-in channel
    "providers": "./providers.json", // native — per-tool provider config
    "permissions": { "tools": ["..."], "egress": ["api.x.com"] }
  }
  install → skills/ · agents/<id>/ · mcp config · Connection config · provider config

Component-level hybrid manifest

Reuse the universal unit formats verbatim — SKILL.md + .mcp.json — so skills & MCP servers from ClawHub / Claude Code marketplaces drop straight in. Agents/channels/providers use Omnipus-native shapes. Distribute via git-repo marketplace.json.

Why not full compatibility?

Only skills + MCP servers transfer cleanly across ecosystems. Claude Code agents differ from our AGENT.md+SOUL.md (needs a converter); hooks/output-styles/monitors are IDE concepts with no equivalent; OpenClaw plugins are JS — not runnable in a pure-Go binary. So: compat where it's real, native where it isn't.

What ships compiled-in (not plugins): 4 base agents (Mia · Jim · Ray · Ava) + Worker subagent + Planner / Explorer / Researcher specialists + 4 embedded skills + 3 runner drivers (Claude Code · opencode · Codex). These are seeded at boot, not installed via the plugin system — there is no installer to deliver a pack in v0.1.0. Beyond that = installable agent packs (v0.2): Maker/creative-media, ops/devops, smart-home, domain specialists ship as bundles once the plugin installer exists. That's why the compiled-in base stays lean — the rest is opt-in, marketplace-installed.
No new runtime, no in-process code: a bundle carries declarations; its only executable parts are MCP servers / sidecars — which already run out-of-process. This keeps the single static binary, pure-Go, no-CGo constraints intact.
Part 3 · execution, runners & isolation — the differentiator

Own process, kernel-confined

A bundle's executable parts (a stdio MCP server, a localhost sidecar like Signal's signal-cli) run as their own process — there is no shared in-process sandbox, because they're separate processes. The question is what wraps that process. The same model extends to a bigger move: a Sub-agent can run another coding agent headless.

 Claude Desktop / Code & most hostsOmnipus

Safety modelcall-time approval only (gates the call, not the code)sandbox + signed/verified + explicit consent + deny-by-default
Remote serversOAuthegress/SSRF rules + "data leaves your machine" consent
Track recordfake Postmark MCP exfiltrating email · Figma MCP RCE · Smithery supply-chainthe kernel cage is exactly what those attacks needed and didn't face
This is the sovereign edge: same process model as everyone, a kernel cage almost nobody applies. A hostile MCP server in Omnipus can be boxed into "see only this workspace, make only these syscalls, reach only these hosts" — Landlock + seccomp are already in the binary.

External-agent runners — a Sub-agent that drives Claude Code, opencode or Codex

A Sub-agent gains an executor field. Its default is our own loop; set it to a runner driver and the Sub-agent dispatches the work to another coding agent running headless. The universal transport is CLI execution with JSON streaming — the only universal way to drive any of them: claude -p --output-format stream-json · codex exec (JSON) · opencode run --format json / opencode serve. Preinstalled drivers: Claude Code · opencode · Codex.

Sub-agent · executor  — default = native loop; or a runner driver
  {
    "name": "refactor-worker",  "class": "sub",
    "executor": "claude-code"     // or "opencode" · "codex" · "native" · (later) "remote-a2a"
    // transport: CLI + JSON streaming — claude -p --output-format stream-json ·
    //            codex exec (JSON) · opencode run --format json / opencode serve
  }
  each run: own-process · Landlock+seccomp · git-worktree-isolated · signed/consent · deny-by-default
  per-run minimal permission grant · creds via the credential store · egress allowlist
  three-level timeouts: per-call · per-task · per-process
The runner contract — ExternalAgentRunner — is bidirectional, not fire-and-forget: events-out (output · tool-calls · diffs · permission-requests) and control-in (permission-decisions · cancel · follow-up-input), with every permission-request consent-routed through Omnipus's own consent/policy layer — and resumable via a stable run/session ID. This is not ACP-only: the CLI floor needs exactly this shape too — Claude Code's --permission-prompt-tool is the permission round-trip and --resume is the stable session ID. So the bidirectional, consent-routed, resumable interface is the v0.1.0 structural shape; a literal ACP driver slots in behind it later with no re-cut. A reserved future executor kind — remote-a2a — lets the Orchestrator's fleet later include remote A2A arms alongside native + external-CLI ones.

Grounded in code that already exists: pkg/providers/claude_cli_provider.go + codex_cli_provider.go already spawn the claude/codex CLIs as LLM providers; pkg/agent/hook_process.go already speaks JSON-RPC-2.0-over-stdio; pkg/sandbox/hardened_exec.go is the sandbox path. The runner reuses existing machinery — it isn't a new subsystem.

Protocol stack — three layers, each DEFERRED in behaviour but HOOKED in shape

The agent space has converged on a small set of de-facto standards. The rule is the same for all three: defer the behaviour/driver, reserve the shape — so the protocol slots in later with no re-cut. Omnipus's stance, audited against the codebase:

LayerStandardHook now · protocol later
Omnipus → tools/dataMCP (Model Context Protocol) — Linux-Foundation de-facto standard for agent→toolshave — go-sdk v1.4.1, pkg/mcp
Omnipus → external coding agentsACP (Agent Client Protocol, Zed; JSON-RPC over stdio) — the de-facto for host/editor driving a coding agentCLI floor now (CLI + JSON streaming — drives any agent) · the bidirectional-runner shape is reserved (events-out + control/permission-in, consent-routed, resumable — the CLI floor needs it too) · protocol-driver later (Omnipus becomes an ACP client behind the same interface)
Omnipus agents ↔ other agentsA2A (Agent2Agent, Google → Linux Foundation, 150+ orgs) — HTTP+JSON, Agent Cards at /.well-known/agent.json, OAuth2/OIDC; the de-facto agent-to-agent peer standardhooks now — work-target is an agent-reference (delegation to + sub-agent executor admit a future remote-a2a kind; v0.1.0 resolves local + CLI only) + Card-projectable agent identity · protocol v1.0.0 (server + client + discovery + auth)
Three protocols, all LOCKED, each deferred in behaviour but hooked in shape: MCP (→ tools — have) · ACP (→ external coding agents — CLI now, bidirectional-runner shape reserved, protocol-driver later) · A2A (↔ other agents — agent-reference + Card-identity hooks now, protocol v1.0.0). The hooks that land in v0.1.0 are exactly the persisted/structural ones: the bidirectional, consent-routed, resumable ExternalAgentRunner interface; the work-target as an executor/to agent-reference; Card-projectable identity. Drivers, the ACP wire and the A2A server/client are additive with no re-cut. Handover stays LOCAL (conversation routing is in-process), and the A2A wire format is EXTERNAL — it never touches the openapi/asyncapi contract. (Acronym collision, for the record: BeeAI's "Agent Communication Protocol" is folding into A2A; "Agent Commerce Protocol"/UCP is a separate commerce vertical — neither is what we mean by ACP.)
The perimeter is the attack surface

Security posture

Independent audits put 12–36% of ClawHub skills carrying vulnerabilities or malware (Koi · Bitdefender · Snyk), and MCP has had real supply-chain breaches. The extension perimeter is the #1 risk in this whole space — so deny-by-default is non-negotiable.

🔏 Signed & verified

Verified-only by default; hash verification on install (already in the registry); the malware/suspicious flags surfaced before install.

🧱 Sandboxed

Every spawned MCP/sidecar boxed by Landlock + seccomp with a per-plugin filesystem + egress allow-list. Remote servers get SSRF/egress controls.

🔐 Consent & gate

Install + each granted permission behind the single password re-type; deny-by-default tool policy; explicit per-plugin capability consent.

  • Agent packs installable — Maker/creative-media, ops/devops, domain specialists as installable bundles

later Optional

  • WASM (wazero) — pure-Go, in-process-isolated runtime for bundled logic without a subprocess. Strongest isolation, but a large new subsystem and no ecosystem targets it — flagged, not committed.
Refactoring-avoidance: the bundle manifest shape + the skill-marketplace registry list are persisted/structural → both already built in v0.1.0 so neither needs migrating later. The installer, Marketplaces UI, Omnipus Marketplace, more providers, and the sandbox-wrapping of bundled processes are additive behaviour (v0.2) → they layer on with no re-cut.
