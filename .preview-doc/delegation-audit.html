As-is audit · grounded in code

How agents engage other agents — today

Four mechanisms already exist in the binary — from handing off a conversation to spawning a subagent. There's even a permission rule engine deciding who may delegate to whom. The gap isn't capability — it's that the rules are invisible (no UI) and inconsistently enforced.

This page is the evidence. For the redesign it motivates, see how it should work →

Validated · the four mechanisms

One axis: give up control → keep control

Handover moves the conversation to another agent. The other three farm out work while the caller stays in charge — differing only in sync/async and ephemeral/durable.

3 & 4 are the same engine (spawnSubTurn) — the Async flag is the only difference. A "subagent" is an ephemeral child turn, not a separate concept.
Each one, grounded

What the code actually does

1 · Handover
worksnot delegation

The handoff tool (ScopeCore, every agent has it) transfers the live session to a specialist. It validates the target, atomically flips session.ActiveAgentID, copies ~50% of the token budget of recent context, writes an audit entry, and emits an agent_switched WS frame.

  • One-way: the caller's turn ends; the user's next message routes to the new agent. pkg/tools/handoff.go · session/unified.go:362
  • Mia (the guide) is told to hand off mandatorily for anything beyond platform help; return_to_default reverts. coreagent/core.go:548
  • UI exists — the active-agent indicator updates on the frame. src/store/chat.ts
2 · Task-for-agent
worksdurable async

An agent calls task_create with an agent_id → the task is stored status=queued with CreatedBy=caller. The heartbeat polls CheckQueuedTasks, groups by agent, and ExecuteTask dispatches to the target via processTaskDirect in that agent's own session.

  • Fully wired execution — not just a label. tools/task.go · agent/task_executor.go · heartbeat/service.go
  • Gated by the CanDelegateTo allowlist (see rule engine below).
  • This is the spine the Personal Assistant rides — Jim "delegates to Ava/Max" this way.
  • UI: agent picker in the Create-Task slide-over. src/components/projects/CreateTaskSlideOver.tsx
3 · Spawn
worksasync ephemeral

The spawn tool starts an ephemeral child turn (spawnSubTurn, Async=true) for background work; the caller keeps going and the result is delivered back over a channel when ready.

  • Depth limit 3, max 5 concurrent, 5-min timeout; children get the parent's tools minus spawn/subagent/handoff — a one-level recursion guard. agent/subturn.go:20,314,414
  • Gated by Subagents.AllowAgents via CanSpawnSubagent. agent/registry.go:125
  • UI: collapsible SubagentBlock in chat. src/components/chat/SubagentBlock.tsx
4 · Subagent
workssync ephemeral

The subagent tool runs the same spawnSubTurn with Async=false — the caller blocks until the child finishes and the result returns directly into the conversation as a tool result.

  • Same depth/recursion guards as spawn.
  • NOT permission-gated — no allowlist checker is attached to the sync tool. agent/loop.go:1487 (no SetAllowlistChecker)
  • UI: same SubagentBlock.
Subagent vs. task — the real distinction: a subagent is ephemeral (in-memory child turn, no persistent identity, dies with the parent), best for "go figure this out and report back within this turn". A task is durable (persisted, survives restart, runs in the named agent's own session), best for "someone owns this piece of work". Handover is neither — it's a baton pass.
The rule engine · validated

Who may delegate to whom

Your recollection is right — there is a permission engine. But it's actually two separate allowlists, default-deny, wildcard-aware, configured only in JSON.

can_delegate_to

Per-agent (or Agents.Defaults) list of agent IDs this agent may create tasks for. Enforced in task_create via buildDelegateChecker. config.go:663 · loop.go:1592 (func), wired :1502

subagents.allow_agents

Per-agent list of agent IDs this agent may spawn. Enforced via CanSpawnSubagent. Empty ⇒ cannot spawn at all. registry.go:125

Both accept "*" (allow-all) and default to deny when empty. Core agents don't seed either — they inherit the (usually empty) global default; custom agents set them via system.agent.create/update.

Gap 1 · Inconsistent enforcement

Two of four paths are gated; sync subagent and handoff bypass the rules entirely. An agent blocked from spawning can still call a subagent synchronously.

Gap 2 · Two models, one concept

"Who may agent X engage" is split across can_delegate_to and subagents.allow_agents with different defaults and code paths. Should be one delegation policy.

Gap 3 · No surface at all

Neither allowlist is in the Agent contract or any screen. An operator can't see or edit the trust graph without hand-editing JSON. The matrix above doesn't exist in the product.

Recommendation

Unify into one delegation policy + a visible trust graph

Model

  • One per-agent delegation policy — collapse the two arrays into delegation: { to, accept_from, modes, depth, budget }, where modes = await / background / task. Handover stays open/ungated by design — it re-routes the conversation, never farms out work, so it's not in the delegation policy. See the full model →
  • Gate the two ungated work-paths (sync subagent + spawn/task) through the policy; leave handover open.
  • Add it to the Agent contract (Constraint #8) so it has a generated type.

Surface (the missing UI)

  • Agent profile → Delegation tab: pick allowed targets + modes.
  • A read-only trust-graph matrix (the table above) at the team/project level.
  • Observe runs: handover trail + SubagentBlock already exist — link them into one "agent activity" view.
Sequencing: the UI + contract field + unify/close-the-gaps is mostly additive and safe — a strong fit for v0.1.0 (R1) IA-lock work (make the existing engine visible) with the enforcement unification landing alongside the workspace tenancy pass. It does not depend on the multi-instance connections rock.
