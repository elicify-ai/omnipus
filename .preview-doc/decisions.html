What's settled

Auth & Onboarding · settled in interview

Single userOne user, one password — no multi-user, no RBAC roles, no tenancy, no per-user isolation. Omnipus is a single-user self-hosted app.
Sensitive settingsProtected by re-typing the same password (sudo-style confirm) — model/billing keys, channel setup, security, deletes. Not a second credential. Maps onto the existing RequireNotBypass guard.
Ownershipowner=username survives only as attribution ("you" vs which agent) — never an access gate. Workspaces/agents/memory are simply yours.
Onboarding3 steps: "What should I call you?" → set password → add a model key. Then auto-provision your Assistant in My Workspace ("meet your assistant").
Profile vs SettingsNo user management (single user) — the only account action is password reset. Personal settings (name · password · appearance · sessions · log out) live under a top-right Profile menu; Settings is the app's config (sensitive = password re-type). Removes the multi-user UsersSection.

Naming & Workspaces · Workspaces

Container word"Workspace" (UX-chosen: Jakob's Law · NNG). One pre-seeded default "My Workspace"; named workspaces for real work. No Personal/General split.
ContextThe existing sidebar workspace switcher — no scope "mode". Assistant → My Workspace; other agents → the selected workspace.
Code renameproject → workspace end-to-end (code · contracts · storage) — a v0.1.0 migration. Pre-ADR: concept-doc only; executed during implementation.

Agents — base agents & sub-agent workers · settled in interview

Base agentsFour base agents (re-cast cores) — Mia · Assistant ⭐ (default front door) · Jim · Orchestrator (planner/PM) · Ray · Scout (research/summarize) · Ava · Builder. You chat with them; heartbeat · own connections · full memory · default-★ · can delegate. Custom base agents allowed.
Re-cut of the coresMia → Assistant ⭐ · Jim → Orchestrator · Ray → Scout · Ava → Builder (unchanged) · Max → retired. Automation is a platform surface (Calendar & Automations), not a persona — an optional marketplace pack if wanted.
Sub-agent workersThe seeded general-purpose worker + custom workers, in their own roster section, each carrying an executor (native | external-cli {Claude Code · opencode · Codex} | future remote-a2a). No heartbeat · no own connection · ephemeral memory · not chat targets · depth-limited · leaner model. A tool you point at work, not a colleague.
AssistantA base agent that's yours — Mia, auto-provisioned, bound to My Workspace, cross-workspace recall via its agent-global private room.
Beyond baseEverything past the four base agents — creative-media, ops/devops, smart-home, domain specialists — ships as marketplace agent packs, not baked in. Preinstalled = 4 base agents + 3 runner drivers (Claude Code · opencode · Codex).
Voice fieldA nullable voice field is added to the agent schema in v0.1.0 (additive on the base agents Mia · Jim · Ray · Ava) — unused until TTS in v0.2.0, so adding voices later isn't a contract change.

Delegation & Performance · Delegation

Two primitivesHandover = routing (the conversation moves) · Delegation = work. Delegation modes: await · background · task; always to a named agent.
v0.1.0 policyStart simple: the full policy contract schema (to · accept_from · modes · depth · budget) ships in v0.1.0 (additive, complete) — but only to + modes are enforced/surfaced now (one policy + a trust-graph screen + gate the 2 currently-ungated work paths). Handover stays open (it only moves your conversation). accept_from + budget enforcement land later — adding it isn't a contract change.
OrchestrationPlans = a DAG of task-delegations (blocked_by); a coordinator runs them on task_status_changed.
Max parallel agentsA v0.1.0 setting (Settings → Performance, behind the password re-type): caps concurrent agent runs; excess queues. CPU/RAM-aware recommendation (e.g. "8 cores · 16 GB → 6"), with an over-limit warning. This is the concurrency window — now user-tunable.

Plugins & Marketplaces · Plugins & Marketplaces

ScopeDesign-now, foundation-only — lock the manifest shape + the marketplace-provider list in v0.1.0; the installer + Marketplaces UI come later. Plugins are declarative bundles (skills + agents + MCP + channels + provider-config) — a composition layer over subsystems Omnipus already ships, not a new runtime.
ExecutionOwn-process, kernel-confined — a bundle's executable parts (stdio MCP server · localhost sidecar) run as their own process under Landlock/seccomp + signed/verified + explicit consent + deny-by-default. No in-process code (would break single-binary/pure-Go). Remote MCP URLs = egress/SSRF controls + a data-leaves-your-machine consent prompt. (Claude Desktop/Code spawn MCP servers unconfined — Omnipus boxes each one with the kernel sandbox it already has.)
ManifestComponent-level hybrid — an Omnipus-native bundle manifest that reuses the universal unit formats verbatim (SKILL.md · .mcp.json) so skills + MCP servers import directly; agents/channels/providers use native formats; consume git-repo marketplace.json for distribution.
MarketplacesClawHub (wired, default) · GitHub-repo-as-source (InstallFromGitHub already works) first-class in v0.1.0. Second batch (v0.2.0+): the Omnipus Marketplace goes live & replaces ClawHub as the default source · MCP registries (official · Smithery · Glama) · Claude Code git-repo marketplaces.
Provider modelThe skill-marketplace provider model is the per-tool/per-Connection provider model a third time — RegistryManager already coordinates N registries (SearchAll fans out, partial-failure tolerant). Gap = RegistryConfig single ClawHub config → list of marketplaces: the same one-time single→list refactor as Connections and tool-providers.
SecuritySigned/verified-only by default + kernel sandbox + consent + deny-by-default + password-gated install. Backdrop: 12–36% of ClawHub skills carry vulns/malware (Koi · Bitdefender · Snyk) plus real MCP supply-chain breaches.

Agents, Runners & Protocols · Plugins & Marketplaces · Delegation · locked

Base rosterFour base agents (re-cast cores) — Mia · Assistant ⭐ (default; memory-rich personal front door) · Jim · Orchestrator (planner/PM) · Ray · Scout (research & summarize) · Ava · Builder (agent & skill builder). The minimal set shipped on every install.
Max retiredNo Max persona in base. Automation is a platform surface (the Calendar & Automations page) — authored by the Assistant from chat ("want me to do this every morning?") and run by the platform, not a personality. (Available as an optional marketplace pack if wanted.)
Marketplace packsEverything beyond the four base agents — Maker/creative-media · ops/devops · smart-home · domain specialists — ships as marketplace agent packs, installed as plugin bundles, not baked in.
OrchestratorSupervisor pattern on EXISTING primitives — tasks · blocked_by DAG · the delegation graph · Max-parallel · git worktrees. No new engine; it coordinates what's already there.
External-agent runnersA Sub-agent gains an executor field and can drive another coding agent headless. Universal transport = CLI execution with JSON streaming (claude -p --output-format stream-json · codex exec · opencode run --format json/serve). Preinstalled drivers: Claude Code · opencode · Codex. Each run is own-process, kernel-confined (Landlock/seccomp) + git-worktree-isolated + signed/consent + deny-by-default; per-run minimal permission grant; auth via credential store; three-level timeouts; egress allowlist. Grounded in existing code (claude_cli_provider.go · codex_cli_provider.go · hook_process.go JSON-RPC-stdio · hardened_exec.go).
Preinstalled agentsOn a fresh install: the 4 base agents (Assistant ⭐ · Orchestrator · Scout · Ava) + the 3 runner drivers (Claude Code · opencode · Codex). Everything else arrives via marketplace packs.
Protocol stanceMCP (agent→tools/data — Linux-Foundation de-facto) = have (go-sdk v1.4.1, pkg/mcp) · ACP (Agent Client Protocol, Zed — host→coding-agent driving) = CLI+JSON-streaming floor now, protocol future (Omnipus becomes an ACP client) · A2A (Agent2Agent, Google→Linux Foundation, 150+ orgs — agent↔agent peers, Agent Cards) = future. Clean layering: MCP → tools · ACP → external coding agents · A2A → other agents.
FoundationThe Sub-agent executor field + an ExternalAgentRunner interface are the v0.1.0 structural shape; the extra drivers, ACP and A2A are additive with no re-cut.

Protocols — defer behaviour, reserve shape · locked

Three protocols, three layers. Each is deferred in behaviour but hooked in shape in v0.1.0 — the refactoring-avoidance rule: defer the driver/wire, reserve the addressable shape.

MCP agent→toolsHave it. modelcontextprotocol/go-sdk v1.4.1, pkg/mcp — shipped. The tool/data plug already in place.
ACP host→agentDeferred (additive driver later). Zed Agent Client Protocol — host drives a coding agent. v0.1.0 hook = the ExternalAgentRunner interface is bidirectional (events-out: output · tool-calls · diffs · permission-requests + control-in: permission-decisions · cancel · follow-up-input), consent-routed to the consent/policy layer, and resumable (stable run/session id). Not ACP-only speculation — the CLI floor needs the same shape (Claude Code stream-json + --permission-prompt-tool + --resume).
A2A agent↔agentDeferred — protocol lands v1.0.0 (server: expose Omnipus agents w/ Agent Card · client: call remote agents · discovery · auth). Agent2Agent (Google → Linux Foundation). v0.1.0 hooks = (1) the work-target is an agent-reference — delegation to + sub-agent executor admit a future remote-a2a kind (v0.1.0 resolves local + CLI only); (2) Card-projectable agent identity — a stable id + declared skills/capabilities/description a future Agent Card (/.well-known/agent.json) projects from (no new fields — just don't tie identity to something un-addressable).
The ruleDefer the behaviour, reserve the shape. Handover stays local (conversation routing is in-process). The A2A wire format is external — it does not touch openapi.yaml/asyncapi.yaml, so Constraint #8 is untouched.

Skills & self-improvement · Plugins & Marketplaces · Learning · locked

Default skillssummarize · skill-authoring · plan · daily-briefing — a tiny embedded default set, shipped via go:embed + a first-boot seed (today filesystem-seeded only).
skill-authoringFull lifecycle — create · edit/refine · validate · version · deprecate. Replaces the one-shot skill-creator; the edit verb is the self-improvement.
New v0.1.0 capabilitysystem.skill.create + system.skill.edit — the self-improvement verb. Today only install / remove / search / list exist — and as STUBS, not wired to the real pkg/skills engine. Two v0.1.0 items: wire the stubs + add create/edit.
ScopingPer-agent allowlist + progressive disclosure (anti-bloat). Single-user ⇒ gating is per-agent policy + password-re-type consent, not RBAC roles. Skill writes are consent-gated + versioned (rollback/review).
Procedural memorySkills are the editable arm of self-improvement; the Dreamcatcher / Learning loops propose skill create/edit from repeated workflows.
Open questions

What's left

The interview closed the big ones (auth, tenancy, agents, delegation). What remains is minor, deferred, or tune-with-traffic.

Small calls for the ADR

  • Q1 blocked_by validation — ship the field inert until a cycle/orphan validator exists; don't let the UI write unvalidated edges.
  • Q2 Sub-agent "test run" — do Sub agents get a manual test-run button, or are they invoke-only via delegation? lean: a test-run button
  • Q3 Custom agent creation — can the user create custom Primary and Sub agents, and is that itself password-gated? lean: yes; not gated (it's yours)

Deferred / tune with traffic

  • Q4 Memory weights — confidence drift, recall ranking, archive & Dreamcatcher thresholds → spec defaults, tune post-launch.
  • Q5 Provider OAuth lifecycle — Gmail/Calendar watch renewal + 410 resync, the heavy part of v1.0.0 (Google first).
  • Q6 Default seed migration — new installs seed "My Workspace"; existing "Main" renamed in place.
  • Q7 Realtime approach — native speech-to-speech vs a streaming STT→LLM→TTS pipeline → defer to v1.0.0.
Nothing here blocks v0.1.0. The grounded as-is for delegation is in the audit; the cost story is on Impact; the release shape is on the Roadmap.
