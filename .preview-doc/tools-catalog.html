Builtin Tool Catalog

Every tool compiled into the single Omnipus binary — 85 active builtins (87 compiled; 3 retired in the v0.3 task-system refactor: cron, task_add_dependency, task_add_todo; +1 new: plan). This page is the reference list: what each tool does, who can call it, whether it's always loaded or fetched on demand, and how dangerous it is. Generated from the live tool registry (GET /api/v1/tools), re-categorized into the proposed domain scheme, with the v0.3 end-state applied.

How to read this

Three dimensions per tool

Access — who can call it (the live enforcement axis; today core/general, fail-closed — see ADR-018)
open any agent privileged core agents default; a custom agent needs an explicit policy allow gated needs an extra operator flag on top of policy (e.g. browser_evaluate_enabled)
Manifest — token strategy (proposed: compressed-manifest model — the agent sees every tool's name+purpose always; full schemas fetched on demand)
full always loaded — high-frequency; full schema in context compressed manifest entry only; full schema fetched on demand (saves ~7–11k tokens/turn)
Risk — security / destructiveness
🟢 read read-only / safe 🟡 write mutating, recoverable 🔴 delete destructive / irreversible ⚡ exec arbitrary code / JS 🔐 admin privileged platform config

Counts: 38 read · 33 write · 8 delete · 4 admin · 2 exec.   Manifest: 13 full · 72 compressed.   The 8 🔴 delete + 4 🔐 admin + 2 ⚡ exec tools warrant the most care (re-auth, admin-ask fence, audit). MCP-server and skill tools layer on top at runtime; workspace.shell/workspace.shell_bg are omitted by design (experimental, config-gated).

The agent scratchpad = a task (unified, v0.3)

Every agent gets a session scratchpad for in-session planning — but it is not a separate system. It rides on the task substrate, so there is one record type, one store, one lifecycle:

  • One tool, plan (TodoWrite-style): the agent sets its full current todo list [{text, status}] in one call. Replace-semantics, not append — the agent rewrites the whole list (so no todo IDs are needed), which fixes the append-only dead-end of the old task_add_todo.
  • Agent-unaware task creation. The first plan call in a session auto-creates a scratchpad-flagged task for that agent and reuses it thereafter. The agent never sees a task_id and never calls task_create for its own planning — it just "sets its plan."
  • Read-on-write. plan returns the full updated list, so the agent always sees its plan after every write (no separate read tool).
  • Promotion, not a second path. A scratchpad task becomes a real, visible board task only when the work is delegated or committed — same record, the flag flips. Fleeting plans stay hidden and clean up at session end; durable work persists and is delegatable / schedulable.

Retires: task_add_todo (→ plan's replace-semantics), task_add_dependency (→ folded into task_update), cron (→ scheduled tasks via task.Trigger + per-agent heartbeat). General task tools: 6 → plan · task_create · task_update (real edit) · task_list · task_delete.

Substrate changes: Todo {Text, Status} (pending/in_progress/completed); SetTodos(taskID, []Todo) full-replace; a scratchpad task flag (hidden, session-scoped, agent-owned) vs a durable task. Open choices for the ADR: promotion trigger (implicit-on-delegate vs explicit commit vs operator) and scratchpad retention (clean up at session end vs retain-as-audit).
