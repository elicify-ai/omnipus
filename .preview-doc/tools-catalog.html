Builtin Tool Catalog v0.3 to-be

The proposed v0.3 end-state of the builtin tool surface — 85 tools across 11 categories. This is the to-be catalog (pre-ADR), not the live registry: it applies the task-system refactor — retires cron / task_add_dependency / task_add_todo, adds todos, broadens task_update, and renames system.task.* → task_*_in_workspace. See docs/internal/design/tasks-system-refactor-2026-06.md.

85 tools · 11 categories tasks 9 (5 current + 4 cross-workspace) · system 40 24 open · 60 privileged · 1 gated
How to read this

Three dimensions per tool

Access — who can call it (the live enforcement axis; today core/general, fail-closed — see ADR-018)
open any agent privileged core agents default; a custom agent needs an explicit policy allow (cross-workspace for task_*_in_workspace) gated needs an extra operator flag on top of policy (e.g. browser_evaluate_enabled)
Manifest — token strategy (proposed: compressed-manifest model — the agent sees every tool's name+purpose always; full schemas fetched on demand)
full always loaded — high-frequency; full schema in context compressed manifest entry only; full schema fetched on demand (saves ~7–11k tokens/turn)
Risk — security / destructiveness
🟢 read read-only / safe 🟡 write mutating, recoverable 🔴 delete destructive / irreversible ⚡ exec arbitrary code / JS 🔐 admin privileged platform config

Counts: 38 read · 33 write · 8 delete · 4 admin · 2 exec.   Manifest: 13 full · 72 compressed.   The 8 🔴 delete + 4 🔐 admin + 2 ⚡ exec tools warrant the most care (re-auth, admin-ask fence, audit). MCP-server and skill tools layer on top at runtime; workspace.shell/workspace.shell_bg are omitted by design (experimental, config-gated).

The agent scratchpad = a visible board task (v0.3)

Every agent gets an in-session scratchpad for lightweight planning — but it is not a separate system. It rides the task substrate behind one tool: one record type, one store, one lifecycle.

  • One tool, todos(goal, [{text, status}]) (TodoWrite-style): the agent sets its full current checklist in one call — replace-semantics, not append (rewrites the list, so no todo IDs needed), fixing the append-only dead-end of the old task_add_todo. goal is the title of the task these todos serve.
  • Agent-unaware task creation. The call creates-or-updates a board-visible task titled goal with those todos as its checklist. The agent never calls task_create or sees a task_id. No hidden flag, no promotion step.
  • Read-on-write + re-injection. todos returns the updated list, and the loop re-injects the agent's current goal + todos at the start of each turn — so the plan survives context compression without a read tool.
  • Flat checklist vs multi-wave plan. todos = one task, flat list (no deps). A multi-wave plan = many tasks linked by blocked_by (a DAG) via task_create. "plan" is reserved for the dependency-linked case.
  • Current vs cross-workspace. task_* works in your current workspace (auto-resolved); task_*_in_workspace takes an explicit workspace_id to target another workspace (Orchestrator; privileged).

Boundary (seed prompt): Use todos for the throwaway checklist of this turn; use task_create + dependencies for a durable multi-wave plan.

Retires: task_add_todo (→ todos), task_add_dependency (→ folded into task_update), cron (→ scheduled tasks via task.Trigger + heartbeat). Renames: system.task.* → task_*_in_workspace (drop the misleading system. prefix — tasks are agent-work, not platform-admin; see docs/internal/design/tasks-system-refactor-2026-06.md §4).
