How it should work · a design

Agent collaboration, designed

Today there are four overlapping mechanisms and two half-wired permission lists. This is the target model: two primitives, one delegation policy expressed as a graph, and the cross-cutting rules (ownership, context, results, scale) that make it coherent.

Grounded in — and motivated by — the as-is code audit → (what exists, what's missing, where the gaps are).

Step 1 · the reframe

Two primitives, not four tools

The four mechanisms collapse onto one distinction: does the conversation move, or does work get farmed out? These are different layers and should stop being lumped together.

Handover belongs to the routing layer — it only moves your conversation, so it stays open / ungated by design; the handoff tool performs a handover. Delegation is the work primitive — the one the trust-graph governs. The rest of this page designs delegation.
Step 2 · one primitive, three commitments

You always delegate to a named agent — you choose how committed

"Ephemeral subagent" vs "durable task" shouldn't be two tools you pick between. It's one act — ask agent B to do W — with a mode that sets how committed the work is. The runtime decides ephemeral-vs-durable from the mode.

ModeCallerWorkerUse when…Today
awaitblocks for the answerephemeral sub-turn of B's personayou need a result to continue your own turn (a lookup, a check, a draft)subagent
backgroundkeeps going; notified on doneephemeral sub-turna side-quest that shouldn't block you; result soonspawn
taskhands it off; tracked on a boardB's own durable session, survives restarta real piece of work someone should own — maybe long, maybe a specialisttask_create
The decision guide, in one line: need it to keep talking? await  ·  need it done while you work? background  ·  need it owned? task  ·  need the user to talk to someone else? handover.

Why "always to a named agent": delegation should mean asking someone — Ray, Planner, a custom specialist — not conjuring an anonymous clone. The target's persona, skills, tools and memory are what make the result good. An ephemeral worker is just "that agent, as a throwaway turn." This also gives the permission graph something real to reference.

Implication — we must seed a default worker. If every worker needs a resolvable identity, then "fan out without naming a specialist" needs a real target to resolve to. So we ship a built-in general-purpose worker. Confirmed gap: today an un-named spawn runs an ad-hoc prompt + the parent's tools, with no identity (pkg/tools/spawn.go:98-122) — and worse, it bypasses the allowlist entirely: the gate is if agentID != "" && t.allowlistCheck != nil (spawn.go:100), so no agent_id ⇒ no check — exactly the ungoverned anonymous spawn we're replacing. (This does not remove direct spawning — the engine and the capability stay; spawn/subagent just become delegate(mode=…) against a real identity.)

The general-purpose worker is a sub-agent worker, lean by design — a terse "do the unit, return a result" prompt, a cheap/fast default model (you may spawn hundreds), no greeting · no own connection · no heartbeat · ephemeral memory (a run-log, no continuity). It inherits the caller's tool scope bounded by policy. It mirrors Claude Code's own general-purpose default subagent. Subagents are not leaves by rule — the bounded subagent delegation model lets any subagent carry depth ≥ 1 + a trust set; the general-purpose worker simply defaults to to: [] because it has no use for further delegation.

The roster has two tiers — base agents vs. sub-agent workers. Base agents (the four seeded cores re-cast by role — Mia · the Assistant ⭐ (default front door) · Jim · the Orchestrator (planner/PM) · Ray · the Scout (research) · Ava · the Builder — plus any custom you add: chat · heartbeat · own connections · full memory · default-★ · can delegate). And sub-agent workers (the seeded general-purpose worker + three default specialist subagents — Planner (deep decomposition; delegates to Explorer + Researcher within its bounded policy) · Explorer (file + memory exploration) · Researcher (external-source research) — + custom workers, each carrying an executor — native · external-cli · future remote-a2a — a separate roster section, deliberately stripped: no heartbeat · no own connection/identity · ephemeral memory (run-log, no continuity) · not chat targets (invoked only via delegation; a "test run" button is the exception) · not default-★ · a leaner/cheaper model). A tool you point at work, not a colleague. Specialists with depth-bounded delegation policies ship compiled-in for v0.1.0; anything else arrives later as marketplace packs. Note: Max is retired from the base — automation is now a platform surface, not a persona. The two axes don't collide: sub-agent worker is a roster tier; spawn/subagent are how any agent runs as an ephemeral child turn.
Three specialist subagents ship by default (compiled-in, v0.1.0):
  • Planner — deep decomposition and planning; produces the task DAG / workflow; delegates to Explorer + Researcher within its bounded policy (depth=1, to=[Explorer, Researcher], modes=[await, background]) to gather context before planning. Invoked by Jim.
  • Explorer — file and memory exploration (internal context). Leaf (to: []).
  • Researcher — external-source research. Leaf (to: []).
All three are Subagents, NOT Mains — no heartbeat, no backlog, no chat targeting; invoked only via delegation. Ray (Scout) is the chat-facing research colleague who delegates to the Researcher subagent (no duplication). These specialists ship compiled-in for v0.1.0; they become installable marketplace packs once the v0.2 plugin installer exists.
Step 3 · the macro form

Orchestration — planning work across a team

1:1 delegation is "do this unit." The other half is authoring a plan: many tasks, across many agents, with ordering — a coordinator decomposing a goal. This is the macro form of task mode, and it's where delegation meets Workspaces, the Calendar and Automations.

Two scales of delegation

  • 1:1 · a task for one agent — "Ray, write the competitor brief." One durable board item, one assignee. exists · agent_id
  • 1:many · a plan for the team — a coordinator emits a DAG of tasks (assignees + dependencies + schedule), then monitors & synthesizes. orchestration

A plan = a DAG of task-delegations

  • Nodes = tasks — each a task delegation, agent_id = assignee
  • Edges = blocked_by dependencies new field — tasks have no ordering today
  • Grouping = workspace + milestone_id exists
  • Timing = start / due / recurrence from the Calendar
A coordinator authors the plan; each node is a durable task on the board, assigned to an agent; gold edges are dependencies that gate execution. A node can itself fan out (Research B → 40 workers).
The coordinator pattern: an agent owns a goal → authors the plan (proposed → you approve → dispatched) → the executor runs each task on its assignee as dependencies clear → task_status_changed events (the contract slot with no producer) unlock the next step and notify the coordinator → it synthesizes. Jim · the Orchestrator is the seeded coordinator — the planner/PM that owns this story: it supervises the tasks · blocked_by DAG, drives the workspace delegation graph, runs the fleet through the Max-parallel-agents window, and isolates parallel work in worktrees. Jim delegates deep decomposition to the Planner subagent (which in turn delegates context-gathering to Explorer and Researcher). Any specialist or the general-purpose worker can also coordinate, but the Orchestrator is the one built for it.
Governed by the same graph: every assignment in a plan is a task edge — the coordinator's delegation.to must cover each assignee (or a role:). It can't assign to agents it isn't allowed to delegate to, and the whole plan carries the originating owner (#406) as attribution (single user). Orchestration is delegation at the plan level, not a new permission surface.
The target is an agent-reference (A2A-ready, LOCKED). The delegation to target is an agent-reference — in v0.1.0 it resolves to a local agent, but the same reference can resolve to a remote A2A agent later, so the policy / trust-graph never reshapes when peer agents arrive. Handover stays local — it moves a live conversation, which is inherently in-process. And the Orchestrator dispatches its fleet arms to native · external-cli · (later) remote-a2a executors — the same agent-reference resolution, one more executor kind. See Plugins · the protocol stack.
Step 4 · one policy, a directed graph — per workspace

The delegation graph — per workspace, start with out-edges

Replace the two disconnected allowlists (can_delegate_to + subagents.allow_agents) with one delegation graph per workspace. The graph lives on the workspace (its Team tab), keyed by the team. v0.1.0 ships to + modes + depth and gates the delegation work-paths; handover stays open by design (it only moves your conversation, never farms out work). The in-edge (accept_from) and budget are reserved/inert in v0.1.0 — sketched below in muted text.

# workspace: Acme — delegation graph (team edges), governs the delegation work-paths (await / background / task)
# Node Jim in this workspace's team; edges express who Jim may ask *within this workspace's team*
workspace: acme
  team:
    jim:
      to:      [ray, planner, "role:research", "*"]  # out-edges — who Jim may ask  (v0.1.0)
      modes:   [await, background, task]              # which commitments (default: all)  (v0.1.0)
      depth:   3                                     # max recursion below me (see scale)  (v0.1.0)
      # --- reserved / inert in v0.1.0 ---
      # accept_from: [mia, "owner:agents"]             # in-edge — who may ask Jim
      # budget:      { concurrency: 10, tokens: 200k }  # throughput valve + cost ceiling
    planner:
      to:      [explorer, researcher]                 # bounded: depth ≥ 1, explicit trust set
      modes:   [await, background]
      depth:   1

Handover is not in this policy — it is ungated by design (it only re-routes your conversation). The delegation policy is per workspace (owned by the workspace, keyed by core_team) and surfaced in two places — the workspace Team tab and the Agents area "Workspace Teams" view — always workspace-scoped, one source of truth. My Workspace is pre-seeded with the default team (Mia · Jim · Ava · Ray · Planner · Explorer · Researcher) and default edges. The v0.1.0 effective-delegation check is just the out-edge plus the existing single-user attribution and depth/cycle guard:

A may delegate W to B in mode M  iff ALL hold:
  • B in A.delegation.to  (A may ask B) — v0.1.0
  • M in A.delegation.modes  (v0.1.0)
  • within depth  and  no cycle A…→A  (single user · owner = attribution, threaded through)
  • later: A in B.accept_from (in-edge)  and  within budget
A visible, editable directed graph — the mental model the engine already half-encodes, finally surfaced. This graph is per workspace (the workspace's Team tab); the nodes are the agents on this project's team. Edges carry their allowed modes; a node with no in-edges accepts no delegation. The Planner subagent node carries a bounded policy (depth=1, to=[Explorer, Researcher]) — not a leaf, just bounded.
Gate the delegation work-paths through this one policy — closing the two ungated work holes today (sync subagent and spawn/task). Handover stays open by design — it only moves your conversation, so the trust-graph governs delegation, not handover. One model, one place to reason about who may farm out work.
Step 5 · scale & safety

Should you be able to spawn hundreds of subagents? Yes — through a window, within a budget

The current hard caps (max 5 concurrent, one level only) conflate three things that should be separate controls. Pulling them apart is the answer to "why a limit at all?"

↔ Width (fan-out) scale freely

How many total. Mapping over 300 files, 100 search angles, a per-customer sweep — these are legitimate. Width should be bounded by a token/cost budget, not a magic number. 500 workers is fine.

⥄ Concurrency Max parallel agents

How many at once. The user-facing "Max parallel agents" setting (v0.1.0, Settings → Performance, behind the password re-type) — this is the concurrency window, now tunable. It does not cap the total; excess simply queues and drains through the window. Recommended from your hardware: clamp(min(cores−2, RAM_GB÷1.5), 2, 16) — e.g. 8 cores · 16 GB → 6 — with an over-limit warning.

↧ Depth (recursion) stay bounded

How many levels deep. This is where runaway lives — keep it hard-bounded (3–5) plus cycle detection. Deep trees, not wide ones, are the danger.

Hundreds of workers, ten at a time, until the budget is spent. Exactly how a parallel map should behave — and how Omnipus's own Workflow engine already runs (concurrency ≈ cores, a high total backstop, budget-scaled).

So why limit at all?

  • Cost — each worker burns tokens; unbounded fan-out is unbounded spend.
  • Resources — each is a real agent loop (RAM/CPU/file handles); this very pod OOMs if you run too many at once.
  • Provider rate-limits — 429s if you blast 500 calls in parallel.
  • Cycles — A→B→A must be caught, or it never ends.
  • Legibility — a 10,000-node tree is unreadable; budgets keep trees comprehensible.

The redesign

  • Lift the hard count cap → fan-out scales with the token/cost budget.
  • Keep a concurrency window (throughput valve) — now the user-tunable "Max parallel agents" setting (v0.1.0); queue the overflow.
  • Keep depth bounded + add cycle detection on the call-stack.
  • Drop the strict-leaf rule — the hard "worker can't delegate" rejection is removed. A subagent may carry depth ≥ 1 + an explicit trust set (bounded subagent delegation), enabling "specialists that use specialists" (e.g. Planner → Explorer + Researcher). The existing depth field is the real bound; depth-N + cycle + budget is safer and more capable than a blanket ban.
Step 6 · what makes it whole

The cross-cutting rules

These are the parts the as-is hand-waves — and where "half-baked" becomes "designed".

🔐 On-behalf-of attribution

Omnipus is single-user, one password — no multi-user, no RBAC, no tenancy. Delegated work carries the caller's owner (#406) purely as attribution: B acts for you, and the owner stamp threads you → A → B → tools so every action traces back to the same person. Sensitive settings are guarded by re-typing the one password (sudo-style), not by per-user permissions. This spine already exists.

🧠 Context & memory flow

B receives the brief (explicit context) + its own recall — its private room (agent-global) plus the current workspace's shared room — and an optional bounded slice of A's thread. B does not get A's private room. Knowledge flows between agents through the shared workspace room (the workspace's shared room), attributable by author (git-synced), never by copying private journals.

📨 Results never lost

await returns inline. background delivers on the live turn — and if the parent already finished, the result becomes a notification + is appended to the originating session (no silent "orphan" drop, which is a real as-is gap). task result lands on the board + can fire a completion automation.

🔎 Observability & discovery

One call-tree activity view unifies handovers + delegations + tasks (today they're two disconnected UIs). And a capability directory — agents advertise skills (Ray=research, Ava=build) — so A can pick the right target instead of guessing IDs.

Step 7 · it hangs together

A worked flow

In a workspace (say Acme), the user asks Jim · the Orchestrator to "prepare a competitor brief and schedule a review." One request exercises every mode under the single owner (owner=you — attribution; the workspace is just the context it runs in).

  1. You → Jim (Orchestrator) — normal chat. owner=you is stamped on the session.
  2. Jim delegates task to Ray (Scout) — "deep competitor research, cite sources." Tracked on the board, owned by Ray, owner=you inherited. Jim keeps talking to you.
  3. Ray fans out background ×40 — one sub-agent worker per competitor/source, run through the Max parallel agents window, the rest queued. Findings land in the workspace's shared room.
  4. Jim schedules the review on the platform — a task with a trigger/due date lands on the Calendar. No separate automation persona — scheduling and recurrence are a platform surface (a task with a trigger), owned by owner=you.
  5. You want the details — Jim hands over to Ray so you can dig into the research directly (handover is open — no policy gate). Baton moves; Jim steps back.
Every delegation step is governed by the one policy; handover is open by design. All stamped with owner=you (single user — attribution only), visible in one activity tree, with the research knowledge now in the workspace's shared room for next time. No orphaned results, no runaway fan-out.
