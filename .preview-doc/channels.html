The outside world

Channels & Connections

A Channel is how an agent reaches the world — Telegram, Slack, Webhook, Calendar, API. Today each is a system-wide singleton. The redesign makes each a list of Connections with an identity (an agent's own account, or yours) — the one structural change that per-agent bots and the Personal Assistant all depend on. Email is not a conversational channel — it is a tool (a per-agent mailbox account in Connectors, worked on heartbeat, unhandled mail → Board tasks).

Precise words, no overlap

Channel · Connection · Identity · Binding

Channel

A type of two-way conversational link: Telegram, Slack, Webhook, Calendar, API. Email is not a channel — it is a tool over a mailbox account (see below).

Connection

A configured instance (a specific bot, webhook) with its own credentials. Every channel is multi-instance — v0.1.0 ships with a cap of one per type; the cap lifts in v0.3.

Identity

Whose account a Connection is: an agent (a worker's own @RayBot) or you (your account, run on your behalf). Your-identity Connections live in My Workspace, where the Assistant operates them. Agent-identity Connections carry their operating workspace. The model is identity-centric: routing is by agent binding (ResolveRoute), not by project tag.

Binding

Which agent handles a Connection (or a single conversation within it) — resolved by ResolveRoute from the bindings list (peer → guild → team → account → default).

Email Mailbox

NOT a Connection / channel. Email is a per-agent mailbox account (IMAP/SMTP creds + identity) configured in Connectors. The agent reads/sends mail via email tools (read_inbox · search_email · read_message · send_email · reply) on heartbeat (pull, not push). Unhandled mail becomes Board tasks. Keyed by (agent, workspace) 1:1 — one mailbox per agent, living in one workspace.

SUPERSEDED 2026-07-03 (operator decision, ADR-033): ownership is now the (agent, workspace) PAIR — the same agent holds a different mailbox in each workspace (different roles, different inboxes), and several agents may each have mailboxes in one workspace. The "v0.3 cap lifts" milestone below shipped early on hotfix/v0.1.1. See docs/internal/architecture/ADR-033-per-pair-mailboxes.md.

Same family, three words: Channel = the type · Connection = a configured instance · "Connectors" = the screen that lists them (also where a mailbox account is configured, but that is not a Connection — it is an email tool account).
Today · as-is (verified)

System-wide singletons — one per type

Verified hard limit: a channel is a single shared instance for the whole system. The config is a struct with one field per type (config.go:774); the manager keys by type name (manager.go:113, hardcoded if-ladder at :582-708); credentials are per-type; and the bus addresses by type name only — no instance id. You can route a shared bot's conversations to different agents (ResolveRoute / bindings), but you cannot give Ray his own bot or connect your own mailbox.

What works today exists

  • ~13 in-process channels (Telegram, Discord, Slack, Matrix, IRC, Google Chat, WhatsApp…), each a compile-time factory
  • Per-channel routing to a default agent + bindings (peer → guild → team → account → default)
  • Credential-routed secrets (SEC-23): token/secret/key fields go to the encrypted store, a <field>_ref is written to config — no plaintext persisted
  • A WhatsApp native QR pairing seam; a generic WebhookHandler seam

What it blocks

  • Per-agent bots — Ray can't have his own @RayBot
  • The Personal Assistant — needs your own connected account (Telegram, Calendar…)
  • Multiple Slack workspaces / multiple Telegram bots at once
The new axis

Identity — agent vs. user

The same Connection plumbing carries two kinds of identity — an agent's own account, or yours (you're the single user). This is what makes both per-agent bots and the Personal Assistant fall out of one model.

Same Connection plumbing — only the identity (and which workspace it lives in) differs. See Personal Assistant.
Identity-centric, not project-tag-centric (M3, confirmed 2026-06-21). A Connection's "workspace" is driven by identity: user-identity connections default to My Workspace (the Assistant operates them); agent-identity connections carry their operating workspace. Routing is always by agent binding (ResolveRoute, peer→guild→team→account→default) — the workspace field (workspace_id on ChannelInstanceConfig) scopes where the connection lives, not where to route messages. Connections are globally managed (Connectors screen) and the workspace field is additive alongside the identity migration.

🔌 Webhook seam exists

Inbound: a generic webhook connection (Zapier/n8n/Make → Omnipus). Outbound: a webhook-out action — signed POST on an event, with retry + log. Untrusted inbound → HMAC + sender allowlist.

🗓️ Calendar · 🔑 API seams exist

Calendar: a source connection (iCal → provider OAuth → CalDAV; see Calendar). API: scoped API keys for external automation (least-privilege vs today's full-user tokens).

Email — a tool, not a channel · LOCKED 2026-06-21

✉️ Email: mailbox account + tools

Email is not a conversational channel — it does not belong in the Channels framework. Instead, an agent gets a mailbox account (IMAP/SMTP creds + identity), configured in Connectors, and reads/sends mail through email tools. This preserves the pure-Go transport while fitting naturally into the agent's heartbeat loop.

How it works

  • Mailbox account (IMAP/SMTP) configured in Connectors — your address + an app-password, pure-Go (emersion/go-imap/v2 · go-message · go-sasl), no CGo
  • Agent reads/sends via email tools: read_inbox · search_email · read_message · send_email · reply
  • Pull, not push — the agent works its inbox on heartbeat (not an inbound stream)
  • Mail the agent can't fully handle → Board tasks (makes email work visible on the board without a dedicated inbox UI)
  • Ownership: (agent, workspace) — 1:1. A mailbox belongs to one agent and lives in one workspace. An agent has one mailbox, not one per workspace.

Phased delivery

  • 0.1.0 email tool + account config in Connectors + IMAP/SMTP transport. One mailbox = the Assistant's address (your email), in My Workspace. No dedicated inbox UI.
  • v0.2 workspace Email tab — inbox UI (incoming mail + agent replies/actions). Shows only when the workspace hosts an email-enabled agent.
  • v0.3 per-agent mailboxes (cap lifts); provider OAuth (Gmail one-click, Google → MS Graph).
  • v1.0 delegated OAuth (full Gmail/Cal integration).
Dropped: "a thread = a session." An email is not a conversation — it is input to the agent's inbox, processed on heartbeat. The old framing implied an email channel session model that doesn't match the tool/mailbox design.
The redesign · the one big rock

Singleton → multi-instance Connections

This is the highest-blast-radius change in the whole plan — per-agent bots and the Personal Assistant gate on it. The thesis: land the instance shape early (capped at one), lift the cap later.

What changes

  • Config (config.go:774): one field per type → a list of instances {id, identity, agent_binding, secret_ref} — a breaking config-shape migration
  • Contract (Constraint #8): the OpenAPI channel schemas (ChannelEntry / ChannelConfigureRequest) carry an instance id → regenerate Go/TS
  • Manager (manager.go): if-ladder → loop over instances; map keyed by instance id
  • Bus (bus/types.go): add an instance_id — an in-process Go struct field, not an asyncapi change — threaded through dispatch + every send
  • Credentials (channelCredKey): cred key per instance

Sequencing — shape first

  • v0.1.0 land the instance shape (a list capped at one per type) + the OpenAPI change + the Connectors UI (instance list, "add connection"); email ships as a mailbox account in Connectors (tool, not a Connection — see Email section)
  • v0.3.0 lift the cap → real multi-instance · per-agent mailboxes (email cap lifts) · provider OAuth for email (Gmail one-click, Google → MS Graph) · the generic webhook channel · per-agent bots · more channels
  • v0.4.0 user-identity connections (your Telegram/Calendar) deepened + the Assistant's full account vault
  • v1.0.0 chat multi-instance retrofit · two-way calendar
Because the breaking config/OpenAPI migration is done up front in v0.1.0 (cap = 1), v0.3.0 only lifts a constraint — it doesn't re-cut config, the bus, or the UI. That's the foundation-first thesis applied to the rock. See Impact · Roadmap.

External integration rides Channels

An inbound webhook connection (Zapier/n8n/Make) + scoped API keys on the REST surface (create/run task, schedule, send-chat).

Omnipus → External

A webhook-out action in Automations: on an event, POST signed JSON with retry + log. Generalizes cron's deliver path.

Agent → External

Agents already reach Zapier/n8n + 1000s of actions via MCP — the established outbound path, no new channel needed.
