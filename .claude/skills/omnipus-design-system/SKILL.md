# Omnipus Design System

The design system is enforced mechanically by a blocking CI job, `design-system`, in
`.github/workflows/pr.yml` — not by convention, and not by review. That enforcement is
solid: it refuses a new raw `<button>`, untokenised color, spacing, or type size, and a
`src/components/ui/*` file that isn't fully catalogued. What it does not do is teach you
the rule before you break it — an agent normally discovers a rule by failing CI, then
guesses at the fix.

Every rule below is a mistake actually made during the C1 token migration — by a
subagent or by the lead — and caught by a gate rather than avoided by knowing the rule.
Each cites the script or test that enforces it, so you can verify it yourself rather than
take it on trust.

## 1. Controls — never hand-build one

Never write:

- a raw `<button>` or `<dialog>` JSX element
- `document.createElement('button' | 'dialog')`, or a React element-factory call
  (`createElement`, `jsx`, `jsxs`, `jsxDEV`) constructing one
- a `role="button"`/`"radio"`/`"switch"`/`"tab"` attribute on a plain, lowercase tag
- a bare or `window`/`globalThis`-qualified `confirm()` call
- a `Checkbox` or `input[type=checkbox]` wearing `role="switch"`
- an `@radix-ui/*` import, or a low-level shadcn/ui-kit import, from outside the
  catalog's own wrapper

Use the catalogued component instead — `Button`, `IconButton`, `SegmentedControl`,
`RadioGroup`, `ConfirmDialog`, `Switch`, … (see `src/components/ui/` and
`design-system/catalog.json`).

**Enforced by** `scripts/design-system-locks/controls.mjs` (1,319 lines), which fires one
of seven rules: `controls/raw-button`, `controls/raw-dialog`, `controls/global-confirm`,
`controls/checkbox-as-switch`, `controls/radix-import`,
`controls/shadcn-low-level-import`, and `controls/parse-error` (fails closed on a parse
failure — an unparseable file is treated as a violation, not skipped). There is no
separate "element factory" rule: `document.createElement` and JSX/React factory calls are
folded into `raw-button`/`raw-dialog` whenever they construct a `button`/`dialog` tag.

## 2. Values come from tokens — never infer a value from a token's name

Colour, spacing, type size, and line height are registered tokens in
`src/styles/tokens.generated.css` (generated by `scripts/design-system/tokens.mjs` — do
not hand-edit). A literal value is a lock finding, not a style choice.

**The spacing scale is not linear — do not guess a token's pixel value from its number:**

| Token | Value | Token | Value |
|---|---|---|---|
| `--space-0` | 0px | `--space-3` | 16px |
| `--space-0-5` | 2px | `--space-4` | 24px |
| `--space-1` | 4px | `--space-5` | 32px |
| `--space-2` | 8px | `--space-6` | 40px |
| `--space-2-5` | 12px | `--space-7` | 48px |
| | | `--space-8` | 64px |

`--space-3` is 16px and `--space-4` is 24px — an 8px jump, not the 4px you'd guess by
assuming a fixed step. Getting this wrong once would have made every tree indent 50% too
large; a reviewer caught it by reading this file, not by trusting the name.

**Enforced by** `scripts/design-system-locks/spacing.mjs` (the closed spacing scale —
its one sanctioned exception is a 1px hairline border) and
`scripts/design-system-locks/typography.mjs` for type size and line height.

## 3. Tailwind v4 ships OKLCH, and the color names lie

Tailwind v4 (this repo runs 4.3.3) computes its palette in OKLCH. Two named colors can
look close enough to fool a human without being the same token. This repo's own
`--color-warning` is the trap: it's internally named `--primitive-color-amber`, but its
actual value, `#EAB308`, is byte-identical to Tailwind's **`yellow-500`** — not
`amber-500` (`#F59E0B`, a genuinely different color). Swap a raw color for a token only
on byte identity, never on whichever name looks closest. This single trap accounted for
roughly 300 findings in the C1 migration that were correctly left alone, because they
were a different color, not an untokenised one.

**Enforced by** `scripts/design-system-locks/css-colors.mjs` (CSS) and `ts-colors.mjs`
(TS/TSX, including class builders like `cn`/`clsx`) — both match raw color literals
against the token set by value, not by name.

## 4. Alpha on a brand color — `color-mix`, never `rgba`

To apply transparency to a brand color, write:

```css
color-mix(in srgb, var(--color-warning) 20%, transparent)
```

never a raw `rgba(...)` — even as one argument inside a `color-mix`, gradient, or
`light-dark()` call; the lock checks every color-bearing argument, not just the
top-level one. Real compliant usage: `src/components/settings/DiagnosticsSection.tsx`,
`src/components/ui/model-selector.tsx`.

**Verified by** the lock's own fixture suite, `tests/design-system-locks/css-colors.test.mjs`:
a `color-mix` over `var()` tokens produces zero findings; a raw component anywhere inside
one (`#fff`, `rgba(0,0,0,.5)`) fires `css-colors/raw-color`.

## 5. Shadows have their own token family — look under elevation, not color

`--elevation-flat`, `--elevation-raised`, `--elevation-floating`, `--elevation-overlay`
in `tokens.generated.css` are a separate family from the color primitives, interleaved
alphabetically among unrelated tokens rather than sitting next to `--color-*`. Two lanes
independently concluded "no shadow tokens exist" because they only searched the color
tokens. Grep the whole file for `--elevation-`, not just for "shadow" or "color".

## 6. Governed data is not chrome — leave it raw, and say so

Some color usage is deliberately raw because the color is *data*, not a design choice —
tokenizing it would be wrong, not incomplete. Confirmed examples in this codebase:

- **File-type icon colors** — `src/components/chat/AttachmentCard.tsx` (`'#E5484D'` for
  PDF, `'#2563EB'` for Word, …).
- **Audit-log event/decision taxonomy** — `src/components/settings/AuditLogViewer.tsx`
  (`EVENT_STYLES`, `DECISION_STYLES`).
- **Mermaid diagram theme** — `src/components/chat/mermaid-renderer.tsx`, with its own
  comment explaining why (`theme: 'base'`, because Mermaid's `'dark'` theme only lets you
  override ~12 of its ~100 theme variables).
- **Avatar colors** — `src/lib/constants.ts`'s `AVATAR_COLORS`, where the hex value, not
  the name, is documented as the source of truth.

One caution: **task priority (P1–P5) is not a clean precedent to copy.**
`src/components/workspaces/TaskCard.tsx` and `TaskNode.tsx` use raw Tailwind classes for
P1–P4; `TaskDetailPanel.tsx` and `CreateTaskSlideOver.tsx` use semantic tokens
(`--color-error`, `--color-warning`) for the same ladder. The two are inconsistent with
each other today — treat it as an open question, not an example, whichever file you see
first.

If you find raw color in one of the confirmed categories above, it's very likely
intentional — report it if you're auditing, don't "fix" it into a token.

## 7. Focus — one rule owns every cue

The entire product's focus ring comes from one selector, `src/styles/globals.css`:

```css
:focus-visible:not([data-no-focus-ring]) {
  outline: 1px solid var(--color-accent) !important;
  outline-offset: 2px;
}
```

A per-component `focus-visible:ring-*` or `focus-visible:outline-*` utility is banned —
even one that looks harmless duplicates the ring instead of composing with it.
**Enforced by** `src/styles/globals.focus.test.ts`, which (a) checks `globals.css` for
that exact selector and value, and (b) walks all of `src/**/*.ts(x)` (excluding tests)
asserting zero occurrences of `focus-visible:outline` / `focus-visible:ring`.

The only escape is `data-no-focus-ring` — valid only paired with a replacement focus cue
on a parent surface, never used to just remove the ring. Two worked precedents:

- **ChatScreen composer** (`src/components/chat/ChatScreen.tsx`) — the input textarea
  (`data-testid="chat-input"`) carries `data-no-focus-ring`; the replacement cue,
  `focus-within:border-[var(--color-accent)]`, lives on the wrapping
  `data-testid="composer-card"`.
- **ModelSelector search field** (`src/components/ui/model-selector.tsx`) — the
  `CommandInput` carries `data-no-focus-ring` inside a `Command`, with a comment citing
  it as "the sanctioned opt-out ... whose focus is shown by its parent surface."

## 8. Text on an error fill

`--color-error` is `#EF4444`. Put `text-[var(--color-primary)]` on it (`--color-primary`
resolves to `#0A0A0B`, a near-black) — never `text-white`. Measured contrast:
white-on-`#EF4444` is 3.76:1; `--color-primary`-on-`#EF4444` is 5.26:1 — white fails WCAG
AA for normal text (4.5:1 minimum), the token color passes. Real usage:
`src/components/ui/button.tsx`'s destructive variant, `src/components/layout/Sidebar.tsx`,
`src/components/layout/AppShell.tsx`.

This pairing is a design precedent, not a dedicated automated contrast check — the
raw-color locks (`css-colors.mjs`/`ts-colors.mjs`) catch an untokenised fill or text
color, but not a *correctly tokenised, wrongly paired* one.
`src/components/screens/ConnectorsScreen.tsx` still has `text-white` on a raw
`bg-red-600` today — an existing outlier, not a pattern to copy.

## 9. Publishing a component is a four-part contract

Adding a component under `src/components/ui/` and exporting it is not enough. A
published component needs all four of:

1. An entry in `design-system/catalog.json` (`source`, `classification`, `exports`,
   `publicExports`, `publicTypes`).
2. A re-export in the barrel, `src/index.ts` (e.g.
   `export { Button, buttonVariants } from './components/ui/button'`).
3. An explicit `@source "../components/ui/<file>.tsx";` line in
   `src/styles/library.css`. Tailwind's automatic class discovery is off in this project
   (`@import 'tailwindcss' source(none);` — there is no `tailwind.config.*` file at all;
   Tailwind v4 config here is CSS-native). A component missing its `@source` line
   compiles, renders, and ships with **no styles applied**, silently.
4. A manifest, `design-system/manifests/<name>.json`, declaring all eleven verification
   *kinds*: `unit`, `interaction`, `axe`, `keyboard`, `browser`, `pointer`,
   `reduced-motion`, `forced-colors`, `root-size`, `zoom`, `reflow`. A component can have
   many individual checks (Button has 23), but every one of the eleven kinds must appear
   at least once — enforced by the `requiredManifestKinds` list in
   `scripts/design-system/catalog.mjs`.

The repo doesn't call this the "four-part contract" internally — its own name for the
underlying mechanism is the coverage chain "public export → catalog → manifest → story →
executed check" (`scripts/design-system-locks/coverage.mjs`) — but two tests jointly
assert all four parts agree:

- `scripts/design-system/catalog.test.mjs` — `validateCatalog()` cross-checks the catalog
  against `src/index.ts` exports and against every manifest's required check kinds.
- `scripts/design-system/public-api.test.mjs` — diffs the catalog's `primitive`/
  `composite` entries against the literal `@source` lines in `library.css`, and asserts
  the `source(none)` disabling line is present.

## 10. `applicable: false` means "genuinely does not apply" — never "not tested yet"

A manifest check can be marked inapplicable, but only with a truthful `reason`:

```json
{ "id": "separator-interaction-not-applicable", "kind": "interaction", "applicable": false,
  "reason": "Separator has no interaction behavior beyond its covered presentation contract." }
```

(real example, `design-system/manifests/separator.json`). Browser tests are *generated*
from the manifest: `tests/design-system/browser.spec.ts` iterates
`manifest.checks.filter(item => item.applicable && browserKinds.has(item.kind))` and
emits one Playwright `test()` per surviving check. Marking something `applicable: false`
when it actually does apply doesn't skip a test — it means **no test is ever generated
for it, silently, forever.**

## 11. Verify Storybook checks against the static build, never the dev server

`npm run build:storybook` writes to `dist/storybook`; `npm run storybook` (dev server,
port 6006) is a separate script CI does not use. `verify:design-system` and
`audit:design-system` both read `--index dist/storybook/index.json` — the static build's
manifest — never a live server URL. Recorded precedent from the C1 migration: checks run
against the dev server showed 16-of-18 failing, and the same checks against
`dist/storybook` at the same commit showed 18-of-18 passing. Always run
`npm run build:storybook` first, and check against the resulting `dist/storybook`,
before trusting a design-system check result locally.

## 12. Touch targets — the later sibling wins an overlap

`SegmentedControlItem` (`src/components/ui/segmented-control.tsx`) grows its hit region
under `pointer-coarse:` to the touch minimum:

```
pointer-coarse:h-[var(--target-touch-minimum)] pointer-coarse:min-w-[var(--target-touch-minimum)]
```

with a code comment explaining why it must: adjacent controls narrower than the touch
minimum get overlapping `[data-ds-action]` hit regions, and *the later sibling wins the
overlap* — a tap near the boundary selects the wrong control.
`[data-ds-action]` (defined in `src/styles/library.css`) is a shared `::before`
hit-region expander used across several controls (`tabs`, `slider`, `sheet`, `switch`,
`dialog`, `button`, `checkbox`).

This one is currently a documented code comment, not a dedicated automated regression
test — treat the comment as binding, and follow the `SegmentedControlItem` pattern for
any new control with adjacent narrow targets.

## 13. Running the gates, in order

Full inventory, `scripts/design-system-locks/` (9 scripts):

| Script | Proves |
|---|---|
| `policy.mjs` | Loads/builds the live token policy (`colors.json`, `foundations.json`) the other scanners consume. |
| `controls.mjs` | No hand-built controls (rule 1). |
| `css-colors.mjs` | No raw CSS colors (hex/named/`rgb`/`hsl`/`oklch`), including inside `color-mix`/gradients. |
| `ts-colors.mjs` | Same, for colors reaching the DOM through TS/TSX class builders. |
| `typography.mjs` | Type size / line-height come from tokens. |
| `spacing.mjs` | Spacing comes from the closed scale (one 1px-hairline exception). |
| `status.mjs` | Status-token literals are registered, not invented. |
| `coverage.mjs` | The export → catalog → manifest → story → executed-check chain (rule 9) is unbroken. |
| `audit.mjs` | Orchestrates all of the above; hard-blocking, no `continue-on-error`. |

CI job `design-system` (`.github/workflows/pr.yml`) runs, in this order — later steps
depend on files earlier steps produce:

1. `npm run tokens:check` — generated tokens match source.
2. `npm run test:design-system:unit`
3. `npm run test:design-system:locks` — the six-scanner fixture/adversarial suite that
   proves the lock scripts themselves still catch what they claim to.
4. `npm run test:design-system:application-styles`
5. `npm run test:design-system:components`
6. `npm run build:storybook` — writes `dist/storybook` (rule 11).
7. `npm run test:storybook`
8. `npm run test:design-system:browser` — runs the manifest-generated Playwright checks
   (rule 10).
9. `npm run verify:design-system` — reads `dist/storybook/index.json`.
10. `npm run audit:design-system` — the Stage B audit; hard-blocking.
11. `npm run test:design-system:package`
12. Baseline checkout/build/measure, then `npm run build` and
    `npm run measure:design-system-bundle` / the bundle audit — production bundle
    budget and Storybook-exclusion check.

Steps 9–10 must run after 6–8 — they read the static build's index and the evidence
files the executed checks produce.

**Typecheck trap:** `tsconfig.json` is a project-references root with `"files": []` — a
bare `tsc --noEmit` silently type-checks nothing and exits 0. Use `npm run typecheck`
(`tsc -b --noEmit`).

## Escape hatches, all of them

| Situation | Escape hatch | Condition |
|---|---|---|
| A component genuinely has no behavior for a check kind | `applicable: false` in its manifest, with a truthful `reason` | Never for "not tested yet" |
| A surface needs to own its own focus cue | `data-no-focus-ring` | Only paired with a replacement cue on a parent surface |
| A value is governed data, not a design choice | Leave it raw (rule 6) | Report it in an audit; don't tokenize it |
| Spacing needs a 1px line | Raw `1px` | The one sanctioned exception in `spacing.mjs` |
