## Executive summary

The spec is a revision behind its own ADR on the single decision with the largest blast radius in it. Four ADR sections written after revision 3 — **D1.1b** (renderer-process cap, memory formula, admission gate), **D1.1c** (LRU eviction, no error surface, no REST path, no UI change, soft overshoot, thrash detection) and **D1.1d** (three further rulings) — **reverse or replace the spec's entire pool-admission model**, which is still built end-to-end on "refuse at the cap, never evict, and give the operator a close button". That model is load-bearing in 6 FRs, 2 user stories, 4 BDD scenarios, 3 success criteria, 5 TDD rows, 2 behavioural contracts, 3 §5 non-behaviours, an error type, a resolve-outcome enum value and a contract amendment — every one of which is now wrong. Separately, the ADR's **primary** memory control (`--renderer-process-limit`) does not appear in the spec at all, and its stated security precondition is contradicted by the shipped `ValidateURL`.

**Findings: 5 CRITICAL, 9 MAJOR, 5 MINOR, 4 OBSERVATION (23 total).**

**Verdict: BLOCK.**

The four round-2 fixes the task asked me to re-verify **all held** and are confirmed against source (§ Observations O-301…O-304). The block is entirely drift plus the two consequences of D1.1b that the ADR itself flags and the spec has not absorbed.

## Unasked questions

1. **When the pressure gate trips and nothing is evictable, does the pool refuse or overshoot?** D1.1b says refuse; D1.1c says never refuse. The ADR does not reconcile them and the spec has not noticed (M-304).
2. **What is the LRU recency key?** Last tool call, last viewer detach, last tab activity, or last acquire? `ReapIdleSessions` already keeps `lastActivity` and `emptySince` per session — is the pool reusing them, and do they mean the same thing at browser granularity?
3. **What does an evicted workspace's `BrowserManager` do?** FR-040a establishes that a live key with no Chrome is a legal state after idle close. Eviction produces the same state by a different route — does it take the same path, and does an in-flight *panel* stream on an evicted (not idle-closed) instance get the same `browser_status` frame FR-046 was going to send?
4. **Does an eviction produce an audit event?** FR-027 records creation and first cross-agent use. An eviction silently ends a signed-in session's process; under D1.1c nobody is told. "Which agent acted as the signed-in user" (US-13) is answerable; "why did my workspace cold-start" is not, unless thrash detection fires.
5. **Is `--renderer-process-limit=4` compatible with the live panel?** The panel's capture path holds a tab; the D2 spec adds `browser_snapshot`. At N=4 with cross-site embeds, does a workspace with the panel open plus three tabs already hit the limit, and what does Chrome do at the boundary — reuse, or refuse the navigation?
6. **Does `max_total_tabs` still have a purpose?** If the renderer limit is the memory guard, the global tab budget bounds nothing an operator cares about (M-306). Keeping a config key whose stated rationale has been retracted is its own maintenance cost.
7. **What happens on a 3-browser box with 10 workspaces and 4 concurrent users?** D1.1c's worked example assumes *"one or two active at a time."* The spec's own §7 personas (two clients, two workspaces, delegated sub-turns) suggest higher concurrency, and the answer is continuous thrash — visible only if M-301 ships.
