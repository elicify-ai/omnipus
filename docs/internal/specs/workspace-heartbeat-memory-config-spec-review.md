- **Spec reviewed:** `docs/internal/specs/workspace-heartbeat-memory-config-spec.md` (now carrying §1.1 Amendment A1)

- **Mode:** plan-spec (full structural + 8-lens review)

## 1. Executive Summary

Amendment A1 cleanly closes three of the four round-1 CRITICALs by *changing the design*, not papering over it: F-01 (drop the auth gate — matches `handleWorkspacePut` having no owner gate, `rest_workspaces.go:664`), F-03 (dedicated `/settings/memory` endpoint instead of the redacting `PUT /config`), and F-04 (config-flag-driven delete-guard instead of fail-open cron read). Those are real fixes and verified against code.

**But the round-1 CRITICAL F-02 is NOT closed — it has only moved.** A1 says the standing session is "created eagerly when the heartbeat is enabled… stamped `workspace_id`… its id stored at `member_configs[a].heartbeat.session_id`… the cron job *continues* that session (`SessionModeContinue` using the stored id)." Against the code this has **two missing mechanisms**: (1) the eager-creation site is unspecified and `NewScheduledSession(owner)` (`pkg/session/unified.go:292`) takes no workspace and never sets `WorkspaceID`; (2) **`cron.JobSpec` has no `SessionID` field** (`pkg/cron/service.go:1010-1023`), so the reconcile path that builds heartbeat jobs via `cs.AddJobFull(JobSpec{...})` (`heartbeat_schedule.go:192-199`) **cannot inject the stored `session_id`** — it will mint a *new* `NewScheduledSession(owner)` on first continue tick (`schedules.go:506-515`), with no `workspace_id`, orphaning the eagerly-created one. The spec's central data dependency (US-8 pinning under the workspace) is still unimplementable as written.

A second new CRITICAL: **A1/F-02's delete-guard reads `member_configs[...].enabled`, but the guard fires in `deleteSession(id)` which is handed only a session id** (`rest.go:4338`) — the spec never specifies the reverse index (session_id → which workspace/member) the guard must walk, and the only link is the `member_configs[a].heartbeat.session_id` field, which requires scanning **every workspace file** on every session delete. That lookup is unspecified and O(workspaces).

**Findings:** 2 CRITICAL · 8 MAJOR · 5 MINOR · 4 OBSERVATION.

**Verdict: BLOCK** (down from 4 CRITICAL to 2; both remaining CRITICALs are mechanism gaps, not decision gaps — addressable in-spec without an ADR amendment, though F-02 likely needs a small contract touch).

## 4. Test Coverage Assessment

- **Negative paths:** Good (DS-1 validation, DS-2 delete-guard).
- **The two CRITICAL mechanisms are untested:** no test asserts the *fired* heartbeat session id == the eager session id and carries `workspace_id` (F-02); no test defines the delete-guard's session-id→enabled lookup inputs (G-01). These are the load-bearing data dependencies and both are unverified.
- **Boundary gaps:** no exact-at-cap body test; no interval ceiling/overflow test (F-12, F-14).
- **Concurrency:** E5 names the race; no test exercises concurrent PUT + reconcile or the sibling-field lost-update (F-17).
- **Cascade transactionality:** T14 covers happy GC; partial-failure (config GC ok, reconcile fails → orphan job) and workspace-delete cascade (F-13) are untested.
- **SPA "active" derivation:** no test that a *disabled* `type=heartbeat` session shows an enabled trash (F-16).
- **`Session.type` ordering:** no regression test for an unknown enum value nuking the list (F-11).
- **Memory endpoint:** T18 tests the tab; no test that `PUT /settings/memory` leaves sibling config (provider keys, ports) untouched (G-02).

## 5. STRIDE Threat Summary

| Component / flow | Threats identified |
|---|---|
| `PUT /workspaces/{id}` member_configs write | **Elevation/Tampering (accepted):** no owner gate (A1/F-01, matches `rest_workspaces.go:664`) — any authenticated user writes any workspace's heartbeat body, which runs in a privileged agent (F-21). **DoS:** body cap + interval floor mitigate; missing interval ceiling (F-14). **Lost-update:** sibling-field clobber under concurrent PUT (F-17). |
| `DELETE /sessions/{id}` delete-guard | **Tampering/Repudiation:** guard is now config-flag-driven (good, no fail-open), but the **session-id→workspace lookup is unspecified** (G-01) — a missed lookup = silent fail-open in practice. Audit-on-409 specified (good). |
| `PUT /settings/memory` (new) | **Elevation:** auth level unstated (G-02) — if not admin-gated, a user-role account flips global budgets/rate-limits/model allow-list. **Data corruption:** merge must not clobber sibling config trees. |
| Heartbeat body → agent run | **Injection:** verbatim prompt to a tool-enabled agent; weaker authz than the replaced agent form (F-21). |
| Cron job name `heartbeat:<ws>:<agent>` | **Parse:** ws/agent identity encoded in the job name and parsed back; IDs are ULIDs (low risk) but the parse contract is unspecified (relevant to F-06 reconcile keying). |

## 6. Unasked Questions

1. **What exact code creates the eager session, and how does its id reach the cron job's `SessionID`** given `JobSpec` has no `SessionID` field? (F-02 — the round-1 CRITICAL that A1 did not actually close.)
2. **How does `deleteSession(id)` resolve whether `id` is a protected heartbeat session** — full workspace scan, reverse index, or session-meta stamp? (G-01)
3. **Is `IsMain()` = `!IsWorker()` (includes `core`, so Mia qualifies) or `Type=="Main"` (excludes Mia)?** US-7's own Mia example forces the former. (F-08)
4. **Is `PUT /settings/memory` admin-only**, and how does it merge only the 8 fields without clobbering `agents.defaults.*`/`storage.retention.*` siblings or provider keys? (G-02)
5. **How do two save scopes coexist in one autosave-driven `AgentProfile`** without the agent autosave firing on heartbeat-field edits? (F-09)
6. **What triggers reconcile from the workspace-PUT path** (today only agent create/update/delete reconcile), and in what order relative to persist + GC? (F-05, F-06)
7. **Does the live (pre-cutover) `type=scheduled` heartbeat session get re-stamped, or stay unpinned** until re-enable creates a new one? (F-22)
8. **Does workspace-delete delete or merely unprotect the standing sessions**, and where in the existing cascade? (F-13)
9. **Byte or rune cap on `body`,** and what is exactly-at-cap behavior? (F-12)

## 7. Verdict & Next Action

**Verdict: BLOCK** — 2 CRITICAL findings remain. Amendment A1 genuinely closed round-1 F-01, F-03, F-04 (verified against code). But round-1 **F-02 is not closed — it moved**: the eager-session→cron-continue wiring is unimplementable as written (`JobSpec` has no `SessionID`; `NewScheduledSession` sets no `workspace_id`; the continue path mints a fresh session). And the amended delete-guard introduces **G-01**: no specified session-id→enabled lookup, with the only available path an O(workspaces) scan.

Both CRITICALs are **mechanism** gaps (specify the wiring + a tiny contract touch for `JobSpec.SessionID`), not **decision** gaps — so they are addressable in `/plan-spec --revise` **without** another ADR amendment, *provided* the operator confirms (a) adding `SessionID` to `cron.JobSpec`/the heartbeat job, and (b) the delete-guard's lookup strategy (recommend: stamp `workspace_id`+`type=heartbeat` on the session and do an O(1) workspace load). If the operator prefers a session-meta `protected` flag instead, that reopens ADR-027 D4 → escalate to `/albert`.
