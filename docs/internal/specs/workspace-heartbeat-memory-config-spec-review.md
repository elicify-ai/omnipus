# Grill Review — Workspace-scoped heartbeat config + global memory settings UI

- **Spec reviewed:** `docs/internal/specs/workspace-heartbeat-memory-config-spec.md`
- **Source ADR:** `docs/internal/architecture/ADR-027-workspace-scoped-heartbeat-and-global-memory-ui.md`
- **Mode:** plan-spec (full structural + 8-lens review)
- **Reviewer stance:** adversarial, read-only. Assume the worst interpretation ships.

---

## 1. Executive Summary

The spec is well-structured and the BDD/FR/traceability scaffolding is largely complete. But three load-bearing assumptions are **false against the current code**, and one is internally self-contradicting — each will cause the feature to ship broken or insecure as written:

- **The authorization model the spec mandates (US-2/FR-006: owner/admin → 403) does not exist for workspaces.** `handleWorkspacePut` is `withAuth`-gated but, per FR-1.9 (#406), has **no owner/admin access gate** — every authenticated user can write any workspace. The spec demands a 403 path that the codebase deliberately removed. This is unresolved and either reopens a closed decision or is untestable.
- **The heartbeat session has no path to a `workspace_id`.** `CronJob` carries no workspace field and `NewScheduledSession(ownerAgentID)` takes no workspace. FR-010/FR-021/US-8 ("stamp `workspace_id`", "pin under the workspace, not 'No workspace'") have no described mechanism. This is the linchpin of US-8 and it is unspecified.
- **The Memory tab's transport (US-6 "existing config surface" = `PUT /api/v1/config`) is admin-only AND redacts fields on GET**, so a naive read-modify-write round-trip writes `[redacted]` back over real secrets. The spec says "admin" loosely but never reconciles "admin" (config) vs "owner/admin" (workspace) vs the redaction round-trip hazard.

**Findings:** 4 CRITICAL · 9 MAJOR · 6 MINOR · 4 OBSERVATION.

**Verdict: BLOCK.**

## 4. Test Coverage Assessment

- **Negative paths:** Good coverage on member_config validation (DS-1) and delete-guard (DS-2).
- **Boundary gaps:** No exact-at-cap body test (16384 vs 16385); no interval upper-bound / overflow test (F-12, F-14).
- **Concurrency:** E5 names the race but no test exercises concurrent PUT + reconcile, or the read-modify-write lost-update (F-17). Given shared workspace files, this is a real gap.
- **`workspace_id` stamping:** **Untested** — the central data dependency for US-8 pinning has no assertion (F-02).
- **Member-removal/cascade transactionality:** T14 covers the happy GC but not partial failure (GC config ok, reconcile fails → orphan job) (F-05, F-13).
- **SPA "heartbeat active" derivation:** No test that a *disabled* `type=heartbeat` session becomes deletable in the UI (F-16).
- **Idempotency:** `TestReconcile_Idempotent_NewKeying` is listed (good), but no test that a workspace PUT that doesn't touch member_configs leaves heartbeat jobs untouched.

## 5. STRIDE Threat Summary

| Component / flow | Threats identified |
|---|---|
| `PUT /workspaces/{id}` member_configs write | **Elevation/Tampering:** no owner gate (F-01) — any authenticated user writes any workspace's heartbeat body, which then runs in a privileged agent (F-21). **DoS:** body cap + interval floor mitigate; missing interval ceiling (F-14) allows pathological/overflow values. |
| `DELETE /sessions/{id}` delete-guard | **Tampering/Repudiation:** fail-open (F-04) lets a deletable window open under read error; audit-on-fail-open unspecified. Audit-on-409 is specified (good). |
| `PUT /api/v1/config` Memory tab | **Information disclosure / data corruption:** redaction round-trip (F-03) can blank live secrets; admin-only gate is correct but the read-modify-write hazard is real. |
| Heartbeat body → agent run | **Injection:** verbatim prompt to a tool-enabled agent; trust boundary weaker than the prior admin-gated agent form (F-21). |
| Cron job name `heartbeat:<ws>:<agent>` | **Spoofing/parse:** workspace identity encoded in a string name and parsed back (F-02) — colon-in-id or malformed names could misroute; agent/ws IDs are ULIDs so low risk, but specify the parse contract. |

## 6. Unasked Questions

1. **What is the authorization model for workspace member_config writes, given FR-1.9 removed the owner gate?** (F-01 — must be answered before any 403 requirement is testable.)
2. **Where does the standing heartbeat session get its `workspace_id`?** Job-name parse, new cron field, or runner param? (F-02)
3. **What exact endpoint + auth + merge semantics does the Memory tab use**, and how does it avoid writing back redacted secrets? (F-03)
4. **What does "cron state unreadable" mean for an in-process store, and why fail open?** (F-04)
5. **When CoreTeam shrinks via PUT, what triggers GC and reconcile, in what order, and what if reconcile fails after the config is GC'd?** (F-05)
6. **Are the agent-level heartbeat wire fields removed or kept-ignored?** (F-10)
7. **Is the existing `HEARTBEAT.md` body loss (not just the enabled flag) intended at cutover?** (F-07)
8. **Which predicate is "Main-type"** for the tab, the write-validation, and reconcile-skip? (F-08)
9. **Do pre-cutover `type=scheduled` heartbeat sessions get re-stamped to `heartbeat`,** or stay unpinned until recreated? (F-22)
10. **How do two independent save scopes coexist inside one `AgentProfile` slide-over** without one discarding the other's edits? (F-09)
