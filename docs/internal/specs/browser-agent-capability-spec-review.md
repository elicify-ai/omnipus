## 1. Executive summary

The spec was written one commit before the ADR received two operator rulings, and it has not been reconciled with either: it still specifies the omit-values snapshot design that was **declined**, and it still proposes `deny` for delegation-tier workers on `browser_upload_file`, which the ruling **explicitly forbids**. The ADR's stated hard prerequisite for that tool — open issue #659 — appears nowhere in the document. Beyond the drift, the recovery verb for a wedged tab is itself gated by the two mechanisms a wedged tab disables, the snapshot cap requirement contradicts itself in adjacent sentences, and the `file://` route the spec adds names a tool that four of the six seeded browser-using agents are policy-denied from calling.

**Findings:** 5 CRITICAL · 13 MAJOR · 9 MINOR · 3 OBSERVATION (30 total).

**Verdict: BLOCK.**

Credit where due, because it changes what needs re-checking: the spec's code citations are unusually reliable. Roughly twenty `file.go:line` references were re-read independently and every one reproduced — `serve_web` at `web_serve.go:46`, the 62-name Tier 3 fixture, the OR-semantics of `ValidateToolPolicyCoverage`, the tab-0-only listener, the seven previewed names, `capGetText`'s mechanism, the `FSOp` table, all four `text_selector.go` seam symbols. The findings below are about decisions and contracts, not about a spec that invented its own facts.

## 4. Test coverage assessment

**What the plan does well.** The ordering is genuinely risk-first: the two cheapest, highest-consequence tests (`TestValidateOverrideKeys_PanicsOnUnknown`, `TestToolPolicyCoverage_SixNewBrowserTools_NoGaps`) run before any behaviour lands, and the boot-coverage test is explicitly required to be **red first**. Several assertions are written to be un-fakeable on purpose — the `change` event asserted by a page listener rather than by reading `.value`; the upload denial asserted **at the `SetUploadFiles` seam** rather than by the absence of a file; the dialog test asserting a *subsequent* CDP call returns rather than that the dialog vanished. That last one is the right oracle and the spec is right to call it "THE acceptance test".

**Where it is weaker than it looks.**

1. **The dialog acceptance test does not prove what the spec claims.** §8's scenario clicks, handles, then calls `browser_get_text{selector:"body"}` and asserts it returns. That proves the tab answers CDP **after an explicitly handled dialog** — the case where the mechanism worked. It does not prove the ADR's actual guarantee ("the session cannot be left wedged"), because it never exercises the paths where the handle does *not* happen: the C5 lease/viewer lockout, the M5 listener-absent cases, and a dialog raised inside `browser_navigate`'s own load. `TestDialog_UnhandledDialogNamedInTimeout` covers one of those and only for a listener that was correctly installed. Add: dialog while a human holds the live view; dialog while another action tool holds the lease; dialog on a tab whose ctx was recreated; dialog opened before the tab was adopted.
2. **FR-020's tier test is oracle-free for the residual tier** (M7) — it will pass with a typo'd tool name.
3. **US-8/AC3's oracle is the wrong layer** (C4) — it asserts policy *resolution* where the failure is a *hang*.
4. **No concurrency test beyond two writers.** FR-023 has one scenario with exactly two contenders and no assertion about ordering, starvation, or a holder that never releases (M10).
5. **No idempotency / retry tests.** Agents retry. Nothing covers a repeated `browser_handle_dialog` after the dialog is already gone (AC4 covers "none pending" but not "handled twice in a race"), or a repeated `browser_upload_file` against the same input.
6. **The performance test has no runnable definition** (M2), and §10 order 24's placement in the same table as executable tests overstates its status.
7. **Level choice is sound** — the policy/tier/string tests are unit, the CDP-behaviour tests are integration against real Chrome, and only the budget test is E2E. No over-escalation.

## 6. Unasked questions

These are questions the spec should have answered and did not. They are prompts for the author, not findings.

1. **What happens to the write lease and the pending-dialog map when `ReapIdleSessions` (`manager.go:2986`) tears down a browsing context mid-lease?** The reaper exists and takes `m.mu`; the lease and the dialog state are new state on `sessionEntry` with no teardown story.
2. **Does `browser_snapshot` count against the ADR-066 context budget separately from its own cap?** Round-1's unasked question 7 asked this. The spec answers the *cap* and never answers the *budget* — a 64,000-char snapshot plus a 64,000-char `get_text` in the same turn is 128,000 characters of context from two tools that each individually "obey the cap".
3. **What does the `ask` prompt for `browser_upload_file` actually show the operator?** An approval that names only the tool is not a decision. The path? The target origin? Both? This is the entire value of the `ask` the operator ruled for.
4. **`browser_select_option` "multi-select accepts an array" — what is a partial match?** Two of three labels resolve: error, or apply the two? Nothing says, and there is no dataset row.
5. **What happens when role+name matches an element inside an iframe?** The `data-omnipus-tsel` marker plus `chromedp` `ByQuery` are document-scoped; `GetFullAXTree` is not necessarily. This is the most likely way the new locator silently resolves nothing on a real site.
6. **`browser_press_key` with no locator and nothing focused** — no-op, error, or dispatched to the document? The spec rules it takes the lease and skips the gate but never says where the keystroke lands.
7. **If A-3 rules Tier 2 for `browser_snapshot`, who ratifies growing ADR-071's previewed set?** That set was "sized at 7 by a deliberate ADR-071 decision" and the spec's own recommendation grows it to 8. That is an amendment to another accepted ADR, and it also adds a preview line to **every turn's** manifest — a token cost the spec never quantifies.
8. **A dialog raised during `browser_navigate`'s own load (`onbeforeunload`)** — navigate holds the lease and is wedged *before* it returns a tab handle. Which tab does `browser_handle_dialog` target?
9. **Does the `serve_web` route in the `file://` error survive `gateway.preview_enabled = false`?** That flag is live and read per-request (ADR-044); with it off, `/preview/` 404s and the pointer is again a dead end — for Jim too, the one agent who can call `serve_web`.
10. **What is the actual `contracts/` posture if `browser_snapshot`'s handle format is ever consumed by the SPA?** §6 correctly finds no `contracts/` change is triggered today because tool results cross as opaque text. Worth stating that the handle is deliberately *not* a wire type, so a future ActivityPanel rendering of it (C2's mitigation ii) does not accidentally become one without the 5-step process.
