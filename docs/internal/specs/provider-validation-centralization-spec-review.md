# Grill Report: Centralized Provider-Key Validation Spec

**Spec under review**: `docs/internal/specs/provider-validation-centralization-spec.md`
**Reviewed**: 2026-06-29
**Mode**: plan-spec (full structural + 8-lens review)
**Reviewer disposition**: adversarial / read-only. The four locked decisions (D1–D4) are NOT re-litigated; they are pressure-tested for *correct and complete implementation*.

---

## Executive Summary

This spec is well-structured, traceable, and mostly internally consistent — but it ships with **two latent production misclassifications** baked into its own datasets, a **contract that two of its four flows cannot legally satisfy**, and a **central optimisation ("validate only when key changed") whose detection mechanism is undefined and, as the request contract stands, unbuildable as described**. It also asserts an OpenRouter capability ("account-filtered model list") that **does not exist in the codebase**, and requires CLI-side audit logging through a path that **has no audit logger wired in**.

**Findings**: 4 CRITICAL, 7 MAJOR, 5 MINOR, 4 OBSERVATION.

**Verdict: REVISE** (4 critical findings — borderline BLOCK; the C-class findings are each fixable in-spec without re-architecting, so REVISE with mandatory resolution of all four C-findings before `/taskify`).

## Test Coverage Assessment

- **Negative paths**: well covered (InvalidKey, transport, empty key, 422-not-persisted).
- **Boundary**: Dataset B covers empty/whitespace/long-key/unicode/empty-catalog. Good.
- **Missing**: (a) `403 + credential marker` vs `403 PERMISSION_DENIED` discrimination test (C1); (b) `gemini 400 INVALID_ARGUMENT model-not-found → valid` (M6); (c) empty-body 429 → unreachable (M5); (d) SPA "omit api_key on model-only edit" (m4); (e) "validation passed but store locked / reload failed" (M3); (f) re-auth-token-burned-on-422 (M4).
- **CLI audit tests (#18/#20)** are blocked by C4 (no CLI audit logger).
- **Concurrency/idempotency**: re-saving the same key (C3) and concurrent PUT (O3) are named in edges but have no test.

## Unasked Questions

1. **What exactly is "the key changed"?** (C3) — the spec's biggest unresolved hinge. Pin it to a body-level check, not a decrypt-and-compare.
2. **Which marker is in which set?** (M2) — the classifier's actual content is unspecified; Dataset A is a quiz with no answer key.
3. **Does `permission_denied` block or warn?** (C1) — it is *currently* a credential marker but the spec wants its 403 to warn. Cannot be both.
4. **Where does the CLI get an audit logger?** (C4) — D4 mandates CLI audit but the CLI has no logger.
5. **Does OpenRouter actually expose an account-filtered model list?** (M1) — no; the spec asserts a capability that isn't there.
6. **What happens to the single-use re-auth token when the save is 422-rejected?** (M4) — burned, forcing re-auth on retry?
7. **Does validation run before or after `storeCredential` and `TriggerReload`?** (M3) — determines whether "persists nothing" actually holds.
8. **Can the Test/probe responses legally carry `validation`?** (C2) — not under the current contract schemas.
9. **Will re-saving the *same* key trigger a fresh billable probe?** (C3 consequence) — and is that acceptable cost?
10. **Does a native-Anthropic key ever validate, or always proceed-as-Unreachable** because the probe hits `/chat/completions` not `/messages`? (O4)
