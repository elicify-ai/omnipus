## 1. Executive summary

The revision is real work, not a re-labelling: 26 of the 30 round-1 findings are genuinely fixed with new requirements, scenarios, tests and dataset rows behind them, and the two hardest ones — the `Page`-domain question and the fast-path round-trip sequence — are closed against dependency source rather than deferred. I re-read roughly thirty code citations and every one reproduced, including the arithmetic ones nobody would have checked.

What survives is narrower and sharper. Three things block. The `browser_upload_file` seed is asserted in two flatly contradictory states by two BDD scenarios and neither state is producible from the spec's own edit-site list, because §11 footnote ³ confuses the coverage validator's OR-semantics with the runtime resolver's most-restrictive-wins. FR-007's replacement oracle — the one the withdrawn latency budget was traded for — is false on the current click path: `chromedp.Click` appends `NodeVisible`, which issues the `DOM.getBoxModel` the dataset row asserts is never issued. And the two #659 gate tests contradict each other and cannot both be committed: one asserts a GitHub issue's state from inside a Go unit test, the other is required to fail permanently while being listed as the gate that unblocks Stream B.

Beyond those, the lease's relocation is 80% complete — it is tombstoned in the matrix, the TDD plan and the edit sites, but still lives as in-scope work in §1, as an observable promise in §4 and as a holdout in §13 — and §15's single named cross-spec blocker was already resolved in this branch's own HEAD commit.

**Findings:** 3 CRITICAL · 11 MAJOR · 9 MINOR · 3 OBSERVATION (26 total).

**Verdict: BLOCK.**

**On the "all 30 FIXED, none deferred" claim in §14:** 28 are genuine. Two are mislabelled — **M2** is a *withdrawal* (the ≤150 ms budget is gone and what replaced it is a different, weaker claim, which is defensible but is not a fix of the original requirement) and **M10** is *relocation* (the finding now belongs to another document). Both dispositions are correct on the merits; the label is not. See m8.

## 6. Unasked questions

Questions the revision should have answered and did not. Prompts for the author, not findings.

1. **If `chromedp.Click` runs its own `NodeVisible` check after the gate, does the gate still need `CondVisible`?** Dropping it would take the fast path to one `Runtime.evaluate` and remove a duplicated check on the hottest path in the change. Keeping it needs a reason, because C2 shows the duplication is real.
2. **What is the resolved order between FR-034's `visible_only` mode and the four-condition error contract?** With the switch flipped, `ErrNotActionable` presumably never fires — so SC-003's "no bare timeout" and S-09's oracle describe only one of the two shipped modes. Which errors does an operator see in `visible_only`?
3. **Who owns removing FR-034?** SC-009 requires the removal issue to exist and be named in the doc comment, and §5 forbids leaving the switch indefinitely — but nothing names the person or the trigger threshold on the FR-032 counters. "Deleted in the same change that acts on the data" needs someone to decide the data says act.
4. **Does `browser_select_option` by `value` exist?** FR-009 says "accepts `value` **or** `label`" and not one scenario or dataset row exercises `value`. If it is a real parameter it needs a row; if `label` is the only supported form, FR-009's text is wrong.
5. **What does the operator's `ask` prompt for `browser_upload_file` actually render?** B-3 correctly flags that this is the approval flow's change, not the tool's, and files it against #659's work. It is still the entire value of the `ask` the operator ruled for, and "filed as a note" is the weakest of the three dispositions in §15. Should it be a stated exit condition on #659 rather than a note?
6. **When D1 lands `--user-data-dir`-per-workspace, how many Chrome processes does the §10 integration suite start?** §6 correctly warns that tests must stand up their own workspace and that FR-007/SC-004 must run one workspace at a time. Nothing states the resulting process count or memory footprint against the CI worker, and the repo's own testing policy exists because that box OOMs.
7. **What happens to the pending-dialog map and the `dialogListeners` key when `ReapIdleSessions` tears a tab down mid-dialog?** §2.1 says the reaper is "not modified by D2" and routes its lease interaction to D1 — but the dialog state is D2's own new state on `sessionEntry`, and edit site 15 mentions eviction only "at tab teardown". Is the reaper's teardown that site?
8. **If A-3 rules Tier 2, who ratifies growing ADR-071's previewed set?** §12 A-3 now correctly says this needs ADR-071's ratifier rather than this spec's approval — good — but it still does not name them, and §15 item 1 asks the operator to rule without saying whether that ruling is sufficient.
9. **Is `browser_snapshot`'s exemption from the lease traceable?** D1 §14.2 rule 3 cites it as "D2 **FR-018**", but FR-018 is the *values-by-default* requirement; the snapshot's read-only exemption has no FR number in this spec, only prose in §5 and Stream D. A cross-spec citation to a requirement that says something else will not survive the next revision of either document.
