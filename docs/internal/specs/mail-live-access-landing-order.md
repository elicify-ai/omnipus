# Mail live access — landing order and interface ownership

- **Status:** Active coordination record — the landing-order and interface-ownership companion to the six mail-live-access implementation specs (W1–W6) and ADR-20261001 (*Mail live access: pooled connections, folder discovery and a bounded cache*). Written by the architect, 2026-10-02, after the four grill reviews of the spec set all returned BLOCK.
- **Scope:** This document decides **who owns each interface, in what order the work may start, and how the contract-first sequencing rule is applied without deadlocking**. It is spec-only: no production code, no contract-file edits, no tests. It reopens no founder decision; founder-settled answers (Q1=A, Q2=B, Q3=A, Q4=A, Q5=A, #1170–#1175, and the 2026-10-02 preview/download update) are treated as final.
- **Why this exists:** the four grill reports — `adr-grill-1.md` (W1+W2), `adr-grill-2.md` (W3 panel), `adr-grill-3.md` (W4-features + W5-integration), `adr-grill-4.md` (W6 proof + cross-spec) — share one root cause: obligations that one spec **consumes or tests** but that **no production spec publishes**, plus at least one obligation (raw-error redaction) that two specs each assumed the other owns. The specs' sequencing rule ("no code before the contracts are regenerated", Hard Constraint #8) turns that gap into a deadlock instead of preventing a bad hand-rolled type. Until one owner is named per interface, six workers correcting six specs in parallel cannot agree.
- **Certainty convention:** **Verified** = checked first-hand in this task (command output or `file::symbol` read, or a grill finding whose evidence table shows the same check). **Inferred** = reasoned from cited evidence, not re-run here. **Unknown** = no evidence either way.

## 1. Bottom line

**Nothing may be dispatched until three things exist, in this order:**

1. **The one prescribed spec-correction round lands across all six specs**, carrying the ownership assignments in §2 below (each is one row or one paragraph — none is a rewrite). Gate: every row of the §2 register names its single publisher inside a spec file on this branch.
2. **The contracts wave runs, owned by backend-lead in the ADR's W0 role** (ADR-20261001 work-package table, "W0 — contract owner: backend-lead"): schemas edited, `scripts/gen-contracts.sh` run, generated Go/TS/Zod artifacts committed atomically. Gate: `make verify-contracts` green and the regenerated artifacts merged, before any wire-consuming production code or any wire-asserting test goes green.
3. **Only then do the parallel production waves start** (§4). qa-lead may write RED tests in parallel with the corrections, but a RED test whose consumed deliverable has no publisher is **stranded**: the proof package may write tests only (W6 spec, §16 "File-ownership fence"), so nobody would be permitted to make it green. That is the exact ownership inversion the vault-records failure came from — reported complete, wired to nothing.

**Why dispatching RED today would strand tests, concretely:** W6's T1–T6 (instrument record) bind to an emitter that zero production specs implement (verified: `grep -c -i "duration_ms|acquire_wait|socket_count|instrumentation record"` over the W1, W2 and W5-integration spec files → 0 hits each); w4's T36 and w3's US-3 bind to a MIME classifier and paging/search shapes that no spec builds (verified: `grep -c "message_ref"` over W1/W2/W5-integration → 0; `grep -c -i "next_cursor|has_more|view_limit_reached"` over W5-integration → 0). RED written against a shape nobody will build is red forever, and the one rule that should prevent a fake fix (contract-first) is the rule that makes the gap fatal — unless the contract wave itself has an owner. It now does (§5).

## 3. The ownership rules

**R-1 — One publisher per interface, forever.** Each register row names exactly one publisher. A consumer may bind to the frozen shape; it may never re-implement, parallel-type, or quietly extend it. The mechanical guards that make this real: `scripts/check-no-handwritten-wire-types.sh` (hand-written parallel wire types are lint-caught), `make verify-contracts` (stale generated artifacts fail), and each spec's one-writer-per-file fence. Note the instrument check: `verify-contracts` catches *stale* artifacts, not hand-written types — the DoD that cites it for the hand-written claim must name the guard script instead (adr-grill-2 F-12).

**R-2 — Disagreements resolve in this order, one named role per level.**
1. **The two leads involved** — resolved by pointing at this register; the register is the first authority, the specs second, the ADR third.
2. **The architect** — any disagreement about the *shape* of a wire contract, an internal interface freeze, or *who publishes* an interface not in this register. The architect's decision is final unless it touches a founder-settled decision or a founder-visible product behaviour.
3. **The founder** — product, cost or risk decisions only (§6), plus any dispute over a design this document itself authored (recusal rule: the architect never adjudicates a disagreement over their own ruling; those escalate).
4. Team-lead conducts all escalations; a worker never takes a disagreement to the founder directly.

**R-3 — When a consumer needs a field the publisher has not added, the fix path is, in order:**
1. **Stop at the boundary.** Never hand-write a parallel type, never widen a frozen signature locally, never "temporarily" duplicate a generated shape (Hard Constraint #8; the guard script catches exactly this).
2. **Check the register and the publisher's freeze table.** If the field exists in the publisher's spec but not in the generated artifacts, it is a regeneration gap: the W0 owner regenerates; nobody else touches anything.
3. **Request the field from the publisher** — spec-to-spec, through team-lead, one sentence: which row, which field, why the frozen shape cannot serve. The publisher's lead amends its own spec, adds the schema (or asks W0 to), and regenerates — one atomic commit, per the 5-step contract procedure.
4. **If the publisher declines or the two leads disagree**, architect tie-break under R-2.2; the tie-break is recorded as a dated line in this document's register row, not as a side edit.
5. **Only if the tie-break changes founder-visible behaviour** does it become a §6 founder question.

**R-4 — No second implementation of the same thing.** Concretely: one MIME walker (row 15), one recipient rule (`BuildReplyRecipients`, gateway and tool both call it), one exclusion-gate decision (row 18), one presence registry (row 11), one generation construction (row 12), one instrument record shape (row 17), one save-receipt lookup (row 22). Where two specs' tests assert the same observable, the *end-to-end* oracle lives with the publisher's package and the consumer's tests assert the seam (the adr-grill-1 I-4 rule: W1's T16/T21 assert W1-observable callbacks; the cache-visible consequences are W2's V-2 and W6's T15). The proof package writes tests only — it never becomes the fallback implementer of a missing emitter (that is how row 17 would have failed).

## 5. The deadlock ruling

**The rule as written:** "no code before the contracts are regenerated" (Hard Constraint #8, restated in every spec). **The defect:** with no W0 owner dispatched, the rule blocked the very work it protects — six specs each waiting for a sibling that did not exist, with hand-rolled types as the only escape (the thing the rule exists to prevent).

**Ruled, effective on merge of this document:**

1. **Who generates the contracts:** backend-lead, in the ADR's W0 role — the work-package table already names this owner ("W0 — contract owner: backend-lead … Land/freeze each phase's contract changes before its production work"). No seventh spec file is written for the wave; the authoritative requirement set is the union named in Wave B, and this document's register is the cross-check that no consumer queue row is missed. One writer per contract file, always.

Genuine product, cost or risk decisions only. Everything else in the four grill reports' question lists is settled by this document (§2/§5) or is a mechanical correction. Each question: context and impact, options, recommendation, one-line answerable.

**Q-B — Does `email-watch/` get the exclusion too, and a deletion story?**
Context: the watcher state file persists raw error text today (row 19 fixes the *content*; this decides the *file's* lifecycle). The two specs recommend different defaults: w5 recommends exclude + purge on pair removal; w2 defaults to exclude-only, no deletion change.
- **A — Exclude + purge on pair removal** (closes the disclosure path completely; changes what backups contain — hence founder confirmation). *(Recommended.)*
- **B — Exclude only, no deletion change** (files accumulate indefinitely, as today).

**Q-C — Refresh-on-open: only when stale, or exactly once per event?**
Context: the ADR's founder-brief-derived rule refreshes headers/counts on open or folder switch **only when absent or older than 5 minutes**; w3's US-1 pinned "exactly one live refresh per event, even when fresh". The difference is how often the panel dials the server — the pooling design's core load concern — and what the panel tests assert.
- **A — Restore the ADR's stale-gating** (live refresh on open/switch only when absent or >5 min stale; manual Refresh always; own-action refresh unchanged). *(Recommended — matches the design, the measurement plan, and w3's own §3.1/MC-W3-2.)*
- **B — Keep exactly-one-live-per-event** as a deliberate amendment (more live dials; must be recorded as a dated ADR correction and disclosed to the measurement lanes).

**Q-D — Folder search: which fields?**
Context: the ADR requires the revised spec to define "exact supported matching fields and limits" for the folder-scoped server search (row 4). This is the user-visible capability boundary, not an implementation detail.
- **A — SUBJECT + FROM/TO substring matching, server-side IMAP header search, 25/200 bounds.** *(Recommended — w3's own recommendation; enough to make "search to find older messages" honest.)*
- **B — SUBJECT only** (smaller surface; weaker answer to the 200-row wall).

**Q-E — Saved mail-derived files: ordinary workspace rules, or extended restriction?**
Context: w3's UAT holdout 5 expects zero network requests from a **saved** mail attachment's markdown; the ADR and w3's own positive control make the mail-restricted resource policy apply to the **temporary view only** — after Save, a file is an ordinary workspace file. The founder's Q5=A settled scripts-off + per-file checkbox for saved HTML; it did not settle saved non-HTML resources.
- **A — Ordinary workspace rules after Save; rewrite holdout 5 to target the temporary view** (e.g. the same attack from an unsaved preview). *(Recommended — matches the ADR and the recorded positive control; no new policy layer.)*
- **B — Extend the mail-restricted resource policy to saved non-HTML files too** (a design change beyond Q5's answered scope; must be recorded as a founder decision and reconciled with the positive-control baseline).
