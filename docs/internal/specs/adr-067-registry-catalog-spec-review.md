## 1. Executive Summary

The spec is unusually thorough on the happy path and on greenfield enforcement, but it inherits three false beliefs about the code it says it keeps "unchanged", and each one ships a real defect: the existing version comparator cannot order the spec's own `YYYY.M.D` version format (the catalog would refuse every October release and every day-10 release as a "regression"); the existing puller *accepts* a release with no `.sha256` sidecar, which the spec asserts is rejected — and with signing not adopted, that is the one integrity check the design has; and the spec validates nothing about the `api` URL that every API key is about to be sent to. The assembly-side "last known good on disagreement" rule is also unimplementable as written, because the two registries disagree on tokeniser-rounded numbers for a large share of models, which turns "open an issue" into a standing flood.

**Findings: 3 CRITICAL · 14 MAJOR · 11 MINOR · 6 OBSERVATION.** **Verdict: BLOCK.**

## 4. Test Coverage Assessment

- **Test levels:** sensible — unit for parsing/dispatch, scoped gateway tests for REST, two CI gates. T24 (AST scan) is the right tool for "no vendor cases".
- **Atomic-landing requirement (HIGH-impact flag, §3):** it *is* testable, and the spec should say how rather than calling it a process rule: deleting `GetDefaultAPIBase`/`IsKnownProtocol`/`knownProtocols` in the same commit as the table-backed factory makes a partial state a **compile failure** at all 13 call sites — that is the enforcement. T24 adds the AST guard so nobody re-adds a vendor case. What is *not* testable is "the regression set green at landing" — that is CI. Recommend the spec state: "Partial state is prevented by deleting the three symbols in the same change; T24 prevents regression; the PR is not mergeable until §7.2 is green." Also recommend splitting the work into reviewable commits inside one PR (add table + protocol path first, delete switch second) — the PR lands atomically, the history stays readable.
- **Negative tests missing:** URL scheme/host rejection (F-03); sidecar absent → reject (F-02, currently inverted); truncated body (F-05); unknown id with `api_base` (F-09); mixed known/unknown pool (F-14); entitlement on a non-listing protocol (F-12); weak ETag / unquoted ETag (F-29).
- **Boundary tests missing:** version ordering across day-10 / month-10 / year rollover (F-01); `protocols[]` invariants (F-19); `ProbeProviderRequest.id` has DS rows for "" and 300 chars but no `maxLength` in the schema, so the 300-char case is "unknown provider" by accident, not by contract.
- **Concurrency:** T14 covers the refresh mutex; nothing covers `GET /providers/catalog` racing an apply (the served bytes and the ETag must come from one atomically-swapped pair — say so).
- **Idempotency:** DS-4.8 (equal version applied) matches `refreshLocked`'s `Compare < 0` check — correct.
- **Regression blind spots:** `pkg/voice/audio_model_transcriber.go` and `pkg/providers/legacy_provider.go` are named in the impact table but no test in §7 exercises them after the collapse; `cmd/omnipus/internal/onboard/validate_integration_test.go` depends on `GetDefaultAPIBase` (lines 11–14, 439, 586) and must be rewritten — not listed in §7.3.

## 6. Unasked Questions

1. Which field is the catalog provider key for an agent — `ModelConfig.Provider`, the `provider/` prefix on `Model`, or both, and what happens when they disagree? (F-06)
2. What does `custom` mean now — a row, an exception, one endpoint or many? (F-07, F-08)
3. What does the assembly job do when `models.dev` **removes** a provider or model that a configured agent uses? (`status: retired` covers models the registry marks retired; it does not cover rows that vanish. Does the job carry them forward from last-known-good forever?)
4. What happens to a model's `context_window` when an operator has a per-agent override (ADR-066 D2 "override can only lower") and the catalog later **lowers** the window below the override? The spec says the ladder decides; ADR-066 says `min(override, catalog)`; neither says the override is re-clamped on refresh.
5. How does a closed disagreement issue feed back into the published value? (F-04)
6. Is the transport built from a catalog `api` URL subject to the SEC-24 SSRF dialer, the internal-CIDR egress block (v0.2 #155), and the proxy setting on `ModelConfig.Proxy`? (F-03)
7. What is the disposition of every factory case that is neither in the nine local-file ids nor obviously in models.dev — `longcat`, `modelscope`, `azure`, `azure-openai`? (F-16)
8. When the catalog refresh changes the popular set or a provider's `api` URL, do already-constructed provider instances pick up the new URL on the next turn, or only after reload? (Today a provider instance is built once per agent; the spec's "table" is read at construction. State whether refresh triggers `TriggerReload`.)
9. Does `GET /api/v1/providers` (configured-only, FR-029) still return `models[]` filled from the catalog for each configured provider, and is that the surface the picker's "configured models" reads — or does the SPA join `GET /providers` with `GET /providers/catalog` itself? US-9.AC1 implies the former; US-7.AC6 implies the list is thin.
10. What is the user-visible behaviour when the embedded snapshot is valid but **older** than a persisted file that fails the new URL validation (F-03)? The persisted one is ignored with one WARN (FR-010) — and the operator never learns that their last good pull was rejected for a new rule, only that the snapshot is serving.

## 7. Verdict

**BLOCK.** F-01 (version ordering halts refresh every October and on day 10), F-02 (missing sidecar is trusted, and the spec asserts the opposite), and F-03 (no URL validation on the endpoint keys are sent to) must each be resolved before task decomposition. F-04 (disagreement rule floods issues and marks most of the catalog disputed) is assembly-side but is the contract this spec claims to define, and the fix changes the document shape, so it belongs in the same revision.
