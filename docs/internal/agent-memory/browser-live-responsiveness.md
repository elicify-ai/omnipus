Research done 2026-07-16 with the operator on why the live browser panel feels slow (scrolling, rendering, video), on branch `bugfixes2`.

**Root cause (structural, ADR-038 trade-off):** the live view is a full-page JPEG-per-frame CDP screencast pipeline: Chrome renders → CDP screencast frame → JPEG encode → base64 (~33% overhead) → WS text frame → Fly proxy → SPA `<img>` swap. Parameters are constants in `pkg/tools/browser/live.go` (~:21-24): `screencastQuality=60`, `1280×720`, `everyNthFrame=1`, plus a CDP ack round-trip per frame (5s timeout) that stalls the frame rate when slow. Each frame ≈50–150 KB → 1.5–4.5 MB/s at 30fps; on the constrained pod + Fly proxy hop each frame round-trips 100–500 ms, so every scroll step lags by that much. Video playback is the worst case (full-frame changes at 24–60fps → pipeline saturates, ack throttles to a few fps). This is inherent to screenshot streaming (ADR-038 chose CDP screencast over VNC/RDP/SPICE), not a code bug.

**No audio (videos are silent):** `chrome-headless-shell` (see `pkg/tools/browser/installer.go` ~:23) has no audio stack; CDP `Page.startScreencast` carries no audio track; the `BrowserScreencastFrame` WS type has no audio channel. Fixing needs full Chrome + an audio capture/stream (WebRTC or similar) + a new wire channel — a v0.3-scale feature, not a tweak.

**Already fixed** (commit `998c8f11`, earlier that day): double-cursor (synthetic yellow cursor overlay removed — native cursor used while driving) and scroll lag from `setCursorPos` re-rendering the whole component (incl. the screencast `<img>`) on every pointer move.
