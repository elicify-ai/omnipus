File-Sending & Skill-Install: what's broken and how to fix it

Two things you noticed while testing — an agent couldn't send you a file it clearly had, and skills an agent installs go to the wrong place. Both are real. Here's exactly why, in plain English, with the fix.

1 · The short version

Bug 1  Sending files. There is one tool that sends a file to you in chat: send_file. It checks paths with the same function read_file uses — but it was wired up with narrower settings and never updated when the other file tools got two upgrades. So send_file's "allowed files" list is a strict subset of what the agent can actually read. The everyday result: an agent working in a shared workspace can read/create a file there, then fails to send it. Your instinct is right — this restriction is an accident of wiring, not a security decision.

Bug 2  Installing skills. There are two ways a skill gets installed, and they disagree. The button in the UI (POST /api/v1/skills/install) installs to the central skills folder — correct. The chat tool (install_skill) installs into the calling agent's own private folder — wrong. So when an agent installs a skill by talking to it, no other agent (and no UI screen) can ever see that skill. The "central registry + per-agent checkboxes" you remember already exists and works; only the chat tool writes to the wrong place.

Bug 2b  The Ava case. You asked Ava to install skills for a new agent; they landed on Ava instead. That's a direct consequence of Bug 2 plus two more gaps: install_skill has no "which agent" parameter, and create_agent has no way to hand skills to the agent it creates. There is currently no path — tool or API — that says "give skill X to agent Y."

Good news The target design is mostly already built. The fixes are small and land on a handful of known lines. Bug 2's core fix is essentially one call site.

2 · Problem 1 — Agents can't send files they can read

What you saw

An agent had access to a file but couldn't send it to you. It likely replied with something like "access denied: path is outside the workspace" or "file not found".

What's actually happening

send_file is the only tool that delivers an arbitrary local file to you as a chat attachment. (pkg/tools/send_file.go; it's the sole caller of MediaResult in pkg/tools. send_email is a different channel and has no attach-file support.)

It validates the requested path with validatePathWithAllowPaths (pkg/tools/filesystem.go:26-87) — the very same function used by read_file, write_file, list_directory, and bash. So in principle the rules are identical. The problem is that send_file is fed narrower inputs than read_file, through two wiring gaps:

Gap 1 — the everyday one: shared-workspace re-rooting isn't applied to send_file

When an agent belongs to a Workspace's team, all its file tools are re-pointed for that turn to the shared project directory workspaces/<id>/work/ instead of the agent's own private agents/<id>/ folder. This is unconditional — no feature flag (pkg/agent/loop.go:5603-5673, via WithTurnWorkspaceDir).

read_file, write_file, list_directory (through the shared rerootable helper) and bash (pkg/tools/shell.go:507) all honor this. send_file does not — it has zero references to the re-rooting mechanism and always validates against the agent's private workspace.

Effect: a file the agent just created or read in the shared work/ directory is checked by send_file against the wrong root. A relative path resolves to a nonexistent spot under the private folder → "file not found"; an absolute path into work/ fails the "inside my workspace?" check → "access denied: path is outside the workspace". This needs no special configuration — it happens for any team agent using the default shared project directory.

Gap 2 — the escape-hatch one: AllowReadOutsideWorkspace isn't applied to send_file

When an operator turns on the read-anywhere escape hatch, read_file/list_directory become fully unrestricted (pkg/agent/instance.go:133-134 computes readRestrict = restrict && !AllowReadOutsideWorkspace). But send_file is built with the raw RestrictToWorkspace flag and never sees AllowReadOutsideWorkspace (pkg/agent/loop.go:1449-1455). So even with the hatch open, read_file can read the whole host but send_file stays boxed in.

How a file actually reaches you (for context)

send_file → registers a media://<uuid> reference (NO copy of the file is made) → WebSocket "media" frame with URL /api/v1/media/<ref> → gateway streams the ORIGINAL file from disk (http.ServeFile) → SPA renders it as an inline image / download card

Refs: pkg/media/store.go:52 (no copy) · pkg/gateway/webchat_channel.go:149 · pkg/gateway/rest.go:8801. The file is served straight from wherever it lives — there is no "uploads" copy step that would need its own directory rules.

What is correctly restricted — and must stay

One restriction on send_file is deliberate and shared symmetrically with read_file: an agent cannot read or send files from another agent's private workspace (isCrossAgentPath, pkg/tools/filesystem.go:98-115; red-team tests in redteam_cross_agent_test.go). That's an intentional insider-isolation control and is not the cause of your complaint. Likewise, secret files like master.key / credentials.json should remain non-readable in the first place (pkg/sandbox/sandbox.go SecretFilesRelative).

Is your thesis right? assessment

For this bug: yes. There is no comment, test, or design doc anywhere claiming send_file is deliberately narrower than read_file for anti-exfiltration reasons. The narrowness is an accidental omission — send_file simply wasn't updated when the re-rooting refactor and the readRestrict computation were added to the other tools.

One nuance on "restrictions should only ever be at the sandbox/access level, never at send": as an absolute rule that's slightly too strong. An agent may legitimately need read access to system files for its own operation without that meaning it should hand every such file to a user (egress control is a valid defense-in-depth layer in multi-tenant setups). But that's a future, deliberate, named policy — it is not what exists today. Today the correct fix is simply: make send_file's allowed-file set equal read_file's. If we can read it, we can send it.

The fix

  1. Give SendFileTool the same rerootable behavior the other file tools have, so it honors the per-turn shared-workspace directory (closes Gap 1).
  2. Construct send_file with the same readRestrict value read_file uses, instead of the raw RestrictToWorkspace flag (closes Gap 2).
  3. Keep the cross-agent guard and the operator AllowReadPaths whitelist exactly as they are — they already apply to both tools equally.

Net effect: send_file's "can I send this?" answer becomes identical to read_file's "can I read this?" answer, at both the kernel (Landlock, already identical) and app level.

3 · Problem 2 — Skills install to the wrong place

Three "skills folders" that don't line up

The codebase has three different on-disk skill locations, and the tools disagree about which one to use:

FolderMeant to beWho writes here
$OMNIPUS_HOME/skills/ The central / global registry ✔ Seeded at boot; scanned by every agent as the "global" tier; written by create_skill, edit_skill, and the UI's POST /api/v1/skills/install.
$OMNIPUS_HOME/workspace/skills/ Shared "default workspace" tier Where the system tools list_skills / remove_skill look.
$OMNIPUS_HOME/agents/<id>/skills/ An agent's private folder the bug The chat tool install_skill writes here — into whichever agent invoked it.

The core bug: the chat install_skill tool writes per-agent

install_skill computes its target as filepath.Join(t.workspace, "skills", slug) (pkg/tools/skills_install.go:97-98), where t.workspace is the calling agent's own private workspace, baked in when the tool is built once per agent (pkg/agent/loop.go:1480 passes agent.Workspace). It has no "target agent" parameter — only slug, version, registry, force.

So a skill Jim installs by chatting lands in agents/jim/skills/<slug>/ — and is invisible to:

  • the GET /api/v1/skills catalog the UI shows (it reads the default agent's view of skills);
  • every other agent's own skills loader;
  • validateSkillIDs — so that skill can't even be granted to another agent through the UI, because the backend doesn't believe it's installed.

Two install paths, two behaviors: the UI button (POST /api/v1/skills/install) installs to the central folder — visible everywhere (pkg/gateway/rest.go:4437). The chat tool (install_skill) installs to the caller's private folder — visible to no one else. Same word "install", opposite outcome.

What already works (your "central registry + per-agent" memory is correct)

  • Central catalog: GET /api/v1/skills lists installed skills from the global tier.
  • Per-agent enablement data model: AgentConfig.Skills []string (pkg/config/config.go:771) — empty/absent means "all skills allowed"; a non-empty list means "only these." Enforced each turn by WithSkillAllowlist (pkg/agent/context.go:161-196).
  • The UI you remember: the Agent profile's Skills section renders the central catalog as one checkbox per skill and saves the chosen list via PUT /api/v1/agents/{id} (src/components/agents/AgentProfile.tsx). This is exactly "install once centrally, then toggle per agent" — and it works, for skills installed via the central path.

So the whole "skills behave like tools: one central registry, enabled per agent" model is already built. The only thing off-model is the chat tool's write location.

4 · Problem 2b — Why Ava installed skills for herself

You asked Ava (the agent-builder) to install skills for a brand-new agent. Three separate gaps combine to make that impossible today:

  1. create_agent can't hand over skills. Its parameters (pkg/sysagent/tools/agent.go:83-149) include name, model, soul, etc. — but no skills field. It creates an empty skills/ folder for the new agent and never puts anything in it.
  2. install_skill can't target another agent. The tool call is dispatched against Ava's tool registry, whose install_skill was built with Ava's private workspace. There is no argument, and no runtime hook, to redirect the write to the new agent. So it lands in agents/ava/skills/.
  3. No "assign skill X to agent Y" exists anywhere. Not as a tool, not as an API. The closest thing (the global REST install) gives the skill to everyone, which is not the same as equipping one specific agent.

Could delegation solve it? In theory Ava could delegate "install this skill" to the new agent, and thanks to delegation identity rules the install would correctly run as the new agent (into its own folder). But it dead-ends twice today: (a) no agent tool can create the workspace delegation trust edge a new agent would need — only a human via PUT /api/v1/workspaces/{id}/delegation; and (b) a fresh agent's default tool policy denies install_skill outright (NewCustomAgentToolsCfg, pkg/coreagent/core.go:1085 — allows only read/list/remember/recall). Not a practical path without changes.

5 · The proposed model — one rule for both problems

The same principle fixes both areas: store centrally, gate per-agent. That's already how tools work, how skills are meant to work, and (after Problem 1's fix) how files should work.

Files

Rule: if an agent can read a file, it can send it. Access is decided once, at the read/sandbox layer (kernel Landlock + the app-level workspace rules). send_file stops computing its own narrower answer and reuses read_file's. No separate "send allow-list."

Skills

Rule: every install goes to the central registry ($OMNIPUS_HOME/skills/); which agent may use a skill is controlled by that agent's Skills allow-list. Concretely:

  • Point the chat tool at the central folder. Change install_skill's target from the calling agent's workspace to the global skills dir. Per the investigation, "once that one call site is corrected, nothing else needs to change" for basic central install — the catalog, allow-list, UI, and validation already do the rest.
  • Preserve "install for myself". When an agent installs a skill for its own use, also add the slug to that agent's Skills allow-list (if it has one) so the self-serve experience still works after the central move.
  • Add "equip another agent". Give install_skill an optional agent_id (and/or add a small dedicated "assign skill to agent" operation) that installs centrally and adds the slug to the target agent's allow-list.
  • Let the builder equip at creation. Add an optional skills: [] parameter to create_agent that seeds the new agent's allow-list (installing any missing ones centrally first). This is the clean fix for the Ava case.
  • (Optional) enable the delegate path for "go install this for yourself," if we want it: needs an agent-reachable way to add a delegation edge and a policy that lets a new agent hold install_skill.

8 · Decisions we need from you

  1. Files: confirm the target rule is simply "if the agent can read it, it can send it" (no separate send-only restriction now). If you ever want a deliberate egress boundary later, we'd add it as a named, tested policy — not an accident.
  2. Self-install after centralizing: when an agent installs a skill for itself, should we auto-add it to that agent's allow-list, or install centrally-only and leave enablement to the UI? (Recommended: auto-add, so nothing regresses.)
  3. Cross-agent equipping: prefer an agent_id parameter on install_skill, a dedicated "assign skill to agent(s)" operation, or both?
  4. Ava/builder flow: is a skills: [] parameter on create_agent the flow you want (equip at creation), plus post-creation assignment?
  5. Delegate-install: in scope now, or leave for later? It needs two extra changes (edge creation + policy) that the other fixes don't.
  6. Release phase: these touch agents/skills/workspaces — per the routing rule that's v0.3 territory, but the file-send fix is a small correctness bug that could ride a hotfix. Which phase do you want each in?
