**Reviewed:** `/Users/danielpiatkowski/AI-Agent-Workspace/omnipus/wt-agent-refresh/docs/internal/design/dev-team-setup-design-2026-09-25.md` (read-only; not modified by this review)

---

## Verdict

**APPROVE WITH CHANGES.**

The architecture is sound and unusually well-evidenced: one shared rules file, one orchestrator living in the main session, small single-job role files, and a mechanical guard keeping them honest. No finding below questions that fundamental shape. One High finding (the `tools:` allow-lists as written would cut every implementer off from GitNexus, breaking a MUST rule in root CLAUDE.md) must be resolved **before rollout steps 3–4**; two Mediums (shared-rules length, one model name inside the adopted shared-rules file) should be resolved **before step 1 lands**. The rest are cheap fixes that can ride the normal drafting work.

Counts: **1 High / 13 Medium / 6 Low**.

## Notes

**What this review verified itself (evidence, not trust):**

- Frontmatter ground truth: all six existing files use `name`, `description`, `model`, and (three of them) `skills`. No existing file uses `tools:` — §4.2 introduces it to this repo. That is legitimate (the field is real in Claude Code 2.1.x; this session's own agent list shows per-agent tool restrictions), but it makes H1's resolution mandatory, not optional.
- `.claude/settings.json` holds `enabledPlugins` only, as §2.1 states.
- `.claude/shared/agent-rules.md` exists at the recommended path, is 241 lines, and its header names all ten consumer roles plus the six plugin reviewers — consistent with §6.3.
- Skills inventory: 11 `SKILL.md` files, six of them **nested** under `.claude/skills/gitnexus/` — the basis of M9.
- Independence scrub (founder dimension): the design document is clean — no model names, tiers, ladders or CLI names (grep, case-insensitive). D2: nothing to flag in the document. D3: one model name in the adopted shared-rules file → M12.
- The §5.3 claim "no CI workflow or repo script runs Claude" was re-checked and holds: the only workflow matching "claude" (`evals-nightly.yml`) passes a judge-model name string to a Go eval runner; it never invokes the Claude CLI. The other grep hits are scripts that mention the CLAUDE.md filename.
- Cited paths that exist as claimed: `docs/internal/false-green-patterns.md`, `docs/internal/v01-implementation-plan.md`, `scripts/guards.sh` (discovery header confirms zero-wiring claim), `scripts/check-agents-md-sync.sh`, `pkg/sandbox/backend_darwin_seatbelt.go`, `.opencode/agents/`.

**On the boundary questions posed to this review:**

- **qa-lead vs uat-validator vs pr-test-analyzer** — clean separation once stated: qa-lead *authors tests*, uat-validator *verifies UI behaviour evidence*, pr-test-analyzer (plugin) *reviews PR test coverage*. Three different objects of work; no finding needed. The real friction is elsewhere: qa-lead's local-run scope and the unnamed test-integrity-auditor overlap (M8).
- **Role-boundary verdict overall** — the catalogue's "Owns / Must never" columns are the right instrument; the three soft spots are ci-triage vs tree ownership (M7), architect's three hats (M6), and the unassigned surfaces in L4.

**Testability:** the §10.2 dry-run table is the strongest part of the design — every role has a known task and pass criteria, including the headless variant for team-lead. The gaps are recording evidence (L5) and adversarial dispatches that prove the shared rules outrank dispatch prompts (M11b) — the one behaviour the whole design leans on that no current dry-run tests.

**Order-sensitivity worth restating:** H1's resolution belongs before rollout steps 3–4; M1 and M12 belong before step 1 lands (the shared-rules file is adopted there). Everything else can ride the normal drafting and review flow.
