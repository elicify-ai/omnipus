Omnipus · Target design · Judge & Plan Supervisor

Judgment first

The Judge decides whether work is done the way a capable human reviewer would — by reading the written acceptance criteria and Definition of Done, weighing the real evidence, and making a considered call. Technical checks stop being a requirement and become what they should have been all along: optional supporting information, used when they happen to apply.

The two principles

1

Never dependent on technical checks

A task or plan must be fully judgeable with zero technical acceptance criteria. Exit codes, command runs, and action counts are extra signal — welcome when the work happens to be technical, irrelevant when it isn't. Drafting an email, researching a topic, writing a strategy memo: none of these have an exit code, and the system must treat them as first-class work, not an afterthought.

When a technical check is present and applicable, the Judge reads its result as one more piece of evidence — informative, sometimes decisive, never the gatekeeper that decides whether judging is even possible.

2

Judge written criteria like a human would

The primary basis for every verdict is the written acceptance criteria and the Definition of Done — read with common sense, in context, as a whole. Not pattern-matched, not reduced to a checklist of mechanical lookups. A human reviewer asks: does the actual work, as evidenced, genuinely satisfy what was asked? That is the question the Judge answers.

Human-style judgment does not mean lenient. The Judge stays skeptical: the worker's own summary is a claim to verify, never proof. No evidence still means not done. But the reasoning over the evidence is judgment, not a program.

One skill governs how every goal becomes criteria

Today, how a goal turns into acceptance criteria depends on where it was created — chat goals go through a compiler, agent-created tasks improvise, and each path has its own quality. In the target state there is one built-in skill — a shipped coaching guide, like the built-in skills agents already use — that governs criteria-writing everywhere, automatically:

  1. A goal arrives — a person types it in chat, or an agent is creating a task or plan. The path doesn't matter; the skill triggers automatically in all of them.
  2. The skill guides the rewrite. The agent restates the goal clearly and breaks it down into distinct, judgeable acceptance criteria and a Definition of Done — written in plain language, following the quality bar the skill defines (below).
  3. Unclear goals get questions, not guesses. If the goal is ambiguous — success could reasonably mean two different things — the agent asks the person (or the delegating agent) before locking anything in. A criteria set built on a guess is worse than a short delay.
  4. The result is echoed back for confirmation. The person sees the criteria in plain language — the actual things the Judge will later hold the work to — and confirms or amends before the goal goes active. (Chat goals already have this confirm step; it extends to become the universal pattern.)
  5. Technical checks attach only where they earn their place. The skill teaches when a real command check genuinely adds value — and that its absence is normal, not a deficiency.

Because it's a skill — a readable, editable document, not compiled logic — the quality bar can be tuned, improved, and versioned without touching the engine. And because it's built-in, every fresh install has it from day one.

What good acceptance criteria and DoDs look like

The skill's core content. A good criterion is one a fair reviewer — human or Judge — can rule on with confidence, and the person who set the goal would recognize as their intent:

  • Outcome, not activity. It describes what exists or is true when the work is done — not the steps taken. "The summary covers all three quarterly reports" — not "read the reports."
  • Observable. Its truth can be seen in real evidence: something produced, changed, sent, or visible in the record of what happened. If no evidence could ever show it, it can't be judged.
  • Specific enough to fail. A criterion that any half-effort would satisfy isn't a criterion. "The email is polite, addresses each of the customer's three questions, and proposes a concrete next step" can fail; "the email is good" can't.
  • One thing per criterion. Each criterion is separately judgeable. Bundling three requirements into one line means a partial failure gets an unclear verdict.
  • Complete but minimal. Together, the criteria cover everything that matters for "done" — and nothing that doesn't. Padding with easy criteria dilutes the meaningful ones.
  • Written for the judge that will read them. Plain language, no insider shorthand, no references to context the Judge won't have.
Good

"The research note names at least three competitors, states each one's pricing model with a source, and ends with a recommendation the reader could act on."

Fails honestly if any part is missing; judgeable from the produced document alone.

Not good

"Do thorough competitor research and write it up well."

"Thorough" and "well" can't fail — any output arguably qualifies. The Judge is left guessing what the goal-setter meant.

Good

"Every customer question from the ticket is answered in the reply; the tone stays apologetic about the delay without over-promising a date we can't commit to."

Two criteria, each independently judgeable against the actual reply text.

Not good

"Handle the ticket. Also the tests should pass."

"Handle" is activity, not outcome — and a test check bolted onto a non-technical goal is noise, not rigor.

What this means for the Judge

The evidence hierarchy inverts. Today the system leads with the machine-checkable and treats prose as the leftover category. In the target state:

  • Written criteria are the spine of every adjudication. Every criterion is judged on its written meaning against whatever real evidence exists — output produced, files changed, the visible record of what actually happened.
  • Technical results are annotations, not prerequisites. A passing test strengthens the case; a failing one raises a flag the judgment must address. Neither replaces the judgment itself.
  • The safeguards stay. Independent per-criterion evaluation, evidence-before-verdict, fail-closed on missing evidence, the worker's claim treated as data and never as instruction — all of these survive unchanged. They are how the human-style judgment stays honest.

What this means for the Plan Supervisor

Its role does not change — it remains the correction authority that acts only when a plan can't move on its own. What changes is what it receives: verdicts grounded in judgment of the written Definition of Done, not in whether a command exited zero. Its own rules carry over untouched:

  • It never redefines what "done" means — it changes how the plan gets there.
  • It never manufactures a false pass, and a replacement for failed work must be genuinely different work.
  • It recognizes repetition as a loop, and ends a plan honestly when the goal is truly out of reach.

Sequencing

now Fix the drift: let every criterion type actually be created everywhere it's already officially supported.

next The criteria skill: author the built-in skill defining the quality bar above; wire it to trigger automatically on all three creation paths — chat goal, task, plan — including the clarifying-questions step.

next Make pre-classification optional — plain language becomes the default for tasks and plans, matching how chat goals already work.

later The four UI changes above — editor defaults, the criteria-first goal card, verdict display, creation flows — once the skill and the loosened authoring land, so the screens reflect the mechanism instead of leading it.

The one-line test for every future change: could a completely non-technical task — no code, no commands, no files — still be given a meaningful Definition of Done and receive a fair, evidence-grounded verdict?

If yes, the change honors this design. If no, it doesn't ship.
