## Decision

### 1. Suspension is schedule state, never execution state (D5)

Persist optional `Trigger.Suspended bool`, JSON `suspended,omitempty`, alongside `type` and `config`. Missing means false. Keep `IsRepeating`, `SeriesRetired`, all task/run statuses, results, goal state and session identity unchanged. A suspended recurring task remains a recurring task and remains Calendar-only. [D5; E1, E3]

| Operation / state | Exact semantics |
|---|---|
| Suspend | Only a user-surface `once` or `recurring` trigger qualifies. Persist true; remove its armed job and invalidate pending old callbacks. Repeating Suspend is a successful no-op. Heartbeats keep their own controls and are refused here. |
| Already admitted work | Suspension does **not** Stop a run or its helpers, cancel an admitted dispatch, or freeze the current run's attempt loop. Admission and suspension are serialized: whichever commits first wins. After suspension commits, no **new automatic schedule admission** is allowed. Explain this distinction in both controls and approval. |
| Resume | Persist false; preserve anchor, rule, zone and task status. Recurring: arm the first occurrence **strictly after server now**. Once: arm only if `at_ms > now`; an elapsed once stays unfired. Repeated Resume is a no-op. For D2's recurring→once conversion or once move, a future once must remain eligible even if the last run's mirror is Done/Failed: narrow the scheduler's current terminal-once exclusion, not the task-status vocabulary. Otherwise converting a completed recurring run would silently create an inert schedule. |
| Missed positions / end | Never back-fill. `COUNT` continues to count **planned calendar positions**, including positions elapsed while suspended; `UNTIL` keeps its original end instant. A series may exhaust during suspension. Resume succeeds but reports no future fire; the user can edit the rule or use Run now. This matches existing next-occurrence semantics. [E2, E4] |
| Explicit Run now | Allowed while suspended, under the normal run permission, authority, dependency, plan and overlap gates. It does not clear suspension, consume a future position, or move the rule. Future occurrence requests still refuse; task-level and past/current occurrence runs remain separate. [E7] |
| Schedule edit / clear | An actual rule/time/end edit follows the Calendar's existing re-anchor/count-restart rules; changing suspension alone never re-anchors. Replacing once/recurring preserves suspension. Clear installs canonical `{type:"manual",config:{}}`, removing suspension with the trigger. Clear never starts the task itself. [E9] |
| Other writers | Title/progress/assignee/result/checklist updates, run resets, completion and retries preserve suspension. Ordinary trigger replacement cannot implicitly Resume. REST trigger input contains only type/config; only the narrow Suspend/Resume operations change the flag. `create_task` / `update_task` reject supplied scheduling keys with “Use schedule_task to change a schedule”; they never acquire a trigger parameter. |
| Validation / disk / downgrade | `ValidateTrigger` still fully validates a suspended rule and its assigned agent; suspension is not a way to store an invalid rule. Manual + true is invalid. Old per-task files decode false; write the flag only on mutation, with the existing lock/atomic-write discipline. **An older binary ignores the flag and can fire suspended work: rollback while relying on suspension is unsafe.** [E1, E2] |

**Scheduler implementation obligation:** checking the flag once at the top of `RunScheduled` is insufficient. Extend `OnTaskUpserted`, boot `Reconcile`, `RunRecoverySweep`, `rearmRrule` and the final automatic-admission seam. Every arm/re-arm must re-read current persisted state, not trust a delayed notification's task snapshot. A due callback must match the currently tracked **job ID and trigger generation** and pass a conditional, lock-held reset/admission before any task status, run or session is created. Job identity prevents a pre-Suspend callback from becoming valid again after Resume restores identical rule content. The existing trigger hash naturally includes the new flag, but a hash alone is not an admission fence. [D5; E3]

Use the existing per-task striped lock for the write/admission ordering; where nested locks are necessary, order **task lock → scheduler lock → cron-engine lock**, never the reverse. Release locks before executor launch, callbacks or event publication. Work already admitted may finish; a rejected stale/suspended callback creates neither a run nor a synthetic “skipped” record. Preserve overlap recording for real overlap, and the existing unreadable-task diagnostics. Task persistence is authoritative; engine jobs remain derived state rebuilt at boot. [E2, E3]

**Close the alternate-entry hole:** `CheckQueuedTasks` currently considers every assigned `next` task, without a trigger predicate. New scheduled creation must persist its trigger before notification, never create a dispatchable manual task then patch it later. Queue/dependency/follow-up admissions must not start a task waiting on a time trigger, suspended or not; enforce this at the shared **new-run** admission boundary, not just the queue scan. Pass a trusted internal scheduled-fire admission context from `SpawnTriggeredRun`; do not infer source from `occurrence_ms` (nil for once) or run kind (also used by other automatic starts). Explicit runs and retries belonging to an already admitted run retain their existing paths. This is necessary to deliver D1/D5, not a second executor. [E5]

### 2. One mutating agent tool (D2–D4)

Add `schedule_task`, general scope, Tasks category, discoverable through the existing tool search. Do not enlarge the upfront-tool set merely to add it. It calls shared domain operations, **not** authenticated operator REST endpoints. Keep the UI's server validator and occurrence engine authoritative. [E8, E10]

| `action` enum | Required inputs | Effect |
|---|---|---|
| `create` | `task`, `schedule`; no `task_id` | Create task + paired goal + trigger as one operation, initially Inbox like the Calendar; no immediate run. Require title, prompt, agent_id, nonempty criteria and distinct dod. Optional description, priority, tags, todos, due, blocked_by and run_isolated use existing validation. Workspace defaults to current/default resolved workspace. |
| `set` | `task_id`, `schedule`; no `task` | Add/replace a once/recurring schedule; edit time/rule/end; recurring→once and moving a once event use this same action. Preserve suspension. |
| `clear` | `task_id` only | Set manual. Already manual is a no-op. |
| `suspend` / `resume` | `task_id` only | The semantics in §1; no free-text reason changes the schedule. |

Accept optional `workspace_id` as a same-workspace assertion and optional `expected_schedule_hash` as a concurrency precondition for existing tasks. Reject contradictory action fields, unknown keys and wrong JSON types; never silently discard them. Scheduling is **local to the resolved current workspace**: foreign create/arm/mutation refuses before writes, with guidance to use delivery-only `create_task` and let the receiving team schedule locally. Existing task ownership remains assignee **or** agent-namespaced `CreatedByAgent`, not the mixed human/agent `Owner` field. Preserve create-task delegation/depth/readiness checks, attribution and `Initiator`; do not turn an agent-created scheduled task into an operator-created one. Re-authorize arming against the assignee's current workspace graph; suspended/clear operations do not grant execution. [D2; E5, E6, E15]

**Structured schedule input, not raw RRULE:**

```text
once:     { kind: "once", at: RFC3339-with-offset }
recurring:{ kind: "recurring", start_at?: RFC3339-with-offset, tz?: IANA-zone,
            frequency: minutely|hourly|daily|weekly|monthly|yearly,
            interval: integer 1..99,
            weekdays?: [MO|TU|WE|TH|FR|SA|SU],
            monthly?: { mode: day_of_month, day: 1..31 }
                   or { mode: nth_weekday, ordinal: 1..5|-1, weekday: weekday-code },
            end: { kind: never }
              or { kind: on_date, date: YYYY-MM-DD }
              or { kind: after_count, count: integer 1..100000 } }
```

On create/new recurrence, `start_at` and `tz` are required. On an existing recurring `set`, omitted `start_at` means a rule/end-only edit anchored at **preparation time**, matching the UI; freeze that instant before approval, never recalculate it after approval. Preserve its existing zone; a supplied different zone refuses. A supplied offset must match that zone at the chosen instant. A once input is an absolute instant and does not acquire a stored series zone. Weekly requires at least one unique weekday; monthly requires exactly one monthly mode; fields for another frequency refuse. Emit no raw-rule escape hatch. [D2, D6; E9]

Compile the same forms the editor emits: weekdays → weekly `BYDAY`; monthly day 29–31 → the existing last-day clamp form; nth weekday → `BYDAY`/`BYSETPOS`; end date → 23:59:59 in the rule's zone converted to UTC; count → `COUNT`. Daily/hourly/minutely/yearly use the anchor as today. Call `ValidateTrigger` afterwards, including its 60-second floor, 512-character rule bound, zone checks and liveness/count limits. Shared fixtures must prove UI/compiler parity, including daylight-saving and short-month behaviour; no new occurrence engine or runtime dependency. [E2, E9]

**Result:** generated `ScheduleTaskResult`: `task_id`, `workspace_id`, `agent_id`, task `status`, canonical `trigger`, `schedule_text`, `schedule_hash`, up to three `next_occurrences_ms` (planned positions), nullable `next_fire_ms`, `persistence` (`saved`), `scheduler_state` (`armed|disarmed|exhausted|unavailable`) and `warnings[]`. Suspended/manual/expired schedules have null next fire. Persist task and goal before notifying/arming; reuse the existing goal-write cleanup on creation failure. If persistence succeeds but arming fails, return the saved ID with `scheduler_state=unavailable` and an explicit warning, **not** “scheduled successfully” and not an instruction to create a duplicate. Make the new scheduling coordinator return an observable arming outcome; today's void notification cannot prove activation. [D1, D5; E3, E6]

Errors use the existing tool error/permission/delegation paths, not a new structured-failure discriminator. Examples: “Select at least one weekday”; “Repeat interval must be 1–99”; “No time schedule to suspend”; “The series time zone cannot be changed here”; “Schedule changed while approval was pending; read it again and request approval for the new schedule”; “Cannot run a future occurrence; it will run at its scheduled time.” Preserve shared server validation details and return storage faults as faults, never empty success. [E2, E7, E16]
