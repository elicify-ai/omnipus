Critical Assessment — Unified Goal/Plan/Subagent Design v2.1

Adversarial architecture review · 2026-07-22 · 5 viewpoints + SOTA/code grounding · target: docs/internal/design/unified-goal-plan-subagent-target-design-v2.1.html

An evidence-driven assessment from five perspectives — the end user, the Judge, the plan owner, the orchestrator, and the subagents — each grounded against the shipped codebase (pkg/agent/*) and current 2025–2026 multi-agent state of the art. Verdict first, then findings, then the comparison and risk register.

A−Design
B+Ship-readiness

Verdict: a genuinely best-in-class target design whose ambition outruns its currently-shipped substrate in the exact places it honestly labels “NEW.” The integration-level novelty is real and unmatched (verification-first goals compiled from intent, an immutable-DoD judge with a three-rung evidence ladder, typed bidirectional agent↔human session control, parallelism-as-an-artifact-problem) — nothing in LangGraph, CrewAI, AutoGen, OpenAI Agents SDK, Devin, or Claude Code combines these. The reuse claims are mostly accurate against the code (plan_engine, goal_loop, steering, async_notifier, cancel, the Judge seed, IsPrivilegedAgent all verified). The defects cluster into three honest themes: (1) the Judge is under-fed with evidence, especially at plan scope; (2) the human-answer UX has no real surface (and no channel story at all); (3) append-only immutability and one-hop messaging lack correction vocabulary. All fixable as normative text + a few targeted additions — none requires abandoning the thesis.

The 5 blockers (must resolve before implementation)

Blocker 1 FR-6a "child shares parent transcript" is refuted by the code

Research · pkg/agent/subturn.go:504-506, 611-614 vs design §4

The design's session-control plane leans on delegated children sharing the parent's transcript session (FR-6a). The code says the opposite: the child runs in an ephemeral, in-memory store so its turns "never pollute or persist to the parent's session history." If attach/peek/audit assume a shared transcript, that is a reversal of today's isolation, not a reuse — and every "session-scoped message," "attach to child transcript," and "task_id = session_id alias" inherits a child-session identity that doesn't cleanly exist today.

Decide explicitly: either drop the FR-6a "shares transcript" claim (children are isolated, messages are the only bridge) and re-derive attach/peek on the durable DelegateTaskState.SessionID alone, or declare shared-transcript a deliberate reversal with its own migration. State which.

Blocker 2 The "answer a specific question" UX has no affordance — and no channel story

User A-1 / A-5 · design §4 (MAJ-8, N-9)

The design promises "a reply is never mis-consumed as an answer" via correlation_id, but specifies no UI mechanism. The chat surface is a single free-text composer today (GoalIndicator.tsx); nothing binds a message to a question. And Omnipus ships ~14 channels — on Telegram/Discord a per-question reply button is literally impossible (free text only). This is the most-used interaction (worker asks → you answer) and it's unfulfillable as specified.

Define the SPA primitive (a question card with its own reply box emitting respond(correlation_id), visually distinct from the new-message composer) AND a channel fallback (reply-quoted messages; explicit FIFO binding to the oldest open question when the channel can't carry correlation).

Blocker 3 Idle-settlement "persisted evidence" is overstated — two of three sources don't exist in this amendment

Judge B-1 · acceptance criterion G-3 · verifier_adjudication.go:266-272, 397-405

G-3 claims idle judges "artifacts, write-set-scoped diffs, latest checkpoint." Verified: (a) write-set diffs are deferred — the git layer (§3d) is explicitly a separate spike-gated ADR, go-git is absent from go.mod today; (b) checkpoints have no carrier for a chat goal — they're child→parent messages, and a top-level chat goal has no parent. What the idle Judge actually receives is the same last-20k-token transcript tail as the claim path. G-3 is untestable for the gap it claims to close.

Rewrite G-3 to the honest basis ("transcript window + workspace artifacts; diffs/checkpoints are co-requisites pending §3d/§4") — or make the git layer / chat-goal checkpoint a co-requisite of the idle trigger, not a deferred dependency.

Blocker 4 The plan-level Judge is evidence-starved, and the anti-gaming guard can't reach it

Judge B-2 / B-6 · plan_engine.go:1394-1426 (buildPlanClaimText, planClaimTruncateLimit=500), verifier_adjudication.go:266 (plan-scope window = "")

The plan Judge's entire view of member work is each member rendered as a 500-char self-reported summary + plan title/goal/description, with an empty plan-scope transcript window. The design's N-2 defense ("flag artifacts authored after an unmet verdict to the Judge") has no channel to reach it — the plan Judge receives no artifacts at all. So the "low likelihood" judgment is unjustified precisely where evidence is poorest: a prose-only DoD has no deterministic rung, and a forgeable tail member is judged on a 500-char claim. The member-Judge (rich evidence) and plan-Judge (poor evidence) judging the same work makes the plan-Judge strictly more error-prone.

Give the plan Judge a structured evidence composition per member (artifact paths, the member's [goal:evidence] line verbatim, and write-set diffs when §3d lands) — not a 500-char Result. Route the post-hoc-artifact flag through this composition. And surface the evidence asymmetry in the plan-tile UX so a failure over all-green members is interpretable.

Blocker 5 Append-only immutability has no vocabulary for "a done member's criteria were wrong" or "a frozen member was transiently failed"

Owner C-1 · design §3

Immutability preserves evidence beautifully for execution failures but is mute on two real correction shapes: (1) a member is done but its criteria were mis-compiled and don't support the DoD — you can't un-score it, and the plan-lint (write-set overlap only) can't catch semantic non-contribution; (2) a member is frozen on a flaky/transient failure but the only revival is Stop/Play, which zeroes JudgeRounds and re-queues every failed member — a sledgehammer for one flaky member. The fixed-point ("owner extends toward the DoD, never edits the goal") assumes the only correction is "add more work," but real correction is often "this completed work shouldn't count" or "this failed work should be retriable."

Add a supersede relation (a tail member marks a done member's outcome as ignored-by-the-Judge, reason in the revision entry — record stays immutable, only weighting changes) and a targeted retry that distinguishes transient vs structural freeze (an attempts-exhausted member individually retriable without a full Stop/Play while the plan still has rounds).

Perspective · the end user (UI)

Walking the real journeys: set a chat goal → worker pauses → you answer → completion; create a plan → Execute → a member needs input → plan re-plans → you Stop/Play. Where is it confusing, dangerous, or underspecified?

A-3 The pill taxonomy silently drops a shipped wire state

src/components/chat/GoalIndicator.tsx:56,72,91,96 vs design §1

Today's enum is 4 values: active / paused_judge_unavailable / brake_fired / cleared. The design's new 6-state taxonomy (active / waiting-on-user / re-planning / judging / done / failed) drops paused_judge_unavailable — a state production rate-limited plans hit routinely, which is neither "active" nor "judging." Conflating it misleads. Terminal pills (green/red) also have no lifecycle (today they collapse to nothing via cleared).

Add judge_unavailable and a queued (cap-admitted-not-started) state; specify terminal-pill retention.

A-4 Stop-then-Play on a member cancelled mid-run is a data-loss ambiguity

design §3 (Play semantics) · plan_engine.go distinguishes failed vs cancelled

Play resets failed members to attempts 0 and preserves done. But a member that was running when Stop hit is cancelled (not failed, not done). Does a member 90% through its work warm-resume, or restart from zero? A user pressing Play expecting "continue" and getting "restart from scratch" is a wrong-button-equals-data-loss scenario.

State explicitly which path applies (reset to attempts 0, or warm-resume via resumed_from) and document it on the button.

A-2 / A-6 Multi-goal rendering & the re-planning window are undescribed

design §1 (per-goal-id pills) · §3b (re-planning)

GoalIndicator.tsx takes a single goalStatus today; N stacked bottom-right pills (overflow? ordering? which is "waiting"?) and the cap-queued sub-state are undefined. While the owner reasons through correction, plan/member tiles are undescribed — a user seeing "re-planning" for 90s doesn't know whether to wait, Stop, or intervene.

Pill-list layout rule + queued sub-state; specify the plan-tile state during awaiting-owner-correction.

The evidence ladder collapses at plan scope — the weakest evidence feeds the most consequential (whole-DoD) verdict.

B-3 Internal contradiction: does the first idle consume a round?

§6 (N-13) vs §8 acceptance (G-2, G-3, G-4)

N-13 says the first idle settlement is "free" (no round), mirroring the bare-claim first bounce (G-4). But G-2/G-3 say idle "consumes a round" unconditionally. Both can't hold — the acceptance table contradicts the design prose; an implementer cannot satisfy both.

Pick one. Recommended: idle mirrors the bare-claim ladder (first idle with no evidence = free steer, no round; subsequent idles consume a round) — amend G-2/G-3.

B-4 No "criterion unverifiable" verdict — impossible criteria fail-closed-by-exhaustion

§6 fail-closed · §1 feasibility gate (N-5) only vets reachability

A compiled (or owner-authored) criterion like "the refactor feels maintainable" is syntactically valid, policy-reachable, and genuinely unverifiable. The Judge has no verdict type for "cannot be verified as written" — it can only return unmet every round until exhaustion → failed, burning the token budget (B-7). For chat goals there's no owner loop to route back to the author.

Add a criterion_unverifiable verdict that routes to the author (chat: re-prompt rephrase; plan: surface to owner) instead of burning rounds.

B-5 The 20k window is "last N tokens" — load-bearing early evidence gets truncated

verifier_adjudication.go:397-405 (renderVerifierWindowText)

For a long task, the foundational decision / the original failing test / the first artifact — the load-bearing early evidence — walks off the back of the window. [goal:evidence] is the claim, not a pinning mechanism; there's no "keep this artifact/diff in the always-included evidence block" concept.

A worker-pinnable structured evidence block that rides outside the 20k budget, distinct from the transcript tail.

B-7 Token budget silently debited by Judge retry calls

judge.go:243-251 (retries on judgeRetryBackoff, returns Unavailable only on ctx cancel)

A sustained SEC-26 rate-limit makes the verifier retry internally — each retry debits tokens but consumes no round. The scope can brake to failed(budget_exhausted) for reasons the user reads as "the Judge kept failing," with no round ever spent.

Don't debit failed/retry verifier calls against the token budget, or surface "verifier retrying" as a distinct pill state (ties to A-3's missing judge_unavailable).

Perspective · the plan owner

Persistent session; plans, then re-plans by appending tail members; receives critic feedback; bounded by JudgeRounds and a token budget.

C-2 The awaiting-owner-correction gate can be pre-empted; owner re-dispatch after a crash sweep is undefined

§3/§3b/§4/§5 · plan_engine.go:605 (dispatchReadyMembers dispatches members, not the owner)

A steer into an owner session parked on a child's needs_input can silently pre-empt the park (the state machine permits needs_input → running : steer), abandoning the open child question. Worse: the §5 boot sweep fails non-terminal sessions to failed(interrupted) — including the mid-deliberation owner — but the owner is not a dispatched member, so there is no defined re-dispatch path for the owner session itself after a sweep.

Normative rule that a steer into needs_input must carry/dismiss the open question or queue behind it (no silent pre-emption); and define owner-session re-dispatch explicitly (symmetric to Play's cancelled→approved edge).

C-3 The token budget is a cliff with no burn visibility and a broken Play-after-exhaustion path

§6 / §3 / §7

No "approaching budget" signal (the owner learns it's out only at the brake); remaining-budget isn't surfaced in the re-planning prompt, so the owner can't self-ration; and after failed(budget_exhausted), Play re-runs failed members but the per-plan budget isn't refunded — so Play immediately re-brakes unless the operator raises the restart-gated token_budget, an operability step the design never states.

80%-consumed non-terminal signal; expose remaining-budget in the re-planning prompt; explicit operability note for Play-after-exhaustion.

C-4 The write-set lint can't handle exploratory work — the design's own headline use case

§3c (write-set partition, lint) · §3b step 1 (delegatable research/decomposition)

Disjoint write-sets work for construction with knowable outputs. They break for exploratory work the design explicitly wants: a research/decomposition member, a "find the flaky-test root cause" member, or data analysis have unknowable write-sets until they run. Declaring work/** is rejected; a guess means runtime writes outside it surface only post-hoc as contention evidence. The "parallelize every plan kind" claim is undermined for exactly the cases it markets.

An explicit exploratory mode that opts out of write-set declaration but is hard-forced sequential; a runtime guard that an undeclared write triggers an immediate plan-correction event; qualify the "every plan kind" claim honestly.

C-5 The integrity guard covers tail members but misses the owner authoring the DoD itself

§1 (chat mint-gate) vs §3b (owner authors plan DoD) · §9 BOM

§1 applies a mint-gate (feasibility + echo-confirm + amendment diff) to chat goals compiled from intent. But a plan's owner-authored DoD enters via create_plan with no echo-confirm-to-user and no user-side feasibility gate documented. That's a bigger integrity hole than the self-attesting-tail case: an owner can pass its own goal by compiling an easy DoD at the start — no tail required, no red-team catches it. The owner also authors the revision diagnosis, and the Judge can adopt that framing.

Extend the §1 mint-gate to plan DoDs; prompt the Judge to form its own diagnosis from raw member outcomes rather than adopting the owner's framing.

Perspective · orchestrator & subagents

The parent steering children; and the children (native + 3P external-CLI) running, asking, being steered, handing back.

D-1 Typed messaging is strictly one-hop — it does not compose across chain-depth-3

§7.7 O-5, §4 P2M-10 · pkg/agent/cancel.go (cancel cascades; delegate.steer does not)

At depth 3 (you → Ava → Worker), the grandchild's message_parent reaches Ava, never you — you see it only if Ava re-emits it (re-framed, new correlation). Visibility is one-hop (inbox_unread_count = direct children only). Cancel cascades down the spawn chain; steer does not — course-correcting a misbehaving grandchild is a game of telephone. The depth-3 cap survives, but the typed-messaging/warm-resume story is effectively depth-1.

Opt-in transitive visibility (descendant messages relay with original-sender identity); a steer_descendant the runtime walks down the spawn chain.

D-2 The per-type ceiling is per-parent-inbox — one noisy child DoSes its siblings

§7.5 P2M-9, §4 caps table

The 20-open-question ceiling is on your inbox aggregated across all children. Child A spams 20 questions; child B's genuine blocker bounces back to B as a tool error. "Never silent drop" holds (B gets an error), but operationally B can't reach you — a functional drop caused by a sibling.

Make the per-type ceiling per-child (each child has its own 20-question budget against you). One-line semantic fix, operationally critical.

D-3 delegate.cancel on a plan member with dependents fails the entire plan

plan_engine.go:560-562, 1158-1171 (planStuckAfterMemberCancel → failPlanLocked(StoppedByUser))

You soft-cancel one wasted child that happens to be a plan member with downstream blocked_by dependents. Verified: the engine's planStuckAfterMemberCancel then fails the whole plan with StoppedByUser. You wanted to stop one run and re-dispatch; you bricked the plan. A routine per-child session op cascades into plan failure silently — no documented link between delegate.cancel and the plan-engine consequence.

Refuse delegate.cancel on a member with dependents with a clear error, or trigger a plan-correction event that appends a replacement tail — not a whole-plan failure.

D-4 / E-5 For 3P/external-CLI children, needs_input is fiction and warm resume is native-only

§4 MAJ-10 · task_executor.go:560-575 (terminal marker proven) vs unvalidated mid-run extraction

For a 3P child (claude-code/codex/opencode), your respond to a question does not resume warm — the process ends and you cold-resume. So for 3P, needs_input is today's cold re-delegate relabeled. And the claim that mid-run marker extraction "already proves this works" is overstated: the terminal [goal:evidence]/TASK_STATUS line is proven, but robust extraction of mid-run progress/blocker/checkpoint from arbitrary 3P CLI output is unvalidated.

Be blunt: 3P children get fire-and-collect semantics in typed-marker clothing — warm resume is native-only. For 3P, advertise only progress/artifact/handback; drop question/needs_input (honest fire-and-collect beats a cold-resume pretense). Downgrade the "proven" claim to "terminal proven; mid-run is a spike."

E-2 Idle settlement conflates "forgot the claim line" with "was still working, the timer fired"

§8 (idle detection) · §6 N-13

Two identical-looking "no claim, idle" causes: (1) you forgot the evidence line on completed work (a teaching steer is fair); (2) you were genuinely mid-work and the ~60s quiet window fired while you were slow (adjudicating incomplete work as if claimed is unfair). Both look identical to the gate. The unmet verdict from (2) feeds the correction loop as if you'd failed — an honest slow worker burns rounds for velocity, not correctness.

Idle should require "no declared in-progress intent in the last checkpoint" (open sub-tasks/unreached next = mid-work, re-arm, don't adjudicate). Distinguish claimed-but-bare (teach) from genuinely-mid-work (re-arm).

E-3 Write-set confinement can't be renegotiated, and the .git deny is over-broad

§3c/§3d

If mid-run you discover the fix is in bar.go but you declared foo.go, you're trapped — your correct edit surfaces as "contention" rather than committing; you must hand back and let the owner re-plan (high friction for a routine debugging discovery). And denying work/**/.git blocks legitimate read-only git log/blame/show a worker commonly needs — the threat model is mutating ops, the blanket path-deny is broader.

A request_write_set_expansion child→parent message (cheap on the existing primitive); model the .git deny on operation (permit log/blame/show/diff, deny commit/amend/rebase/rm), not path.

E-1 / E-4 Ad-hoc delegate inboxes strand across parent lifecycle; a non-answer respond resumes you into confusion

§4 MAJ-9 · §7.3 M-3 · §7.5 P2M-2

Plan-member inboxes are keyed to the durable plan id (good); ad-hoc delegate inboxes are keyed to the spawning session id — a parent compact/restart/Play strands your question(wait=true) on a dead key; the new generation never sees it (7-day retention surfaces it to the human, not the new parent). Separately, respond(correlation_id, answer) validates nothing about whether answer addresses the question — a parent draining its inbox can hand you an unrelated directive that closes your question and resumes you warm into confusion (TTL resets, no auto-handback). decision_request has choices[] validation; question does not.

Key ad-hoc inboxes to a durable parent handle (chat id), or document handback across lifecycle boundaries; on respond, re-prompt the child with BOTH the answer AND a re-statement of Q1 (re-emit question if unanswered), and add a cheap answer-type sanity check mirroring choices[].

What is genuinely sound (verified)

§5 Boot sweep — correctly identifies the #1 production hole (persisted lifecycle survives restart, goroutines/queues don't) with a concrete sweep + a verified precedent (orphan_watch.go). The Temporal-replay trade-off justification (LLM turns aren't replayable) is the right honest scoping.
§9 BOM / carrier table — every mechanism has a home; the four anti-parallel-systems rules (name-existing-or-justify-new, one-concept-one-impl, skills+grants over new agents, BOM-as-review-gate) are exemplary discipline. pkg/skills/embedded/plan/SKILL.md confirmed to ship — the planner is an extension, not a fork.
The awaiting-owner-correction gate — fixes a verified live bug: post-unmet the phase reverts to dispatching (plan_engine.go:67-70), so with all members terminal the next tick re-judges unchanged state, burning JudgeRounds until exhaustion.
Verifier is genuinely read-only & unprivileged — core.go:53-54 (read_file/list_directory/inspect_session); the Judge is type=system = non-privileged/capped (so the token-budget-bypasses-exemption point is accurate). AND-combine with deterministic rungs first is verified sound.

What could not be verified

  • Warm-resume across a process boundary (M-4) — §5 names it as a requirement, says "answered here, not left implicit," then implicitly answers it ("swept to failed(interrupted) unless warm-resume can reconstruct it"). The reconstruction criterion is never actually specified — the single biggest unproven engineering risk.
  • go-git envelope — merge/worktree limits + auto-commit cost on large/media-heavy trees are unmeasured; the whole §3c/§3d model rides on it (design's own OBS-3).
  • 3P mid-run marker parser robustness — terminal-claim extraction proven; mid-run typed-marker extraction from arbitrary CLI streams is not.
  • Pill pixel feasibility — the bottom-right pill's fit with /loop status (which shares GoalIndicator.tsx today) and composer occupants wasn't visually confirmed; the wire-enum gap (A-3) is verified from source, the layout fitment is not.
  • Numeric defaults (15s debounce, 4 wakes/h, 20 ceiling, ~60s quiet window) are plausible but unvalidated — operator tuning items.
