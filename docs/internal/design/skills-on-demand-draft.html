Skills on demand First draft

Design proposal · for discussion

Stop carrying every skill everywhere.

How an Omnipus agent should find a skill, be allowed to use it, and load it only at the moment it is needed — including the skills and instructions that belong to a code project it is working in.

Status First draft · nothing decided Answers Issue #663 Phase v0.3

How to read this

A draft written to start a conversation, not end one. Where I made a call, I say so and you can overturn it. Where the answer is genuinely yours, I have not quietly picked one — those are collected at the end as thirteen open questions. Nothing here has been built. Everything I say about current behaviour was read in the code rather than taken from documentation, because on this point the documentation and the code disagree in two places.

01

What goes wrong today

A skill is a written instruction sheet an agent can follow — “here is how we write release notes”, “here is our invoice process”. Omnipus can find them, install them, write them, refine them and delete them. The one thing it has no proper way to do is pick one up when it turns out to be needed.

In place of that there is a per-agent list of skills. It was meant to say which sheets this agent may pick up. The code reads it as which sheets this agent must always be holding — and pastes every one of them, in full, into the agent's instructions on every single message.

Today

Give Mia five skills. Ask her “what's the weather?” and she carries all five instruction sheets into that question. And the next one. And every one after that.

Proposed

Mia sees a one-line summary of each of her five skills and carries none of them. When a task actually calls for one, she picks up that one.

Two things follow, and both get worse over time:

  • It costs money on every message and crowds out the conversation. Every model call has a fixed budget. Instruction sheets nobody asked for are spending it. Worse, this particular block sits outside the part of the prompt that gets cached between messages, so it is paid for in full every time.
  • It punishes exactly what v0.3 is built to encourage. The concept has agents writing and refining their own skills over time — skills as a kind of memory that compounds. Under today's rule, a growing skill library makes every conversation more expensive. Being generous with permissions and being cheap to run are currently in direct conflict, and they should not be.

Two things I found that make it worse than the issue says

The permission list is not actually a permission barrier. Because there is no proper way to activate a skill, the system prompt tells the agent to do it by reading the skill's file with the ordinary file-reading tool. That works — and it goes nowhere near the permission list, which only governs the menu and the slash-command path. An agent that knows or guesses the path of a skill it was never granted can simply read it. So requirement two is not only tidying up a misused list; it is closing a gate that is currently ajar.

An empty list means the opposite of what you would guess. An agent with no skills listed today has access to everything installed. An agent with a list is restricted to it — and force-fed it. So the current design punishes being specific twice over. That is worth fixing on its own.

The good news

Most of the machinery exists and is pointed the wrong way. Omnipus already builds a short menu of skill names with one-line descriptions; already filters that menu to what an agent is permitted; and its skill loader already searches three locations in priority order. What is missing is the single verb that turns a menu entry into a loaded skill — and the deletion of the code that force-feeds the whole menu regardless. This is rewiring, not construction.

02  ·  Requirement one

Activation that works the way it does in Claude Code

You asked for this to behave like the skill tool I use on myself, so let me describe that honestly, from the inside.

I never carry skills. What I am given is a menu: a list of names, each with one line saying what it is for. A few words each. When a task matches one of those lines I call a tool naming that skill, and only then do its full instructions arrive. Then I follow them.

Two separate moves: see the menu, then order the dish. Today Omnipus builds the menu and then serves every dish on it anyway.

The proposal

Keep the menu Omnipus already builds. Add the missing verb: one tool an agent calls with a skill's name, which loads that skill and nothing else. Delete the code that force-loads the list.

Two consequences worth naming ahead of the mechanics:

  • A skill's description becomes a product decision, not a label. That one-line description is the only thing an agent sees before choosing. A vague description means a skill that never gets used. Quality pressure moves from the body of a skill to its first line — which is also where the skill-authoring workflow should start pushing back.
  • Permissions become free. Once nothing loads until it is asked for, granting an agent twenty skills costs nothing until one is used. You can be generous without paying for it.

Where Omnipus differs from my own harness — deliberately

It has already solved this exact problem once, for tools. Omnipus has far too many tools to show an agent at once, so it built a search-then-load arrangement: agents see a short searchable index and pull in a tool's details on demand. That work also learned a lesson the expensive way, which we should inherit rather than rediscover — filtering what an agent may load is not enough while the menu still lists things it may not have. Skill activation should be built on the same shape, with that fix already in it.

It has real subagents. I can only load a skill into my own head. Omnipus can hand a job to another agent. So the tool should offer a second mode: instead of loading the skill here, hand it to a subagent to carry out. The consequence is what matters — a long instruction sheet never touches your conversation at all, and you get a result back rather than a transcript. The trade is that you lose the back-and-forth; you get an outcome, not a collaboration.

Its delegation has a rule that constrains this. In Omnipus, when one agent hands work to another, the second runs entirely as itself — its own permissions, its own settings, deliberately not the sender's. That is a decision the project already made and defends, and it is enforced in the code: a delegated agent is handed the target's skill list, never the sender's. So the subagent mode cannot be used to slip a skill past the receiving agent's own permissions. Which list should govern the hand-off is open question 2.

03  ·  Requirement two

The permission list is the gate — not a second check bolted on

One library, many library cards. There is a single place where installed skills live, shared across the whole installation. Each agent has a card listing which of them it may borrow. Being on the card costs nothing until the agent actually borrows something.

This is the same shape Omnipus already uses for tools, which is the point — it should not feel like a new idea to anyone operating the system.

The gate has to sit in four places, or it is not a gate

  1. The tool call. An agent naming a skill it may not use is refused, with a message saying so plainly rather than failing quietly.
  2. The menu. An agent should not see the name or description of a skill it cannot use. This is the lesson Omnipus already learned on the tools side, where loading was gated but the search results were not — so a denied item's name and description leaked through anyway.
  3. The human shortcut. Typing /some-skill in chat forces a skill on for one message. A person should not be able to push a skill onto an agent that is not permitted it.
  4. The back door. Reading a skill's file directly with the ordinary file-reading tool must stop being the documented way to activate one. As long as it is, every other check is decoration. This is the finding from section 1 and it is not in issue #663.

What existing installations lose

Today, listing a skill on an agent means “always on”. Afterwards it means “may be loaded”. Anyone relying on the always-on behaviour — knowingly or not — loses it on upgrade. And separately, every agent with an empty list goes from unrestricted access to whatever we decide empty should mean. Nothing breaks loudly; behaviour just quietly changes in two directions at once. That is open question 4, and I do not think a release note settles it.

04  ·  Requirement three

A project's own skills, and its own instructions

You flagged this as contradictory, so let me state the contradiction before resolving it.

A coding project carries its own skills in its own folder, and its own instruction file (CLAUDE.md or AGENTS.md) explaining how to work on this codebase. That is a filesystem idea. It lives in a directory, travels with the repository, and appears the moment you are working inside it.

An Omnipus workspace is not that. It is a project in the business sense — a team of agents, a task board, a shared memory, a set of conversations. It might be pointed at a repository. It might be a purely conversational space with an inbox and a calendar and nothing on disk at all.

My answer: don't add a concept. Use the one you already built.

I am proposing we do not introduce a separate “project” alongside workspaces. Two overlapping containers is exactly the confusion the Workspaces redesign exists to end. And there is a stronger reason: the answer is already in the codebase.

A workspace can already have real folders on your disk attached to it — you point Omnipus at your acme-api checkout and its agents can work in it directly, without copying anything. Internally these are called mounts, and they are how the project decided to answer “let agents work in my own folders”. An earlier design had a “repository” field on the workspace instead; it was deleted, on the grounds that it was a setting that did nothing. Mounts replaced it and actually work.

So the rule is: when a folder you have attached to a workspace looks like a code project, that project's skills and instructions come along. When nothing attached looks like one, nothing happens — no setting, no warning, no opt-out.

That last clause is what dissolves the tension. The mechanism is silent when there is nothing to find. A conversational workspace never encounters it. Nobody has to understand it until it becomes useful to them. And because a workspace can have several folders attached already, work spanning three repositories needs no new design — though it does need a decision about what happens when all three carry instructions, which is open question 8.

Three shelves, most specific wins

First The project's own skills Found in the folder attached to this workspace. Available only while working here, and travelling with the repository, so a colleague who clones it gets them too.
Then Your installed library The one central place skills are installed to, shared across the whole installation. This is the shelf per-agent permissions are about.
Then What Omnipus ships with The four skills built into the binary. Always present, always last.

Same name in two places → the more specific one wins

Two things make this cheaper than it sounds. First, the skill loader already has exactly these three shelves in exactly this order — the first is currently aimed at a per-agent folder that nothing writes to, so this is largely a change of address for a shelf that already exists and is already understood by the rest of the system. Second, the file format already matches: an Omnipus skill and a Claude Code skill are the same thing on disk, deliberately, so a repository's existing skills are already readable as they are.

There is also a note in the Workspaces concept itself anticipating this exact move — it says keeping skills global is today's behaviour, and flags re-pointing that first shelf at the workspace as a deliberate choice available to whoever writes the decision record. So this is not me pushing against the direction; it is me taking an option the direction left open.

The instruction file rides an existing rail

Omnipus already injects one instruction note into every message: the workspace's own instructions, which the product calls Project Instructions. A repository's CLAUDE.md is the same thing, written by a different tool, for the same purpose.

So it should be a second source for the layer that already exists, not a new layer with its own rules. Your workspace instructions first, the repository's file after, each labelled so the agent knows which is yours and which came with the code. No new mechanism, one new source, and the ordering already makes your intent outrank the repository's.

The part I am least comfortable with

A folder you attach to a workspace is one your agents can write to — that is the whole point of attaching it. Which means an agent could edit the project's own skills, and the project's own CLAUDE.md, and thereby rewrite its own instructions.

Omnipus takes this seriously elsewhere: the workspace's own instruction file was deliberately moved out of agents' reach for precisely this reason, and permission lists are kept in a directory agents cannot touch at all. This proposal would put a set of agent-followed instructions back inside agent-writable space for the first time. It is a real regression against a principle the project already holds, it is open question 9, and I do not think this should ship without an answer to it.

And the ordinary trust problem

Separately from self-modification: project skills are instructions an agent will follow, sitting in a folder that may have been cloned from someone else. Roughly a fifth of skills in public registries have been found to carry something malicious, which is why installing one through Omnipus is signed, hash-checked and password-gated. Reading one out of a folder is none of those things. My proposal is one switch per workspace — trust this project's skills — off by default, plus the rule that project skills are never loaded automatically, so there is always a moment where a person could read one first. That is open question 5.

One thing this depends on

There is a known unfixed problem underneath all of this: an agent's assembled instructions are built once and cached per agent, with no notion of which workspace it is currently working in. Move the same agent from one workspace to another and it can carry the first one's context with it. That is already logged as an open blocker in the concept work. A per-workspace skill menu cannot be correct until it is fixed — so this is a genuine prerequisite, not a detail. Related: whatever we do must not end up scanning a large repository on every message just to decide whether the cache is stale.

05

What a real turn looks like

Ray is on the Acme workspace, which has your acme-api checkout attached. That repository carries two skills of its own and a CLAUDE.md. Ray is separately permitted six skills from your installed library. You ask him to cut a release.

  1. Ray starts the turn carrying no skill instructions at all — just a menu of eight names and their one-line descriptions, filtered to what he is allowed to use.

  2. He is carrying the repository's CLAUDE.md, because instructions are a different kind of thing from skills: they describe where he is working, so they apply to the whole turn rather than to one task.

  3. He reads “cut a release”, scans the menu, and calls the skill tool naming the project's own release-checklist skill.

  4. The gate checks it: a project skill, in a workspace whose project skills you have trusted. Allowed. Its full instructions arrive — for this turn only.

  5. Halfway through he needs release notes written. He hands that to Ava as a subagent, with your library's release-notes skill. Ava runs as herself under her own permissions and hands back finished notes — the instruction sheet never enters your conversation with Ray.

  6. Your next message starts clean. Nothing carries over that the next task has not asked for.

06

What I decided without asking

Five judgement calls I made on my own, so you can overturn any of them cheaply now rather than expensively later.

  • Reuse the existing three-shelf loader rather than build a separate mechanism for project skills. It already ranks them correctly and already reads the right file format.
  • Treat a repository's instruction file as another source for the instruction layer that already exists, not as a new layer with its own rules.
  • Hang project-ness off folders already attached to a workspace — no new concept beside workspaces, and no revival of the deleted “repository” field.
  • Leave the per-agent permission list where it is, on the agent, for this draft. There is a real argument for moving it — open question 12.
  • Make discovery silent when there is nothing to find, so conversational workspaces need no configuration and no way to switch it off.
07

Open questions

Thirteen. Each says what it is and where I lean if forced — but none of these is mine to close. Two of them (5 and 9) I think should block shipping.

About the tool itself

01What is the tool called, and is it one tool or two?

Naming it Skill matches what the wider ecosystem calls it and what a model will expect. But every other Omnipus tool is a lowercase verb — find_skills, install_skill. And is “load it here” versus “hand it to a subagent” one tool with a mode, or two tools?

I lean One tool, one lowercase name, with a mode for the two behaviours. Fewer menu entries, and the choice between them is genuinely one decision.

02When one agent hands a skill to another, whose permission counts?

If Ray delegates to Ava with a skill, does Ray's permission matter, Ava's, or both? Omnipus's existing rule — a delegated agent runs entirely as itself — argues for Ava's alone. But then Ray cannot reliably hand off work, because he cannot see what Ava may use.

I lean Both must permit it, and the refusal names which one blocked. Safer, and it fails in a way that tells you how to fix it.

03Does anything stay always-on?

Some things genuinely should apply to every message — a house style, a tone of voice. Do we add an explicit “always load this one” marker, or is the honest answer “that isn't a skill, put it in the agent's instructions”?

I lean No marker. An always-on skill is an instruction wearing a costume, and the marker would slowly recreate the problem we are fixing. But this is a product call, not a technical one.

About the switch-over

04What happens to existing installations on upgrade?

Behaviour changes in two directions at once. Agents with a list stop carrying those skills. Agents with an empty list currently have unrestricted access to everything installed — and would presumably stop. Options: do it and note it in the release; show a one-time notice naming the affected agents; or migrate each agent's current list into its instructions so behaviour is preserved and can be cleaned up later.

I lean A one-time in-app notice. A release note is not read by the person whose agent changed behaviour. But the empty-list half needs its own answer — silently restricting agents that could previously use everything is the larger change of the two.

10The “inherit skills” toggle on the agent form does nothing.

The new-agent screen offers an inherit-skills switch for subagents. It never reaches the backend — it only leaves the field out of the request, so the subagent ends up with an empty list, which today means unrestricted. Should a subagent with no list of its own inherit the delegating agent's permitted set, or have none?

I lean Fix the label to match reality rather than build inheritance, since inheritance sits awkwardly against the rule that a delegated agent runs as itself. You may want the inheritance anyway.

13How long should the menu be?

Today the menu silently shows at most twenty skills and hides the rest behind search. Once nothing loads automatically, that cap stops being a cost control and becomes the limit on what an agent can discover — and v0.3 plans for agents writing their own skills, so catalogues will grow. Keep twenty, raise it, or make it a setting?

I lean Raise it, since the reason it was capped largely disappears with this change. What the right number is, I would not guess without measuring.

About project skills

05Who decides a project's skills can be trusted, and how?

Project skills are instructions from a folder that may have come from someone else, with none of the signing, hash-checking or password gate that installing a skill goes through. My proposal is one switch per workspace, off by default. Alternatives: trust automatically, on the grounds that you attached that folder yourself; or approve each project skill individually the first time it is used.

I lean The single switch, off by default, for a first version — but I think this should block shipping rather than be decided in passing.

09An agent could rewrite its own instructions. Is that acceptable, and if not, what stops it?

A folder attached to a workspace is writable by the agents working there. So an agent could edit the project's skills and its CLAUDE.md — instructions it will then follow. Omnipus deliberately keeps its own equivalents out of agent reach; this would be the first exception. Options: accept it and say so; record what was approved and re-ask when it changes; or only read project skills and instructions from a location the agent cannot write.

I lean Record what was approved and notice when it changes — it preserves the feature while removing the silent part, which is the part that actually bites. Like question 5, I think this blocks shipping.

06Which folder do we read project skills from?

The .claude/skills convention is what actually exists in repositories today, so reading it means real content works on day one with no author effort. But it is another product's folder name sitting inside our feature.

I lean Read both — our name and theirs — with ours winning a name clash. Compatibility is the whole point, and refusing their folder name buys us nothing.

07Which instruction files, and how much of them?

Both CLAUDE.md and AGENTS.md exist in the wild, sometimes both in one repository, sometimes one per sub-folder. And they get long — this repository's own is thousands of words, a permanent cost on every message. Root file only? Both names? A size limit, and what happens when a file exceeds it?

I lean Root file only, both names accepted, size-capped with a visible warning when it truncates — silently truncating instructions is worse than not loading them.

08What if a workspace has several folders attached?

That already works today, so multi-repository work needs no new design — but it does need a rule. If three attached repositories each carry skills and each carry a CLAUDE.md, do we load all three sets, only the one the agent is currently working in, or ask you to mark one as primary?

I lean All attached folders contribute skills (they are only offered, never forced), but only one contributes instructions, because instructions are unconditional and three of them will contradict each other.

About scope and direction

11The Workspaces concept says two different things about this. Which one holds?

One page lists skills as global and “available to all agents”, which read strictly means no per-agent permission at all. The locked decision ledger says the opposite — per-agent allow-list, default deny. I have assumed the ledger wins and the other line is loose wording. Separately, the same concept says skills stay global “not per-workspace” while explicitly flagging the workspace overlay as an option someone could take; I have taken it.

I lean My readings are right, but both are worth one sentence from you — if the first is wrong, requirement two changes shape entirely.

12Should skill permission belong to the agent, or to the agent's place on a workspace?

Today it sits on the agent, globally. Omnipus deliberately moved delegation trust the other way — to a per-workspace setting — reasoning that the same agent on two projects should be trusted differently in each. The argument applies word for word to skills. One catch: the obvious place to put it, the per-agent settings already stored on a workspace, is a file agents can write — so it would have to live in the protected store instead, which is more work than it looks.

I lean The argument is real, but it is bigger than issue #663 scoped and I have not assumed it. If you want it, decide now — it is far cheaper before the tool exists than after.
