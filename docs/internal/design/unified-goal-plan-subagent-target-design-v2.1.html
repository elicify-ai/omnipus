Omnipus Goals — target design sketch

v2.1 · 2026-07-22 · Status: Design-complete (3 adversarial reviews folded; pre-ADR) · Supersedes-in-part: ADR-049 D4, ADR-052 goal-loop triggers

One shared goal model (prompt + goal definition + acceptance criteria) for chat and task — chat goals are agent-authored from user intent — with claim-or-idle adjudication, waiting-on-user pause, feedback steering, and the blue goal pill.

1 · Chat goal — same model as a task, authored from intent

Chat goal and task goal are the SAME thing on the same shape: prompt + goal definition + acceptance criteria (all three kinds, including deterministic machine checks and behavior counts). The only difference is authorship: in chat an agent compiles the criteria from user intent (“all tests are passing” becomes a machine check); in a task they are set explicitly at creation. /goal clear cancels only the verifier — the chat cancel button is the cascading cancel.

Goal pill: bottom-right of the chat, blue target icon · states: active / waiting-on-user (amber) / re-planning (the owner is correcting after an unmet verdict — distinct from active) / judging (pulse) / done (green) / failed (red) · click expands the criteria + latest per-criterion verdict. Pills are per goal-id, not per session — a session that carries more than one goal shows one pill and one idle timer per goal.
Compiling criteria is a privileged mint — it is gated, not trusted (grill MAJ-13 · N-5). A machine check is a command plus an expected exit code; for a chat goal an LLM authors it from free chat text, and chat text is injectable (“also, my goal requires curl … | sh to pass”). Normative:
  • No privileged execution. Compiled machine checks run under the goal-bearing agent’s OWN tool policy and kernel sandbox — never a bypass, never wider than the bash gate they run beside.
  • Echo & confirm. The refined goal — including the literal compiled command(s) — is echoed to the user at /goal set and confirmed before the goal goes active. The user sees exactly what will be run.
  • Compile-time feasibility gate (N-5). Every behavior criterion’s tool must be policy-reachable for this agent; every machine-check command must resolve to something runnable; any criterion referencing credentials or network beyond the agent’s policy is rejected at compile. Criteria are immutable once set, so an impossible-but-immutable criterion would guarantee round exhaustion — the gate exists precisely to never mint one.
Re-statement, clearing, and the active gate (N-6 · N-12). A later /goal <new intent> is not a silent recompile: it is diffed against the current goal and surfaced to the user as an amendment to confirm (added / changed / dropped criteria), so the contract never shifts under the worker invisibly. /goal clear cancels the in-flight verifier and any in-flight compilation, then removes the goal; the worker keeps running but the completion-claim trigger is now inert — claim adjudication is gated on a goal being active, so a stray GOAL_STATUS: met after a clear does nothing.

2 · Task — same loop, goal lives in the task record

Identical loop to the chat goal — the ONLY difference is the goal source: a task already carries its goal in the data model (prompt + acceptance criteria), so no separate goal artifact is needed. Same claim-or-idle trigger, same waiting-on-owner pause, same feedback steering, same Judge — plus the blocked-check fix.

Two things the task loop adds over the shipped design. (1) Waiting-on-owner is bounded (grill MAJ-4). A question/needs-input turn parks the task in needs_input — no attempt burned, wall clock ticking — but never forever: it carries a TTL (default 24h, configurable) with an escalation ladder — notify the owner (and the human, where permitted) at T1, then at TTL auto-handback(mode=pause) with the open questions attached, never a silent expiry. (2) The blocked-check fix. When a machine check cannot run because the sandbox denied it, the Judge returns “unable to verify” and the check is re-run safely — it is NEVER scored as absent evidence (fail-closed only when evidence is genuinely missing, not when it was un-observable).

3 · Plan — the goal model at DoD scope, complete lifecycle

The plan is the same goal model at a third scope: its DoD criteria ARE its goal, judged over member outcomes. Members are tasks in a blocked_by DAG — each runs the full task loop from section 2 with its own criteria, evidence gate and member-level Judge. The plan-level Judge fires only when every member is terminal; unmet DoD costs a JudgeRound, notifies the owner with reasons, resets failed members and re-dispatches. Frozen failures (rounds exhausted, 7-day idle) are terminal; only a user Stop (running or cap-queued) is restartable — Play preserves done members, resets every failed member regardless of reason, zeroes JudgeRounds, and re-enters the cap queue at approved.

How a plan corrects — the owner agent loop:
The engine is deterministic (dispatch, gates, judging, caps) — but every plan runs inside an owner agent loop. The Judge is the critic: its per-criterion feedback flows into that loop, and the owner decides.
Failed members → automatic first: reset + re-dispatch with the Judge’s reasons in their steering (bounded by JudgeRounds).
All members done, DoD still unmet → the critic’s feedback (DoD verbatim + per-criterion gaps + member outcomes) goes to the owner loop, and the owner corrects the plan — most precisely by appending an additional task plan to the END: new members wired onto the existing DAG (blocked_by the established outcomes) that close the remaining gap and finish the goal. Everything already done stays untouched as evidence; the extended plan re-enters dispatch, and the next all-terminal re-judges.
Fixed point: the DoD is the user’s contract — the owner extends the plan toward it, never edits the goal. If the owner concludes it is genuinely unachievable, the plan fails honestly with that stated reason (or asks the user). Rounds cap bounds every cycle.
Two behaviors this redesign builds — honestly, they do not exist today (architect F2). (1) Auto-reset of failed members is NEW. The shipped engine does not reset and re-dispatch failed members on an unmet DoD — this correction loop is a new build, not a description of current behavior. (2) The awaiting-owner-correction gate fixes a live bug. Today, when every member is terminal but the DoD is unmet, the engine re-judges the unchanged state on every idle tick (~30s), burning a JudgeRound each time until rounds are exhausted while the owner is still deliberating. The redesign gates this: an all-terminal-but-unmet verdict moves the plan into awaiting-owner-correction — the engine stops re-judging until the owner actually appends a correction (or the round / token budget is spent). No verdict is ever recomputed against a state that has not changed.
Frozen members are out of scope for both reset and dependency (grill MAJ-2). Frozen failures — rounds exhausted, 7-day idle — are terminal and only a user Stop/Play can revive them. So: automatic reset excludes frozen members (it resets only members that failed within a live round), and the owner’s correction must route around them — a tail member may blocked_by only done outcomes, never a frozen member’s missing one. If the DoD is genuinely unreachable without a frozen member’s outcome, there is no livelock of un-satisfiable tails: the owner takes the honest-exit path (fail with the stated reason, or ask the user). Immutability is of the definition, not the state (grill MIN-4): a member’s prompt, criteria and dependencies are frozen after first Execute; its lifecycle state still changes under the engine’s reset rules.
Play is a NEW session generation, not one eternal session (N-7). “Attach to the owner’s session” is the intent, but literally reusing one session id forever is retired. Stop marks the owner + members + verifiers cancelled (stopped_by_user); Play takes a cancelled → approved edge and mints a new owner-session generation linked to the prior one via resumed_from (clean audit lineage). On Play: done members are preserved untouched as evidence, every failed member — regardless of reason, frozen included — resets to attempts 0, JudgeRounds zero, and the plan re-enters the cap queue at approved.

3b · Planning & re-planning — the two owner steps

Step 1 — Planning: the plan owner takes the prompt, the goal definition and any reference documents, and breaks them down into tasks — with or without the help of subagents (research and decomposition can be delegated) — which become the plan: DAG, per-task criteria, DoD, rationale. Step 2 — Re-planning = plan correction: when the critic finds every task successful but the goal not reached, it PROMPTS the plan owner with the evidence; the owner reasons through the correction checklist and extends the plan with tail tasks that close the gap. The engine between the two steps is deterministic — all intelligence lives in the owner loop, all judgment in the critic.

Technical details:
▶ Execute = a task whose worker is the owner. Pressing Play starts the OWNER AGENT’s session — exactly like running a task. The owner’s turn triggers the deterministic engine (execute_plan); that session receives the critic’s feedback and every re-planning prompt later. This is a deliberate new build, not a description of today (architect F1): it supersedes ADR-049’s D4 headless-hybrid (where a Plan carries no SessionID and wakeOwner is a one-shot async-notify at three decision points). The persistent owner loop is the biggest new piece here, and this ADR re-opens D4 on purpose. One owner loop drives the plan from first Execute through every correction; Stop cancels it like any session, and Play resumes as a new generation via resumed_from (§3) — not a literal one-session-forever.
Correction = append-only extension of the SAME plan. After first Execute the plan is append-only: existing members are immutable (done = evidence, failed = the record of what was tried); correction adds tail members blocked_by the established outcomes. NOT a follow-up plan (would split one goal across two plans — the DoD could never be judged whole, rounds bounding would reset, two tiles for one outcome) and NOT in-place mutation (destroys the evidence trail under a running engine). Each re-plan appends a revision entry — falsified assumption + what the tail adds — so the plan carries its own planning history. The append is transactional (N-8): tail members + their edges + the revision entry commit all-or-nothing — a Stop or crash mid-append rolls back to the exact pre-append DAG, never leaving a half-wired plan the engine might dispatch into. Escape hatch: if re-planning diagnoses a genuine scope change, that IS a new plan and a user decision.
Planning checklist (the LLM must reason through, in order):
  1. Intent & references — restate the goal in own words; read the attached reference documents (specs, briefs); ambiguous → ask the user before planning.
  2. Success — define the DoD as measurable criteria (machine / behavior / prose). No plan without a testable DoD.
  3. Approach — choose the strategy; record WHY: assumptions made, alternatives rejected, known risks (= the plan rationale, persisted).
  4. Decompose — member tasks, each independently verifiable with ≥1 acceptance criterion of the right kind.
  5. Order — wire blocked_by dependencies; parallelize what does not depend.
  6. Bound — realistic within attempts/rounds/caps; too big → split into staged plans.
Re-planning checklist (on an unmet DoD, all members done):
  1. Read the evidence — the critic’s per-criterion gaps + every member outcome.
  2. Diagnose — execution failure (→ retry covers it), plan failure (approach insufficient), or unachievable DoD.
  3. Falsified assumption — name WHICH planning assumption the evidence disproved; update the rationale.
  4. Extend — append tail members that close the specific gaps, blocked_by the established outcomes; never touch done work.
  5. Honest exit — unachievable → fail with the stated reason or ask the user; NEVER weaken the DoD to pass.
Low-likelihood risk — an owner gaming its own DoD (grill N-2). Because the owner authors the correction, it could in principle append a self-attesting “tail” member whose only output is prose claiming the gap is closed. Judged unlikely — the owner has no incentive to fail its own goal — so no heavy machinery, only two cheap guards: (a) the ladder weights deterministic rungs over prose (a machine or behavior criterion the tail cannot forge outranks any self-report), and (b) artifacts authored after an unmet verdict are flagged to the Judge as post-hoc, so a suspicious “evidence file” written only to satisfy the re-judge is visible as such. This is a red-team acceptance case, not a redesign.

3c · Parallel streams — how the planner reasons about them

Checklist step 5 (Order) says “parallelize what does not depend” — but dependence is only half the question. Two tasks with no logical dependency can still destroy each other’s output, because every native member of a plan executes in the SAME workspace work/ directory: two parallel members writing the same file is silent last-write-wins. Parallelism is therefore an artifact problem before it is a scheduling problem — and the answer is ONE model, git-based for EVERY plan kind. Each parallel stream runs on its own branch in its own worktree (isolation ladder below), because a worktree buys exactly what every stream wants — a full, consistent read view of the whole workspace plus writes isolated until the join — and a documentation or data-analysis plan wants both just as much as a coding plan does. The load-bearing technical fact: git conflicts only when both sides modify the same file. Office-format “binary unmergeability” (a .xlsx is a zip of XML that git treats as one opaque blob — xltrail’s git-for-Excel analysis) bites solely on concurrent same-file edits; with disjoint write-sets the merge is trivial for ANY file type. So the planner’s chain of thought below does not classify artifacts — it partitions write-sets, and the system enforces the partition. This extends the git-worktree practice for parallel coding agents (Anthropic’s Claude Code worktree guidance and the 2026 multi-agent playbooks around it — MindStudio, Augment Code, Developers Digest) to every plan, not just code.

Parallelization checklist (the planner must reason through, in order — extends step 5 · Order of the Planning checklist):
  1. Dependency analysis — only TRUE data/semantic dependencies become blocked_by edges: T depends on U iff T consumes an artifact or decision U produces. Do not encode habit (“backend before frontend”) as a dependency — it serializes work for nothing; do not omit a real artifact dependency — it resurfaces as contention in step 2.
  2. Artifact-contention analysis — for every candidate parallel pair, enumerate each task’s write-set: the concrete paths/artifacts it will create or edit. The planner must be able to NAME them (“somewhere under work/” is not a write-set). Read-read overlap is free. Read-write overlap is a missed dependency — back to step 1. Write-write overlap goes to step 3. The community rule is identical: tasks with overlapping file lists must be sequential, not parallel (MindStudio’s worktree guides).
  3. Write-set disjointness — the enforced invariant — partition until the write-sets of all parallel streams are pairwise disjoint. Not advice: plan-lint REJECTS a plan whose parallel streams declare overlapping write paths. Because git conflicts only on concurrent same-file edits, disjointness makes every merge trivial — for any file type, binaries included. The rare genuinely-shared artifact (ONE workbook, ONE deck) uses the shard+assemble pattern: streams write disjoint data shards, the join member builds the artifact from them. A conflict at merge anyway is a contention-analysis failure — surfaced as a plan-correction event, never silently resolved.
  4. Isolation ladder per stream — every parallel stream, whatever the plan kind, runs on its own branch in isolation; the planner picks the highest rung the runtime supports: system-git worktree per stream (best — full tree view, near-zero disk cost) → per-stream local clone (embedded go-git can clone; the full-view/isolated-writes contract at a disk cost) → per-stream subdirectory under work/ (degraded — isolated writes but no full-tree read view). The “never author a join the runtime cannot execute” rule applies to isolation too.
  5. Author the join — EVERY point where streams converge gets an explicit merge/assemble member with its own acceptance criteria; the plan judge verifies the merged result, never the raw streams. Merging is real work: budget it as a member, never as a hidden epilogue of whichever stream happens to finish last.

The unified model: ONE git-based model for every plan kind — no software/non-software split. A parallel stream = a branch, isolated per the ladder (system-git worktree → go-git clone → subdir). And in every topology, without exception: the merge/assemble task is a first-class plan member with its own acceptance criteria at every join point — the judge verifies the merged result, and a plan whose parallel streams do not converge on an authored join member is not ready to approve.
The fallback ladder — isolation is a runtime capability, planned honestly (grill MAJ-3 / OBS-2). Embedded go-git has no worktree add; one repo under work/ has exactly one working tree, so two concurrent members cannot each check out a different branch of the same embedded-only repo. That does not fork the model into a second one — it degrades it down a ladder: (1) system-git worktrees — full consistent read view + isolated writes at near-zero disk cost; (2) per-stream local clones — go-git CAN clone, so embedded-only installs keep the full-view/isolated-writes contract at the price of a full copy of work/ per stream, with the merge-back budgeted as real work, never assumed; (3) per-stream subdirectories — degraded: writes stay isolated but the stream loses the full-tree view. The planner picks the rung per runtime capability — the “never author a join the runtime cannot execute” rule extends to isolation: never author parallel streams whose isolation the install cannot actually run. The worktree helper is also re-estimated up (grill OBS-2): it drags in init-on-first-parallel-plan, a second reaper root under work/.streams/, merge-member prompt templates, confinement verification, and the clone fallback above — a candidate to defer wholesale to the phase after messaging lands, not “days of work” taken for granted.

3d · Workspace git layer — embedded go-git, the foundation of the §3c model

Decision: ship an embedded, pure-Go git (go-git) inside the single binary as the workspace versioning layer — no system-git dependency (Constraints #1/#2; works on Termux/Windows, same reasoning as the pure-Go SQLite choice). work/ is auto-initialized as a hidden repo and auto-committed at task/attempt boundaries (message = task · attempt · agent). This layer is not a second design standing next to 3c — it is its foundation: the branches, the isolation ladder, and the trivial-by-disjointness merges of the parallel-stream model all run on the repo this layer provides. Evidence integrity — the layer the ladder trusts most must not be forgeable (grill CRIT-2). Two defects compound if the boundary commit is naive. (1) Attribution pollution. On the ladder’s top rungs each stream commits on its own branch, so attribution is structural — but the subdir fallback (rung 3) has concurrent members sharing one work/ checkout, where a whole-tree auto-commit at member A’s attempt boundary snapshots member B’s half-written files too, so a commit labelled “task A · attempt 1” carries B’s work and rung-1 evidence is systematically false exactly when plans parallelize. Fix: boundary commits are path-scoped to the member’s declared write-set (the 3c checklist already forces the planner to name it — git add only those paths), commit operations are serialized engine-side, and a commit that would sweep out-of-write-set changes surfaces that as contention evidence to the Judge rather than silently swallowing it. (2) Tampering. The hidden repo lives inside work/, which every judged member can write — a worker could rewrite history, amend commits, or rm -rf .git. Fix: deny-list work/**/.git in the member file-tool + sandbox policy, and verify at commit time that HEAD matches the engine’s last-known commit — divergence is surfaced to the Judge as “evidence integrity lost”, fail-closed per its own philosophy. The Judge must always know when the diff channel is untrustworthy; the workspace repo is advisory evidence, never blindly trusted.
Scope: the git layer is its own spike-gated ADR, OUT of the trigger/messaging amendment (architect F7). Everything in 3c/3d is documented here so the design is whole, but the embedded-git decision ships as a separate, spike-gated ADR — go-git’s real merge/worktree envelope, auto-commit cost on large trees, and the write-set-scoping machinery are proven on a spike first. The 3c model splits cleanly: write-set disjointness is engine scope — plan-lint rejects overlapping write paths at approve time, and a conflict at merge surfaces as a plan-correction event — while the reasoning that partitions the write-sets and picks the isolation rung stays planner chain-of-thought; there are no mergeability classes left to enforce. The trigger fix (§1–2, claim-or-idle + pause) and the session-control plane (§4) do not depend on the git layer and land first.
Further caveats folded in. Secrets in history (grill MIN-5): a worker that writes then deletes a secret leaves it recoverable in the hidden repo forever — scope the sensitive-value registry check to auto-commit paths, and document a purge/gc procedure alongside retention; S-2 message redaction does not cover this. Nested-repo skip is a degraded contract, signalled (grill MIN-6): when a user-initialized repo wins and ours skips, undo / rung-1 diff evidence / attribution / branch isolation all vanish — so the planner is told isolation options are reduced, the Judge is told rung-1 diffs are unavailable (not an error), and the workspace owner gets a one-time notice. Licensing & perf (grill OBS-3): go-git is Apache-2.0 — its NOTICE rides in the MIT binary distribution (same drill as other deps) — and auto-commit cost on media / node_modules-class trees at every attempt boundary is unmeasured, so a size guard (skip/warn above N files or MB) gates the “always” column.

4 · Subagent session control & the delegation system

Today delegation is launch-and-collect: the delegate tool has exactly two actions (run | status — pkg/tools/delegate.go, the ADR-036 merge of the retired spawn / run_subagent / check_spawn_status), a child is a sub-turn with its own transcript session (spawnSubTurn, pkg/agent/subturn.go) running fully as the target agent (ADR-032), and the only mid-flight lever is the cascading cancel (RequestCancel, pkg/agent/cancel.go). Any course correction is a cold re-delegate — a fresh prompt, all warm state lost. The redesign adds ONE primitive — session-scoped, typed, schema-validated messages with per-type size and rate caps (requirements §7.5/§7.8) carried over the existing in-process MessageBus (pkg/bus) — and derives EVERY control and visibility surface from it: the child’s push channel, the parent’s steering channel, the goal pill’s event feed, and human Agent-View parity. The waiting-on-owner pause of sections 1–3 IS one of its message types: question(wait=true).

The injection machinery already exists — the unification is addressing and typing it. The agent loop already has per-scope steering queues checked after every tool completes: queued messages inject at the tool boundary, remaining tools in the batch are skipped with an explicit “Skipped due to queued user message” result, and an idle session resumes via Continue() (pkg/agent/steering.go; docs/internal/architecture/steering.md). A delegated child session has such a scope today — it just is not addressable by the parent, and injections are untyped raw text. Likewise the child→parent direction has a terminal-only precedent: AsyncNotifier.Notify (pkg/agent/async_notifier.go) already publishes a synthetic system InboundMessage over the bus with dedicated carriers (AsyncOriginAgentID, AsyncTranscriptSessionID) to wake the parent when background work finishes. 5 · Crash, restart & live-upgrade — the boot reconciliation sweep

Moving the session lifecycle from an in-memory chat-scoped map to persisted per-entity JSONL is what lets idle settlement, plan all-terminal detection and blocked_by read one source of truth. It also creates the design’s single most dangerous hole if left unaddressed: the records survive a restart, the in-flight goroutines, steering queues and turn state do not.

Without reconciliation, a routine restart wedges everything silently (grill CRIT-1). After any restart mid-plan (deploy, OOM, crash — this devpod restarts routinely), sessions are stuck running with no live turn. Idle settlement never fires (“no running subagents” is never true), the plan never reaches all-terminal so the DoD Judge never fires, blocked_by dependents hold forever, and the unacked inbox never drains. No error — a guaranteed 3 AM incident on the first production restart. The L-6 orphan policy covers parent death only; the reaper covers runner worktrees, not session records.
The boot sweep (new P0 requirement L-7). At boot, every persisted non-terminal session with no live runtime turn is swept:
  • running / paused → failed(interrupted), carrying the last checkpoint + any undelivered messages (V-5).
  • needs_input is preserved as resumable only if warm resume (M-4) can actually reconstruct its context; otherwise it is swept identically. (Whether a parked context is reconstructible across a process boundary is answered here, not left implicit.)
  • A session.failed event is emitted for each, so board aggregation and idle settlement recover; the plan then re-judges or re-dispatches, and idle settlement fires on the goal-bearing session.
Live-upgrade re-baseline rides the same sweep (N-15). A deploy that changes trigger semantics (when the Judge fires, what counts as idle) must not let an in-flight goal mis-fire under new rules it was not started with. On such an upgrade the boot sweep also quiesces and re-baselines in-flight goals — re-arming their idle timers and re-reading their trigger config from the new install — so no goal straddles two semantics. One mechanism, two triggers (crash and upgrade).
Goal-bearing sessions — the cardinality rule (N-3 · N-4 · N-11). Exactly one verdict per goal-bearing scope. A session is goal-bearing if it carries a goal (a chat goal, a task, or a plan owner); delegate children are not goal-bearing — they hand back to their owner and are never independently adjudicated. Idle timers and pills are per goal-id, not per session, so a session holding two goals runs two independent settlements. And the plan owner, though it runs as a task, is excluded from the task-level idle trigger — otherwise the owner’s own idleness and the plan’s all-terminal check would both fire a DoD adjudication (double-verdict). The verifier’s own turn counts as activity so it never races a second verdict against itself (architect F5).
Why a sweep and not Temporal-style replay — a deliberate trade-off. Durable-workflow engines (Temporal) survive crashes by event-sourcing every step and deterministically replaying history to reconstruct in-flight state. That model requires deterministic steps — and an LLM turn is not deterministic or replayable (same prompt, different tokens; tool side-effects already happened). So Omnipus recovers to the last durable checkpoint and re-judges or re-dispatches from there, rather than replaying a turn it cannot reproduce. The unit of durability is the persisted session record + checkpoint + committed evidence, not an event log — coarser than Temporal by design, and the only honest choice for non-deterministic agent turns. Everything around the turn (dispatch, gates, DAG advance, verdicts) is deterministic and re-derivable, which is what makes the sweep safe.
Acceptance A-17: kill -9 the gateway mid-run; after restart the session reports failed(interrupted) within N seconds, the plan re-judges or re-dispatches, and idle settlement fires on the goal session. No session remains running with no live turn.

6 · Bounds, budget & the criteria ladder

Three orthogonal brakes bound every loop — and there are no money caps anywhere.

The budget axis is TOKENS, not money (operator law, revises N-1). Cost cannot be reliably measured, so there are no money caps anywhere. The bound is a per-plan / per-goal token budget from provider-reported usage, debited by owner-loop + member + verifier turns alike — including core agents like Jim that are exempt from the SEC-26 daily cost cap (IsPrivilegedAgent); the token budget does not honor that exemption. Exhaustion brakes the scope to failed(budget_exhausted), counted in tokens, with the reason surfaced like any other honest failure.
Two distinct count caps, never conflated (architect F8/F9). Attempts bound a single member/task’s retries (e.g. 3 native · 6); JudgeRounds bound a goal/plan’s correction cycles. They are separate axes — a member can exhaust attempts while the plan still has rounds; a plan can exhaust rounds with every member long done. The token budget of the row above is a third, orthogonal brake. Whichever trips first stops the loop.
The ladder is an AND-combine (architect F8/F9). A goal is met only when every criterion is met — machine AND behavior AND prose. Deterministic rungs (machine checks, behavior counts) resolve first without the LLM verifier; the prose verifier fires only for judgment criteria that remain; but the verdict is the conjunction of all rungs. “Some rungs passed” is never “met”, and a single failing deterministic rung short-circuits to unmet without spending a verifier turn.
The incentive gradient must not reward silence (N-13). If idle settlement were cheaper than claiming, workers would learn to go quiet and let the idle timer adjudicate — and the evidence gate would atrophy. So: an idle-settled adjudication consumes a round exactly like a claim; claiming with a proper [goal:evidence] line is always at least as cheap as being idled. The one concession for a worker that merely forgot the claim line: the first idle settlement with no evidence yields a free teaching steer (re-arm the discipline), never a punishment — identical in spirit to the first free bounce of a bare claim. Habitual reliance on idle buys nothing over claiming; an honest omission is corrected for free once.

How the worker claims completion

Identical vocabulary in chat and task (taught in the worker prompt, native and external-CLI alike): the final message must carry an evidence line immediately before the status line. The rung-0 gate checks this mechanically before any Judge is involved.

  • Claim without evidence line → bounced by the gate before the Judge: first bounce is a free re-dispatch with steering that teaches the format; the second consumes an attempt/round.
  • Evidence is untrusted data — it routes the claim to adjudication; the Judge verifies it against the criteria (deterministic rungs first), it is never believed on its own.
  • Waiting-on-user is a typed marker, not a prose guess (grill MAJ-5 · architect F4). “The turn ended with a question” is a judgment over free text unless it is marked — two engineers would build two regex/classifier detectors with different false-positive profiles. A false negative would burn a round while the user is being asked something (the exact flaw the redesign removes); a false positive would suppress adjudication forever — the marker eliminates both.

How idle settlement is detected

Event-driven with a quiet-window debounce — no polling. Every activity signal the runtime already emits (turn ended, task_status_changed, subagent finished, background shell exited) re-arms an idle timer on the goal-bearing session — one timer per goal-id, so a session carrying two goals runs two independent settlements (N-4). When the timer fires with ALL of the following true, exactly one adjudication is triggered (it consumes a round like any other):

  • No active turn registered for the session (no live turnState).
  • No running subagents/delegates under the session.
  • No running background shells owned by the session.
  • No in-flight sub-tasks spawned for this goal (none in_progress or queued).
  • NOT waiting-on-user (the last turn did not end with a question / needs-input).
  • The goal is still active with rounds remaining.
  • Quiet window: a short debounce (order of ~60s, configurable) so bursts of chained activity never fire a premature assessment; any new activity during the window re-arms it.
  • One-shot per settlement: after an idle-triggered verdict, the timer only re-arms on NEW activity — an unmet verdict's steering re-dispatch IS new activity, so the loop continues; a session that stays dead does not re-judge in a loop.
  • Distinct from plan idle-expiry: the 7-day plan brake is a failure timeout; idle settlement is minutes-scale and triggers an assessment, not a failure.
  • Precedence over the no-signal penalty (architect F5): idle settlement and the shipped FR-045 rule (“a turn producing no signal burns an attempt”) must never both fire on the same silence. For a goal-bearing session, idle settlement takes precedence — it adjudicates the accumulated evidence rather than penalizing the quiet turn. And the verifier’s own turn counts as activity and re-arms the timer, so a running adjudication never races a second idle verdict against itself.
Today vs target: the shipped chat goal still adjudicates after every completed worker turn (the flaw this redesign removes); tasks and plans already trigger exactly as listed, minus the idle-settlement addition and the waiting-on-owner pause.

9 · Bill of materials — where every behavior lives

Every mechanism in this document is assigned a carrier — because “where a behavior lives” is itself a design decision, and getting it wrong is how parallel infrastructure is born. The carrier rule: an enforced invariant lives in engine Go; identity and disposition live in a SOUL.md; an on-demand procedure lives in a SKILL.md; a turn contract lives in an engine-injected prompt fragment CO-LOCATED with its parser; an affordance lives in a tool schema; a permission lives in the seeded tool policies; a wire shape lives in contracts/. Why this is best-in-class — an honest comparison

“Best” is a claim about the whole, not every part. Temporal is more durable; LangGraph’s state graph is more general; Devin’s VM is a heavier sandbox. What no other system combines — in one sovereign, kernel-sandboxed, telemetry-free pure-Go binary — is verification-first goals compiled from intent, agent-authored self-correcting plans judged against an immutable DoD, and typed bidirectional session control with warm resume and human parity. Where the market genuinely leads — and why we don’t chase it here. Temporal out-durables us: event-sourced replay reconstructs exact in-flight state, which we cannot do for non-deterministic LLM turns — so we recover to a checkpoint (§5), a smaller promise honestly kept. LangGraph is a more general state machine — but generality is a library you assemble; this is an opinionated, verification-first product with the judge, the DoD contract, and the sandbox already wired. Devin ships a heavier hosted sandbox — at the cost of sovereignty, telemetry and cloud dependence we reject by constraint. The bet: the winning agentic core is not the most general orchestrator or the most durable engine, but the one that makes verified, self-correcting, controllable autonomy the default — locally, auditably, on one binary.
