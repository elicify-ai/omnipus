# Does Omnipus have mobile in mind? — independent review

**Verdict: Partly.** The design system's *rulebook and verification machinery* take mobile seriously — there's a real touch-target scale, a real narrow-screen (320px) and 200%-zoom test harness, and a genuinely sophisticated fix for the iOS on-screen-keyboard bug most web apps get wrong. But the *application itself* still has a concrete, measurable defect that will visibly annoy every phone user (typing in almost any text box zooms the whole page in), and two whole screens — the calendar and the task board — have no phone-adapted layout at all, only "doesn't technically break" horizontal scrolling. None of the phone-specific checking has ever run on a real phone or real Safari.

---

## 1. What's already good

- **The viewport meta tag is unusually well thought through**, including a comment explaining *why*: `viewport-fit=cover` (keeps content clear of the iPhone notch/home-bar) plus `interactive-widget=resizes-content` (makes the on-screen keyboard resize the page instead of just covering it). Evidence: `/Users/danielpiatkowski/AI-Agent-Workspace/omnipus/wt-release-session/index.html`.
- **The app shell has a hand-built fix for a hard iOS Safari bug**: when the keyboard opens (or you tap anywhere while it's open), iOS silently shifts the visible area without telling the page, which normally makes headers jump off-screen. `AppShell` tracks the browser's real "visual viewport" and re-pins itself every time it changes, with a written incident history of the two related regressions it had to fix along the way. Evidence: `src/components/layout/AppShell.tsx::AppShell` and the pure-math helper `src/components/layout/appShellViewport.ts::computeAppMetrics`.
- **Touch targets are a real, encoded rule, not a suggestion.** The design system defines a minimum tap size of 24 px on a mouse/trackpad and 44 px on a finger (the same as Apple and Google's own guidelines), and it's wired into components today — e.g. the shared `Input` control is already 44 px tall specifically under `(pointer: coarse)`. Evidence: `design-system/tokens/foundations.json::target.pointer.minimum` / `target.touch.minimum`, `src/components/ui/input.tsx::Input`.
- **The test suite actually simulates a phone**, not just a narrow desktop window: one Playwright project runs Chromium with real touch emulation at 390×844 (an iPhone-sized screen) and checks that every documented touch target is truly reachable — testing eight points around each button's edges and corners, and confirming that enlarged tap zones don't overlap their neighbours. Evidence: `playwright.design-system.config.ts` (`chromium-coarse-pointer` project), `tests/design-system/browser.spec.ts` (the `pointer` check block).
- **Reflow at 320px (the narrowest phone width, e.g. an iPhone SE) and 200% zoom are both wired as automated, per-component checks**, not left to a human to remember. Most of the 36 catalogued components (Button, Dialog, Sheet, Field, Table, Calendar, etc.) declare these checks as applicable. Evidence: `tests/design-system/browser.spec.ts` (`reflow` / `zoom` check blocks), `design-system/manifests/*.json`.
- **Navigation genuinely collapses for small screens.** The sidebar switches from a pinned column to an overlay + hamburger below 1024px, and the workspace tab strip (Chat/Tasks/Calendar/Library/Team) collapses from a full row into one "Active ▾" dropdown below 1152px. Evidence: `src/components/layout/Sidebar.tsx` (`SIDEBAR_PIN_BREAKPOINT`), `src/components/workspaces/WorkspaceTabBar.tsx` (comment block describing the `@6xl` container-query strategy).
- **Slide-over panels are capped to fit a phone screen** (90% of viewport width, scroll-contained) rather than rendering at a fixed desktop pixel width that would force horizontal scrolling. Evidence: `src/components/ui/sheet.tsx::sheetSizeWidth` / `sideDefaultWidth`.
- **The login and onboarding password/username fields already do the small, easy-to-miss mobile-friendliness things right**: correct `autoComplete` values (so the phone's password manager/keyboard suggestions work) and a password-visibility toggle sized to a 44px tap target. Evidence: `src/routes/login.tsx` (lines ~189–222), `src/routes/onboarding.tsx` (lines ~806–996).
- **The manifest "not applicable" reasons are argued, not asserted** — e.g. Popover explicitly excludes the CSS-zoom check because CSS `zoom` doesn't reflect real browser 200% zoom for a portalled floating element, and says real-zoom evidence is still owed as a manual release check. That's a credible, checkable reason, not a rubber stamp. Evidence: `design-system/manifests/popover.json` (`popover-zoom`).

## 3. What was checked vs. not checked

**Checked:**
- The definition and migration-plan documents (`docs/internal/design/design-system-definition.md`, `design-system-foundation-policy.md`, `design-system-migration-plan.md`) for what mobile behaviour is actually promised and in-scope right now.
- The machine-readable tokens (`design-system/tokens/foundations.json`) for breakpoints, touch/pointer targets, density and root-size values.
- Every component manifest (`design-system/manifests/*.json`) for which components declare reflow/zoom/pointer/reduced-motion/forced-colors checks as applicable, and read the stated reasons for the ones marked not applicable.
- The actual browser-verification code (`tests/design-system/browser.spec.ts`) and its Playwright project list (`playwright.design-system.config.ts`) to see what these checks really do, not just that they exist.
- Application shell/navigation code (`AppShell.tsx`, `appShellViewport.ts`, `Sidebar.tsx`, `WorkspaceTabBar.tsx`), the shared `Input`/`Textarea` primitives, `Sheet`, the login/onboarding forms, the Kanban board (`BoardView.tsx`), and the calendar (`FullCalendarView.tsx`, `CalendarScreen.tsx`).
- `index.html` for the viewport meta tag; grepped the whole `src/` tree for `safe-area`, `dvh`/`vh`, `autoComplete`/`inputMode`, and `touch-action` usage to see how consistently mobile-aware patterns are actually applied versus how they're documented.
- Live-rendered three Storybook stories in a real (Chromium) browser at a 375px-wide viewport and took screenshots: the default `Input` (confirmed the 12.25px computed font size directly, not just from reading the class name), a narrow-viewport `Table` story, and a `Sheet` overlay. Screenshots saved under `dist/design-system-baseline/cli-lanes/claude-mobile-review/`.

**Not checked (named limitations):**
- No real phone and no real mobile Safari or Android Chrome — everything mobile-specific here is either code-read or Chromium's touch *emulation*, which is a good proxy but not proof, especially for the iOS-specific keyboard-resize behaviour `AppShell` is built around.
- No landscape-orientation testing.
- No on-screen-keyboard behaviour was actually triggered and observed (Storybook stories don't have a live keyboard to open); the `AppShell` keyboard-handling logic was verified by reading the code and its own test file, not by reproducing the bug it fixes.
- Did not rebuild Storybook or the SPA, and did not run the design-system audit/fixture/lock suites — per the task's ground rules, since other agents are actively editing those scripts and tests right now.
- Did not view the actual application screens (chat, board, calendar, settings) live in a browser — `dist/spa` was available but out of scope for this review; all Layer 2 (application) findings come from reading the source code, not from clicking through the running app.
