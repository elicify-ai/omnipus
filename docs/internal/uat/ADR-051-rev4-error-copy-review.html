Error-message translation — critical review & rewrite

1. Brand voice and the rules I used

From docs/internal/brand/brand-guidelines.md §6 (Voice Personality): Sophisticated, Protective, Visionary, Calm, Reliable, Approachable. Tone spectrum:

  • Technical context (API, logs) — surgical, precise, minimal jargon, confidence.
  • User interface (dashboard, onboarding) — clear, helpful, efficient, lowers complexity.
  • Marketing — visionary, empowering, secure, inviting.

The brand archetype is the Sovereign Deep (Sage + Caregiver). Errors fall in the user-interface band, so my rewrites apply the calm, helpful, lowers-complexity rule, with the technical-band rule reused for the optional Verbose chat diagnostic surface.

Rewrite rules I applied

  1. Name the cause, not a vague "service." The failure usually lives in model / provider / network / attachment / request shape. "AI service" is brand-wrong and uninformative.
  2. Lead with the user, not the system. "Couldn’t read this model" beats "The model rejected this."
  3. State what to do. Each new copy names a recovery action: retry, switch model, drop turns, remove flagged content.
  4. No "Please" excess. One politeness per message; "please retry" once max.
  5. No apologies for the product. "Sorry, an error occurred" is un-Omnipus; describe what happened.
  6. Code-names are fine in chrome. Operators see media_unsupported in the activity log; end-users see plain English.
  7. Short. ≤ 22 words, one sentence where possible, two max.
  8. Brand-words preserved. Keep Omnipus, model, attachment, turn, tool — drop AI service, The system.

3. Source attribution — should we prefix “Provider:” on upstream errors?

Yes, with nuance. The reason it matters: today, when the upstream rejects a request, a user has no way to tell whether Omnipus or the model provider is at fault. A short attribution prefix closes that gap, sets correct support expectations, and protects the brand when the cause is clearly upstream.

The four options I considered

OptionExampleProsConsVerdict
A. No prefix
status quo		 “The model refused this request. Retry once, or pick a different model.” Clean, calm. Ambiguous — feels Omnipus-blaming when upstream rejected. ✗ keep
B. “Provider:” literal prefix
your suggestion		 “Provider: the model refused this request. Retry once, or switch models.” Maximum clarity, zero ambiguity. Slight enterprise / blame-shift tone; “Provider” is jargon. ≈ partial
C. “From the model:” prose “From the model: it refused this request. Retry once, or switch models.” Natural English, sets source without jargon, keeps calm tone. 3 words overhead per message. ✓ recommended
D. Inline parenthetical + Verbose chip “This model refused the request (upstream). Retry once, or pick a different model.”
+ “Open provider details ▸” in Verbose chat		 Shortest in-chrome; escalates detail in Verbose. Two surfaces to keep aligned; not as visible to users. ✓ if you want minimal chrome

My recommendation: option C — “From the model:”

It reads like plain English, doesn’t blame a nameless “service,” and sets the right expectation (the failure is upstream of Omnipus). Reserve no prefix for issues we own outright (Omnipus gateway 5xx, attachment-handling bugs) so users know where to report.

If you still want the literal “Provider:” prefix (option B)

Apply it to the same rows as option C, and keep it as the title case Provider. Use a colon, not a dash. The example for A2 would become:

"Provider: the model refused this request. Retry once, or pick a different model."

How I’d roll it out

  1. Pick option C (recommended) or option B (your literal suggestion) — either is defensible.
  2. Add the chosen prefix to rows A1–A8 in section A of this report (the “Improved” column).
  3. Add a tiny visual treatment: render the prefix as a muted <small>From the model</small> tag in MessageItem.tsx so the bubble stays one voice.
  4. Mirror in Go userMessages so transcripts and WS frames carry the same prefix.
  5. Cover with a test in llm-error.test.ts asserting each code starts with the chosen prefix (or none).

Two parallel catalogs exist today (Go userMessages + SPA codeToDisplay). They already diverge on media_unsupported, unknown, context_too_long. The bubble is built from SPA copy, the transcript/frame carries the Go copy. I review both and call out divergence.

9. F. Diagnostic surface — Verbose chat → Technical details

Rendered by MessageItem.tsx when Verbose chat is on and the wire carried a non-empty errorDetail. This is the surface where it IS OK to leak provider identity, model slug, status code, body preview — that’s the point. The current prefix-free dump is fine; I’d only tighten the **header**.

  • Today: a collapsed disclosure under the error bubble, body shown as preformatted text.
  • Proposed header: "Technical details — provider, model, status, body preview". Tells the operator what they’re looking at, no surprise.
  • Safety: keep the ERROR_DETAIL_MAX_CHARS cap; show a "copy to clipboard" affordance so operators can paste into an issue without scrolling.
  • Recommendation: leave the body content verbatim (it is diagnostic by design) but fix only the header string.

10. G. Cross-cutting judgments

  1. Kill "The AI service…" everywhere. The failure is usually model / network / attachment, not a nameless service. Both Go and SPA strings need to lose that phrase.
  2. Unify Go userMessages and SPA codeToDisplay. Today SPA ignores wire message for the bubble — good for safety, bad for one voice. Prefer one canonical map (contract or a shared copy pack generated alongside the wire types).
  3. unknown must not stay generic when the real cause was media_unsupported after strip-retry exhaustion. The SVG-history pollution case should surface media copy, not "Something went wrong talking to the model." That's a classification/display bug as much as a copy bug.
  4. tool_args and schema rarely hit end-users. If they do, soften and point to Activity / Verbose. Avoid "schema" in user chrome.
  5. Agent-context markers should stay machine-parseable but sound like calm system notes. Square brackets are fine for downstream grep; the prose around them should read like an engineer's footnote, not a kernel panic.
  6. Upload toasts must never concatenate raw msg. That string comes from the server body and can leak paths, IDs, or stack traces. Use an allow-list of safe causes (size, type, network).
  7. "Server" → "Omnipus" on 5xx and fallback paths. We are the server. We can own the failure without inventing a third party.
Live bug observed in the multi-format UAT: after send_file of an SVG, subsequent turns in the same session can surface row A9 ("Something went wrong talking to the model") because the SVG MIME survives in history and the provider rejects it. A copy fix alone does not solve this — the presentation path must sanitize outbound/history SVG (rasterize or strip) the same way it does inbound SVG. Track this as a follow-up ADR item.
