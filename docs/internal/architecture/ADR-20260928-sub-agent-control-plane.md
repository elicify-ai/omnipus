### What is wrong, in one line each

1. **An owner-only question has no path to the owner, and the owner's answer no path back.**
2. **The only enforced interrupt is `cancel`, which ends the whole subtree.** `steer` is advisory.
3. **`steer` on a finished child silently starts new work** (#1011 D4).
4. **A parent cannot tell "not yet seen" from "seen and ignored"**; the queue is in memory.
5. **A restart throws delegated work away** — failed, goal ended, each level woken separately.

## Decision

### Vocabulary

**Amended 2026-10-06 — founder decision:** the current lifecycle display is `working / done / failed / stopped`; `done` maps to `completed`. The `waiting for answer` / `needs_input` row and question-expiry clauses below are historical, removed by **Steering commands: no person question**. Completed means the turn ended, not that its chat was archived or hidden.

**[2026-09-29, F0929-1/F0929-2]** The founder's ruling replaces the 2026-09-28 draft's five-word vocabulary with the Claude Code model: a session never ends and is never deleted, only a turn ends, and every session is always resumable (RESUME, D3/D8 — the renamed `follow_up`, F0929-5). There are exactly **five session states** — `working`, `waiting for answer`, `done`, `failed`, `stopped` — and `stopped` **replaces both** `paused` and `cancelled`: one alive, resumable state, whatever produced it.

| Word (2026-09-29) | Meaning | Record | Supersedes (2026-09-28 draft) |
|---|---|---|---|
| **working** | a turn executing, `queued` to run, or `running` waiting on its own descendants | `queued`, `running`, no current Stop marker | `live` (renamed only) |
| **waiting for answer** | asked a question and waits for the answer | `needs_input` | `parked` (renamed only) |
| **stopped** **[2026-09-30]** | alive and resumable, no compute/slot; the remaining lifetime budget freezes while stopped except when expiry already spent it (Q19, D6); a question may remain open across Stop (D1.7) | `LifecycleStopped`, separate persisted `stop_note {at, by, seq, cause: stop/redirect_pause/cascade/restart/timeout}`; the old `Stop` marker remains the in-flight dispatch fence only (D2) | merges the prior `paused`, `cancelled`, and restart-only `interrupted` outcomes; Q19 also folds `LifecycleTimedOut` into `stopped` |
| **done** | the turn ended with a final answer | terminal `completed` | the successful half of `finished` |
| **failed** | the turn ended with a real error — never a stop, a cascade, or a restart | terminal `failed`, real error reason only | the erroring half of `finished` |

**[2026-09-30, F0929-Q19=A]** `LifecycleTimedOut` is retired as a distinct outcome: exhausting a session's **lifetime execution budget** writes `LifecycleStopped`, `stop_note.cause: "timeout"`; RESUME grants a fresh budget (D6). This does **not** change the separate 24-hour owner-question park expiry, which still writes `failed(owner_unreachable)` or `failed(answer_timeout)` (F1011-Q2, D1.8). Stop, timeout, question expiry, and terminal `done`/`failed` never clear an active goal as a side effect (F0929-6; D7).

**"Unfinished" for a parent's completion check (D6, D6b), after F0929-7 — restated precisely because the rule changed:**

| Child state | Blocks the parent's "done"? | Why |
|---|---|---|
| `working` | **Yes** — unchanged | The parent naturally waits; nothing to decide |
| `waiting for answer` | **Yes** — unchanged (F1011-Q4, D6b) | The question itself already wakes the parent; the 24-hour limit (D1.8) bounds the wait |
| `stopped` | **No, not by itself.** The transition to `stopped` tells the parent (D6's notice) and the parent **decides**: resume it (it becomes `working` again and blocks until it finishes), do the work itself, or explicitly report the goal open despite the stopped helper. The parent never hangs waiting on a stopped child (F0929-7, revises R-Q2 for this case only) | A stop is a decision point, not a silent block |
| `done` / `failed` | No | Terminal in the ordinary sense (though the session itself is still resumable per F0929-1 — "terminal" here means the turn is over, not that the session is gone) |

### D1 — Historical owner-only questions (removed 2026-10-04)

**Amended 2026-10-06 — precedence clarification:** this entire D1 section is historical only. **Steering commands: no person question** removes its pause, relay, acceptor, question record and expiry. Do not implement it or cite it as a current requirement.

**[2026-09-30; F0929-R2-Q1=C]** The *answer path* retains R§8.2's guarantee: **no agent at any level authors an authenticated answer to an `owner_required` question.** The founder separately permits a parent to withdraw that question through redirect/RESUME and send its own instruction without owner approval; this accepted single-user risk is not represented as an authenticated answer (D1.7, Consequences). This ADR amends R§8.2 only for that withdrawal path.

**1. The parent chooses.** A child's `owner_required` question reaches the parent's inbox as today (wake-eligible, `pkg/agent/async_notifier.go::wakeableSessionMessageKinds`).

| Move | Verb | Effect |
|---|---|---|
| Relay upward | new `delegate(action="escalate", session_id, correlation_id, note?)` | Relay record + one-hop forward (step 2); returns the **new** relayed `correlation_id` |
| Withdraw the question **[2026-09-30]** | `redirect` or RESUME on the waiting child (D2; F0929-R2-Q1=C) | Question and relays close `superseded` **without an owner answer**; the parent's new instruction is parent-authored, not an authenticated owner answer (D1.7) |
| Stop or Stop all **[2026-09-30]** | `stop` on the child, or `stop_all`/`/cancel` (D7) | Session lands `stopped`, **question and relays remain open** until answered or 24-hour expiry (F0929-R2-Q2=A) |
| Try to answer | `respond` | Non-error guidance: "This question needs the owner. Use action=escalate to pass it up, or redirect/RESUME the child without an owner answer." Nothing changes |

Escalating a `self_ok` question is allowed; from then on the **first** answer to arrive wins (a parent `respond` on the original, or the owner's answer through the relay) and the other is closed `superseded` (MIN-004).

**2. Relay one hop at a time.** `escalate` mints a new `correlation_id` (runtime-generated, returned in the tool result) and appends a `question` to the relaying parent's upward inbox with: the child's text **verbatim**; the parent's `note` in a separate labelled `relay_note` field; `authority: owner_required`; `relay_of: {session_id, correlation_id}` (one hop down); `origin: {session_id, correlation_id}` (the first asker, copied unchanged). The relay record is stored **in the relay ledger of the relaying session** (the D4 ledger), not only in the inbox, so it is resolvable regardless of `inbox_ack` (MAJ-002). The relaying parent does **not** park. Relayed entries do **not** increase `Depth` — the hop count lives in the `relay_of` chain — so the inbox depth cap never refuses a relay (MAJ-003). This is R§8.7's strict one-hop default; FR-135 stays unbuilt.

**3. Owner terminus.** The hop stops at the tree's root (`pkg/session/lifecycle_edge.go::SteeredBy.RootSessionID`). When the relayed question lands in the root's inbox, the **runtime** — not the root agent — shows it in the root conversation as a persisted `subagent_message` event (kind `question`, [A sub-agent is a session steered by another session](./ADR-091-steered-sessions-replace-subagents.md) D7's status-line contract) carrying a short **question code** (e.g. `Q-3F2A`). The root agent is woken and may explain it; the runtime entry is the "shown" anchor.

**4. Strict owner answer (F1011-Q5; fixes CRIT-001).** A `respond` whose target question is `owner_required` is accepted only as an **owner answer**, and an owner answer is valid only if **all** hold:

| Check | Rule |
|---|---|
| Who **[round-3 MAJ-002]** | Look up the **server-authored provenance on the persisted user entry** by its server-generated message ID and session ID. Its authenticated principal must equal the target session's non-empty `Owner`; that metadata alone is **not** proof of authorship. Agent text, a client-chosen ID, a bot/integration/channel message with no gateway principal, and unproven historical entries fail closed |
| When | The candidate entry's **durable append ordinal in that session** is strictly greater than the runtime-authored shown-question entry's ordinal in that **same** session; a timestamp or inbox arrival is not sufficient |
| Which | The persisted exact text names the question code, **or**, when exactly one owner-only question is open at that root, it is the only eligible owner entry after the shown anchor; a competing candidate is ambiguous and refused visibly |
| Once | Atomically reserve the server-generated message ID for this question in the relay/question ledger before dispatch; a second use or concurrent direct/relay answer is refused, and a dispatch failure retains a visible retryable reserved-answer intent (D1.5) |

**[2026-09-30; round-3 MAJ-002] Server-written answer provenance.** On the authenticated web-gateway intake (`pkg/gateway/websocket_chat.go::wsHandlerHandleChatMessage.persistUserMessage`), persist the **server-generated entry ID**, session ID, exact accepted text, authenticated connection principal (`wc.userID`, not the client-supplied sender/ID), and **monotonic per-session append ordinal** together on the accepted user transcript entry. The runtime-authored shown-question entry also receives that session's append ordinal. Introduce a restricted server-side authenticated-user-append path: only authenticated gateway intake supplies this principal from its connection; generic agent/tool transcript writers cannot mint or set trusted provenance, and an attempt to provide it outside this path fails visibly. Serialize the provenance, message and ordinal under the same session write lock so none can exist without the others; look up the stored entry and its trusted provenance on every direct or relayed answer, including after restart. `pkg/session/daypartition.go::TranscriptEntry` currently has only `ID`, `Role`, `Content`, `Timestamp`, `ClientMessageID` for this path; transient `bus.InboundMessage.GatewayUserID` is not durable. A candidate answer whose provenance/transcript append fails must receive a visible refusal **before** agent dispatch or question consumption, never today's logged-only continuation. Keep trusted provenance and append ordinal server-internal, not in SPA/gateway frames; any future exposure is contract-first (Hard Constraint #8). The answer delivered downward is **that stored message's exact text, copied by the runtime** (`answer_source: owner`, `owner_message_id` = trusted server ID); the root agent's `respond` names that ID and question code, never supplies answer text. The agent's optional `note` travels labelled.

**Two answer paths, both strict.** (a) In the root conversation, as above. (b) **Directly in the child with an open question** (MAJ-001/006 — defined here, it did not exist): a **server-persisted, gateway-authenticated** owner entry (same trusted-provenance lookup and `Who` check against the child's own `Owner`) typed into a `needs_input` **or stopped-with-pending-question** session answers that session's one open question — the ordinary inbound path (`pkg/agent/revive_inbound.go::runInboundTurnWithRevival`) gains this branch: reserve the trusted source/answer/delivery intent, then explicitly resume the child; close question/relay `applied` only after delivery. `When` compares that child's stored shown-entry ordinal to the candidate's ordinal in the same transcript; `Which` is implicit only with exactly one pending question in that session; `Once` shares the root relay's reservation rule. An agent-created user-looking transcript entry is never an owner answer. For a stopped child this new owner message is an explicit post-boot action, not replay. This path is built through the ordinary inbound path, **not** through `WithDelegatePrincipal`.

**5. Down in one traversal.** The runtime follows `relay_of` from the root to `origin` and resumes the asker with the owner's text through the same native / external split `executeRespond` uses today: `pkg/tools/delegate_park.go::resumeNative` for a native child, `::dispatchThirdParty` for an external command-line child (MIN-005). Intermediate parents run **no** turn for the answer; each gets a non-waking info entry. Each relay record closes `applied`. The `respond` relay branch validates against the relay record (open, not superseded, chain intact), **not** against the target's `needs_input` state (MAJ-002: the relaying parent is never parked). **[2026-09-30; round-3 MAJ-002]** The server resolves the stored source **before** reserving it. The reservation of `(server_message_id, question_id)`, the question's chosen-answer identity, and a durable downward-delivery intent commit together under the question/relay writer; competing direct and relayed answers race on that same question identity, first committed reservation wins. Relay closure and child dispatch follow that durable intent idempotently. If a crash or error splits reservation, relay closure, or dispatch, retain `answer_pending_delivery`, report the incomplete step visibly and reconcile its intent at recovery without permitting another question/message use or falsely marking a relay `applied`; a **pre-crash** accepted answer waits for a fresh explicit post-boot RESUME before dispatch (D8.5), while a newly submitted post-boot owner answer itself qualifies as the new action (D1.7). Finish `applied` only after the asker has received the answer. An expired/withdrawn question cannot be reserved; previously reserved delivery is recoverable without inventing a fresh owner answer.

**6. Worked example (three levels).**

```
Owner (signed in) ─ root chat R
                     └─ A (team lead)
                          └─ B (worker)
1. B asks owner_required Q (corr b1) and parks            B: needs_input
2. B → A inbox: question Q (b1); A wakes
3. A: escalate(B, b1) → runtime mints a1, relay record A:{a1 → (B,b1)}
      R inbox: question Q, relay_of=(B,b1), origin=(B,b1), corr a1
4. runtime shows Q in R as "Q-3F2A"; R's agent explains it to the person
5. owner writes "Q-3F2A: yes, use the staging key" (message m7)
6. R agent: respond(A, a1, owner_message_id=m7)
7. runtime: Who/When/Which/Once pass → copy m7 → a1 applied → b1 applied
      → resume B with m7's text; A gets an info entry; m7 consumed
```

**[2026-09-30; MAJ-005/006] 7. Question state across a stop or an explicit withdrawal.** Stopping a waiting child (single Stop or Stop all) moves it to `stopped` but preserves the **open question, original `TTLDeadline`, shown-entry session ID and append ordinal, and relay chain** in a durable pending-question record separate from `NeedsInput` (which `pkg/session/lifecycle.go::persistLocked` clears outside `needs_input`). The root display marks it *open on a stopped helper*, not withdrawn. A valid signed-in owner answer later follows the same Who/When/Which/Once checks and resumes **that helper** explicitly even if its parent is still stopped; the parent's upward messages wait until that parent resumes. A self-ok answer takes the existing authorized `respond` path. The answer consumes exactly one question and closes each relay `applied`. Expiry still runs while stopped (D1.8). A direct parent's `redirect` **or RESUME** of a `waiting for answer` child **or a stopped child with that question still open** instead closes the pending question and relays `superseded` with reason `parent_redirect`/`parent_resume`, visibly marks the root entry withdrawn, records a `pkg/audit` entry for an `owner_required` withdrawal, and starts the child with a runtime-authored fact: "Question <code> was withdrawn without an answer from the owner; this is a parent instruction, not a verified owner answer." The parent instruction itself is not filtered; a parent may still claim approval in it. **Accepted risk, F0929-R2-Q1=C:** in the supported single-user instance the owner ultimately controls the parent agent, but the child may act on an untrue parent claim. Do not silently treat such a claim as an owner-signed answer. If an answer arrives after withdrawal or after expiry, refuse it as stale, report the reason, and do not consume the owner's message.

**[2026-09-30; MIN-005] 8. The 24-hour question-park limit.** A boot and periodic expiry check uses the original `TTLDeadline` even if the helper was later stopped. Expiry fails the asker visibly (`failed(owner_unreachable)` for `owner_required`, text "owner could not be reached"; `failed(answer_timeout)` otherwise), sends a fatal error upward (D5), and closes open relays `superseded`. This expiry is **not** Q19's session lifetime timeout: Q19 gives a timed-out **working** turn `stopped` and a fresh budget on resume. Expiry does not clear the goal (F0929-6). A failed session can still be explicitly RESUMEd (new generation); escalation does not extend the question TTL.

**[2026-09-30] 9. Audit.** Every owner answer and every parent withdrawal of an `owner_required` question writes a `pkg/audit` entry with question id, relay chain, actor, source action, `owner_message_id` if answered, and outcome; withdrawal has no owner message id.

### D2 — `stop` and `redirect`: runtime-enforced, non-terminal, no cascade

**Amended 2026-10-06 — founder decision:** Stop ends only this session's current turn; helpers keep working. All human/agent stop entries and Redirect's stop half use `AgentLoop.StopSession`: polite now, force at 3 s, detach 3 s after force, against the selected execution only. `cancel_grace` and the public `hard` option are removed. A tree-scope stop changes the scope, never the mechanism.

**[2026-09-30; F0929-2/F0929-4]** `stopped` replaces the old `paused`/`cancelled` states, but this is **not just a rename**: the old `Stop` marker becomes an in-flight fence, a separate `stop_note` preserves the landed reason, same-generation RESUME clears the fence and note atomically, and the tree-scope stop is non-terminal (D7). These changes amend the prior review's mechanism and race outcome.

**[2026-09-30; CRIT-001] Relation to the existing Stop marker.** `LifecycleRecord.Stop` (`json:"stop"`, `pkg/session/lifecycle.go::LifecycleRecord`) and `pkg/session/lifecycle_edge.go::Stop` are **only the current-generation dispatch fence**, `{at, generation, by}`. They are not the lasting cause note. Add a *separate* persisted `stop_note` field `{at, by, seq, cause, boot_seq?, last_activity_at?}`; no second object uses the JSON key `stop`. The `stop` action writes its ledger intent and, in one `LifecycleStore.Mutate`, the current-generation Stop marker **and** `stop_note` before releasing the lock; then it interrupts only this turn (`pkg/agent/steering.go::Interrupt`, hard escalation after the existing grace). `completionDisposition` reads the fence/note rather than inferring a stop from `context.Canceled`. Landing `LifecycleStopped` clears the Stop marker and retains `stop_note` **in the same mutation**. `LifecycleRecord.Stopped()` is redefined as `State == LifecycleStopped || (Stop != nil && Stop.Generation == Generation)`; `persistLocked` accepts a note on `LifecycleStopped`, rejects a terminal state with a current fence as today, and rejects a stopped record lacking a note or still carrying a current fence. Raw current-marker readers, including both boot sweeps and dispatch/delivery guards, must distinguish in-flight stopping from landed stopped state. A legal `done`/`failed` terminal write that **commits before** a Stop fence is accepted leaves no active fence or note; once a current-generation Stop fence commits first, the stop-completion path lands `stopped` instead. Neither path implicitly ends a goal (D6/D7). No lock is held over interrupt or a model call.

**[2026-09-30; round-3 CRIT-001] One outcome/publication commit boundary.** A model-produced final answer is *not* a completed turn, a parent notification, or permission to use `<child>:<generation>:final` until a single `LifecycleStore.Mutate` commits **both** `done`/`failed` and a durable, unpublished final-delivery outbox entry containing the outcome, exact upward message payload and deterministic final id. This lifecycle mutation is the linearization point: it checks the producing **execution identity** (including `run_id`), current generation, terminal state and current-generation Stop fence **under the same lock**. A late completion from a replaced execution cannot commit against the resumed run, even at the same generation (round-4 R4-MAJ-001). If Stop's fence commits first, this mutation refuses the final, writes **no** final outbox entry, appends **no** parent inbox message/frame, and the stop path lands `stopped`. RESUME on that stopped session keeps the generation, so its *later* committed result is the first legitimate user of that generation's final id. If completion/outbox commits first, Stop observes `done`/`failed`, is superseded, and cannot create a stop note. Keep the unpublished payload durably until delivery succeeds; a process crash before the atomic commit has no published final and the ordinary boot stop applies. A producer must not call the upward deliverer before this commit (`pkg/agent/steer_completion.go::AgentLoop.deliverSteeredCompletion`; `pkg/agent/steer_audience.go::SteerUpwardDeliverer.Deliver`).

**Publish only a committed outbox.** After the winning mutation, append the exact committed message to the direct parent's inbox with that id; then retry idempotent frames/wake and record delivery progress. An existing id with the same committed payload/identity means retry downstream effects if unacknowledged; a same-id/different-payload collision is a visible consistency error, **never** an acknowledgment or silent suppression. A genuinely acknowledged matching id means this committed result was already consumed; do not send a second final. Keep the committed payload until parent inbox delivery is durable, and retain the final id/commit identity as replay prevention after payload retirement. If append, frame, wake, or progress persistence fails, retain a retryable outbox and surface the failure rather than claim delivery. Reconcile it before any boot stop/notice decisions for that record: a committed terminal/outbox is published/retried, an uncommitted `queued`/`running` record is stopped, and a Stop-fenced record finishes stopping without publishing. `pkg/agent/boot_sweep.go::SteerBootRecovery.finishFromFinal` must **not** turn a non-terminal record into `done`/`failed` merely because an inbox final exists: require the matching lifecycle/outbox commit (otherwise report the inconsistent record visibly and do not consume the id). Parent consumption/ack never acts as the lifecycle winner. Crash cases and both winners are pinned in T11.

**Legal post-terminal delivery writes [2026-09-30; round-4 R4-MAJ-002 / CRIT-001].** The earlier outbox shape put mutable `delivery_progress` in a terminal lifecycle record without a legal writer. Correct it with **narrow delivery-metadata-only journal appends**, not unrestricted terminal mutations. The existing `LifecycleStore.Mutate` remains the **one outcome/outbox commit**; ordinary `Persist`/`Mutate` still reject a same-generation terminal lifecycle append through `persistLocked`/`ErrLifecycleTerminalImmutable`. Add the proposed store operation **`LifecycleStore.UpdateFinalDelivery(session_id, generation, commit_id, expected_delivery_revision, command)`**, owned by the same concrete lifecycle store and its per-session lock. Its command is only `advance_progress` or `retire_payload`; it accepts no lifecycle record or replacement outcome/payload. It appends a typed `final_delivery_update` envelope to that session's lifecycle journal, **not a `LifecycleRecord` and not through `persistLocked`**. Lifecycle tail/list readers must distinguish these envelopes from lifecycle records, so delivery progress cannot become a session state or reset a newer generation. This is a bounded clarification of the terminal-generation invariant in [An open conversation must keep the ability to delegate](ADR-093-open-conversation-must-keep-delegation.md)::“Invariants this ADR will not break”: terminal **outcome records** remain immutable; only their delivery metadata and replay-safe payload retirement have this separate legal path.

**Protected commit and allowed metadata.** The terminal mutation commits `{session_id, generation, commit_id: producing run_id, execution_id, message_id, outcome, parent_session_id, payload_hash, exact_upward_message}`. `payload_hash` identifies the exact stored upward envelope, including sender, destination and content. Outcome, failed reason and all lifecycle fields outside the explicitly retired outbox payload bytes, generation, producing execution/commit id, final message id, destination and payload identity are immutable. The update operation reads that **historical committed generation**, verifies its exact identity under the same owning lock, and appends only `{kind: final_delivery_update, generation, commit_id, delivery_revision, delivery_progress, payload_retired}`. Missing progress means revision 0/all pending; no post-commit initialization write is needed for recovery. `delivery_progress` contains monotonic durable facts `inbox_appended`, `frames_persisted`, `wake_recorded`, `ack_observed`; facts refer to this exact committed message. A publisher records successful normal inbox/frame/wake/ack receipts, not merely attempted calls or a caller's unverified boolean. Store validation rejects unknown/noncommitted identities, mismatching commit/payload/destination, changed outcome/final identity, regressing progress and a stale expected revision; a concurrent publisher reloads and retries without losing progress. An identical already-recorded effect is idempotent. No lifecycle lock spans parent publication, wake or acknowledgment.

**Payload retirement is the second command, not a terminal mutation.** `retire_payload` is allowed only after the exact parent inbox append is durable **and** either its required frames/wake are durably recorded or the matching inbox id is durably acknowledged. Until then the committed exact payload remains recoverable. First append a durable retirement marker retaining the protected tuple, hash, delivery revision and replay-prevention identity; then atomically compact that journal, removing **only** this final's exact payload bytes and redundant delivery revisions. Every lifecycle outcome/field and committed identity remains unchanged; other generations, pending finals, stop notes, open questions and control ledgers are untouched. Compaction must retain an outcome/outbox descriptor and the complete delivery summary for every committed final. A crash before the marker keeps the payload; after the marker/before compaction leaves harmless retained bytes; after atomic replacement preserves the marker/identity and prevents republication. A failed progress append or compaction is visible and retryable, never an implicit acknowledgment. This retirement concerns the internal outbox copy only, never deleting session or transcript history (F0929-1/D8.8).

**Discovery after a newer-generation RESUME.** Add the proposed `LifecycleStore.ListPendingFinalDeliveries` read alongside the update operation: scan committed outcome/outbox descriptors and delivery envelopes for **all generations**, not just `Load`'s current tail. Delivery envelopes are joined only to their matching protected commit; an orphan, corrupt or mismatching envelope is a visible consistency error and cannot authorize publication or retirement. Explicit RESUME of a committed done/failed G may create G+1 immediately while G's result is still pending; it neither copies G's outbox into G+1 nor hides, supersedes, acknowledges or retires it. `UpdateFinalDelivery` may advance/retire G after that resume without writing an old `LifecycleRecord` behind G+1 or changing G+1's queue/run. Publisher retry and boot discovery include every such pending committed final independently of the current execution, and retain each `<child>:<generation>:final` replay identity after retirement. Committed-result retry is delivery only, not permission to run the child. D8 and T11 require this all-generation recovery path.

**Negative controls (T11).** Exercise the actual terminal guard and proposed update/compaction operation on the same real store: a generic terminal `Mutate`/`Persist`, a replacement outcome/failed reason, final id, generation, producer/commit identity, destination or payload/hash, an update without a matching commit, a progress regression/stale revision, and premature payload retirement must be refused visibly, with the protected commit and current newer-generation tail unchanged. Neither a permissive terminal-mutation switch nor a fake progress store is a legal implementation.

**[2026-09-30; CRIT-001 / round-4 R4-MAJ-001] Same-generation resume and restart fence.** An explicit RESUME or redirect on a landed stopped session writes its ledger intent first, then atomically clears the current `stop_note`/any current marker and its stop-effect metadata, changes the **same-generation** state to `queued`, and installs a **new execution identity** with the intended control id and current boot epoch. Only an explicit request in the *current* boot can dispatch it. A crash between that mutation and dispatch leaves `queued` (never runnable at boot); boot recovery first converts every interrupted `queued`/`running` record back to `stopped` with a new `cause: restart` note, keeps the pending instruction in the ledger, and requires a **new explicit RESUME** to release it (D8). That fresh action creates a fresh execution identity; preserved instruction/control ids are not permission to reuse the pre-crash execution. If the final answer had landed first, its terminal write wins and no stop note survives (F0929-race). This couples clearing the old note to an auditable queued state, not to an unprotected runnable turn (`pkg/session/lifecycle.go::persistLocked`; `pkg/agent/boot_sweep.go::SteerBootRecovery.recoverSteered`). `stopped` gets its first production writer and replaces `LifecyclePaused`/`LifecycleCancelled`; a timeout stop uses the same mechanism (Q19).

**Execution identity and effect-boundary checks [2026-09-30; round-4 R4-MAJ-001].** The internal identity is `(session_id, generation, boot_seq, run_id)`, not generation/session alone. Persist it under the lifecycle lock **before admission**, and copy it unchanged into the admission entry and live execution handle. Initial admission and each later new-turn admission, including an ordinary working-session wake, get a fresh runtime-generated `run_id`; an explicit RESUME/redirect/authorized answer that dispatches a replacement uses that fresh action's accepted `control_id` as its `run_id`. Queue-to-active promotion and idempotent retries of that same admission keep the identity. A new admission never reuses a previous run's identity, turn-state/cancel handle or provider-cancel slot, even at the same generation and in the same boot. This adds no user-visible generation or control state (D4; F0929-5).

Every accepted Stop, the tree-scope stop, redirect-stop or timeout captures the selected execution identity and its own `control_id` in durable ledger intent and lifecycle-internal `stop_effect` metadata **with** the fence/note. Cascade callbacks carry each reached node's stamped pair, not a later session lookup. Every delayed control effect must carry and check that pair: graceful interrupt, hard-escalation timer, queue removal, never-ran stop finalization and live-turn stop/completion writes. Queue removal compares the full identity **under the queue lock** and removes only the matching admission; there is no preliminary session-wide removal. A live interrupt/escalation resolves and pins only the matching immutable execution handle under registry synchronization, then invokes that handle after releasing locks; it never resolves the session's replacement handle or its new provider-cancel function. Durable stop finalization and completion compare the execution identity **inside** their lifecycle mutation; stop finalization also requires the same still-current `stop_effect.control_id`. Checking before scheduling a callback is insufficient. A stale callback is a no-op on current state, queue and live work; an unfinished obsolete control gets an explicit `superseded` receipt, while an already-final receipt stays historical. A notice for an already-committed stop may still finish delivery under that old transition's dedup key, but cannot rewrite the new run's note/state or receipt (D4/D6).

No lifecycle, cascade or registry lock spans an interrupt, model call or wait for a turn to exit; retaining the two-pass traversal does not permit retaining a cascade lock across live effects. The execution-identity checks replace generation-only targeting in `SteerCanceller.cancelStamped`, `AgentLoop.SteerGenerationCancel`, `AgentLoop.requestCancelForGeneration` and `steerAdmission.removeQueuedSession`, including the second queue-removal path in `AgentLoop.cancelDelegatedSubtree`; they also cover the delayed `Interrupt`/`InterruptSessionHard` paths and `terminaliseNeverRanStop`. The existing generation-bumping source is not proof of safety for this new same-generation design. T27 forces the old-effect/new-RESUME interleaving through normal production dependencies.

**`redirect`** — `delegate(action="redirect", session_id, text)`, retained by the 2026-09-29 rulings (ruling 8: "Redirect (/stop-redirect) stays; Steer stays live-only"). Its sequence-fence mechanism now also uses D2's execution-identity checks: the stop half targets the selected old run and the resume half installs a fresh run identity (round-4 R4-MAJ-001). **Atomicity by sequence fence, not by a held lock (fixes CRIT-003):**

1. Under the child's record lock: assign `seq = R`, persist the ledger intent `redirect(R, text)` and, in the lifecycle mutation, both the current-generation **Stop fence** and separate `stop_note` (`cause: "redirect_pause"`); release the lock. A crash between intent and mutation leaves a pending intent for D4 boot reconciliation, never a runnable turn.
2. Interrupt the live turn exactly as `stop` (no lock held).
3. When the turn has ended (`stopped` by the note), the resume path starts the new turn with `text` as the newest instruction. At that moment every ledger control with `seq < R` still `queued` is marked `superseded`; controls with `seq > R` stay queued behind the instruction, in `seq` order.

Any steer that arrives while the redirect is in flight gets `seq > R` and is therefore delivered **after** the new instruction — never between the halves, and never lost. The turn-completion write takes the record lock on its own and never waits on the redirect (the deadlock the review found cannot arise). `redirect` on a stopped child skips step 2; on a waiting-for-answer child it closes the question `superseded` and resumes with `text`; on a done/failed child: "already finished — use RESUME".

**[2026-09-30; CRIT-001] Resuming a stopped child.** `redirect` (new instruction) or RESUME on **any non-working** session (F0929-5) resumes a stopped child on the **same generation** by the atomic note-clear/queued transition above; only `done`/`failed` mints a next generation. A signed-in owner's new message into its stopped session is also an explicit resume; no boot replay counts as one. Any ancestor may resume an owner-stopped child (F1011-Q6); the last `stop_note.by`/`cause` is copied to the receipt and the D2 resume instruction *before* the active note is cleared, so both the child and parent can see who stopped it. A waiting-for-answer session uses the D1.7 question rule instead of silently discarding its question (D2/D7).

**What a resumed turn runs (F1011-Q8, fixes MAJ-008).** The runtime **never** rebuilds the resumed turn from the last `user` transcript entry. It continues from the persisted conversation and appends one system note before the model call:

> You were stopped at <time> (cause: <stop|redirect|cascade|restart|timeout>). The last completed tool call was <name> at <time>, if known. Continue from here; do not repeat actions that already completed. <new instruction, if any>

If the stopped session had no turn in flight (waiting on descendants), resume flips it to `working` and wakes it only if stored upward messages are pending.

**Who may call them.** Delegate actions retain their ordinary ancestor authority and external-worker limits. Human `/stop` and `/stop-redirect` act on the **current chat, root or helper**, not on a helper selected by that chat (D9; **Amended 2026-10-06 (founder)**). External command-line children (`rec.Is3P`) retain the delegate action's named `not_steerable` guidance to the unchanged delegate actions `stop_all` / `resume`.

### D7b — Clear exactly one helper goal; tell that helper to decide about its own helpers **[2026-09-30; F0929-Q20/Q21]**

**Context.** `pkg/tools/delegate.go` has no child-goal action; `pkg/agent/goal_outcome.go::clearGoalByUser` operates on the caller's session only. Once Stop ceases to end goals (D6/D7), a parent needs an explicit way to clear a helper goal. The founder ruled that even a **working** helper's goal may be cleared, with notice to that helper, and no clear cascades (`coordination/PLAN-2026-09-28.md`, Q20/Q21).

**Decision.** `delegate(action="clear_goal", session_id)` requires an authorized ancestor and clears the named helper's **own active goal only**, exactly one session per call; it does not stop or restart its turn, withdraw a question, or clear any descendant goal. It has the same goal-ending semantics as the helper's own `/goal clear`. A working helper receives a runtime-authored prompt at its next safe turn boundary: its goal was cleared; decide whether to stop its own helpers or clear *their* goals. A stopped or waiting helper retains that distinct notification durably for its next explicit resume/answer; no notification wakes a stopped helper, no automatic recursive action occurs. Clearing a parent's own goal issues the same prompt to **that parent**. Every helper may separately decide about its own descendants, so a multi-level tree is handled recursively by agent decisions, never an automatic cascade. This goal-clear notification is **distinct** from D6's stopped-child notice: it fires on an explicit goal clear, not on a child stop, and the two can coexist without either acknowledging the other. A missing active goal returns a visible non-error "no active goal"; a successful receipt names the target session and cleared goal id. The `clear_goal` ledger entry becomes `applied` only after goal state and its own notice are durable. Backend-lead owns contract edits/regeneration (root `CLAUDE.md`, Hard Constraint #8).

**Consequence.** A working helper can continue its present turn without a goal; the parent must explicitly Stop it if that is also intended. The accepted distinction between the goal's lifecycle and the session's lifecycle prevents clearing one goal from silently cancelling a subtree (Q20/Q21, D6).

### D8 — Restart is just an automatic stop; the parent is told and decides (amends [A sub-agent is a session steered by another session](./ADR-091-steered-sessions-replace-subagents.md), §7; supersedes the draft's "interrupted" design)

**[2026-09-30, F0929-3]** Founder ruling, verbatim: "Restart of Omnipus = automatic stop of working sessions; parent told." The **architect's consequence**, not quoted founder text: withdraw the 2026-09-28 draft's separate terminal `failed(interrupted)` state, `restart_interrupt` note and special-case drop; use ordinary D2/D6 stopped-session machinery with `cause: "restart"`.

**1. Boot order [2026-09-30; OBS-001].** Keep `SteerBootRecovery.sessionIDs`'s existing stable enumeration; no edge-order rewrite is needed. Pass one persists the boot epoch, discovers **committed terminal/outbox outcomes and their delivery summaries across all generations** through D2's proposed `ListPendingFinalDeliveries`, then independently finishes in-flight stops/stops each current eligible `queued` or `running` steered record **without its own committed outcome** (no turn starts). A committed final for G does not exempt an uncommitted working G+1 from restart Stop. Pass two retries publication of **every pending committed final, even if its session's current tail is G+1**, creates each stopped child's **direct-parent** notice and reconciles control ledgers, then batches wakes for parents still working (D2/D6/D8.4). This order prevents a parent wake from observing a half-recovered subtree without imposing a new graph traversal or claiming a parent was resumed automatically. A stop-note/notice pair is recoverably retried if a crash separates the passes.

**2. Which sessions are stopped by a restart — same test as the draft's "interrupted", renamed.** A native steered session whose state is `working` (`queued` or `running`) **without an in-flight Stop fence**. A record with that fence first finishes its already-accepted stop and retains its original cause; do not overwrite it with `restart`. **Not** affected: an already-`stopped` record (note unchanged), a reconstructable `waiting for answer` (question preserved), or a standing root ([An open conversation must keep the ability to delegate](./ADR-093-open-conversation-must-keep-delegation.md), D3). External command-line children keep today's handling (their process is gone; RESUME runs a corrective successor, ADR-091 D5).

**3. What an affected session becomes.** `stopped`, with a stop note `{at, by: "restart", seq, cause: "restart", boot_seq}` — an ordinary stop, not a distinct terminal state; no more `failed(interrupted)` record and no more separate `restart_interrupt` note (D4). **Its goal is untouched** — not because a goal-ending step was specially skipped (the draft's "`EndSessionGoal` skipped in `failInterrupted`" framing), but because **no stop of any kind ends a goal** (F0929-6): there is no goal-ending step in the restart-stop path to skip in the first place. `boot_seq` is still a monotonic boot counter persisted in the data dir, now carried on the ordinary stop note. `PlanEngine.bootSweep` still leaves steered records to `SteerBootRecovery` (avoids a second writer racing the same record).

**4. Direct-parent notices at boot [2026-09-30; MAJ-009].** The D6 notice is persisted **eagerly for each child actually stopped** at restart, to its direct parent's inbox before any wake or control receipt says `applied`. This is not one aggregate root message: in root → C → D, the root receives C's stop; C receives D's stop even when C itself is stopped. A working parent receives one coalesced wake for the batch of distinct notices after the stop sweep; a stopped or waiting-for-answer parent retains its notices without a wake, reading them when explicitly resumed/answered. The root does not act in C's place on D. Deduplicate each transition with D6's `(parent_id, child_id, child_generation, stop_seq)` key, and the parent wake with `(parent_id, boot_seq)` for this boot; repeated sweeps neither create new transitions for an already-stopped child nor replay wakes after a consumed inbox id. If storing a notice fails, keep a durable retry item and report the failure: do not silently claim delivery. F0929-3/F0929-7 are satisfied at every directly affected level without automatically starting any stopped parent.

**5. Boot never starts a turn; waiting-message reconstruction is deferred to #1198 (founder 2026-10-06).** Boot order is: persist a monotonic boot epoch; read each **atomic lifecycle/outbox commit** (D2), finish an in-flight stop and stop each interrupted `queued`/`running` steered session that has no committed final; persist its direct-parent notice; then reconcile ledgers and retry committed final publication/receipts **without dispatch**. **[Round-4 R4-MAJ-002]** Retry scans all committed generations rather than only the current tail; delivery progress and retirement use D2's legal `UpdateFinalDelivery` path. An old G final remains pending/retryable when explicit RESUME has created G+1, and updating G's delivery metadata never changes G+1's state or identity. An inbox final without a matching committed outcome cannot repair a stopped or working lifecycle record (`finishFromFinal` is replaced by commit-based reconciliation, not an inbox-first promotion). A `redirect`/RESUME accepted before the crash remains `queued` with the original instruction, identity and sequence (`restart_pending`), visible via `status`/`peek` and the parent's notice. The first **new explicit RESUME in this boot** releases valid pending controls in order (D4); a second restart requires a second new RESUME. Thus neither recovery nor an old accepted control restarts a turn. An explicit owner answer to a retained open question is also a **new** post-boot action, not replay (D1.7). A stopped child's explicit RESUME or redirect continues the same generation (D2), with a note naming the restart; there is **no Q2=B held-claim phase to reconstruct**. The next `met` claim is checked afresh against direct working/waiting children (D6), independently of criteria-free quiet-subtree completion (D6b). No prior control is silently marked `applied` or lost.

**6. Unfinished until decided — corrected to F0929-7, not the draft's rule.** The draft: "an interrupted descendant with a kept goal counts as unfinished until it is resumed and finishes, or is dropped with `cancel`." **This is now wrong**, for the same reason as D6's Q2=B correction: a restart-stopped descendant does **not** block a claim by itself (`hasRunningOrQueuedDescendant` must return false for it, D6). What survives: the parent must still be **told** and must still **decide** — deciding is not automatic, but not-blocking and not-deciding are different things. The D6 stopped-child notice (not a claim-specific trigger) is what covers this case now, not a claim-blocked notice specific to interrupted descendants.

**7. Deadline without downtime (MIN-009) — unchanged.** Time between `last_activity_at` (the record's last persisted update before the crash) and the resume is added to the stop-time credit (renamed from `paused_for` — D6); downtime never consumes a session's lifetime budget.

**8. Housekeeping — F0929-1.** No automatic deletion is introduced; "housekeeping" in the draft referred to nothing that exists and stays withdrawn. A never-resumed stopped session and its transcript remain addressable even after its goal is explicitly cleared (`clear_goal`, D7b, or its own `/goal clear`); hiding a helper from the UI is separate #1083 work, not session deletion. This ADR does not build any chat deletion path or new retention rule.

**9. The race rule, restated for restart specifically (F0929-race; design, not a verified new test outcome).** A restart's stop reaches a session either before or after its final **lifecycle/outbox commit** (D2): before → `stopped`, with no final id published; after → the committed generation's `done`/`failed` and outbox descriptor survive, and boot retries publication through D2's delivery-only operation without changing that generation's outcome. If a later explicit RESUME already created working G+1, boot still stops that uncommitted current run while retrying G's result; neither G+1 nor payload retirement hides G's commit. A merely generated but uncommitted answer does not win; parent acknowledgment alone cannot repair a missing commit. **Either way the session must never be `working` by itself after the reboot.** Historical `e4d9a126c` and inspected release `e12924a46c` `tests/adr091/steered_sessions_test.go::assertStopLandedOn` already accept `LifecycleCompleted` through `legalTerminal`; the assigned ADR worktree at `f59369ac3` rejects it. The implementation must reconcile the test with both new outcomes, `LifecycleStopped` (non-terminal) and committed `done`/`failed` (terminal), and add T11's explicit race/order, outbox, and restart assertions; merely changing the helper's accepted terminal enum is insufficient. T4/T6 require new state names at build time.

**10. When that step is readmitted, RESUME its **same stopped member session** and history (D2 note), not a newly created step session and not an old instruction replay; only a step that never had a session may create one. An already-working step is not dispatched a second time. ### D9 — Chat Stop, second Stop / Esc or `/cancel`, and redirect

**Amended 2026-10-06 (founder):** the controls below are the same on **web, CLI and channels**, in **root and helper chats**. This replaces the extra control and helper-only redirect design. Authority: founder decision, 2026-10-06.

| Input | Effect in this chat |
|---|---|
| Stop click 1 / Esc 1 / `/stop` | Stop **this chat's current turn only** (`scope: session`); helpers keep working. Open a **3 s window**. |
| A second Stop / Esc / `/stop` within that window | Stop this chat plus its whole helper tree, including queued helpers (`scope: tree`); never ancestors or siblings. **The second press is the confirmation.** |
| `/cancel` | Stop this chat and its helper tree immediately, without a first press or confirmation window. |
| `/stop-redirect <instruction>` | Stop **this chat's current turn**, then continue **this chat** with the instruction. Works in **any chat, root or helper**; its helpers keep working. |

**No separate button, menu control or armed offer.** The window belongs to the same chat and expires after 3 s or on focus/chat change; the next press then counts as a first press. Esc consumed by a dialog, editor or menu dismisses that surface only and does not count as a Stop press. The existing Stop remains usable for the second press even if its first press has already ended the turn.

Plain Stop leaves background shells running; a second Stop / Esc within 3 s, or `/cancel`, kills them. Agent delegate `stop` / `stop_all` is unchanged: one helper's current turn / that helper's tree. The 3 s interaction window selects scope; it is not an immediate-force control and does not change D2's stop stages. Replies name the requested scope and distinguish accepted/pending from landed stopped or failed; plain Stop never claims helpers were stopped.

`/stop`, `/stop-redirect` and `/cancel` are distinct, conversation-scoped commands, not aliases. `/stop-redirect` never selects a helper on behalf of the current chat and never refuses merely because the current chat is a root. No `/steer` alias is added; `/goal stop` remains a goal-clear alias, not a session Stop.

### D10 — Rollback is out of scope

Undo/rewind will not be built (#1011 F4). Resumability covers "continue from here"; irreversible actions are gated **before** the action (the Ask policy, root `CLAUDE.md` Hard Constraint #6), never rewound. D2's resume note is the only related safeguard.

### Historical consequences (2026-09-30; superseded where they conflict)

**[2026-09-30]** These are the consequences of the current decision; older incompatible choices live only in the superseded appendix.

### Positive

- The owner-only round trip works at any depth, and the owner answer is bound to **who** (signed-in owner), **when** (after it was shown), **which** (question code or the only open one) and **once** (consumed) — the four gaps the review found in the draft are closed.
- Enforced `stop` / `redirect` with receipts; `steer` cannot start work by accident.
- Pending controls survive a restart **without running**: a fresh explicit RESUME releases them (D4/D8); stopped children keep their goals and original conversations, and restarted plans reuse the same step sessions (D8.10).
- **[corrected]** One vocabulary (working / waiting for answer / stopped / done / failed) across tools, status, UI and completion — now genuinely one, since `stopped` folds what were three separate ideas (`paused`, the terminal side of `cancel`, `interrupted`) into a single alive, resumable state (Vocabulary).
- **[2026-09-30]** No session outcome (Stop, timeout, done, failed or restart) **implicitly** ends its own goal; independent natural `met`/exhaustion adjudication still ends goals, and deliberate `/goal clear`/authorized `clear_goal` remains explicit (D6/D7b).

### Negative

- **[2026-09-30; F0929-R2-Q1=C] Accepted owner-question bypass risk, single-user posture.** A parent may RESUME or redirect a helper waiting for an `owner_required` answer without obtaining that answer; this withdraws the question with an audit entry and injects a factual "unanswered" notice (D1.7), **but does not verify or block the parent's new instruction**. A parent can falsely claim approval, and the child may act on it. The earlier assurance that an agent can never bypass the owner-only question is therefore narrowed: only the **owner-answer path** enforces Who/When/Which/Once; owner-only question withdrawal is permitted by the founder. In a supported single-user instance Who normally identifies the one owner; When/Which/Once still prevent wrong-message attribution for actual answers. The root agent also chooses which owner message to cite when the owner wrote a code; only the owner's words are copied, not the agent's note.
- **Owner answers need a gateway identity:** a channel conversation (Telegram, Discord, …) has no `GatewayUserID`, so an owner-only question from a channel-rooted tree can only be answered by the owner in the web app (in the child's session) or it expires at 24 h. A dev install running without authentication has an empty owner identity and **cannot** answer owner-only questions (fail-closed). Both accepted by the founder (2026-09-28): see [Founder answers to the open items](#founder-answers-to-the-open-items).
- A new durable artefact (the ledger) with its own crash rules and compaction.
- **[2026-09-30; round-4 R4-MAJ-002]** Delivery-only lifecycle journal envelopes add typed readers, historical-generation discovery and bounded atomic compaction. Pending payloads remain on disk until durable delivery/retirement proof; replay identity summaries remain afterward. Stream discovery rather than accumulating full payloads in memory; footprint and supported-platform durability remain unmeasured implementation gates (D2/D4/T11).
- `stopped` gets its first writer (**corrected**, was `paused`); readers must check the stop note.
- A stopped child's background shells keep running.
- `wait=false` questions and blockers are exempt from every upward cap and could be used to flood a parent's inbox.
- A child waiting for an answer can now hold back a whole tree's "done" for up to 24 hours (D6b) — **unchanged by 2026-09-29**, still true.
- **[new]** A stopped child no longer blocks its parent's completion by itself (F0929-7) — a parent that never checks its inbox for the stopped-child notice could, in principle, claim `met` while a helper it should have looked at sits stopped indefinitely; this trades a hang (the old failure mode) for a possible silent-to-the-user-but-not-silent-to-the-agent oversight (the notice fires; whether the agent acts on it is the agent's judgment, same as any other inbox message).
- **[2026-09-30]** A parent may bypass a pending owner-only question by explicitly withdrawing it via RESUME/redirect; audit and a fixed "unanswered" note make the risk visible but cannot verify the parent's new instruction (D1.7). Multi-level stopped-child notices and session/plan mirrors add durable state and delivery/retry work (D4/D6/D8).
- Wire changes in seven-plus schemas (the `stop`/`pause` rename adds field renames on top of the draft's count) plus at least four new action schemas (`stop`, `redirect`, `escalate`, `clear_goal`); new SPA work to render receipts, question codes, and the stopped/decide notice.

### Neutral

- The existing cascade traversal remains the downward primitive ([A sub-agent is a session steered by another session](./ADR-091-steered-sessions-replace-subagents.md), D8), but its outcome is now resumable `stopped`; the current-generation `Stop` marker is an in-flight fence distinct from a landed `stop_note` (D2/D7).
- FR-135's opt-in shortcut stays unbuilt.
- #1000's 200-item steering cap and wake bypass are baseline, not changed.
