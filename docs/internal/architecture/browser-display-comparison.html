How the live browser panel should reach your screen

Three ways to show the agent's browser session to a human: stream its pixels, mirror its DOM, or render a rewritten copy in your own browser. This compares them on fidelity, responsiveness, auth, security, and — decisively — whether each can carry the agents' own browsing, not just the human view.

Start here

One fact settles the shape of the decision

The agent must browse autonomously — scheduled runs, no human watching. So a real browser has to exist and execute JavaScript server-side no matter what. Client-side rendering (mirroring, proxy) runs the page in a human's browser; with no human attached, nothing executes.

CONSEQUENCE

Client-side rendering can never be the agents' browser — only an alternative view of it

The server-side Chrome isn't shipped for the viewer; it's the agent's tool, and it stays. Every option below is a way to observe and drive that one server browser. None removes it. This is why every agent-platform vendor surveyed (OpenAI, Anthropic, Browserbase, Steel, AWS, Hyperbeam) keeps the authoritative browser server-side and treats the human display as a detachable window.

SO THE REAL CHOICE IS

Which display layer sits in front of the server browser

Not "ship a browser vs. don't." The only thing any option changes about what we ship is the managed Chrome build (headless-shell → full) and how its frames reach the panel. Judge the three on display quality, drive-ability, and cost — not on whether they save us the browser. They don't.

The field

Three families, honestly framed

Each does something the others can't. The gold one is what we run today plus its planned upgrade; the other two are the "render it in the browser we're already in" ideas, in their two real forms.

Option A · today + upgrade

Pixel & video streaming

The server browser's viewport is encoded to images (today: CDP JPEG screencast) or to real video (ADR-044: WebCodecs H.264/VP8 encoded by Chrome, relayed as binary over the existing WebSocket) and painted into the panel.

  • Pixel-perfect on every page — canvas, WebGL, video, PDFs, cross-origin frames all just work
  • Shows the agent's actual session; take-the-wheel is native (CDP input)
  • It is already the agent runtime — zero new execution model
  • Bandwidth-heavy; today's JPEG path lags 100–500 ms/frame
  • Audio needs the WebCodecs work; no native scrollbar feel
market standard the path with shipping evidence behind it
Option B · the viable client-side one

DOM mirroring

A tiny recorder (rrweb, MIT) is injected into the agent's page via CDP; it streams DOM mutations as JSON over the relay; the SPA rebuilds the live DOM in your browser — native scroll, crisp text, real fonts, near-zero bandwidth.

  • Native scroll & selectable text; tiny payloads; MIT-licensed
  • Sub-second–2 s latency; input maps back via CDP trusted events
  • Still needs the server browser (injection target) — an add-on, not a replacement
  • Goes blank/wrong on canvas, WebGL, DRM video, closed shadow DOM, deep iframes
  • Fragile on hostile/CSP pages; re-validate every version bump
promising add-on great view — until the page fights it
Option C · proxy / rewriting

Client-side proxy render

A rewriting proxy (Surfly-style; open-source Ultraviolet / Scramjet) intercepts traffic, rewrites HTML/CSS/JS, and the rewritten page runs in your browser. Full native rendering with audio, no streaming at all.

  • Full native fidelity with audio, rendered in the user's own engine
  • Every mature engine is AGPL or unlicensed — incompatible with MIT Omnipus
  • Single-origin collapse; security vendors fingerprint it as phishing tooling
  • Perpetual compat treadmill — Google login, CAPTCHAs, banking break
  • Cookie jar lives client-side → can't share the agent's session
wrong tool here built for co-browsing, not autonomous agents

What the market did

Two data points worth more than opinion

Browserbase tried DOM mirroring — and quit it

Browserbase recorded its cloud agent browsers with rrweb, then publicly moved off it to CDP pixel capture. Their post-mortem is almost exactly Option B's risk list:

"Nested iframes break this model almost immediately… Canvas, WebGL, video elements, shadow DOM — anything that isn't normal HTML becomes either flaky or invisible," and replays could silently show current rather than historical data.

browserbase.com/blog/session-recordings

Every agent platform streams pixels; the exceptions prove the rule

OpenAI Operator, Anthropic (VNC), Steel (CDP JPEG over WS — same as us), Hyperbeam & neko (WebRTC), AWS AgentCore (DCV video): all stream a server browser. The one client-side-render product — Surfly — is co-browsing, where a human browser is guaranteed present and it funds a permanent rewriting proxy plus reverse-proxy cookie plumbing for logins.

Convergence holds wherever the agent must act with no human attached.

Reading of the evidence

Where this points — your call

The research doesn't crown a single winner; it separates a base layer that must exist from an optional enhancement that's genuinely attractive for the human view. These are not mutually exclusive.

base Pixel/video stream stays the substrate

It's the only option that is simultaneously the agent runtime, universally faithful, drive-able, MIT-clean, and low-maintenance. ADR-044's WebCodecs relay fixes the two things people actually feel — scroll/video smoothness and (phase 2) audio — while keeping the Go binary a pure byte relay and the JPEG path as an automatic fallback.

This is the recommended target, and it's independent of what we decide about B.

option DOM mirroring as a "reading mode"

rrweb-live is MIT, tiny-bandwidth, sub-2-second, and gives native scroll and crisp text — a genuinely nicer watch for text-heavy pages, and a strong fit for low-bandwidth/mobile viewing. It rides the same relay and panel API.

The honest condition: it must fall back to pixels the moment the page uses canvas/WebGL/video/closed-shadow-DOM — which is common on the sites agents visit. Worth a spike; not worth betting the only display path on.

Not a decision yet. ADR-044 stays in draft with its §6 recommendation suspended pending your read of this. Natural next steps: (1) keep ADR-044's WebCodecs spikes; (2) add one rrweb-live spike behind the same panel API to measure real fidelity fallback rate on agent-typical pages; then (3) /grill-spec the ADR. The proxy family (Option C) is documented as rejected on licensing + autonomy, so it won't resurface unanswered.
