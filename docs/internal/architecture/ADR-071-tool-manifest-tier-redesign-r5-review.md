# Adversarial review — ADR-071 "Tool manifest tier redesign", revision 5 (r5)

- **Reviewed document:** `docs/internal/architecture/ADR-071-tool-manifest-tier-redesign.md`, revision 5 (2026-08-27), 2902 lines.
- **Reviewer stance:** fifth adversarial pass. r1–r4 have already forced four revisions and closed a long list of real defects (TTL/`IsCore` gate, the 89-name arithmetic, the `switch_agent` frame-emission regression, the migration-ordering hazard, and — new in r5 itself — the unfiltered `ToolSearch` match list). This review does **not** re-derive that ground. Every finding below was checked to make sure it is not already resolved, superseded, or explicitly deferred somewhere in r5's text, and every code-fact claim was independently re-verified against source at the current checkout (not merely re-read from the ADR's own citations).
- **Input classification:** `structured-spec` mode. The document has numbered decisions (D1–D5), a "Still open" numbered list, and four full traceability tables (§13–§16), but not `plan-spec`'s FR-xxx/SC-xxx/BDD apparatus.
- **Evidence level:** every code claim below was read directly from `pkg/tools/tools_tool.go`, `pkg/tools/search_tool.go`, `pkg/tools/base.go`, `pkg/sysagent/tools/category.go`, `pkg/agent/loop.go`, `pkg/config/config.go`, and `pkg/config/defaults.go` at the working tree's current state (branch `release/v0.1.1`).

## Executive summary

r5's own §3.2.2 fix and its accompanying claims check out — the `matches`-built-before-`canLoad` defect is real in the current source, and the specified fix is sound. This review found **no factual errors** in r5's code citations. What it found instead are six new gaps in the *mechanism r5 itself just designed*: a hardcoded scan cap that silently disagrees with an operator-configurable setting, a "coverage tripwire" regex that would not have caught 5 of the 13 names in its own seed set, an ambiguous write condition in the no-follow-up counter that can make the counter under-report indefinitely, a missing test for the new scan-cap boundary, no anti-gate-shopping protocol on the one-off manual D5 measurement, and an unlabelled/non-retained metrics design that weakens the "falsifiable revisit trigger" the ADR spends the most words defending. None of these six is a data-loss or privilege-escalation risk — `canLoad` still gates every actual capability grant, as r5 correctly argues — but four of the six directly undermine specific, hard-won correctness properties this revision claims to have established (the drift test's completeness, the counter's falsifiability, the gate's status as "a measurement, not a judgment call"). One further item is a structural observation: by r5 the D2/D3 supporting machinery has grown to roughly 15 new named concepts for what began as a manifest-visibility change, and the ADR's own text half-acknowledges this (OBS-201) without acting on it.

**Verdict: REVISE.** No CRITICAL findings. 5 MAJOR findings, 2 MINOR, 1 OBSERVATION.

## Findings table

| ID | Severity | Lens | Section | Description | Recommended fix |
|---|---|---|---|---|---|
| MAJ-301 | MAJOR | Inconsistency / Incompleteness | §3.2.2 step 2 (`searchCanLoadScanCap`) | `searchCanLoadScanCap = 50` is proposed as a hardcoded, unexported constant bounding the `canLoad` scan. But the value it is meant to accommodate — the number of loadable matches the walk must accumulate — is **operator-configurable and unbounded**: `pkg/config/config.go`'s `MaxSearchResults int \`json:"max_search_results" env:"OMNIPUS_MAX_SEARCH_RESULTS"\`` defaults to 5 (`pkg/config/defaults.go:835`) but has no documented ceiling. An operator running an install with many connected MCP servers (a first-class, encouraged use case per this codebase's own MCP support) who raises `OMNIPUS_MAX_SEARCH_RESULTS` past 50 gets a `ToolSearch` that can **never** return the configured number of results, because the walk hard-stops at 50 lookups regardless of `maxSearchResults`. This is a real, silent divergence between two numbers the ADR never puts side by side. | Either derive the cap from `maxSearchResults` (e.g. `max(50, 10*maxSearchResults)`), or explicitly document/enforce a ceiling on `OMNIPUS_MAX_SEARCH_RESULTS` and cross-reference §3.2.2's cap from wherever that env var is documented, so the two numbers cannot silently disagree. |
| MAJ-302 | MAJOR | Incompleteness / Incorrectness | §3.2.1, assertion 4 (coverage tripwire) | The tripwire regex `^(delete\|remove\|disable\|purge\|wipe\|revoke\|drop\|reset\|destroy)_` (or literal `set_config`) is offered as the backstop that "fails the build" when a future destructive tool escapes the explicit 13-name set. But checked against the ADR's own seed (§3.2.1): **5 of the 13 names — `enable_channel`, `add_mcp_server`, `configure_channel`, `configure_provider`, `stop_plan` — do not match the regex at all.** These are exactly the "alters install-wide configuration" half of the membership rule (§3.2.1: "destroys or overwrites state … **or alters install-wide configuration**"), and the regex covers only the destructive-verb half. A future analogous addition — `enable_debug_mode`, `configure_sandbox`, `add_admin_key`, `stop_workspace` — would silently escape the tripwire the same way `revoke_credential` was the motivating example for rejecting a bare prefix list in the first place. The backstop has the same blind spot as the mechanism it was built to replace. | Extend the tripwire to also match `^(enable|disable|configure|add|remove|set|stop)_` (or, more precisely, derive it from the two clauses of the membership rule separately — a "destroys/overwrites" verb list and a "reconfigures" verb list) — or state explicitly that the "alters install-wide configuration" half of the membership rule has no mechanical backstop at all, so a reader does not credit assertion 4 with more coverage than it has. |
| MAJ-303 | MAJOR | Test Coverage Gap (Phase 3) | §3.2.2, "Required tests" table | The four required tests for the match-list filter (denied-absent, all-denied, ranking-invariance, nil-resolver) do not include a test for the **new `searchCanLoadScanCap = 50` boundary** that step 2 of the same section introduces. Nothing asserts that the walk actually stops at 50 lookups, that it returns the loadable hits found so far rather than erroring, or that a corpus where the first 50+ ranked hits are policy-denied (plausible on a narrow-policy agent connected to a large MCP server) returns a short-but-correct result instead of the expected `maxSearchResults`-length one. This is new mechanism introduced in the same section whose own test table was written, and it ships with zero coverage. | Add a fifth test: construct a corpus/policy combination where more than 50 ranked candidates precede the first `maxSearchResults` loadable ones; assert the result set is shorter than `maxSearchResults` (not empty, not erroring) and that no denied name appears in it. |
| MAJ-304 | MAJOR | Ambiguity / Incorrectness | §4.3.1(a), "Write" step | The write step reads: "record each **newly-promoted** name against the current turn index — only on the `query` path." "Newly-promoted" is never defined against the case where a tool is already in `loadedTools` (from an earlier promotion) and is promoted again by a later ambiguous-band search (§3.2's cross-category/score-band rules can legitimately re-qualify the same tool across multiple, unrelated queries within the same session). Two readings are both plausible from the text: (a) only write on the tool's *first* promotion ever, or (b) write — i.e. reset the turn index — on every `query`-path promotion, first or not. Reading (b) means a tool that keeps getting re-surfaced by search (without ever being called) has its "wasted promotion" clock continuously reset and **never** trips `omnipus_toolsearch_no_followup_total`, silently defeating the exact signal §4.3.1 spends the most text establishing as a "hard prerequisite… not an optional extra." This is a genuine ambiguity in a mechanism the ADR elsewhere insists be "specified to implement," not left for an implementer to infer (§3.2's own words, applied to itself). | State explicitly: the entry is written only the first time a name enters `pendingSearchPromotions` for a given bucket; a subsequent `query`-path re-promotion of an already-pending or already-loaded name is a no-write no-op. (This is also the reading consistent with "harmless for already-promoted tools" language used elsewhere in the ADR for the sibling `markLoaded`/`PromoteTools` calls — but that consistency should be stated, not assumed.) |
| MAJ-305 | MAJOR | Inoperability | §6.6, D5 acceptance gate | The gate is deliberately designed as "a measurement, not a judgment call" (explicit rejection of r2's "approximately," which "puts the pass/fail reading back in the hands of whoever wants the merge"). But the protocol as specified — a manual, one-off, non-CI measurement, with only the passing `B`/`ΔC` pair required in the PR body — has no stated limit on **how many times the operator may re-run it**. Nothing stops re-running a failed or borderline measurement until a passing pair appears, which reintroduces exactly the "pass/fail reading in the hands of whoever wants the merge" failure mode the numeric tolerance was built to eliminate, just moved from the threshold to the retry count. Given the measurement is explicitly acknowledged as noisy enough to need an 80%-not-100% floor "to allow for tokenizer disagreement," a single session's `ΔC` is plausibly variable run to run, so this is not a hypothetical edge case. | Require the PR body to record **every attempt**, not just the passing one — or fix the protocol to a single measurement with no re-run allowed short of a code change between attempts. Either closes the loophole; the current text closes neither. |
| MAJ-306 | MAJOR | Inoperability (STRIDE: Repudiation-adjacent / observability) | §4.3.1(a), the two `/metrics` counters | Both `omnipus_toolsearch_zero_result_total` and `omnipus_toolsearch_no_followup_total` are specified as **unlabelled** `atomic.Uint64` counters exposed on a hand-rolled, in-memory `/metrics` endpoint. Two consequences neither r1–r4 nor r5 addresses: (1) **No per-agent breakdown.** This product's default install runs a 4-agent core roster (per CLAUDE.md), each with a different tool policy and a different Tier-3 exposure. An unlabelled counter aggregates all four; a genuine per-agent problem (one agent's searches consistently miss) can be invisible in an aggregate that looks flat, while noise from one chatty agent can make the aggregate look like it's "rising" when the others are fine — directly undermining the revisit-trigger actions prescribed in §4.3.1/§11 ("Tier 2 should widen," "tighten the ratios"), which are stated as global actions justified by a global number that may not represent any single agent's real experience. (2) **No retention across restart.** The counters are in-process atomics with no persistence; CLAUDE.md states this project ships "no telemetry" and is "community-facing," so a typical self-hosted install has no external Prometheus scraper retaining history across gateway restarts. "Rising against a stable turn count" (§4.3.1's stated trigger condition) requires an operator to be polling and diffing `/metrics` themselves over time — a real but unstated operational assumption behind a mechanism the ADR calls a "hard prerequisite of D3 shipping." | At minimum, label both counters by `agent_id` (bounded cardinality — the roster is small and operator-controlled, unlike an open user-id space) so a per-agent revisit decision is possible. Separately, state explicitly (a one-line addition to §4.3.1) that the revisit trigger assumes the operator is scraping and retaining `/metrics` externally, since that is not this product's default posture — so the gap is a documented operational prerequisite rather than a silent assumption. |
| MIN-301 | MINOR | Incompleteness | §3.2.1, assertion 4 | `administrativeExemptNames` is introduced by name as the tripwire's escape valve ("a one-line reason") but its starting contents are never stated. Checked against the current Tier 1/2/3 lists in §4.1: every existing name matching the tripwire regex is already inside the 13-name `administrativeToolNames` seed, so the exempt set is implicitly empty at ship time — but the ADR never says so, leaving an implementer to guess whether an empty set literal is required or whether the set can be left undeclared until first use. | One sentence: "`administrativeExemptNames` starts empty; the drift test asserts len 0 today, so any future addition is a visible, reviewed diff." |
| MIN-302 | MINOR | Infeasibility (unverified performance claim) | §3.2.2 step 1 | "This costs essentially nothing" (ranking the whole corpus instead of top-K) is argued from `BM25Engine`'s doc comment ("all indexing work is performed inside Search() on every call") — confirmed accurate against `pkg/utils/bm25.go`. But the claim is not benchmarked against a realistically large corpus, and this platform is explicitly MCP-extensible with no documented ceiling on connected-server tool counts. The claim may hold today (a ~90-tool static catalog) and degrade unnoticed as installs accumulate MCP servers, since the index is rebuilt — not cached — on every `Search()` call per the engine's own documented behavior. | Not a blocker; worth a one-line note that this assumption should be revisited if `#654`'s broader caching audit finds corpus size growing materially past the current static-catalog scale. |
| OBS-301 | OBSERVATION | Overcomplexity (Lens 8) | D2/D3 overall, cumulative across r1–r5 | Tallying what D2+D3 now require: a `ManifestVisibility` enum, `previewedLazyToolNames` + `administrativeToolNames` + (per MIN-301) `administrativeExemptNames` — three name-classification sets, four tuning constants (`searchAmbiguityRatio`, `searchCrossCategoryRatio`, `searchMaxAutoLoad`, `searchCanLoadScanCap`), a composite bucket key (`manifestBucketKey`) shared across two maps, a second side-table (`pendingSearchPromotions`) with its own write/clear/dual-sweep/lock-ordering discipline, two `/metrics` counters, one config revert flag (`PreviewAllLazy`, explicitly time-boxed for deletion), a manual acceptance gate plus an offline structural test guarding it, and roughly a dozen newly-required regression/drift tests. This is a large, permanently-maintained surface for a feature whose core tuning parameters are explicitly "reasoned, not measured… flagged as such deliberately" (§11 item 3) and whose payoff (the no-follow-up counter specifically) cannot be validated until real usage data exists post-ship. The ADR's own §7 half-names this cost ("a second map to keep in sync… same closure, same sweep") and §16's OBS-201 records the prior review's version of this concern as "not acted on." Nothing here is wrong in isolation — each piece has a defended rationale and four rounds of adversarial pressure have not found a cheaper way to get the same properties — but the aggregate has not had an explicit "is this still worth it as one shipped unit" gut-check separate from each piece's individual defense. A concrete alternative worth stating explicitly and rejecting (or accepting) at ratification: ship `zero_result` (the simpler, single-counter, no-side-table half of §4.3.1) with D3, and treat the `pendingSearchPromotions` side-table plus `no_followup` counter as a fast-follow once `zero_result` data shows whether Tier 2 is mis-sized — since §4.3.1's own revisit-action table says a `zero_result` rise is acted on *first* in the both-rising case, the no-follow-up signal may not be needed to make the first real decision. | Not a defect — a scope/cost check the ratification conversation should have explicitly, rather than let stand as "recorded, not acted on" a second time. |

## Test coverage assessment

The document's own test-requirement discipline is strong — most sections list required tests inline, including several deliberately designed to fail if a future change silently reverts a decision (e.g. §3.2.2's ranking-invariance test, §3.3's permanence-regression test). The two coverage gaps this review adds are MAJ-303 (the new scan-cap boundary in §3.2.2 has no test) and the implicit gap behind MAJ-304 (no test distinguishes "first promotion" from "re-promotion of an already-pending tool" for the no-follow-up counter, because the write condition itself is ambiguous — a test cannot be specified against an ambiguous requirement). Concurrency coverage for `pendingSearchPromotions` is otherwise good (§4.3.1a test 3/4, mirroring §4.6's cross-agent tests).

## Unasked questions

1. If `OMNIPUS_MAX_SEARCH_RESULTS` is raised operator-side specifically *because* an install has many MCP servers, does anyone re-check that `searchCanLoadScanCap` still makes sense, or does it silently become the effective ceiling instead of the configured one? (MAJ-301)
2. Is there a reason the "alters install-wide configuration" half of §3.2.1's membership rule was left out of the mechanical tripwire, or was it an oversight from focusing on the destructive-verb half? (MAJ-302)
3. Should `pendingSearchPromotions` write on *every* `query`-path promotion or only the first? The ADR is confident about every other piece of this mechanism's semantics; this one gap is out of character with the rest of §4.3.1's precision. (MAJ-304)
4. Given `#654` is explicitly tracking the broader per-provider caching audit, should the D2/D3 supporting-machinery cost (OBS-301) be revisited there too, or is D2/D3's machinery considered final regardless of what `#654` finds about churn frequency?
5. Is there an assumption, anywhere in the surrounding infrastructure (not this ADR), that `/metrics` is actually scraped in a typical self-hosted install? If not, who is expected to notice the revisit trigger firing?

## Verdict

**REVISE.** No CRITICAL findings — r5's headline fix (§3.2.2) is correct and well-specified, and this review independently confirmed its core factual claims against source. The five MAJOR findings are all inside mechanism r5 itself introduced (the scan cap, the tripwire regex, the counter's write semantics, the D5 gate protocol, the metrics granularity) rather than inherited defects from r1–r4, so they do not require reopening any of the four prior rounds of resolved findings — they are additive to r5, not corrections of it.
