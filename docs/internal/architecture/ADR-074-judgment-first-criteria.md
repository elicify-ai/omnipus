# ADR-074 — Judgment-first acceptance criteria: prose-led adjudication, one authoring skill, technical checks optional

- **Status:** **Accepted** — operator-ratified 2026-09-05 (interview; ratification was conditional on no remaining open questions, and the three open items were resolved in the same interview: the ADR-072 numbering collision → renumber the browser ADR to ADR-075; the clarifying-question UX → D4b below; next step → full CI validation before implementation). **Revision 4**; r3 was the post-grill text (two adversarial rounds: r1 REVISE 5C/10M, r2 REVISE 5C/6M, all findings incorporated); r4 adds D4b and the ratification record only.
- **Deciders:** Daniel Piatkowski (operator)
- **Extends:** [ADR-049] evidence-ladder judge; [ADR-052-judge-verifier-architecture.md] (FR-034 behavior kind); [ADR-053-planning-goals-engine.md] (goal compiler, FR-113, D9 feasibility gate — **amended by D4a below**); [ADR-055-plan-supervisor.md] + `plan-supervisor-spec` FR-007/N3 (**amended by D4**); [ADR-072-skill-activation-and-loading.md] D5.1 (**narrow, argued exception in D4**). Design source: `docs/internal/design/judge-plansupervisor-target-design.html` (operator-ratified, 2026-09-05).
- **Revision history:** r1 initial. r2 — corrected r1's five factual errors. r3 — corrects r2's own five: the fresh `/goal set` path has **no** confirm step today (it activates and runs round 1 in the same turn — `goal_loop.go:114-118`, `:152-185`), so D4a now introduces two-phase confirm *as an explicit change*; there is **no** `Goal` REST path and `GoalStatusFrame` carries no criteria, so D5.2 now specifies a new contract surface; `formatGoalEcho` is dead code (test-only caller), so the FR-113 itemization guarantee is stated as *currently undelivered* and D4a's echo step becomes its delivery; the skill-allowlist append is a no-op on existing installs (`core.go:1812-1817` fresh-install gate), so D4 now specifies a marker-keyed migration reconciled with ADR-072 D5.1; PlanSupervisor's allowlist seam is `systemAgentSkills` (not `coreAgentSkills`), which is boot-re-enforced and therefore the one agent where the grant propagates automatically.

## Motivation

(Verified facts, upheld across both grill rounds.) The bias toward technical work lives in specific places:

- **UI:** the shared criteria editor defaults to `check` and cannot mint `behavior` (`AcceptanceCriteriaEditor.tsx:36`, `:147-150`); the Judge's written reason renders at 10px muted (`CriteriaVerdictList.tsx:73`).
- **Tool-schema drift:** four tools hardcode `enum: [check, prose]` against a contract that has had `behavior` since ADR-052 FR-034 — `create_task` (`pkg/tools/task.go:465`), `create_plan` (`pkg/tools/plan.go:165`), `plan_correct` (`pkg/tools/plan_correct.go:223`), `create_task_in_workspace` (`pkg/sysagent/tools/task.go:214`) — and the two criteria parsers behind them (`pkg/tools/task.go::parseCriteriaArgs`, reused by `create_plan`/`plan_correct`; `pkg/sysagent/tools/task.go`'s twin) read only `m["check"]`, physically discarding a `behavior` payload.
- **Engine input assembly (not the rubric):** `JudgeDefaultRubric` is already prose-first; the machine-first surface is `buildJudgeUserContent` (`pkg/agent/judge.go:897`: "Machine-check evidence (real, unfakeable — ordered first)").
- **Authoring:** every criterion must pre-declare a kind everywhere except `/goal`'s marker parser.
- **Goal itemization gap (r2 finding):** the FR-113 "user sees exactly what will run" itemization is **currently delivered by no surface** — `formatGoalEcho` has no production caller (`goal_compile.go:470`, called only from its test), the fresh-set path emits only a `goal_status` frame carrying the condition string, and `GoalEchoCard` never receives criteria or commands (`GoalThreadTailCards.tsx:44-49` passes neither; the card's `literalCommands` prop is never populated).

Target: **written criteria and DoDs are the primary basis of every verdict, judged the way a capable human reviewer would; technical checks are optional, when-applicable supporting evidence — never a prerequisite.**

## Decisions

### D1 — Prose-led evidence framing in `buildJudgeUserContent`

Target section order: (1) prose criteria to judge; (2) workspace file diff; (3) session transcript window; (4) machine-check results — re-headed as supporting context ("deterministic, already verdicted by the engine — supporting context for the criteria above"); (5) worker's completion claim, **LAST — unchanged** (OBS-003/FR-053: a claim is judged against the evidence above it, never the other way around). Scope explicitly includes rewriting the intra-section directional references the reorder invalidates: the two "alongside the machine-check evidence **above**" headers (`judge.go:917-918`, `:927-929`) and the empty-window fallback's "claim **below**" (`judge.go:934-935`). `JudgeDefaultRubric` needs at most a one-line wording touch; it is already prose-first.

**Test honesty (r2 MIN-2):** no existing test pins section order or claim-last — `verifier_antipatterns_adr052_qa_test.go:137-152` pins only the UNTRUSTED-DATA framing/injection ordering, which the reorder does not break. Required-test #8 therefore **adds a missing guard** (claim-last + target order), it does not update an existing one.

**Non-goal:** nothing removes or weakens `check`/`behavior`; they remain deterministic pre-verdicts that never reach the LLM.

### D2 — `kind` optional at authoring time, payload-inferred; one implementation; the gate keeps firing where it exists

**The rule:** absent `kind` + `check` payload ⇒ `check`; + `behavior` payload ⇒ `behavior`; + no payload ⇒ `prose`. An explicit kind mismatching its payload stays a 400 (shape rules unchanged). One implementation — `task.InferCriterionKind` — called by `normalizeCriteria` (before validation) and by **both tool parsers before the ADR-049 D2-rule-5 all-check bash-policy gate** (`pkg/tools/task.go:644→654`; `pkg/sysagent/tools/task.go:335→342`), closing the r1 CRIT-004 bypass on the two paths that have the gate.

**Gate coverage, stated honestly (r2 MAJ-1/MAJ-2):** the all-check gate exists on exactly **two of the four criteria-authoring tools** (`create_task`, `create_task_in_workspace`) and on **zero REST paths** (`rest_tasks.go`'s create applies no policy gate; `bashPolicyChecker` is wired only at the tool layer). `create_plan` and `plan_correct` (whose tail members are agent-assigned tasks — the highest-stakes authoring moment) have no gate today. This is a pre-existing gap this ADR does not widen at the tool layer; at the REST layer, D2 makes the pre-existing hole *easier to land in* (an author no longer needs to name `kind: check` explicitly to create an unsatisfiable all-check assignment). **Disposition:** extending the gate to `create_plan`, `plan_correct`, and the REST create path is a tracked follow-up issue filed on acceptance — named in Deferred, out of this ADR's implementation scope, and required-test #1 is explicitly scoped to the two gated tools.

**Contract shape (request-only relaxation):** shared `AcceptanceCriterion.yaml` stays `kind`-required (server always persists explicit kinds — `normalizeCriteria` guarantees it at both stores: `pkg/task/store.go:494`,`:1302`; `pkg/plan/plan.go:720`, `pkg/plan/store.go:374`); a new `AcceptanceCriterionInput.yaml` (kind optional) is referenced by the four request schemas. **Codegen trap (r2 MAJ-3):** the optionality is documented in `description` ONLY — **no OpenAPI `default:` key** — because `default:` + absent-from-`required` makes openapi-typescript emit the field non-optional, silently defeating the relaxation (the trap is documented in `TaskCreateRequest.yaml:121-125` itself). A required test asserts the generated TS emits `kind` as optional. **Canonical-schema rule:** `AcceptanceCriterion.yaml` is canonical; `AcceptanceCriterionInput.yaml` is derived from it and both carry cross-referencing header comments naming the other — the pair is a known new drift surface, accepted and guarded by a contract test asserting field-set equality minus the `required` delta. Known blast radius: ~10 gateway conversion sites (`rest_tasks.go:585-700`, `rest_plans.go:413-528`) switch to the Input type converting via `InferCriterionKind` — the gateway performs no defaulting of its own. Regenerated Go AND zod ship in the same commit: the SPA edge validator **throws `ApiSchemaError`** on a schema miss (`src/lib/api.ts:932-946` — a throw, not a silent drop; r2 MIN-3), taking the whole payload with it.

**Collateral (upheld from r2's verification):** persisted criteria always carry explicit kinds, so `criterionKey`/`sameShape` see no churn (guarded by required-test #4); `IsValidCriterionKind`'s doc comment gains the new invariant; the SPA continues sending explicit kinds (verified TS-safe); untouched plan Save sends no `dod` PATCH (required-test #10). `author`/`status` stay required: `author` carries security semantics (cross-agent check confirmation), `status` is server lifecycle — neither imposes authoring friction.

### D3 — Drift repair, two independently-safe steps

**D3a (ships first, safe alone):** all four tool schemas widen `kind` to `[check, prose, behavior]`; both parsers gain `behavior` payload decode (`tool`/`min_count`/`max_count`/`scope`, honoring `MinCount`/`MaxCount` pointer semantics — JSON `float64` → `*int`, explicit zero ≠ absent, `criterion.go:64-97`). `kind` stays required at this step.
**D3b (ships with D2):** the four schemas' `required` relaxes to `["text"]` with the inference documented in the description.

### D4 — One built-in criteria-authoring skill (`define-done`); seams and migration named precisely

New embedded skill `pkg/skills/embedded/define-done/SKILL.md`: the ratified quality bar (outcome-not-activity; observable; specific-enough-to-fail; one thing per criterion; complete-but-minimal; written for the judge that reads them; when a technical check earns its place) with worked good/bad examples, plus the clarifying-questions instruction (ask the goal-setter — human in chat, delegating agent for delegated work — before locking criteria when success is genuinely ambiguous).

**Allowlist seams — both, named (r2 CRIT-5):**
- **Core roster (Mia/Jim/Ava/Ray/Planner/Explorer/Researcher):** `coreAgentSkills` (`core.go:1520-1539`) gains `define-done` in each list. This reaches **fresh installs and newly-created agents only** — `SeedConfig` applies it under `isFreshInstall && len(a.Skills)==0` (`core.go:1812-1817`).
- **PlanSupervisor:** `systemAgentSkills` (`core.go:1324-1336`) becomes `["plan", "define-done"]` — an explicit amendment to plan-supervisor-spec FR-007/N3 ("exactly one" → "exactly these two"). Because system-agent allowlists are **hard re-enforced on every boot with an exact-equality overwrite** (`core.go:2068-2071`), this is the one agent where the grant propagates to existing installs automatically. Required-test #7 covers the amended `ExplicitNonNil` expectation AND the three `ReEnforced` tamper cases (`plan_supervisor_seed_test.go:216`, `:232-257`) — one of which ("widened with an extra skill") legalizes exactly this shape for exactly these two names and must keep failing for any other. The `core.go:1401-1402` no-drift invariant ("the rubric and the plan skill MUST NOT DRIFT") extends to span both granted skills: where `PlanSupervisorDefaultRubric` states a criteria-quality rule `define-done` also states, `define-done` is the source.
- **Judge:** no grant — the Judge consumes criteria, never authors them.

**Existing installs — explicit migration (r2 CRIT-4):** the fresh-install gate makes the core-roster append a silent no-op on every existing install, and ADR-072 D5.1 explicitly prohibits re-running the seed ("would silently restore a grant list the operator later emptied on purpose"). **Decision:** a one-shot, marker-keyed, additive-only migration (marker: `skills_migrations: ["adr074-define-done"]` in config, checked/written where SeedConfig runs): append `define-done` to a core-roster agent's `Skills` only when the list is **non-nil AND non-empty AND lacks it**. Nil stays nil (unrestricted already resolves every installed skill); empty-`[]` stays empty (an operator who zeroed the list opted out — respected). **Reconciliation with ADR-072 D5.1:** the prohibition targets *restoring grants an operator removed*; this migration appends a grant that has never existed, which cannot restore anything — a narrow, argued exception, run once, recorded by the marker, named in release notes. User-created agents with curated allowlists are NOT mutated; new custom agents get `define-done` in the default allowlist at creation (`core.go:1902` branch).

**Skill-file seeding on upgrade** (verified): `SeedDefaults` copies any embedded skill whose destination dir is missing (`pkg/skills/embed.go:57-90`) — the files arrive automatically; only the allowlists need the migration above.

**Trigger for `create_task`/`create_plan`/`create_task_in_workspace`/`plan_correct`:** Description() text directs the calling agent to load `define-done` before authoring criteria. Advisory-by-guidance; a hard gate is deliberately not built (unverifiable without deep turn introspection) — revisited if Phase-2 calibration shows skill-skipped criteria measurably worse.

### D4a — `/goal set` gains an LLM compilation turn AND a two-phase confirm — an explicit ADR-053 amendment (r2 CRIT-1/CRIT-3, MAJ-5/MAJ-6)

**Current reality (corrected from r2):** a fresh `/goal <intent>` compiles deterministically (marker parser), activates immediately, and **runs round 1 in the same turn** — "the `/goal` command IS the chat confirmation" (`goal_loop.go:114-118`, `:152-185`). Only the amendment path has echo-and-confirm. `formatGoalEcho` is dead code; no surface delivers the FR-113 itemization today.

**Decision — two-phase for LLM-compiled goals; single-phase preserved for marker-only:**
1. `/goal <intent>` where the text is **marker-only** (every criterion from explicit `[check:]`/`[behavior:]`/`[tests]` markers): today's path unchanged — deterministic compile, immediate activation, same-turn round 1. No LLM, no new latency, no behavior change.
2. `/goal <intent>` with **unmarked prose**: the goal-bearing agent runs a bounded LLM compilation call with `define-done` loaded, producing a skill-governed decomposition (markers still compiled deterministically and never reinterpreted). The result is stored as a **pending goal** and echoed for confirmation — criteria itemized in plain language — and the goal activates **only on the user's confirming reply** (the existing `confirmPendingGoal` mechanism, `goal_loop.go:239+`, extended to be reachable from the fresh-set path; today only the amendment path reaches it). This is a deliberate FR-113 amendment: "the `/goal` command IS the confirmation" narrows to marker-only goals; prose goals get compile → echo → confirm → activate. The clarifying-questions requirement makes a pause structurally necessary anyway — the echo IS where a clarifying question surfaces.
3. **The echo step delivers the currently-undelivered itemization:** the pending-goal echo renders every compiled criterion (plain language first, technical payloads verbatim per-row) — giving `formatGoalEcho` (or its successor) its first production call site, and feeding the D5.2 card. The pending state also gives `GoalThreadTailCards`' currently-unreachable `queued` filter (`goal_triggers.go:64` — never emitted in production, r2 OBS-2) its first real occupant.

**Mechanism (r2 MAJ-5):** a one-shot bounded provider call in the `runVerifierAdjudication` shape — the goal-bearing agent's own identity/model, its own fresh context, `define-done` content injected, schema-forced JSON out — NOT a `spawnSubTurn` (no delegation semantics needed) and never inside an unbounded wait: timeout mirrors the `goalJudgeRoundTimeout` precedent and rationale (`goal_loop.go:517-530` — a synchronous call inside the interactive turn must be bounded or it hangs live chat). **Ordering:** the R5 admission check (`pe.Admit("goal")`, `goal_loop.go:127-134`) moves BEFORE the compile call so a capped user never pays for a refused compile. Cost attributes to the goal-bearing agent; cancellation follows the turn ctx; `agentInst == nil` (`goal_loop.go:99-101`) takes the fallback path.
**Failure fallback:** LLM failure/timeout falls back to today's deterministic parser — `/goal` never bricks.
**Produce-then-veto repair (r2 MAJ-6):** if the D9 feasibility gate (unchanged, still last, still the only net — including its lexical vagueness veto, `goal_compile.go:459-461`) rejects an LLM-produced criterion, the rejection reason is fed back for **exactly one bounded repair attempt**; a second rejection falls back to the deterministic parser with a rewritten, plain-language user-facing message naming which criterion was refused and why (the current rejection text, which steers users toward technical markers — `goal_compile.go:312-314` — is rewritten plain-language-first regardless).

### D4b — Clarifying questions are delivered via a NEW general-purpose structured clarification tool (operator ruling, 2026-09-05 interview)

The clarifying question in D4a is NOT a plain chat message. The operator ruled: a **structured clarification component, similar to the question tool in Claude Code/OpenCode but better** — and, critically, **a general-purpose agent tool, not a goal-specific surface**: any agent may use it for any clarification (goal compilation is merely its first consumer). **Tool name: `AskUserQuestion`** — operator-ruled (interview #3, 2026-09-05) to match Claude Code's tool of the same name; consistent with Omnipus's existing CamelCase precedent for cross-cutting tools (`ToolSearch`, `Skill` — the verb-first snake_case convention applies to domain tools, not this class). Until it ships, D4a's question step falls back to a plain chat message.

**UI rulings (operator interview #2, 2026-09-05 — fixed requirements the follow-up spec inherits):**
- **Chat input is BLOCKED while a question card is pending**, with a **Cancel** affordance always present (dismiss the question, unblock chat, tool returns "cancelled" to the agent). Free-text answering happens through the card itself, never the chat box: **every question always carries a free-text option** in addition to its listed options.
- **Up to 10 questions per tool call**, answered on one card. (Per-question multi-select was the unrejected part of the recommended option and is assumed supported; flagged for one-line confirmation in the follow-up spec, not re-ratification.)
- **Recommended option: badge + listed first, never pre-selected** — the user must actively choose.
- **Rich context in the card**: a question can carry a preview (diff, image, table, criteria list) so the decision is made looking at the thing.
- **Timeout with a safe default — fixed 30 minutes** (operator-ruled, interview #3): when the agent explicitly marks a question default-safe, an unanswered question resolves to the recommended option after 30 minutes. One global value, not agent-tunable — chosen deliberately conservative so a user who stepped away almost certainly had a real chance to answer; background plans accept the half-hour wait. All other questions wait indefinitely until answered or cancelled.
- **Non-SPA channels get plain text, not UI**: on WhatsApp/Telegram/etc. the tool degrades to a numbered-options text message (rendering native UI per channel was explicitly rejected as not feasible/worth it); the reply parses as the answer.
- Explicitly NOT wanted (offered, not selected): answer memory / "always do this" defaults.

The follow-up spec (a **dependency of D4a's question step**) owns the remainder: tool schema, wire frames (Constraint #8), the SPA card, cancel/timeout semantics in detail, the text-degradation parser, and how a delegating agent (rather than a human) answers when the goal-setter is an agent.

### D5 — UI: four surfaces (Sovereign Deep; shared "verifies via" chip)

1. **`AcceptanceCriteriaEditor`:** plain-language field first ("What must be true when this is done?"); kind dropdown removed as lead control; "+ Add technical check" / "+ Add action-count check" quiet expanders; criteria cards show text primary + `verifies via:` chip when a payload is attached.
2. **`GoalEchoCard` — new contract surface required (r2 CRIT-2, corrected):** there is no `Goal` REST path and `GoalStatusFrame` carries no criteria; the card currently renders from a frame that cannot itemize anything. **Decision:** extend the goal wire surface with the compiled criteria breakdown — a `GoalEchoFrame` (or additive optional `criteria` on `GoalStatusFrame`; implementation chooses, via full Constraint #8 process) carrying per-criterion text + technical payload. This is a **prerequisite of D5.2 with its own D8 slot before the UI step**, not a contingency. The card renders criteria plain-language-first with per-row chips (verbatim commands preserved per-row — the FR-113 substance). The chat-text echo emitted at D4a's pending step is the confirm surface in history; the card is the live rendering of the same data; `[kind]` classification labels are not user-facing content in either.
3. **`CriteriaVerdictList`:** the Judge's reason promoted from 10px muted to criterion-text size as the verdict statement. Folded in: id-less criteria silently show no reason (matching is `criterion_id` vs optional `c.id`) — server always sets ids on persist; the UI handles absence explicitly. **Empty-quote render (r2 MIN-4):** the `evidence_quote` line (D7) renders only when non-empty — it is empty on every fail-closed verdict (`failClosedProseVerdicts` constructs no quote), every pre-D7 persisted verdict, and every install whose Judge `SOUL.md` predates the 2026-09-03 rubric (materialized souls are never overwritten — r2 OBS-1; remediation is the operator resetting the Judge soul, noted in release notes).
4. **Create Task / Create Plan flows:** inherit the editor; agent-drafted criteria present for confirmation via one shared `CriteriaBreakdown` component — the same one the goal card uses.

### D6 — Evidence for non-file work: the ship test answered honestly

At **task and goal scope**, the Judge receives the transcript window **when a session resolves** (`judge.go:879-884` allows `""` when none does — r2 OBS-3) plus the workspace diff: a drafted email or research summary produced in-session IS visible evidence there — the ship test passes today at those scopes, conditionally on session resolution. At **plan scope** the window is `""` by construction and non-file artifacts have no evidence class: a real gap this ADR does not close. Closing it (per-member windows for the plan judge and/or a produced-artifact evidence class) is a tracked follow-up issue filed on acceptance and a named prerequisite for declaring the target design fully met. Load shifts accepted and named as Phase-2 calibration metrics: (a) more prose ⇒ more traffic through `classifyNonVerdict`/unable-to-verify/escalate-once (withheld criteria don't consume rounds); (b) **the unvetted-authoring rate** (r2 OBS-4): D2 removes classification friction at task/plan scope with no semantic vetting (only goal scope has the D9 gate), so calibration must watch both judge accuracy AND the quality of what un-gated authoring produces.

### D7 — `evidence_quote` becomes real — with untrusted-content handling (r2 MAJ-4)

`judgeCriterionResponse` gains `EvidenceQuote`; flows to `task.CriterionVerdict` (new **optional** field; contract change to `CriterionVerdict.yaml` — which is `additionalProperties: false`, so the schema lands in the SAME atomic commit as the Go field, else `TestContract_CriterionVerdict_Populated` fails on the unknown key; `FixtureCriterionVerdict_Populated` gains the field — r2 MIN-5); rendered per D5.3.

**Laundering defense:** the quote is, by the rubric's own instruction, a verbatim copy out of the UNTRUSTED-DATA region (diff/window/claim). Therefore: (a) `evidence_quote` carries a `maxLength` (500) in the schema, truncated at the parser; (b) **any re-emission into another agent's prompt — the PlanSupervisor wake above all — MUST wrap it in the same UNTRUSTED-DATA framing `buildJudgeUserContent` uses** (never as bare trusted text); (c) the UI renders it as inert quoted text. The wake enrichment itself stays deferred (see Deferred), but the framing rule is binding on whoever implements it.

### D8 — Rollout order (each step independently green, Constraint #7)

(1) **D3a** (enum + parser widening); (2) **D2 + D3b** (Input contract type, inference helper, gate-ordering fix, tests — one atomic contract commit, Go+zod); (3) **D7** (evidence_quote — atomic contract commit); (4) **goal wire surface** (D5.2's frame/field — contract commit, prerequisite for 6); (5) **D4 + D4a** (skill + allowlists + migration + two-phase compile with fallback); (6) **D1** (input-assembly reorder + new claim-last guard); (7) **D5** UI, last.

## Consequences

**Positive:** non-technical work first-class end to end; one quality bar wherever an LLM authors criteria — including `/goal` (which gains the operator-required rewrite-and-clarify behavior) and `plan_correct` (where bar-lowering risk is highest); the FR-113 itemization gets delivered for the first time; drift repaired; the Judge's grounding quote becomes a real, bounded, safely-framed artifact.

**Risks / accepted limitations:**
- **Prose judgment quality** rides on the Judge model — Phase-2 calibration is the measure; the adversarial suite the floor. Calibration now explicitly watches the unvetted-authoring rate too (D6).
- **D4a changes `/goal` UX for prose goals** (one extra bounded LLM call + a confirm step where none existed). Bounded by: marker-only path unchanged, admission-before-compile, `goalJudgeRoundTimeout`-style bound, deterministic fallback, one-repair-then-fallback on veto.
- **Two-standards authoring:** goal scope keeps D9 semantic vetting; task/plan scope has shape-only vetting. Named, measured (D6), and a candidate for a follow-up gate if calibration says so.
- **All-check gate coverage stays partial** (2 of 4 tools, no REST) — pre-existing, now explicitly tracked instead of implied covered.
- **Contract changes in four places** (Input type; CriterionVerdict.EvidenceQuote; goal echo surface; request-schema references) — each atomic, each through Constraint #8, blast radius enumerated above.
- **Migration is a narrow exception to ADR-072 D5.1** — argued (appends a never-existing grant; cannot restore a removed one), marker-keyed, once.

## Deferred (tracked on acceptance)
**The `ask_user` structured clarification tool's own spec (D4b — a dependency of D4a's question step; chat-message fallback until it ships).** All-check gate for `create_plan`/`plan_correct`/REST create; plan-scope evidence for non-file artifacts; hard skill-trigger gate (pending calibration data); `define-done` trigger on `update_task`/`update_plan` edits; PlanSupervisor wake enrichment with framed `evidence_quote`; `src/lib/api.ts` throw-vs-drop divergence from CLAUDE.md Constraint #8 wording (pre-existing, r2 MIN-3).
