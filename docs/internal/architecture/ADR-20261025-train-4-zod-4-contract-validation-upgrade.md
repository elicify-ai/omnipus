# Train 4: Zod 4 contract-validation upgrade

**Status:** Proposed — decision-ready recommendation; not implementation or landing approval

**Date:** 2026-10-25 (UTC)

**Scope:** GHSA-mrhx-c7xc-m3w5; founder-directed Train 4 fix

**Inspected version:** `e83647cc12b2c08fa58472212e50f279bee4c4ac`

**Classification:** Design task now; security-relevant, cross-tree Feature-size implementation later. No production code, tests, contracts or dependencies changed by this ADR. [S1, S2]

## Context

The web app executes Zod validation for HTTP responses and WebSocket (WS) messages, including its parser worker. The root dependency is 3.25.76; four nested copies are 4.4.3. Both versions fall inside the advisory's `<4.6.6` range. The patch checks **leading upper collection bounds before parsing elements**; it does not invent bounds for an unbounded collection or limit JSON decoding. Production source reachability is verified; a remotely triggerable Omnipus crash is **Unknown**, not demonstrated. [S2, S3, R1–R18]

A simple root version bump is incompatible with the current generator/client pairing. Read-only registry queries on 2026-10-25 confirm `openapi-zod-client` latest is still 1.18.3 and depends on Zod 3; `@zodios/core` latest is 10.9.6 with peer `zod:^3.x`. The application uses its existing fetch transport, not the generated factories: the source import inventory finds no factory/namespace consumer. Dropping those factories alone would not upgrade the emitted validators. [S3, S4]

Keep Hard Constraint #8 and the decisions **OpenAPI 3.0.3 vs 3.1.0 Trade-off**, **`additionalProperties` Policy (Requests Closed, Responses Per-Case)**, **Discriminated-union create contract for agents**, and **SPA Streaming Resilience**. This proposal replaces the REST Zod emitter, not the contract format, transport or Go type generator. [S1, S5]

## Decision — recommendation for approval

### 1. Replace only the REST validator generator

| Option | Decision and reason |
|---|---|
| Upgrade `openapi-zod-client` / Zodios | No compatible newer stable release is available in the inspected registry. Do not force Zod 4 through Zod-3-only dependencies. [S3] |
| **Use `@hey-api/openapi-ts` 0.99.0, Zod plugin only; remove Zodios factories** | **Recommended.** Its tagged documentation/configuration supports Zod 4, reusable definitions, configurable names and disabling request/response generation. MIT license; Node >=22.18.0, compatible with existing CI Node 24. Schema fidelity still requires the acceptance checks below; generation against our full spec has **not** been executed. [S3, S6, S7] |
| Own template / emitter | A smaller Handlebars template can delete the unused clients, but cannot change the old generator's internal Zod-3 schema expressions. A real fork/converter must own records, defaults, unions, strictness, bounds and refinements; it retains old generator dependencies unless replaced entirely. More maintenance than a supported emitter; not the default. [S4, S8] |
| Interim size guard with Zod 3 | Possible containment, **not** the Train 4 dependency fix. A contract-derived array-length check must run before validation and before per-row loops, with the same coverage in worker, inline WS and bespoke HTTP paths. Merely capping logged issues after `safeParse` is too late. Do not silently substitute a generic byte limit: HTTP currently buffers JSON before validation and legitimate Library content can be large. [S2, R1–R18] |

### 4. Size limits beyond the patch

**Yes, explicit bounds are needed for a bounded-resource guarantee.** Existing bounds must remain effective, e.g. SessionState `pending_approvals` 1,000 and `pending_asks` 64. An oversized bounded collection should produce the size error without visiting its elements. Keep size checks leading, before any transform/refinement that could prevent upstream short-circuiting. [S2, S12]

The unbounded Room/Provider list wrappers and per-row loops in R9–R13 remain linear work, and errors inside unbounded nested collections can still accumulate. Neither moving parsing to a worker nor the gateway's 5 MiB **client-to-server** read limit bounds server-to-browser validation. [R1, R5, R9–R16, S12]

**Train 4 recommendation:** ship the patched dependency graph and preserved existing contract bounds together. Before calling this a complete memory-exhaustion defence, backend-lead/frontend-lead must produce a limits table for the unbounded collections: existing producer/page maximum → matching YAML `maxItems`/`maxProperties`, or a documented exception for founder acceptance. No defensible new universal numeric cap was established in this design-only task; do not invent one or truncate valid results. New bounds require founder-approved values, contract-first edits, matching producer behaviour and tests **before** implementation. The interim guard is an emergency option only, not a reason to retain vulnerable Zod or claim the residual risk is solved. [S1, S2, S12]
