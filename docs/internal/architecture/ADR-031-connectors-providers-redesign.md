## 1. Problem Understanding

**Business objective.** Two settings surfaces — **Connectors (Channels)** and **Providers** — present *the whole catalog of what's possible* rather than *what the operator has actually configured*, and hide the one attribute that matters (a channel's workspace→agent binding; a provider's plan/endpoint). A real operator using the shipped Channels screen concluded a channel could bind to only one workspace, and could not find how to serve multiple. The provider surfaces have a second, sharper defect: the **plan/region/API-variant** UX (needed to hit the right endpoint for the Chinese providers) exists **only in onboarding**, and even there it mislabels a *wire protocol* ("Anthropic API") as a *billing plan* `[FACT: onboarding.tsx:331-335]`. The two surfaces are also visually and terminologically **inconsistent** with each other.

**Stakeholders.** Operators/admins configuring channels + providers (primary); the onboarding flow; the SPA settings screens. Deciders: the operator.

**Blast radius.** `ConnectorsScreen.tsx`, `ProvidersSection.tsx`, `onboarding.tsx` (ModelKeyStep), `login.tsx`, a new shared provider/channel **catalog** + **`<BrandIcon>`** component, and vendored brand-logo SVG assets. UI-layer; the backend provider registry + wire contract are read, not restructured (one open question on the catalog's home — §5.2).

**Current-state facts (grounded):**
- **Channels list is flat + binding-blind.** Equal-weight rows, no grouping, workspace binding absent from the row `[FACT: ConnectorsScreen.tsx:502-588]`. Config is a slide-over (`ChannelConfigPanel`) `[FACT]`. A global "+ Add instance" button exists but doesn't communicate "= another workspace" `[FACT: ConnectorsScreen.tsx ~417-430, the add-instance control]`.
- **Providers list — precise current state** (corrected R1 after grill F-03/F-11 verification against `src/components/settings/ProvidersSection.tsx`, 457 lines): **no screen-level empty state / catalog roster** (grep for "no provider"/"configure first"/"roster" → 0 hits), **no company grouping, no brand logos, no Plan/Region/Wire variant badges** (the only `Badge`s are status — "Connected"/"Not configured" at 193-204 — and model-slug chips at 336). Config is an **inline card-section expand** keyed on `expandedProvider` (274-438), **not** a `Sheet`. *One nuance that must not be conflated:* lines 351-354 render a **per-provider model-list** empty state ("No models added yet") — that is the empty *model-slug* list for an already-configured manual provider, a different concept from the screen/catalog empty state FR-1 introduces. Net: the four redesign deficiencies (screen empty-state+roster, company grouping, logos, Sheet-based config) all genuinely hold. `[FACT: ProvidersSection.tsx — verified R1]`
- **The variant UX is onboarding-only.** `AVAILABLE_PROVIDERS` = **30 variants across 15 companies** (corrected R1; my original "47/14" was wrong) + `PLAN_LABELS`/`REGION_LABELS` + the Plan/Region segmented controls live in `onboarding.tsx` `[FACT: AVAILABLE_PROVIDERS from line 74; PLAN_LABELS 331-335; REGION_LABELS 338-342; Plan/Region controls 1436-1554]`; Settings has none. `PLAN_LABELS.anthropic = "Anthropic API"` conflates wire with plan `[FACT: 331-335]`.
- **Backend variant reality (corrected R1).** `knownProtocols` has **61 entries** `[FACT: pkg/providers/factory_provider.go:424-486 — verified count]`, of which **only ~30 are user-selectable API-key providers**. The rest are **pure aliases** (`z.ai`, `zai`, `glm-coding`, `qwen-international`, `dashscope-intl/us`, `alibaba-coding`, `qwen-coding`, `codexcli`, `claudecli`, `copilot`), **CLI executors** (`claude-cli`, `codex-cli`, `github-copilot`, `antigravity`), and **self-hosted infra** (`litellm`, `vllm`, `ollama`, `vivgrid`, `volcengine`, `shengsuanyun`, `modelscope`, `avian`, `longcat`, `mimo`). The Chinese multi-endpoint families in `knownProtocols` are larger than onboarding's company counts: zhipu/z-ai family = **9** ids, qwen/alibaba family = **11**, moonshot ×4, minimax ×4, deepseek ×2. All OpenAI-compatible **except** `anthropic`/`anthropic-messages`/`bedrock` and the `*-anthropic` wire variants. **This 61-backend-vs-30-frontend gap is the core problem G-2=B must reconcile — see §6 G-2 (revised R1).**
- **Login re-onboard button.** `login.tsx:178-190` renders "Set up Omnipus for the first time" → `navigate({to:'/onboarding'})` (+ `Rocket` import, line 4) `[FACT]`.
- **Removing it is safe — with one bounded exception (R2-06).** `_app.tsx` beforeLoad checks onboarding **before** auth and redirects a not-onboarded user to `/onboarding` `[FACT: _app.tsx beforeLoad — onboarding check precedes the token check]`; `onboarding.tsx` beforeLoad bounces an *onboarded* user to `/` `[FACT]`. So the button is a redundant fresh-install shortcut and cannot re-run onboarding on a live system — removal strands nothing **on the happy path** `[INFERENCE, High confidence]`. **Exception:** when `fetchAppState()` *throws* (`_app.tsx:16-21`), the code falls through to the auth check and redirects to `/login`, not `/onboarding` — so during a `/api/v1/state` outage a fresh install lands on `/login` with the removed button gone → no affordance to onboarding. The button-removal doesn't *cause* this (the button lived on `/login`), and a broken `/state` is a broader failure, but the "strands nothing" guarantee holds **only when `/api/v1/state` is reachable** `[FACT: verified _app.tsx catch-branch]`. Plan-spec: accept this (recommended — a dead `/state` breaks far more than onboarding) or keep a minimal fallback link.
- **Reference implementation.** opencode/models.dev flatten `(company × plan × region × wire)` into `<Brand> — <Access Type> (Region)` catalog entries with a subtitle; wire is chosen per-endpoint (SDK adapter); one API key is shared per company; their one regret is having **no explicit `company` field** (grouping via name-regex) `[FACT: opencode local catalog research]`.
- **Logos.** `@lobehub/icons-static-svg` (MIT) is the only set with real Zhipu/GLM, Qwen, Kimi, MiniMax, DeepSeek marks; `simple-icons` (CC0) covers 8/13 channels but dropped Slack (+ OpenAI/Azure/AWS) over trademark; LINE/Meta/Tencent brand guidelines forbid recoloring `[FACT: logo research]`.

## 2. Extracted Requirements

### Functional
- **FR-1:** Both lists MUST show **only configured** entries; the connectable-types catalog appears in an **empty-state roster** and behind "Connect …". **"Configured" is defined (R3/MAJ-002) as "has a persisted config entry", independent of key validity or enabled-state.** An entry with an invalid/expired key, a *disabled* channel, or a provider with *zero model slugs* **stays in the configured list** with a distinct status indicator (reuse the existing "Connected"/"Not configured" status badges at `ProvidersSection.tsx:193-204`) — it MUST NOT vanish (an operator must be able to find a broken entry to fix it). Only a type/variant with **no** persisted config is "connectable" and lives in the roster. `[FACT: user decision; state taxonomy per R3]`
- **FR-2:** Configuring AND creating a new entry MUST use the app's **`Sheet` slide-out** — no modal `Dialog`. `[FACT: user decision; sheet.tsx / ChannelConfigPanel.tsx are the standard]`
- **FR-3:** Rows MUST be **binding-first** and MUST NOT repeat the group's type/company in the row title: group header = type/company + logo; row title = `Workspace → Agent` (channels) / `Access Type · Region` (providers). `[FACT: user decision]`
- **FR-4:** Instances/variants MUST be **grouped** (by channel type / by provider company), header carrying the logo + an in-group "Add another…". Grouping is adaptive: **when the list has ≥1 configured entry it renders grouped rows; when it is empty, FR-1's empty-state roster shows instead (R3/MIN-003 — the two are mutually exclusive states, not a contradiction).** `[FACT: user decision]`
- **FR-5:** A provider **variant is its own endpoint-row** under its company; Plan/Region/Wire/Endpoint are **view-only**; the **API key is editable**; switching plan/region = connect a different variant. `[FACT: user decision]`
- **FR-6:** Variant labels MUST follow `<Brand> — <Access Type> [(Region)]` + a subtitle naming billing model + the **curated endpoint hint** (R3/MAJ-005: a real host for hosted providers e.g. `api.openai.com/v1`, or a **placeholder template** for deployment-configured ones e.g. `<resource>.openai.azure.com`, `localhost:11434` — NOT necessarily a "literal host", since `endpointHint` values are curated display strings, some templated). **Plan-label migration — exact deltas (corrected R2 per grill R2-04; current `PLAN_LABELS` = `{api:'Pay-as-you-go API', coding:'Coding Plan', anthropic:'Anthropic API'}` `[FACT: onboarding.tsx:331-335]`):** `api: 'Pay-as-you-go API' → 'Standard API'` — a deliberate terminology shift (the billing nuance "pay-as-you-go, per-token" moves into the **subtitle**, so the plan label stays short); `coding: 'Coding Plan'` — **UNCHANGED** (already correct); `anthropic` — **DROPPED** (becomes the derived wire badge). ⚠️ Note for plan-spec: "Standard API" is arguably *less* precise than "Pay-as-you-go" for the exact billing distinction the variant UX exists to convey — confirm the subtitle carries it. **`Token Plan` is NOT added to the shipped plan enum at all** (R2-12: don't define-then-suppress a dead branch) — add it only when a real variant maps to it (G-5 confirms none do today). **Wire (OpenAI-/Anthropic-compatible) is a derived badge, not a plan option.** `[FACT: user decision; fixes onboarding.tsx:331-335]`
- **FR-7:** Provider metadata (company/plan/region/wire/label/logo) MUST be **data-driven** from a single catalog, reused by **onboarding AND Settings** (identical logos + terminology). `[FACT: user decision]`
- **FR-8:** Brand logos MUST be **bundled offline** (SVG in-repo → go:embed, CSP-clean, `currentColor` themed) via one shared `<BrandIcon>`; providers → lobehub, channels → simple-icons, with Phosphor/lettermark fallbacks; ship a "identification only, no endorsement" disclaimer. `[FACT: user decision + logo research]`
- **FR-9:** The login "Set up Omnipus for the first time" button (`login.tsx:182-188`) + its `Rocket` import MUST be removed. **The post-login redirect at `login.tsx:32-35` (navigate to `/onboarding` after a successful login when `!state.onboarding_complete`) MUST be RETAINED (R3/MIN-002)** — it is the real path a logged-in-but-not-onboarded admin reaches onboarding; a plan-spec agent must not over-remove it. `[FACT: user decision; safe per §1]`
- **FR-10 (disclaimer — promoted R1 per grill F-09):** Wherever brand marks render (onboarding provider step AND Settings Providers list AND the Channels list), a visible "Logos are trademarks of their respective owners, used for identification only — no affiliation or endorsement implied" notice MUST be present (a footnote under the provider/channel roster is sufficient; it MUST NOT be hidden behind a tooltip-only affordance). Acceptance: the string renders in the DOM of every screen that shows a `<BrandIcon>`. This is the load-bearing mitigation for the G-1=B legal residual, so it is a hard requirement, not a nicety. `[INFERENCE from operator's G-1=B decision + trademark research]`
- **FR-11 (swap mechanism — promoted R1 per grill F-09):** `<BrandIcon>` MUST resolve marks by an indirection (`logoSlug` → embedded asset path) such that removing one brand = deleting one SVG + clearing one catalog field, with **no code change**. An unknown/removed `logoSlug` MUST fall back to the lettermark chip without throwing. Acceptance: a unit test that renders `<BrandIcon slug="__removed__"/>` and asserts a lettermark, no crash. `[INFERENCE; makes "one-line takedown" a checkable control]`
- **FR-12 (SVG sanitization — added R1, hardened R2 per grill R2-09):** Every vendored brand SVG MUST be sanitized before embedding, because `<BrandIcon>` renders inline SVG (required for `currentColor`), an XSS sink if unsanitized. **Prefer an allow-list posture** (strip everything except a known-safe element/attribute set: `svg, path, g, circle, rect, polygon, polyline, line, ellipse, defs, linearGradient, radialGradient, stop` + geometry/`fill`/`stroke`/`viewBox`/`d`/`transform` attributes) over a token denylist — a denylist is inherently incomplete for XSS. **`DOMPurify` is already a dependency (R3/MIN-001)** — use it (`profiles:{svg:true,svgFilters:true}`) at build/embed time rather than authoring a bespoke sanitizer. Acceptance: vendored SVGs pass through a real build-time SVG sanitizer (allow-list), and a test asserts no disallowed element/attribute survives. If a denylist grep is used as a *secondary* check, it MUST at minimum cover `<script`, `<style`, `<foreignObject`, `<use`, `on*=`, `javascript:`, and external `href`/`xlink:href` — and be documented as best-effort defense-in-depth atop CSP, not the primary control. `[FACT: inline-SVG XSS is a known vector — `<style>`/`<use href=data:>`/`javascript:` URIs bypass a naive denylist; CSP does not stop same-origin inline SVG]`

### Non-Functional
- **NFR-1 (consistency):** onboarding and Settings render the same brand + the same plan/region/wire words from one source. `[FACT]`
- **NFR-2 (contract-first):** any byte crossing the gateway/SPA boundary goes through `contracts/` (Constraint #8). Pure-display catalog metadata that never crosses the boundary is exempt — this is the crux of §5.2. `[FACT: CLAUDE.md]`
- **NFR-3 (self-contained/CSP):** no runtime CDN for logos; single-binary, no new *runtime* deps (a build-time dev-dep to extract SVGs is acceptable). `[FACT: CLAUDE.md]`
- **NFR-4 (accessibility/legibility):** lift the current 10px secondary text toward a 12px floor; logos are decorative with an accessible label on the row. `[INFERENCE from prior UI audit]`
- **NFR-5 (a11y — recognition):** the binding/variant must be visible on the row (recognition over recall). `[FACT: UX audit]`

### Constraints
- Single Go binary, embedded SPA, no telemetry, strict CSP, contract-first `[FACT: CLAUDE.md]`.
- Reuse existing components: `Sheet`, `Tabs`, `Badge`, `Button`, `SmartSelect`, `Switch`, `Input` — the prototype exercises these `[FACT: proto.tsx]`. (Corrected R1 per grill F-13: the proto used raw `<div>`+Tailwind for card surfaces, not the `Card` component — the redesign MAY use `Card`, but that substitution is untested, not "proven".)
- **Trademark:** logo SVGs are CC0/MIT (copy OK) but the marks are trademarks; recoloring LINE/Meta/Tencent brushes their guidelines `[FACT: logo research]` — this is decision §5.1.

## 5. Option Analysis (the genuinely-open forks)

The locked decisions (FR-1..FR-9) are ratified — see §6. Options below are only for G-1/G-2/G-3.

### 5.1 — Logo policy (G-1) — **DECIDED: Option B**
- **Option A — Real marks for most, lettermark for the strict ~5-6.** Real recolored logos everywhere except LINE, WhatsApp/Meta, Tencent (WeChat/QQ), OpenAI/Azure/AWS → lettermark chips. Strengths: polish + brand recognition where safe, avoids the guideline-brushing marks. Weakness: mixed visual language; a judgment call on which are "strict." Risk: low. 
- **Option B — Real marks everywhere.** Strengths: maximum recognition, one visual language. Weakness/Risk: recolors LINE/Meta/Tencent (against their guidelines) and re-bundles marks two icon sets *removed* over enforcement (OpenAI/Azure/AWS). Practical risk low for OSS nominative use, but non-zero.
- **Option C — Lettermarks/generic everywhere.** Strengths: zero TM risk, fully on-brand color, uniform. Weakness: loses instant recognition — the reason we wanted logos.

### 5.2 — Catalog metadata home (G-2) — **DECIDED: Option B**
> **Naming-collision note (R1, grill F-04):** a file `src/lib/agents/providerCatalog.ts` **already exists** `[FACT: verified — 3.2 KB]`, and it means something else: per-provider **model-catalogue mode** resolution (`live` vs `manual` listing). Any new frontend catalog artifact MUST NOT reuse that name, and the plan-spec MUST decide whether that file's `live/manual` + `has_models_endpoint` logic folds into the new catalog (it overlaps the `wire`/endpoint concern) or stays separate. The chosen G-2=B is backend-owned, so ideally **no new frontend catalog file is created at all** — the generated TS types are the frontend surface.

- **Option A — Shared frontend catalog const**: company/plan/region/wire/label/logo per user-facing provider id, imported by onboarding + Settings + `<BrandIcon>`. The backend keeps the *functional* truth (base_url/wire behavior via `knownProtocols`); the frontend catalog is the *display* SoT. Strengths: matches the existing `AVAILABLE_PROVIDERS` pattern `[FACT]`, no contract change (pure display, never crosses the boundary — NFR-2 exempt), fast. Weakness: two places know the provider set (backend registry + frontend catalog) — they must be kept in sync manually; a drift-guard test is the mitigation.
- **Option B — Backend-owned, surfaced on the contract:** add a `ProviderCatalogEntry` schema + `GET /providers/catalog`. Strengths: single SoT, contract-first-pure. Weakness: larger (contract + regen + Go), and much of the payload (labels, logo slug, subtitles) is pure presentation that doesn't belong in a wire contract (NFR-2 would otherwise exempt it — see the F-07 caveat in §6).

### 5.3 — Onboarding↔Settings sharing (G-3) — **DECIDED: Option C** (de-risked by G-2=B; see §6)
- **Option A — Shared data + shared sub-components** (`<BrandIcon>`, a `<VariantPicker>` for the Company→Access→Region flow, the catalog, the label constants) consumed by two thin host UIs (the onboarding wizard step vs the Settings Sheet). Strengths: guarantees identical logos + terminology (NFR-1) without forcing a wizard and a settings-panel to be the same component. Weakness: two host layouts to maintain (but they're genuinely different contexts).
- **Option B — One provider-config component reused in both.** Strengths: literal single implementation. Weakness: onboarding is a stepped wizard with probe-and-continue; Settings is a persistent Sheet over an existing config — forcing one component breeds prop-flag soup and hurts both.
- **Option C — Shared catalog + BrandIcon only; duplicate the variant-picker UI.** Strengths: least coupling. Weakness: the picker (the exact thing that must be terminology-consistent) is duplicated → drift risk — defeats NFR-1.

## 6. Recommended Architecture

**Ratified (locked) decisions — recorded, not re-litigated:** FR-1..FR-9 as stated. The shared IA is **"catalog → configure (Sheet) → configured-only list"** for both Channels and Providers; binding-first rows without the redundant group prefix; adaptive grouping; provider variant = view-only endpoint-row + editable key; opencode-style labels with wire-as-badge; one data-driven catalog reused by onboarding + Settings; bundled `<BrandIcon>`; login re-onboard button removed.

**Open forks — DECIDED by operator 2026-07-02 (interview via AskUserQuestion). Albert recorded my recommendation; on all three the operator chose the higher-consistency alternative. Recorded faithfully, with the caveats each carries:**

- **G-1 → Option B — Real recolored marks *everywhere*.** *(Albert recommended A — real-for-most/lettermark-for-strict.)* Operator's rationale: one uniform visual language + maximum recognition outweighs the residual trademark risk. **Consequence Albert must flag:** this recolors LINE / WhatsApp-Meta / Tencent (WeChat/QQ) marks against those brands' guidelines and re-bundles OpenAI/Azure/AWS marks that `simple-icons` *removed* over enforcement. Risk is low for OSS nominative/identification use but **non-zero and legal, not technical** — the "identification only, no endorsement" disclaimer (FR-8) is now load-bearing, not decorative, and MUST ship. `[Evidence level 1 — operator decision; risk per logo research]`
- **G-2 → Option B — Backend-owned catalog surfaced on the wire contract.** *(Albert recommended A — frontend const.)* A new `contracts/components/schemas/ProviderCatalogEntry.yaml` + a `GET /api/v1/providers/catalog` endpoint become the single source of truth; onboarding + Settings + `<BrandIcon>` all read it. Follows Constraint #8 contract-first (generated Go+TS types, not a hand const); larger delta (spec → `scripts/gen-contracts.sh` → committed generated diff → handler). **Three specification holes the grill (F-01/F-02/F-06/F-07) forced closed before this is plan-spec-able:**

  1. **Catalog id-set = the curated user-facing subset (~30), NOT raw `knownProtocols` (61).** `[FACT: 61 verified]` The catalog is seeded by porting today's **30 `AVAILABLE_PROVIDERS`** entries (`onboarding.tsx`) into the backend, then `AVAILABLE_PROVIDERS` is **deleted** (it becomes the catalog's seed, ending the frontend/backend duplication). A protocol id is in the catalog **iff** it is a user-selectable API-key provider; the ~31 aliases / CLI executors / self-hosted-infra ids are **excluded from the catalog but remain instantiable** by `knownProtocols` (nothing about routing/probe changes). Mechanism: a single hand-authored backend allow-list — **use one term, `catalogVisible` (R3/MIN-005)**; the guard's complement is "not `catalogVisible`", not a separately-maintained `catalogExcluded` set.
  2. **Drift-guard redefined (the F-01 fix — the old "every `knownProtocols` id yields one catalog entry" was infeasible: it would force hand-authoring company/plan/logo for CLI/alias/infra ids). THREE properties (third added R3/MAJ-001):** the `pkg/api/generated/contract_test.go` assertion is: **(a)** every catalog `id` resolves to a real protocol — `IsKnownProtocol(id) == true` (after alias-normalization, see G-4); **(b)** every `catalogVisible` protocol is in the catalog — so a newly-added user-facing protocol can't silently miss it; and **(c) every catalog `id` (post-alias-normalization) is a member of the `ProbeProviderRequest` id enum.** Property (c) **re-homes a live cross-boundary invariant that deleting `AVAILABLE_PROVIDERS` would otherwise drop:** `src/routes/-onboarding.test.tsx:1029-1074` currently asserts `AVAILABLE_PROVIDERS ⊆ ProbeProviderRequest` enum ("the UI never offers a provider the probe can't handle") `[FACT: verified — that test imports `ProbeProviderRequest` from the generated schemas and asserts subset]`. Without property (c), a catalog id valid in `knownProtocols` but **absent from the probe enum** would pass the guard yet silently break onboarding's model-list probe. **Retirement plan for that test:** the subset assertion migrates to `contract_test.go` property (c) (or a catalog-seed test); the per-company variant-count assertions (Zhipu=6, Moonshot=4, …) move to a catalog-seed test **or** are dropped with justification (they guarded `AVAILABLE_PROVIDERS` completeness, now the catalog's job). None of the three properties is vacuous.
  3. **`wire` defined; `endpointHost` = reuse the existing curated `endpointHint`, NOT a `GetDefaultAPIBase` derivation (R2-01+R2-03 fix).** `wire` is a **closed enum `{"openai-compatible", "anthropic"}`**, derived, not stored: `wire = "anthropic" if id matches /-anthropic$/ OR id ∈ {anthropic, anthropic-messages, bedrock} else "openai-compatible"`. For the endpoint display, **do not invent a derived `endpointHost`** — the R1 rule ("host of `GetDefaultAPIBase(id)`, or empty for `azure/bedrock/vllm/ollama/litellm`") was **self-contradictory**: `[FACT: factory_provider.go:508/550/578]` `litellm`/`ollama`/`vllm` return **non-empty** localhost URLs, so "or empty" is wrong for three of the five. Instead, port the already-curated **`endpointHint`** field — `ProviderVariant.endpointHint` exists and is hand-authored for all 30 variants `[FACT: onboarding.tsx:67, 80…]` (`api.openai.com/v1`, `localhost:11434`, `<resource>.openai.azure.com`) — into the catalog as its endpoint-display string. It supersedes `endpointHint`; no runtime derivation, no `GetDefaultAPIBase` coupling, and the ollama/vllm/litellm rows keep the host they show today (avoids the R2-03 UX regression). `ProviderCatalogEntry` fields: `id, company, plan, region, wire, label, subtitle, logoSlug, endpointHint`.

  **Drift-guard classification is human-in-the-loop, not machine-derivable (R2-07 clarification).** The alias/CLI/infra vs user-facing partition (the ~31 excluded ids) is a **hand-authored allow-list** in the backend — `knownProtocols` is `map[string]bool`, so company/plan/logo cannot be *derived* from it. The `contract_test.go` guard therefore enforces: "a newly-added protocol ⇒ CI fails until a human triages it into catalog-or-`catalogExcluded`." It catches a *forgotten* id; it **cannot** catch a *mis-classified* one. So this is human-in-the-loop enforcement, not "structural" prevention (see §8 correction).

## 7. Risks and Caveats
- **Trademark — elevated by G-1=B (real marks everywhere):** recoloring LINE / WhatsApp-Meta / Tencent marks contradicts those brands' published guidelines, and OpenAI/Azure/AWS marks were pulled from `simple-icons` over enforcement. This is a **legal, not technical** risk, accepted by the operator for visual uniformity. Mitigations (all mandatory now): (a) the "identification only, no endorsement" disclaimer ships and is load-bearing; (b) marks are used **nominatively** (identifying the provider the operator connects to), never as Omnipus branding; (c) keep the vendored SVGs swappable per-brand so any single takedown request is a one-line catalog edit, not a rebuild. Residual risk remains — flagged, not eliminated.
- **Catalog id-set / drift (G-2=B) — the real hard problem, now bounded (§6 G-2 R1):** the catalog is the **curated ~30 user-facing subset**, not raw `knownProtocols` (61). Drift-guard = the two-property `contract_test.go` assertion in §6 G-2 (every catalog id resolves to a real protocol after alias-normalization; every user-facing protocol is in-catalog-or-explicitly-excluded). The backend-only 31 ids (aliases/CLI/infra) are excluded from the catalog but stay instantiable.
- **New contract surface (G-2=B):** `ProviderCatalogEntry` + `GET /providers/catalog` add wire surface that must go through `scripts/gen-contracts.sh` with the generated diff committed atomically (Constraint #8). Display-string-on-wire tension recorded as the F-07 caveat (§6 G-2) with a localizable split offered to plan-spec. `make verify-contracts` guards drift.
- **Catalog endpoint auth (STRIDE, grill F-08):** `GET /api/v1/providers/catalog` MUST use **`withOptionalAuth`** (it is needed pre-onboarding, exactly like `/providers`), carry **no** credential/config state (only static catalog metadata), and inherit the standard rate-limit. It is a low-severity fingerprinting surface (enumerates connectable providers pre-auth) — acceptable, but the payload MUST be asserted secret-free in the contract test.
- **Picker duplication (G-3=C) — mostly benign given G-2=B:** two picker UIs; **terminology** drift is eliminated (words are catalog data), but **layout/affordance** drift is a manual discipline, not impossible (grill F-15). Documented, accepted as cosmetic.
- **Migration + alias normalization (G-4, grill F-16 + R3/MAJ-004) — THREE cases, all must have a home:** existing configured providers store an id that is one of: **(a) an alias** (`z.ai`, `zai`, `glm-coding`) or region-suffixed id → **normalize to its canonical catalog id first** (alias→canonical table implicit in `knownProtocols`/`GetDefaultAPIBase`) before any fallback, so a valid provider is never demoted to "unknown"; **(b) a known-but-`catalogVisible`=false id that is a legitimate configured provider — the self-hosted/infra set (`litellm`, `ollama`, `vllm`) `[FACT: they have real default hosts, factory_provider.go:508/550/578]`** → these are excluded from the *roster* but are real configured entries, so they MUST render in the configured list under a **"Self-hosted / Custom" group** (with their `endpointHint`), fully functional — NOT demoted to generic-unknown; **(c) a truly unrecognized id** → generic company group + raw id, never crash. The catalog/roster exclusion (`catalogVisible=false`) governs the *empty-state roster* only; it MUST NOT hide an already-configured self-hosted provider.
- **Hard dependency on ADR-029 (grill F-10):** binding-first rows (FR-3, `Workspace → Agent`) and the workspace-first Channel "Connect" flow depend on ADR-029's channel-instance↔workspace binding + mandatory-agent-routing model, which is **still `Proposed`**. Plan-spec should sequence Providers-first or gate the Channels rows on ADR-029.
- **Multi-step Connect-in-Sheet (grill F-10, was "plan-spec detail"):** re-homing the prototype's multi-step Connect flow from a `Dialog` into a `Sheet` is genuinely new interaction design (not a trivial detail). Keep the step model; treat it as an explicit plan-spec design item with its own BDD, not an afterthought.
- **Login removal (FR-9):** verified safe (§1) — but a test should pin that a not-onboarded user still reaches `/onboarding` via `_app` beforeLoad after the button is gone.
- **Big-bang rollback (grill F-19, corrected R2-05):** this redesign replaces two live Settings screens **and** the onboarding model step simultaneously; onboarding is the highest-stakes first-run flow. **There is no SPA feature-flag plumbing** `[FACT: the only `experimental.*` flag pattern is per-agent sandbox config in `pkg/config/sandbox.go` — a backend agent-policy toggle, not a client-side UI gate]`, so "add a feature flag" is **net-new infrastructure, not a cheap known move** — the ADR must not hand-wave it.
