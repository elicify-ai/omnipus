# CSP audit — the embedded SPA's Content-Security-Policy, measured

**Date:** 2026-09-05
**Branch:** `audit/csp-assumptions`
**Scope:** ADR-067 §10.7 / FR-019b — the policy `pkg/gateway/embed.go` serves on every SPA response.
**Verdict:** five of the six documented assumptions **HOLD**. One assumption that was never on the
list is **BROKEN** and has been fixed. A sixth (Shiki) had already been found false and corrected;
it is re-verified here.

---

## Why this audit happened

§10.7 shipped its policy with an unusually honest disclaimer: *"This is a proposal, not a
measurement. Unlike §10.3, no experiment stands behind it."* It then listed six assumptions and the
symptom each would produce if wrong.

One of those six — *"Shiki needs no WebAssembly"* — turned out to be false in **every released
build**. Shiki's default Oniguruma engine is WebAssembly, `script-src 'self'` refuses
`WebAssembly.instantiate`, react-shiki caught the `CompileError` and rendered **nothing** — an empty
box, for every language including `text`. Code blocks did not stop highlighting; the code
disappeared.

The detail that matters most: **the browser console had been naming the policy verbatim the whole
time.** The failure was never hidden. Nobody was reading the console, because no test opened a
browser. That is what this audit fixes, permanently, with `tests/e2e/csp-assumptions.spec.ts`.

## Method

Everything below was driven against the **real artefact**, not against source:

1. `npm run build`, `pkg/gateway/spa/` replaced from `dist/spa/`, and a Go binary built with
   `-tags goolm,stdjson`. The embed was proved to carry that build by grepping the hashed bundle
   name (`index-4Ou71iHy.js`) inside the binary — 40 hits — and by fetching it back over HTTP (200).
2. Gateway started on a free port (6067) with a fresh `OMNIPUS_HOME` (`/tmp/omnipus-csp-home`) and a
   minimal `config.json` carrying `"version": 1`. **`gateway.dev_mode_bypass` was set to `true`** for
   API access during the audit — that is a test-harness setting only, it is not part of any change
   made here, and it must never be true in production.
3. A real Chromium driven by Playwright through each assumption's actual user journey.
4. **Two oracles, never one**: the document's own `securitypolicyviolation` events, and the browser
   console. Both are necessary — see the note below.
5. A **positive control** (test A0) proving both channels fire on a real violation, so a reported
   "zero violations" means *measured* zero rather than *listener never wired*.
6. Every assertion was then **proved able to fail** by mutating the product — not the test — and
   observing red. The mutation table is at the end.

### Why the console is half the instrument

A CSP violation inside a **worker's** realm never reaches the document's `securitypolicyviolation`
listener. During this audit the ICC defect reported exactly this:

```
[violations@pdf-icc] n=0 []
[console:warning] Warning: ICCBased color space: "CompileError: WebAssembly.Module():
  Compiling or instantiating WebAssembly module violates the following Content Security policy
  directive because 'unsafe-eval' is not an allowed source of script in the following Content
  Security Policy directive: "script-src 'self'"."
```

A violation count of zero, next to a console line quoting the policy verbatim. An audit reading only
the structured channel would have closed this as "no violations found".

## The policy under audit

Served on every SPA response (unchanged by this audit):

```
default-src 'self'; script-src 'self'; worker-src 'self' blob:; style-src 'self' 'unsafe-inline';
img-src 'self' data: blob:; font-src 'self' data:; media-src 'self' blob:;
connect-src 'self' stun: turn: turns:; frame-src 'self'; object-src 'none'; base-uri 'none';
form-action 'self'; frame-ancestors 'none'
```

Served on exactly one path — `/pdfjs/pdf.worker.min.mjs` — after this audit: the same string with
`script-src 'self' 'wasm-unsafe-eval'`.

### A1 — "no inline bootstrap script" → white screen at boot

**HOLDS.**

**Journey.** Load `/` and wait for `#root` to mount real content.

**Evidence.** The built `dist/spa/index.html` carries one `<script type="module" src="/assets/...">`
and no inline script. The shell boots to a mounted app (`#root` innerHTML 18,563 bytes) with **zero
`script-src` violations**. In the same session, A0 injects an inline `<script>` under the same policy
and it is refused — so "no violations" here is a measurement, not a dead listener.

**Action.** None. Line annotated MEASURED in `embed.go`.

---

### A2 — "`worker-src` covers the built PDF.js worker URL"

**HOLDS.**

This assumption is dangerous to test naively, and §10.7 says why: *PDF.js does not fail when its
worker is refused — it falls back to parsing on the main thread*, which FR-019c forbids, with a
console warning as the only symptom. "No error" is not evidence.

**Journey.** Open a generated Latin PDF in the Library preview pane.

**Evidence.** The PDF renders (`library-pdf-page` present, 60,711 non-white canvas pixels). The
oracle is Playwright's **own CDP-side view of live workers**, which in-page script cannot fabricate:

```
["http://localhost:6067/assets/ws-parser.worker-Blt2pe6W.js",
 "http://localhost:6067/pdfjs/pdf.worker.min.mjs"]
```

Zero `worker-src` violations. Both the PDF.js worker *and* the app's own `ws-parser` worker are
covered.

**Action.** None. Line annotated MEASURED.

### A2b — the assumption nobody wrote down, and the defect

**BROKEN. Fixed in this audit.**

**The mechanism.** A dedicated worker loaded from a same-origin URL takes its Content-Security-Policy
from **its own response headers**, not from the document that created it. The SPA handler serves
`/pdfjs/pdf.worker.min.mjs`, so PDF.js's parsing worker was running under `script-src 'self'` — and
`script-src 'self'` refuses `WebAssembly.instantiate`.

**Evidence, read inside the worker's own realm** (`worker.evaluate` on the live PDF.js worker,
against the unfixed build):

```
refused: CompileError: WebAssembly.instantiate(): Compiling or instantiating WebAssembly module
violates the following Content Security policy directive because 'unsafe-eval' is not an allowed
source of script in the following Content Security Policy directive: "script-src 'self'".
```

**Why this is a contradiction inside our own build.** `vite.config.ts` ships `pdfjs/wasm/`
deliberately and **fails the build if it is missing**, in its own words:

> `wasm/` missing → a scanned PDF (JPEG 2000 / JBIG2) loses images
> `iccs/` missing → colour profiles are ignored

The policy then refused to let any of it compile. The assets were shipped and unusable. The gateway
serves `qcms_bg.wasm` with a perfectly good `Content-Type: application/wasm` and a header forbidding
its compilation.

**What the user actually got.** PDF.js 6.2.108 ships a JavaScript fallback for two of the three
modules — `jbig2_nowasm_fallback.js` and `openjpeg_nowasm_fallback.js` — reached through a
same-origin dynamic `import()` that `script-src 'self'` permits. So **scanned images still decoded**,
on the slow path, after a wasted fetch-compile-throw per document.

`qcms_bg.wasm` has **no fallback file**. `IccColorSpace.isUsable` compiles it, catches the
`CompileError`, `warn()`s once, and **memoises `false`**. From that point every `/ICCBased` colour
space and every DeviceCMYK colour in every document silently used the crude device conversion
instead of the profile. Nothing blank, nothing thrown — **the colours were simply wrong, in every
released build**, with one console line as the only trace. Print-origin PDFs (overwhelmingly CMYK)
are the common case.

Journey evidence: a generated PDF painting through an `/ICCBased` colour space renders (273,060
non-white pixels — it does not fail), and emits exactly the warning quoted at the top of this
document.

**Library reconfiguration was tried first**, per `embed.go`'s standing rule. PDF.js exposes one knob,
`useWasm: false`. It makes `isUsable` return `false` **without attempting the compile** — identical
wrong colours, minus the one warning that made the defect findable at all. It hides the symptom
rather than fixing the cause, and was rejected for that reason. qcms ships **only** as WebAssembly;
there is no pure-JavaScript qcms, so the move `markdown-shared.tsx` made for Shiki has no analogue.

**Fix — the narrowest one, in two independent dimensions.**

*Scope.* Only the worker script's response carries the widened string
(`spaPdfWorkerContentSecurityPolicy`, `pkg/gateway/embed.go`). The shell, every chunk, every other
asset and the `ws-parser` worker keep the existing policy byte for byte. The main thread still cannot
compile WebAssembly, so **Shiki's pure-JavaScript engine remains a requirement the policy enforces**
rather than a convention. §10.7's "do not add `'wasm-unsafe-eval'` for Shiki" instruction is
unchanged and still binding.

*Keyword.* `'wasm-unsafe-eval'` is **not** `'unsafe-eval'` and does not imply it. It permits
WebAssembly compilation and nothing else — `eval`, `new Function` and string-to-code timers stay
refused inside the worker too. MV-25's directive floor distinguishes the two by substring, and
`TestSpaCsp_WasmKeywordIsNotUnsafeEval` now pins that it does; if that ever stopped being true, this
change would have silently disabled the floor's eval guard.

The worker policy is **derived** from the shell policy rather than written twice, so a directive
added to one reaches the other. The derivation **panics at init** if the directive it edits is
absent: a `strings.Replace` matching nothing would boot happily and serve the worker the policy that
broke it, with test A2b as the only thing that ever noticed.

**Residual risk, stated rather than waved past.** The worker parses hostile PDFs and can now compile
WebAssembly. The bytes it compiles come from three same-origin URLs this build publishes; nothing in
the parser compiles bytes taken from the PDF, so a document cannot introduce its own module. A worker
has no DOM, no cookie access and no ambient authority, and it already runs the full JavaScript
decoders over the same input. The marginal capability is "compile three files we shipped".

**Verification.** Green after fix (worker realm reports `compiled`; ICC document emits no CompileError
warning), red again when the policy branch is disabled and the binary rebuilt.

**Recommendation for the owner:** ADR-067 §10.7's prose should be amended to describe the
worker-scoped policy. The fenced policy block in the spec is unchanged and is still the shell's
policy byte for byte, so `TestSpaServedWithCSP`'s oracle still holds.

### A3 — "Tailwind and Radix need inline styles" → broken layout

**HOLDS, and the allowance was measured *necessary* rather than assumed.**

**Journey.** Boot, `/#/agents`, `/#/settings`, under the shipped policy — zero `style-src`
violations.

**The necessity probe.** The interesting question is not "does the app work with `'unsafe-inline'`"
but "does it *need* it" — an unnecessary relaxation is a security cost with no benefit. The response
header was rewritten in flight to `style-src 'self'` and the same journey re-run. **Settings alone
then reported 13 `style-src-attr` violations**: 12 from `purify.es` (DOMPurify re-applying sanitised
`style=` attributes) and one from React. Under the real policy the same journey reports 0.

**A tightening opportunity, left undone deliberately.** Every violation was `style-src-attr` —
inline style **attributes**. The DOM contained **zero** inline `<style>` elements. So the policy
could plausibly narrow to `style-src-elem 'self'` + `style-src-attr 'unsafe-inline'`, which would
keep the app working while removing the ability to inject a whole stylesheet. That is a real
improvement and it is **not made here**: it needs its own sweep of every screen (this audit exercised
three), and widening-vs-narrowing decisions on a shipped policy deserve their own measurement rather
than riding along with a defect fix. Recorded in `embed.go` so it is not lost.

### A4 — "same-origin WebSocket matches `'self'`" → the live connection silently fails

**HOLDS.**

**Journey.** Boot the app and watch for its live socket; then open one directly and require it to
reach `OPEN`.

**Evidence.** `ws://localhost:6067/api/v1/chat/ws` opens on its own at boot (observed via Playwright's
`websocket` event), and a directly-constructed same-origin `ws://` URL resolves to `open`. Zero
`connect-src` violations. The second oracle matters: a refused WebSocket also constructs without
throwing, so "no exception" would have proved nothing.

**A false RED worth recording.** The first version of this test navigated to `/#/chat` and reported
zero sockets. That is not a route this build serves — the router redirects `/` to the default
workspace's chat, which is where the socket opens. The test was wrong, not the policy. A comment in
the spec records this so the next reader does not re-derive it.

### A5 — "Shiki needs no WebAssembly"

**Was BROKEN; fixed before this audit in the library; re-verified here.**

**Journey.** Open a markdown note containing a fenced `js` block in the Library preview.

**Evidence.** The block renders its text (`const cspAuditMarker8f21 = 1`) with zero WebAssembly or
CompileError console hits. The oracle is the **text**, not the element: react-shiki rendered an empty
`<pre>`, not a missing one, so `toBeVisible()` would have passed throughout the broken period.

**Regression proof.** Reverting `markdown-shared.tsx` to Shiki's default engine and rebuilding
reproduces the original defect exactly — the assertion fails on `toContainText`, i.e. **the code
block is empty**. The guard works.

---

### A6 — "nothing embeds the SPA" → any embedding surface goes blank

**HOLDS — with a caveat that matters more than the verdict.**

**What was measured.** A same-origin page framing `/` is refused, console naming the directive:

```
Framing 'http://localhost:6067/' violates the following Content Security Policy directive:
"frame-ancestors 'none'". The request has been blocked.
```

The frame's `contentDocument` is unreachable and exposes no SPA chrome. FR-006b's control is live and
effective.

**The caveat.** The app's **only** embedding surface — the Library's sandboxed HTML preview frame —
**does not mount in a production build at all**. `LibraryPreviewPane.tsx`'s `PREVIEW_TOKEN_MINTER` is
`null` by design (no `src/lib/api.ts` wrapper for the mint endpoint ships yet), so opening an `.html`
file renders *"Preview unavailable — Rendering it needs the isolated preview endpoint, which this
build does not serve yet"* and the DOM contains **zero iframes**.

So this assumption is true today for a reason that has nothing to do with the policy. When that
minter lands, the frame's `src` is the **isolated preview endpoint** (§10.3's policy, a different
handler) rather than anything the SPA handler serves — so `frame-ancestors 'none'` should remain
correct. A6's second half asserts the current "unavailable" state and carries an explicit instruction
to extend it rather than delete it when the minter ships.

### NOT TESTED — `connect-src`'s `stun:` / `turn:` / `turns:` sources

Exercising these needs a live WebRTC session against a real ICE server and the agent's own managed
Chrome. **Blocker:** out of reach of this harness, which drives a Playwright browser against a
gateway with no browser-tool session running.

Their only measurement remains §10.7's 2026-08-23 amendment — which is itself worth re-reading,
because it contains a **self-correction**: the amendment first blamed `connect-src 'self'` for a CI
failure and was wrong; widening the directive changed nothing and the real cause was a navigation
refusal. The scheme sources stand on their own merits (`browserWebRTC.ts` configures
`stun:stun.l.google.com` unconditionally), not on that diagnosis.

Reported as NOT TESTED. Not reported as passing.

## Other limits of this audit

* **Chromium 151 only.** §10.7's freeze condition is a headed run on Chromium, **Firefox and
  Safari**. Engines genuinely differ on CSP. This audit does not discharge that condition and the
  `embed.go` comment says so.
* **`img-src`, `font-src`, `media-src`, `object-src`, `base-uri`, `form-action`** were not given
  dedicated journeys. They produced zero violations across every screen visited, which is weak
  positive evidence, not a measurement of each directive's necessity or sufficiency.
* The audit ran with `dev_mode_bypass: true`. Nothing measured here depends on the auth mode, but it
  is stated so the run is reproducible and so the setting is not mistaken for a recommendation.

## Proof that the tests can fail

A security assertion nobody has watched go red is an assertion about nothing. Every test in
`csp-assumptions.spec.ts` was made to fail by mutating **the product** and rebuilding — never by
intercepting the request, because an interception that misses reports green and looks like strictness
(a trap `preview-pdf.spec.ts` already records hitting).

| Test | Mutation | Observed |
|---|---|---|
| A0 | CSP header not sent at all | RED — inline script executed |
| A1 | inline `<script>` added to `index.html`, SPA rebuilt | RED — `script-src` violation |
| A2 | `worker-src 'none'` | RED — no PDF.js worker among live workers |
| A2b | worker policy branch disabled | RED — worker realm reports `refused: CompileError` |
| A2b | *(original, pre-fix build)* | RED — same, before any mutation |
| A3 | `style-src 'self'` | RED — `style-src-attr` violations |
| A4 | `connect-src https://csp-mutation.invalid` | RED — socket never opened |
| A5 | Shiki's default WASM engine restored, SPA rebuilt | RED — code block **empty** (`toContainText`) |
| A6 | `frame-ancestors 'self'` | RED — the SPA framed successfully |

Each mutation verified as actually applied (`git diff` non-empty, plus the served header re-read over
HTTP) before its result was believed, and reverted by file copy afterwards. The working tree was
confirmed byte-identical to `HEAD` at the end.

## Changes made

* `pkg/gateway/embed.go` — `spaPdfWorkerContentSecurityPolicy` + `withWasmCompilation` +
  `pdfJSWorkerPath`, the one-path handler branch, and every assumption line rewritten to state
  MEASURED with date, method and verdict.
* `pkg/gateway/embed_csp_test.go` — four tests pinning the worker policy, its derivation, the
  keyword distinction, and the worker filename against `vite.config.ts` and the SPA.
* `tests/e2e/csp-assumptions.spec.ts` — the instrument: eight tests plus a positive control.
* This report.

**Not changed:** the shell policy, the ADR-067 spec's fenced policy block, and anything under
`pkg/records`, `pkg/knowledge` or the view-kinds Go surface.
