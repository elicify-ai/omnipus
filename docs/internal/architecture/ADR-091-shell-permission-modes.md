# ADR-091 — Shell permission modes: Ask / Auto / God Mode; drop the block list; one rule format

- **Status:** Proposed (founder-approved decisions incl. UI, 2026-09-23)
- **Date:** 2026-09-23
- **Deciders:** Daniel Piatkowski (founder, ratifying decision); architect (design, drafting)
- **Supersedes-in-part:** [ADR-036 — Consolidate shell and subagent tools](./ADR-036-consolidate-shell-and-subagent-tools.md) §3.1's deny-pattern axis ("on by default... layered with the operator-extensible custom-pattern mechanism") and its "one approval flow" decision (still valid; this ADR adds the mode selector in front of it, does not reopen it).
- **Extends:** [ADR-077 — Two-layer tool-policy model](./ADR-077-two-layer-tool-policy-remove-fail-closed-backfill.md) — the three modes select which value the `bash` tool policy resolves to at Layer 1; the two-layer ceiling/override model itself is untouched.
- **Evidence baseline:** `release/v0.1.1` @ `838d8092c` (worktree `wt-release-session`), read-only. Findings cited below trace to three lane reports written against this same commit: the as-is call-chain trace, an industry comparison against Claude Code and Codex CLI, and a re-verification of issue #83 and its "Additional" claim.

## Context

### The problem: six mechanisms, no single story

A `bash` call today passes through, in fixed order: (1) a hardcoded ~38-regex deny list (`defaultDenyPatterns`, `pkg/tools/shell.go`) that cannot be disabled and is unconditional even under God Mode; (2) a structural command-substitution guard (`pkg/tools/shell_subst_guard.go::substitutionGuard`); (3) operator-configured deny patterns, global (`config.SandboxConfig.ShellDenyPatterns`) and per-agent (`config.AgentShellPolicy.CustomDenyPatterns`/`EnableDenyPatterns`), both opt-in and off by default; (4) a command-text path-containment scan with an ADR-068 read/write carve-out (`pkg/tools/shell_path_guard.go::guardCommand`); (5) a per-binary exec allowlist that is a no-op unless an operator configures `security.policy.exec.allowed_binaries` (`pkg/policy/evaluator.go::EvaluateExec`); and, earlier in the agent loop, (6) the ADR-077 tool-policy verdict for the tool name `"bash"` itself (global ceiling × per-agent override, strictest wins — default `allow`, so by default nothing above even fires an approval dialog).

None of these six is redundant by design; they accumulated independently across several ADRs (ADR-036, ADR-068, the v0.2 #155 hardening pass) and nothing coordinates between them or explains, to an operator or a founder, what actually stops a destructive command in each mode. Mechanisms 1 and 3 share the same fundamental weakness: they are regexes over lowercased raw command text, and the code's own comment states it plainly — "a list of phrasings, not a judgement about the act." They are defeated by mid-token quoting (`r'm' -rf /`), `$IFS`-based whitespace substitution (`rm${IFS}-rf`), or simple variable indirection (`X=rm; $X -rf /`) — none of which changes what the shell executes, all of which changes what the regex sees. Where a kernel sandbox is present and enforcing (Linux 5.13+, Landlock), it is the real boundary for *where* files can be touched; the deny-pattern layer is the only thing standing between an agent and a destructive *phrasing* against files the kernel would otherwise allow it to touch (`rm -rf .` inside its own already-permitted workspace) — and that is the bypassable layer.

### GitHub issue #83, and its correction

Issue #83's headline claim — "Always Allow" on one command silently grants every future invocation of that binary with any arguments — traces in the codebase to `pkg/security/execapproval.go::ExecApprovalManager` (`CheckApproval`, `PersistPattern`, `matchAllowlistPattern`). Re-verification against `838d8092c` confirms the code still behaves exactly as the issue describes *in that file* — but also confirms `ExecApprovalManager` has **zero production callers anywhere in the repository**; it is referenced only by its own package's tests. Its answering frontend (`ExecApprovalBlock`/`ExecApprovalTool`) and its gating WebSocket frame were deleted by ADR-036 §3.4, which relocated grant consultation to `pkg/security/approvalgrants.go::ApprovalGrantStore` instead. The issue's headline finding is real code with the behavior described, but the code is dead — no chat session reaches it. The **live** "Always Allow" mechanism (`ApprovalGrantStore.Record`) does not have this defect: it fingerprints the entire args object (`command`, `cwd`, `run_in_background`, …) per `(session, agent, tool)`, in memory only, so a differently-worded command does not silently match an old grant.

Issue #83's *second*, "Additional" claim is a different code path and is confirmed **still live**: the operator's opt-in exec allowlist (`pkg/policy/evaluator.go::EvaluateExec`) matches the raw command string against configured glob patterns with no call to `exec.LookPath`, `filepath.Abs`, or symlink resolution anywhere in the match path — an approved pattern like `"git *"` says yes to `git evil-script` without ever checking which file named `git` is about to run. Given an attacker who can place a file earlier on `PATH` than the trusted binary directories, or symlink over an allowed name, the allowlist provides no defense. Decision D3 below closes this gap directly.

### Why simplify now

Six independently-evolved mechanisms with no shared vocabulary is not a security posture, it is an audit liability: neither an operator configuring the system nor a founder answering "what actually stops this" can give a one-sentence answer. Anthropic's own Claude Code and OpenAI's Codex CLI — surveyed for this ADR — independently reached the same conclusion: neither ships a curated "dangerous command" deny list, and both say so explicitly. Claude Code's docs state outright that "Bash permission patterns that try to constrain command arguments are fragile" and point to the OS-level sandbox as the actual boundary. Codex ships no default `execpolicy` rules at all and instead intercepts `execve(2)` at the syscall level. Both treat their text-level rule engines as UX friction-reducers, not security boundaries, and both give deny an unconditional trump card over allow regardless of rule specificity. This ADR adopts that posture for Omnipus.

## Decisions

### D1 — Three modes: Ask, Auto, God Mode

Every bash-capable context resolves to exactly one of three modes (scope: global, per-agent, per-chat — see the three-level merge below and UI presentation):

- **Ask** — every shell command shows the approval dialog. No auto-run.
- **Auto** (the default for fresh installs) — commands run without asking while the kernel sandbox confines them; anything needing more than the sandbox allows asks. Where no kernel sandbox is active — Windows (`pkg/sandbox` has no Windows backend today), or the Linux/macOS app-level fallback (Landlock unavailable, or `sandbox.mode = "off"`) — **Auto behaves like Ask**. This matches the as-is behaviour matrix's own finding: on a fallback platform the app-layer guards are "the only thing standing between the agent and the filesystem/network," so Auto must not silently trust them the way it trusts a real kernel boundary.
- **God Mode** — no approvals, no kernel sandbox, no network egress filter. This is the existing `sandbox.GodMode` field (`pkg/config/sandbox.go`), gated as today behind availability (`--allow-god-mode` or the persisted `GodModeAllowed` grant) and a build tag. This ADR does not add a new bypass switch; it renames the operating posture already implemented and clarifies exactly what it turns off (D6).

**Mode applies at three levels, tighten-only below the global default** (founder UI decision, 2026-09-23), mirroring ADR-077's own ceiling/tighten philosophy:

- **Global default** — Settings → Security (`SecuritySection.tsx`). Sets the operating mode for the whole install. God Mode is **global-only** — it does not appear as a per-agent or per-chat choice — and keeps its existing password step-up (`sandbox.GodModeAllowed`, unchanged).
- **Per-agent** — the agent's Tools & Permissions screen (`ToolsAndPermissions.tsx`) may set a mode **only stricter** than the global default (e.g. global Auto → this agent Ask). It cannot loosen below the global default (an agent cannot set Auto or God Mode when the global default is Ask); God Mode is not offered here at all.
- **Per-chat** — a quick switch in the chat composer ("`[Auto ▾]`") may tighten **further, for that chat only** (e.g. global Auto, agent Auto, this one chat Ask). Same rule: it can only tighten, never loosen, and never offers God Mode.

**Loosening below the global default is not possible at any lower level — that is the rule, stated once here and not repeated at each level below.** Architecturally, the per-chat quick switch is **not** a third entry in ADR-077's two-layer tool-policy maps (Hard Constraint #6: "two layers, no third" is non-negotiable) — it is a session-scoped resolution modifier, applied *after* the existing global-ceiling × per-agent-override merge resolves the `bash` policy value, in the same structural sense that `ApprovalGrantStore` already sits outside the two-layer model as a session-scoped store consulted only once policy resolves to `"ask"`. Implementers must not add a `chat_id` key to `cfg.Sandbox.ToolPolicies` or `AgentConfig.Tools.Builtin.Policies` to carry this; it is new, separate, session-keyed state.

**In all three modes**, the audit log, the prompt-injection guard, and rate limiting stay on. Verified against the as-is trace: God Mode's own field comment already states these three are NOT disabled ("those defend against external threats, not agent freedom") and the call-chain evidence confirms `emitAuditOrDeny`, the guard chain, and rate limiting are not conditioned on `godMode` anywhere in `executeRun`. Nothing in this ADR changes that.

**Operator-authored allow/deny rules stay in force in God Mode**, matching Claude Code's own managed-deny-rule precedent (a managed `deny` rule is the one thing no mode, including `bypassPermissions`, can override). This is consistent with — and narrower than — today's actual behaviour: the as-is trace shows God Mode already floors only the *operator's global ceiling* to `allow`, while an agent's own explicit per-agent tightening (e.g. Judge's `bash: deny`) still resolves under ADR-077's strictest-wins merge. D1 does not change that resolution order; it restates it under the new mode vocabulary and extends it to the new unified rule format (D3).

### D2 — Drop the built-in shell block list entirely

`defaultDenyPatterns` (`pkg/tools/shell.go`, ~38 regexes — this variable already includes `secretGuardPatterns`, appended at package-init time: `append([]*regexp.Regexp{...38 patterns...}, secretGuardPatterns...)`, so dropping `defaultDenyPatterns` drops both in one motion) and the per-agent `AgentShellPolicy.CustomDenyPatterns`/`EnableDenyPatterns` machinery are removed outright — not disabled, not left dormant behind a flag.

**Rationale:** text patterns over a real shell are bypassable by construction (mid-token quoting, `$IFS` substitution — see Context); Claude Code's own docs call this class of rule "fragile"; neither Claude Code nor Codex ships one; the kernel sandbox is the real boundary where one exists. The regex secrets backstop (`secretGuardPatterns`) is, by its own in-code comment, "a backstop over a boundary the kernel sandbox already enforces" — the secret files it names (`master.key`, `credentials.json`, `config.json`, `cli.token`, `auth.json`, backups) live under `~/.omnipus/`, outside any agent workspace, so where a kernel sandbox is active it already denies filesystem access to them independent of command text.

**Architectural resolution, not a separate founder instruction:** the global `sandbox.shell_deny_patterns` field (`config.SandboxConfig.ShellDenyPatterns`) is not named in the founder's list above, but leaving it in place as a second, parallel regex mechanism alongside D3's new unified rule format would recreate exactly the "six mechanisms, no shared vocabulary" problem this ADR exists to close. Reading D2 together with D3's "one rule format," this ADR retires `ShellDenyPatterns` as well: an operator who wants to block a command family expresses it as a `deny` rule in the new format (D3), not a regex. `[INFERRED — flagging this bridge explicitly since the founder's list named the per-agent fields, not this one, by name.]`

**Accepted residual risk, stated plainly:** on Windows (no kernel sandbox exists at all today) and inside an agent's own workspace (where the sandbox, when present, permits deletion by design), nothing in this ADR blocks a destructive command in God Mode, or in Auto running without a kernel sandbox. Auto's fallback to Ask (D1) is the compensating control for the second case; God Mode's inherent posture — no approvals, no sandbox — is the accepted trade of the first, exactly as it is today (God Mode is opt-in, gated, and already documented as removing containment). Nothing about this ADR makes God Mode more dangerous than it already is; it removes a bypassable regex layer that, on the evidence above, was providing a false sense of coverage rather than real containment.

**What survives, decided per guard from the as-is evidence:**

| Guard | Mechanism | Fate |
|---|---|---|
| `defaultDenyPatterns` (~38 regexes + `secretGuardPatterns`) | Regex over lowercased raw text | **Dropped** |
| Per-agent `custom_deny_patterns`/`enable_deny_patterns` | Regex, opt-in | **Dropped** |
| Global `sandbox.shell_deny_patterns` | Regex, opt-in | **Retired**, folded into D3's unified rule format (see bridge above) |
| Structural command-substitution guard (`pkg/tools/shell_subst_guard.go::substitutionGuard`) | Tokenizes `$(...)`/backticks, judges command position, not blanket-refusing | **Survives unchanged** — it parses structure, not text-matches phrasing; the founder's task brief names it explicitly as a survivor |
| Path-containment / secret-exclusion guard (`pkg/tools/shell_path_guard.go::guardCommand` step 4, `inTurnSecretSet`, the ADR-068 read/write classification) | Tokenized absolute-path scan with a proven-read exemption | **Survives unchanged** — tokenized, not regex-over-phrasing; named explicitly as a survivor |
| Per-binary exec allowlist (`pkg/policy/evaluator.go::EvaluateExec`) | Opt-in, raw string match | **Retired, folded into D3** — decision logic replaced; `PolicyAuditor.logDecision`'s audit write survives, retargeted |
| ADR-077 `bash` tool policy (allow/ask/deny) | Global ceiling × per-agent override | **Survives** — now selected via the three modes, see D1/Consequences |
| Session "Always Allow" grant store (`pkg/security/approvalgrants.go`) | In-memory, exact-args fingerprint | **Survives, extended** — see D4 |

### D3 — One rule format and one decision order

Operator-authored rules (allow/deny) and user "Always allow" grants (D4) share one rule format and one resolution order:

- **Order: deny beats ask beats allow, regardless of specificity.** A broad `deny` on a binary is not defeated by a narrower `allow` elsewhere, matching Claude Code's own stated precedence rule verbatim ("the first match in that order determines the outcome, and rule specificity doesn't change the order") and consistent with ADR-077's existing strictest-wins merge for tool policy generally.
- **Chained commands are split before matching.** `&&`, `||`, `;`, `|`, and newlines are split using the **existing** shell tokenizer already in the tree — `pkg/tools/shell_subst_guard.go::splitShellSegments` and `shellCommandHead` — no new parser. Each resulting segment must independently be allowed (by rule or by default posture), or the whole call asks. This mirrors Claude Code's documented behaviour ("a rule must match each subcommand independently") and closes the same class of gap: an allow rule for `npm test` must not silently also allow `npm test && curl evil.com`.
- **Resolve the real binary before matching.** Each segment's leading token is resolved to its actual executable (absolute path via `exec.LookPath` or equivalent) before any rule — operator or grant — is evaluated against it. This directly closes the still-live PATH/look-alike-binary finding against `EvaluateExec` (issue #83's "Additional" claim): a `deny`/`allow` rule written against `git` must bind to the `git` that will actually run, not merely a string that starts with the four letters `g-i-t`.
- **The pre-existing operator exec allowlist is folded into this format, not kept as a second engine.** `pkg/policy/evaluator.go`'s `Evaluator.EvaluateExec`/`MatchGlob`/`FirstToken` — the opt-in, raw-string-matching allowlist keyed on `security.policy.exec.allowed_binaries` — is retired as a standalone decision path. An operator's configured allowlist entries become `allow` rules in the D3 format instead, evaluated with the same resolved-binary/segment matching every other rule uses. Running D3's new engine *alongside* the old glob-matcher would recreate exactly the "six mechanisms" problem this ADR exists to close (grep-verified: `Evaluator.EvaluateExec` has exactly two production callers, both inside `pkg/policy`'s own `PolicyAuditor.EvaluateExec`/`pkg/tools/shell.go`, and `FirstToken`/`MatchGlob` have no callers outside `pkg/policy/evaluator.go` and the already-dead `pkg/security/execapproval.go` — nothing outside the exec-allowlist path depends on this file, so folding it in is safe to do completely). `PolicyAuditor.logDecision`'s audit-log write is preserved, retargeted to log the D3 engine's decision instead of `Evaluator`'s — the audit trail does not go away, only the decision logic it logs.

This is new engine work, not a config flag: the new rule matcher needs the resolved-path step and the segment splitter as a new caller (the splitter's existing callers are the substitution guard, not this).

### D4 — Approval dialog: three buttons, a scope choice, chained commands shown per part

The approval dialog (`src/components/agents/ToolApprovalModal.tsx` — verified path; the coordinator's shorthand named a `chat/` location that does not exist in the tree) is **[Deny] [Allow once] [Allow]** (founder UI decision, 2026-09-23) — replacing today's four-button `Approve`/`Deny`/`Always Allow`/`Cancel`:

- **Deny** — refuses this call. No grant recorded.
- **Allow once** — approves this one call. No grant recorded — functionally today's `Approve`, renamed to make the one-shot nature explicit against the new `Allow` option below.
- **Allow** — approves this call **and** records a session-scoped grant (`ApprovalGrantStore`, in memory only, wiped at session close — unchanged from today's mechanism), with a scope choice presented **above** the three buttons:
  - **"(•) exactly this command"** (default, pre-selected) — today's exact-args fingerprint behaviour, unchanged.
  - **"( ) anything starting with `<suggested prefix>`"** — the new prefix grant, a `{binary, arg_prefix}` rule in D3's unified shape, scoped to the session instead of globally or per-agent. The suggested prefix is computed server-side (binary + leading argument tokens up to the point genuine variation is expected — exact derivation is an implementation detail, not decided here) and shown, not freely typed.

The dialog shows the command and its working folder (`cwd`) — matching today's `BashApprovalPreview.tsx` behaviour — and, for a chained command (D3's segment split), **lists each part separately** rather than showing the raw compound string as one block, so the user can see what each segment resolves to before choosing a scope.

**There is no `Cancel` button** in the new three-button design; Escape/overlay-click/X resolve to `Deny` as they do today (default-deny-on-dismiss is unchanged — Deny remains the default keyboard focus target).

Network tools getting a per-website "always allow this domain" option is **future work, not decided here** — flagging explicitly per the founder's own note, not inferred.

**Session grants are not shown anywhere** (founder UI decision, 2026-09-23) — no list, no chip, no "manage grants" surface. A recorded grant is invisible after the moment it is created; it simply stops future matching calls from prompting for the rest of that chat session, and ends with the chat exactly as `ApprovalGrantStore.ClearSession` already does today. **Explicit consequence:** a user who grants "Allow" and changes their mind mid-chat cannot revoke it except by starting a new chat — there is no in-session undo. This is recorded as a deliberate trade (see Consequences → UX), not an oversight.

### D5 — Delete the dead code

`pkg/security/execapproval.go` (`ExecApprovalManager`, `PersistPattern`, `matchAllowlistPattern`, `NewExecApprovalManager`, `WithAllowlistFile`) and its dedicated test file (`pkg/security/execapproval_test.go`) are deleted outright — definition and all, no deprecation shim, no retirement comment left in its place beyond what CI guard scripts require elsewhere in this repo (house precedent: ADR-037, ADR-061, ADR-077 D3/D6, ADR-088 D9). It has zero production callers today (confirmed by repo-wide grep) and answers a UI flow (`ExecApprovalBlock`/`ExecApprovalTool`) already deleted by ADR-036. Leaving fully-tested, fully-implemented dead code with the exact defect issue #83 describes sitting in the tree is itself a liability — a future reader could re-wire it "to fix #83" and reintroduce a reachable version of the bug this ADR is explicitly not shipping.

### D6 — Fix God Mode's code comment

`pkg/config/sandbox.go`, the `GodMode` field doc comment currently states God Mode forces "shell guard / deny-patterns off." This is stale against actual behaviour: the as-is trace confirms `guardCommand` (guards 1–4, pre-D2) runs **unconditionally in `executeRun` regardless of `godMode`**, and only the **per-agent** custom deny-pattern list is explicitly dropped under God Mode (`agentShellPolicy = nil // drop per-agent deny patterns under god mode`, `pkg/agent/loop_wire.go`) — the global list was never gated on God Mode. Post-D2, with the block list gone entirely, the comment is rewritten to describe exactly what remains true: God Mode floors every agent's effective tool policy at `allow` (operator/per-agent `deny` rules under D3 still apply, D1), forces the kernel sandbox off, forces network egress open, and does **not** disable the audit log, the prompt-injection guard, or rate limiting. No behavioural change beyond D1–D3; this is a documentation-accuracy fix on a field whose actual runtime behaviour is otherwise unchanged by this ADR.

## Consequences

### Security

- Removes a text-pattern layer that was bypassable by construction and, per its own in-code comment, largely redundant with the kernel sandbox — while making the one thing that actually held (the kernel boundary, where present) the explicit story, not an implicit one buried under five other checks.
- Closes issue #83's live "Additional" claim (PATH/look-alike-binary evasion against `EvaluateExec`) via D3's resolve-before-match step.
- Makes issue #83's headline claim explicitly moot going forward by deleting the dead code it was filed against (D5), removing the risk of a future "fix" reintroducing it.
- Accepted, stated risk: on Windows and in agent-workspace-local destruction under God Mode/sandbox-less Auto, no text-pattern layer remains to slow a destructive command down. This is the same trade Claude Code and Codex made and documented; Omnipus now documents it the same way instead of relying on a bypassable regex to appear to cover it.

### UX

- One mode selector (Ask/Auto/God) replaces reasoning about six independent, uncoordinated mechanisms with different defaults and different opt-in postures.
- Fewer prompts for the common case (Auto, the new fresh-install default) while keeping every prompt that does fire meaningful — it fires because the sandbox genuinely could not confine the action, not because a regex matched an incidental phrase.
- The prefix "always allow" option (D4) closes a real friction gap: today, an "Always Allow" grant on `npm run test -- --watch` does not cover `npm run test -- --coverage`, because the grant fingerprints the entire args object. A prefix grant, evaluated per D3's segment/binary-resolved shape, covers the family the user actually meant.
- **Accepted trade, stated explicitly (founder UI decision):** session grants are not shown or listable anywhere in the UI (D4). A user cannot review what they have silently approved for the rest of the current chat, and cannot revoke a specific grant mid-chat — the only way to undo an "Allow" is to end the chat and start a new one, which also clears every other grant made in that session, not just the one the user wanted to revoke. This is a real usability and auditability gap relative to Claude Code's `/permissions` (which lists every saved rule and its source file); it is accepted here because Omnipus's grants are session-only and already self-expire at chat end, unlike Claude Code's durable per-repository rules.

### Migration

**Greenfield, no upgrade path** (founder ruling, established elsewhere in this repo — matching ADR-088's identical "Migration: NONE — greenfield (operator directive)" precedent). `sandbox.shell_deny_patterns`, `AgentShellPolicy.CustomDenyPatterns`, and `AgentShellPolicy.EnableDenyPatterns` are removed from the config schema, not deprecated and not migrated forward into D3's new rule format automatically. An operator who configured these on `release/v0.1.1` gets a clean config on next load with those keys silently dropped (unknown-field tolerance, matching the existing config-load behaviour for retired keys) — not an error, not a silent behavioural promise that the old patterns still apply under a new name. Operators who want equivalent coverage re-author it as D3 rules after upgrade. This is a real, stated behaviour change on upgrade, not a bug: it is the explicit trade of removing a bypassable mechanism rather than translating it forward.

### Interaction with ADR-077

ADR-077's two-layer model (global ceiling × per-agent override, strictest-wins, `bash` defaults `allow` at the ceiling) is the resolution mechanism this ADR sits on top of, not a mechanism it replaces. The three modes (D1) are the **selector** for what the `bash` ceiling resolves to:

- **Ask** sets the effective `bash` policy to `"ask"` — the existing ADR-077 verdict, unchanged mechanically; `CheckGrantOrRequestApproval` fires exactly as it does today.
- **Auto** sets the effective `bash` policy to `"allow"` (today's shipped ceiling default, unchanged), **plus new escalation behaviour**: when the kernel sandbox would deny an action a command attempts, that specific action routes to the same approval flow `"ask"` uses, rather than hard-failing. This is genuinely new engine work — not a config flip — comparable in scope to Codex's sandbox-escalation-to-approval design and to ADR-088 D3's own "this is a BUILD, not a flip" framing for an analogous prior change.
- **God Mode** floors the global ceiling at `allow` for every tool — this is exactly today's already-implemented behaviour (`GodMode` field), unchanged by this ADR except for the comment fix (D6) and the explicit statement that operator/per-agent `deny` rules under D3 still apply on top of that floor (D1), consistent with the as-is finding that per-agent overrides already survive God Mode today.

Per-agent tightening (an agent with an explicit `bash: deny` or `bash: ask`, e.g. Judge, verifier agents) continues to resolve under ADR-077's existing strictest-wins merge regardless of mode — a mode is a ceiling-level default selector, not a bypass of per-agent tightening. The mode's own scope question is now resolved (D1, founder UI decision): global default (Settings → Security) sets the ADR-077 ceiling-equivalent; a per-agent mode override (Tools & Permissions) may only tighten it, using the identical strictest-wins semantics ADR-077 already defines for per-agent tool-policy overrides generally; a per-chat quick switch may tighten further still, for that one chat, as a session-scoped modifier applied after the two-layer resolution rather than as a third policy-map layer (see D1's explicit note on Hard Constraint #6).

## UI presentation (founder-decided, 2026-09-23)

- **Mode choice at three levels, tighten-only below the global default** (D1): global default in Settings → Security (`SecuritySection.tsx`, `GodModeControl.tsx` — God Mode is global-only and keeps its existing password step-up); a per-agent setting in Tools & Permissions (`ToolsAndPermissions.tsx`) that can only tighten (e.g. Auto → Ask); a per-chat quick switch in the chat composer ("`[Auto ▾]`") that can also only tighten, for that chat only. Loosening below the global default is not offered at any lower level — the control itself should not present a looser option, not merely reject one on submit.
- **Approval dialog** (`ToolApprovalModal.tsx`): three buttons — **[Deny] [Allow once] [Allow]** — with a scope choice above the buttons, shown only when `Allow` is the live focus/selection: **"(•) exactly this command"** (default) or **"( ) anything starting with `<suggested prefix>`"**. Shows the command and its working folder; for a chained command, lists each part separately rather than one raw compound string (D4).
- **Session grants are not shown anywhere** — no list, no chip, no management surface. They end with the chat; there is no mid-chat revoke (D4, Consequences → UX). Do not build a grants list as a "nice to have" — it is an explicit non-feature, not an oversight to fill in later.
- **Status signals:**
  - **Chat header mode badge** — shows the effective mode for the current chat. When Auto has no kernel sandbox active, the badge reads **"Auto → Ask"** with an info tooltip: *"No kernel sandbox on this system — commands will ask."* The badge must reflect the resolved, effective mode (after the three-level tighten-only merge), not just whichever level the user last touched.
  - **God Mode banner** — a persistent, red, app-wide banner ("**God Mode is on — agents run without sandbox or approvals**" + **[Turn off]**) shown in `AppShell` for as long as God Mode is on, everywhere in the app, not scoped to one chat — consistent with God Mode being global-only (D1).
- **Contract requirement:** the badge's data (effective mode, whether a kernel sandbox is actually active) must come from a contract-defined status field, per Hard Constraint #8 — not inferred client-side from separately-fetched config and platform-detection logic. See Implementation outline step 1.
- **Design system:** every new/changed component above is subject to `.claude/skills/omnipus-design-system/SKILL.md` — load it before touching `ToolApprovalModal.tsx`, the composer, the chat header, or `AppShell`; the banner and mode badge in particular must use the design system's existing tokens for a persistent alert state rather than inventing new colors/spacing for God Mode's red banner.

## Test plan

- Segment splitting and binary resolution (D3): compound commands, mid-segment substitution, look-alike-binary PATH evasion (regression test directly reproducing issue #83's "Additional" claim, asserting it now fails to auto-approve).
- Mode resolution (D1): Ask/Auto/God Mode → correct `bash` ceiling value; Auto with no kernel sandbox behaves identically to Ask; God Mode floors the ceiling but does not defeat an explicit per-agent or D3 operator `deny`.
- Auto sandbox-escalation path: a sandbox-denied action under Auto routes to the approval flow rather than a hard failure; a sandbox-permitted action under Auto runs with no prompt.
- Always-Allow grants (D4): exact-command grant behaves as today; new prefix grant matches a family of commands and does not match outside the declared prefix; session scope and in-memory-only lifetime unchanged.
- Deletion regressions: `defaultDenyPatterns`/`secretGuardPatterns` removal does not regress the surviving guards (substitution guard, path/secret-exclusion guard) — each guard's own existing test suite continues to pass on the reduced guard chain.
- Audit/injection-guard/rate-limiting invariance: confirm these three fire identically across all three modes, including God Mode (regression against the as-is finding that they are not currently gated on `godMode`).
- Config load: a `release/v0.1.1`-shaped config with the retired deny-pattern and exec-allowlist fields loads cleanly with no error and no silent behavioural promise that the old patterns still apply.
- Fresh-install default: confirm Auto is the shipped default mode and resolves `bash` to `allow` at the ceiling, matching today's shipped default value.
- Three-level mode merge (D1): global default sets the floor; a per-agent override that attempts to *loosen* below the global default is rejected (not silently clamped, not silently accepted); a per-chat quick switch that attempts to loosen is rejected the same way; a per-chat tighten applies for that chat only and does not leak to a second chat with the same agent.
- Approval dialog (D4): `Allow once` records no grant (a second identical call re-prompts); `Allow` with "exactly this command" behaves as today's exact-fingerprint grant; `Allow` with the prefix option matches a family of commands sharing the prefix and does not match outside it; a chained command's dialog lists each part.
- Status signals: chat header badge reflects the resolved effective mode, not the last-touched level; the badge reads "Auto → Ask" with the info tooltip specifically when Auto is selected but no kernel sandbox is active (not merely whenever Auto is selected); the God Mode banner appears in `AppShell` app-wide (not scoped to one chat) the instant `GodMode` turns true and its `[Turn off]` control actually clears it.

## Open questions

*(Resolved by the founder's 2026-09-23 UI decision, no longer open: mode selector scope — three levels, tighten-only, D1; exec allowlist's relationship to D3 — folded in, Removal inventory item 3.)*

1. **`config.ExecConfig.Approval` (`tools.exec.approval`) and `pkg/gateway/rest_exec.go`** — discovered live during this ADR's verification pass (Removal inventory item 4), wired into `SecurityConfig` construction and a REST handler, shaped like a pre-ADR-036 approval surface (`"ask"`/`"off"`, not today's allow/ask/deny vocabulary). Is this genuinely reachable and load-bearing today, or a second piece of dead code adjacent to `execapproval.go` (item 2) that the as-is investigation did not happen to trace? Needs its own reachability check (Definition of Done: is it registered/callable, not just present) before implementation decides whether it is deleted alongside item 2 or folded into D1's mode resolution.
2. **Auto's sandbox-denial detection mechanism** — is "this command needs more than the sandbox allows" detected as a pre-flight predictive check (the app-layer guards evaluate the same filesystem policy the kernel will use, before spawning), or as a runtime catch of the sandbox's actual denial (analogous to Codex's `execve` interception and `Escalate` verdict, converting a kernel-level deny into a retry-with-approval)? These have materially different implementation costs and different false-positive/false-negative profiles; not resolved by the founder's decisions and not obviously implied by existing code.
3. **"Exact" grant scope under the new model** — today's Always-Allow grant fingerprints the *entire* args object (`command`, `cwd`, `run_in_background`, …), so an incidental `cwd` change re-prompts even for identical command text. Under D3's binary/segment-scoped rule shape, should "exact" narrow to command text only (a real behaviour change: broader silent auto-approval across `cwd` changes) or keep today's full-args fingerprint as the "exact" tier and add prefix as a genuinely new, looser tier? Not resolved by the founder's decisions.
4. **Per-segment prefix grants** — does a single "Allow… as a prefix" choice on a compound command produce one rule scoped to the whole compound string, or one rule per segment (mirroring Claude Code's "up to 5 rules per compound approval")? The dialog now shows each chained part separately (D4), which suggests per-segment, but the founder's decision does not say so explicitly — affects both the grant-store shape and the dialog's exact interaction design.
5. **Suggested-prefix derivation** — the dialog's "anything starting with `<suggested prefix>`" option (D4) needs a concrete algorithm for computing the suggested prefix from a given command (binary + how many leading argument tokens). Not specified by the founder's decision; an implementation detail with real UX consequences (too short over-grants, too long is useless).

## Alternatives considered

**Keep the block list as a lower-priority, always-off-by-default layer.** Rejected — a disabled-by-default mechanism that operators can still turn on reintroduces the same false sense of coverage this ADR removes, and every vendor surveyed rejected this shape outright rather than defaulting it off.

**Migrate `ShellDenyPatterns`/`CustomDenyPatterns` forward into D3's rule format automatically.** Rejected under the greenfield/no-upgrade-path ruling — an automatic translation of a bypassable regex into a "real" rule would misrepresent the new rule's actual coverage (a regex pattern and a resolved-binary/segment rule are not equivalent, so a 1:1 translation is not honest).

**Build Auto's sandbox-escalation detection as a predictive pre-flight check only, never a runtime catch.** Not decided — left open (Open Question 2) rather than picked, since the founder's decisions specify the *behaviour* (ask when the sandbox would deny more) without specifying the *mechanism*, and the two approaches have materially different implementation costs.
