# ADR-091 — Shell permission: `ask` + Auto-approve, not a third mode; drop the block list; one rule format

- **Status:** Proposed (founder-approved decisions incl. UI, 2026-09-23; revised 2026-09-23 after a two-pass spec grill returned BLOCK; revised again same day — the permission model and the definition of "safe" are founder decisions, superseding this ADR's first framing of both)
- **Date:** 2026-09-23
- **Deciders:** Daniel Piatkowski (founder, ratifying decision); architect (design, drafting)
- **Supersedes-in-part:** [ADR-036 — Consolidate shell and subagent tools](./ADR-036-consolidate-shell-and-subagent-tools.md) §3.1's deny-pattern axis and its "one approval flow" decision (still valid; this ADR adds Auto-approve in front of it).
- **Extends:** [ADR-077 — Two-layer tool-policy model](./ADR-077-two-layer-tool-policy-remove-fail-closed-backfill.md) — `bash`, like every tool, resolves through the unchanged two-layer ceiling/override merge to one of `allow`/`deny`/`ask`; Auto-approve is a setting that only matters once that merge lands on `ask`. The merge mechanism itself is untouched.
- **Evidence baseline:** `release/v0.1.1` @ `838d8092c` (worktree `wt-release-session`), read-only. Contract shapes verified against branch `adr091/contracts` @ `e6a5cfd4e` (worktree `wt-adr091-contracts`), which already implements this revision's model.
- **Revision note:** the first draft's D1 described three named modes (Ask/Auto/God Mode), with Auto implemented by leaving the `bash` tool-policy value at `"allow"` and bolting a pre-flight check on top, distinguished from God Mode only by a separate flag. **Founder decision, 2026-09-23: this is replaced.** `bash` keeps the same three-valued tool policy every tool has; Auto-approve is a setting meaningful only on `ask`, not a fourth value, and it applies to every `ask`-resolved tool, not `bash` alone (D1, below). A second founder decision the same day defines what Auto-approve treats as safe to clear without a prompt: staying inside the sandbox, evaluated per call (D9, below) — this also corrects D7/D8's "under Auto only" framing, which tied kernel-side rendering to the wrong axis. Both decisions are already implemented in the contracts named above; this text is brought into agreement with them. Everything else from the earlier grill-driven revision (D7's `PathGrants` data model, D8's network compensating control, D3's resolve-and-verify, the global-write step-up) stands unchanged.

## Context

### The problem: six mechanisms, no single story

A `bash` call today passes through, in fixed order: (1) a hardcoded ~38-regex deny list (`defaultDenyPatterns`, `pkg/tools/shell.go`) that cannot be disabled and is unconditional even under God Mode; (2) a structural command-substitution guard (`pkg/tools/shell_subst_guard.go::substitutionGuard`); (3) operator-configured deny patterns, global and per-agent, both opt-in and off by default; (4) a command-text path-containment scan with an ADR-068 read/write carve-out (`pkg/tools/shell_path_guard.go::guardCommand`); (5) a per-binary exec allowlist, a no-op unless configured (`pkg/policy/evaluator.go::EvaluateExec`); and (6) the ADR-077 tool-policy verdict for `"bash"` itself (currently defaults `allow`, `pkg/config/defaults.go:190` — this ADR changes that default, D1).

None of these six is redundant by design; they accumulated independently across several ADRs and nothing coordinates between them or explains, to an operator, what actually stops a destructive command in each state. Mechanisms 1 and 3 are regexes over lowercased raw command text — the code's own comment: "a list of phrasings, not a judgement about the act." They are defeated by mid-token quoting (`r'm' -rf /`), `$IFS` substitution, or variable indirection (`X=rm; $X -rf /`). Where a kernel sandbox is active, it is the real boundary for *where* files can be touched; the deny-pattern layer is the only thing standing between an agent and a destructive *phrasing* against files the kernel would otherwise allow it to touch — and that is the bypassable layer.

### GitHub issue #83, and its correction

Issue #83's headline claim traces to `pkg/security/execapproval.go::ExecApprovalManager` — confirmed still buggy in that file, but the manager has **zero production callers**; ADR-036 §3.4 deleted its frontend and relocated live grant consultation to `pkg/security/approvalgrants.go::ApprovalGrantStore`, which does not share the defect. Issue #83's *second*, "Additional" claim is different and **still live**: the opt-in exec allowlist (`pkg/policy/evaluator.go::EvaluateExec`) matches raw command strings with no `exec.LookPath`/`filepath.Abs`/symlink resolution — an allowed pattern like `"git *"` says yes to `git evil-script` without checking which file named `git` is about to run. D3 closes this directly.

### Why simplify now

Six independently-evolved mechanisms is not a security posture, it is an audit liability. Claude Code and Codex CLI — surveyed for this ADR — ship no curated "dangerous command" deny list. Claude Code: "Bash permission patterns that try to constrain command arguments are fragile"; the OS sandbox is the real boundary. Codex intercepts `execve(2)` at the syscall level and ships no default `execpolicy` rules. Both give `deny` an unconditional trump card over `allow`. This ADR adopts that posture — **and** both tools' actual replacement for the deleted block list: neither ships network access on by default in their most-permissive sandboxed mode (D8/D9).

## Decisions

### D1 — Tool policy stays three-valued for `bash`, exactly as for every tool; Auto-approve is a setting on `ask`, not a fourth value [founder decision, 2026-09-23]

Every tool, `bash` included, resolves through the unchanged ADR-077 two-layer ceiling/override merge to exactly one of the three existing policy values, same meaning for every tool:

- **`allow`** — every call runs, no prompt, none of this ADR's machinery applies.
- **`deny`** — the tool is invisible to the agent. Auto-approve has no effect here.
- **`ask`** — this ADR's machinery applies: the approval dialog (D4), the pre-flight escalation for a call that needs more than the sandbox currently permits (D7 filesystem, D8 network), exact/prefix grants (D3/D4), and Auto-approve's own classification (D9).

**Auto-approve is a separate, boolean setting meaningful only for a tool resolved to `ask` — never a third value the tool policy itself can hold.** When it resolves true for a given call, a call D9 classifies as staying inside the sandbox runs without a prompt; a call D9 classifies as needing more still prompts, Auto-approve or not. When it resolves false, every `ask` call prompts, exactly as `ask` behaves today with no Auto-approve machinery at all. **Auto-approve applies to every tool currently resolved to `ask` — not `bash` alone** (`SandboxConfig.yaml::auto_approve`'s own description, contracts).

**Three scopes, only one of which may loosen** [`contracts/components/schemas/SandboxConfig.yaml`, `Agent.yaml`, `AgentUpdateRequest.yaml`, `AgentCreateRequestMain.yaml`, `AgentCreateRequestSubagent.yaml`, `SessionModeUpdateFrame.yaml`, `SessionModeUpdatedFrame.yaml`, and their inline copies in `contracts/asyncapi.yaml`, verified on branch `adr091/contracts` @ `e6a5cfd4e`]:

- **Global default** — `SandboxConfig.auto_approve` (boolean, fresh-install `true`). The ceiling every other scope starts from.
- **Per-agent** — `Agent.auto_approve_disabled` (boolean, off-only by construction: `true` forces Auto-approve off for that agent's `ask`-resolved tools; there is no value meaning "on," so a per-agent write can never loosen past the global default).
- **Per-chat** — `SessionModeUpdateFrame.auto_approve` (nullable boolean: `true` turns Auto-approve on for this one chat even when the resolved agent × global default has it off; `false` tightens it off for the chat; `null` clears the chat's own modifier back to the agent × global resolution). **This is the one deliberate exception that may loosen**, because a human is present in that session. Session-scoped state (`pkg/agent/sessionmode.go`, new), acknowledged by `SessionModeUpdatedFrame.auto_approve_effective` — not a `config.json` write.

**Turning Auto-approve on for a chat is a human-only action.** The agent-facing `set_config` tool (`pkg/sysagent/tools/config.go`) cannot produce the same effect through either path: the global default lives under `sandbox.*`, and `blockedConfigKeys` (`pkg/sysagent/tools/config.go::blockedConfigKeys`, verified) already refuses the **entire** `sandbox.*` subtree by ancestor closure — the same coverage that already blocks `sandbox.mode`/`sandbox.god_mode`/`sandbox.tool_policies` today extends to `sandbox.auto_approve` automatically. The per-chat modifier is not a `config.json` path at all — it is the `session_mode_update` WS frame, a surface `set_config` cannot reach by construction, not merely by policy (`SessionModeUpdateFrame.yaml`'s own description makes this an explicit requirement, not an accident of scope).

**God Mode is a fourth, orthogonal mechanism — not a mode of Auto-approve and not itself a policy value.** `sandbox.GodMode` (unchanged, `resolveEffectivePolicyWith`, `pkg/agent/compositor.go`) floors every agent's ceiling at `allow`, for every tool — which makes Auto-approve moot for that agent, since nothing is left at `ask` once the floor applies (`SandboxConfig.god_mode`'s own description, contracts, states this explicitly: "which also makes `auto_approve` below moot for that agent"). D6 keeps God Mode's code comment accurate to this.

**Consequence: `bash`'s shipped default changes.** Today `bash` defaults to `"allow"` (`pkg/config/defaults.go:190`) — an accepted risk under Hard Constraint #6 (ADR-077 R1) because nothing distinguished "unprompted" from "God Mode" before this ADR. This ADR's implementation moves that default to `"ask"`, with the global `auto_approve` default `true` — so a fresh install behaves the way the first draft's "Auto" description felt like, but the stored tool-policy value is now honest about what it is, and every other tool's own default is unaffected (Auto-approve is dormant for a tool that ships `allow`, e.g. `fetch_url`, `browser_navigate`, `send_file` — all `allow` by default, `pkg/config/defaults.go:230,233,306-351` — until an operator tightens that tool to `ask`).

**"Kernel sandbox active" predicate** (drives D9's classification and the status badge; one server-derived value, read by both — `SandboxStatus.yaml::kernel_sandbox_active`):

| Platform | Predicate |
|---|---|
| Linux | Landlock applied in enforce mode (`mode: enforce`), not degraded |
| macOS | Seatbelt backend's own active/enabled state, read directly — **not** `SandboxStatus.policy_applied`, which reports the *gateway's own* confinement and is documented false on macOS by design (Seatbelt confines children only, `pkg/sandbox/CLAUDE.md`) |
| Windows | Never — no kernel sandbox backend |

**Tighten-only below the global default, enforced server-side, four writers.** A per-agent write that would loosen (impossible by the field's own off-only shape, but validated anyway) is rejected with 4xx; the write handler re-reads the global default at write time. Four writers must agree: `rest_agents_update.go` (field merge), `rest_agents_create.go` (create-path decode), `pkg/sysagent/tools/agent_apply_args.go` (agent-callable), and the session-modifier's own frame handler (which is the one path allowed to loosen). UI hiding a looser option elsewhere is defence-in-depth only.

**Global-default write requires the password step-up.** The write goes through the **existing** `rest_sandbox_config.go::putSandboxConfig` → `authenticateAndDecode` → `requireReAuth` chain (verified, `pkg/gateway/rest_sandbox_config.go:170,344,355`) — the same step-up God Mode and credential writes use. No new authentication mechanism; the requirement is that the write use this handler. `SandboxConfigUpdate.yaml::auto_approve` is hot-reloaded (no `requires_restart`), unlike `mode`/`allowed_paths` on the same endpoint. **Accepted, pre-existing gap named, not fixed here:** on Windows, `config.json` is not kernel-denied to a spawned child (`FallbackBackend`'s own doc comment: "cooperative processes only"), so an agent's own `bash` tool can write `config.json` directly, bypassing both `set_config` and the step-up gate — a Linux/macOS-only guarantee, documented as such.

**Delegation:** the per-chat modifier inherits to delegated subagent sessions exactly as approval grants do (`ApprovalGrantStore.InheritFrom`); a delegate resolves the tightest of (parent's modifier, delegate's own override). **Mid-turn:** a call is resolved against the tool-policy value and Auto-approve state in force when `resolveToolPolicyAtExec` (the existing TOCTOU re-check, unchanged) last ran for it; a tighten landing after does not retroactively change that call's verdict.

**Regardless of tool-policy value or Auto-approve state**, the audit log, prompt-injection guard, and rate limiting stay on (verified: none conditioned on `godMode` in `executeRun`). **Operator `deny` rules (D3) stay in force in God Mode — new behaviour**: D3 rules are enforced inside the shell tool, downstream of `resolveEffectivePolicyWith`'s God Mode floor, so the floor cannot erase them (matches Claude Code's managed-deny precedent).

### D2 — Drop the built-in shell block list entirely

`defaultDenyPatterns` (~38 regexes, includes `secretGuardPatterns`) and the per-agent/global deny-pattern config are removed outright. **Rationale:** bypassable by construction; neither Claude Code nor Codex ships this; the kernel sandbox is the real boundary where one exists. The secrets regex is a backstop over a boundary (`~/.omnipus/`'s secret files) the kernel already denies independently of command text where a sandbox is active.

**What replaces the coverage, stated honestly:** of the ~38 patterns, the filesystem-shaped ones (path writes, `rm` chains) are covered by the kernel boundary D7 already made explicit. The **network-shaped** ones — `git push`, `ssh …@`, `curl|wget … | sh`, `apt/yum/dnf/npm/pip install`, `docker run`/`exec` — have no filesystem expression at all; **D8/D9 below are their compensating control**. The remaining categories — `shutdown`/`reboot`/`poweroff`, `kill`/`pkill`/`killall`, the fork bomb, `sudo`, `chmod`/`chown`, `eval`, `source *.sh` — are neither filesystem nor network operations, and **nothing in this ADR covers them**. This is the same accepted trade Claude Code and Codex ship and document.

**Accepted residual risk, precisely scoped:** on Windows (no kernel sandbox), in God Mode (no sandbox, no D8), and for the categories above on every platform, nothing in this ADR blocks a destructive command by phrasing. This is not new — the block list was the *only* thing providing even bypassable coverage there, and it is gone.

**What survives, per guard:** structural command-substitution guard (`shell_subst_guard.go::substitutionGuard`) — unchanged. Path-containment guard (`shell_path_guard.go::guardCommand`'s absolute-path scan) — survives; disposition now turns on whether prompt machinery is available for the call, not on a named mode (D9's second consequence, below). Per-binary exec allowlist — retired, folded into D3. ADR-077 `bash` policy — survives, `ask` is where this ADR's machinery lives (D1). `ApprovalGrantStore` — survives, extended (D4/D7/D8).

### D3 — One rule format and one decision order

Operator rules (`config.SandboxConfig.CommandRules`, json `command_rules`, `{action: allow|ask|deny, binary, arg_prefix?}`, config-file-only, no wire schema) and user grants (D4) share one format and order: **deny beats ask beats allow, specificity-blind.** Chained commands (`&&`, `||`, `;`, `|`, newline) split via the **existing** `splitShellSegments`/`shellCommandHead` (`shell_subst_guard.go`) — no new parser; each segment must independently clear, or the whole call asks.

**Resolve-and-verify, not resolve-and-rewrite.** `pkg/tools/shell.go::buildShellArgv` execs `["sh", "-c", command]` on POSIX and `["powershell", "-NoProfile", "-NonInteractive", "-Command", command]` on Windows — `argv[0]` is always `sh`/`powershell`, never the user's binary; there is no argv slot naming `git` to rewrite, and rewriting the `-c` string is attacker-influenced text surgery, the exact class D2 just rejected. Instead: **the D3 matcher resolves a segment's leading token to its actual executable against the child's effective PATH/env, matches operator rules against the resolved absolute path, and re-verifies that resolution immediately before spawn.** The command text itself is never rewritten. The residual window — a swap between resolve and exec (TOCTOU) — is explicitly the kernel sandbox's boundary, not the rule engine's. **Windows [founder decision]:** `splitShellSegments` is a POSIX operator set (`| ; & \n \r`) that does not model PowerShell grammar, and there is no `argv[0]` there either. On Windows, D3/D4 grants and rules are **exact-command only** — no prefix option, no chained-segment splitting — a documented limitation, not a partial POSIX behaviour.

**Exec allowlist folded in, not run alongside** (`Evaluator.EvaluateExec`/`MatchGlob`/`FirstToken`, keyed `security.policy.exec.allowed_binaries`, retired; configured entries become D3 `allow` rules, operator re-authored — greenfield, no auto-conversion). `PolicyAuditor.logDecision`'s write survives, retargeted — but see D7's audit note: `logDecision` is unexported, single-caller, and its four-string signature carries no room for mode/level/scope, so the *new* D7/D8/D4 events route through `ExecTool.emitAudit`'s existing `audit.Entry.Details map[string]any` instead.

**Honest gap:** D3 rules bind to a segment's head and do not see through interpreters — `sh -c 'rm -rf X'`, `xargs rm`, `find … -exec rm`, `awk 'system(…)'` escape a `deny` on `rm`. Friction layer, not containment; the kernel is the boundary.

### D4 — Approval dialog: three buttons, a scope choice, chained commands per part

`ToolApprovalModal.tsx` is **[Deny] [Allow once] [Allow]**, replacing `Approve`/`Deny`/`Always Allow`/`Cancel`. **Allow** records a session grant with a scope choice: **exact** (default — command text + `cwd`, unchanged from today) or **prefix** (new — `{binary, arg_prefix}`, ignores `cwd`, token-boundary matched so `npm run test` does not match `npm run testfoo`). `run_in_background` is a separate match dimension for both scopes. Chained commands grant one rule per segment; a later partial match prompts only the unmatched segment(s).

**Suggested-prefix algorithm:** resolved binary plus leading sub-command words, stopping at the first flag/path-shaped-arg/URL token. A leading env-assignment is stripped before deriving; the grant matches under any assignment value. A known wrapper (`sudo`, `env`, `timeout`, `xargs`, `sh -c`) is **not** stripped — the prefix is derived starting from the wrapper.

**`cancel` stays in the wire enum, with no button.** `ToolApprovalModal.resolution.test.tsx` verifies Escape→`deny` (leaves the approval unresolved on a network failure, so a later snapshot can still bring it back) and the old Cancel→`cancel` (resolves it locally on a lost-server 404) behave *differently on purpose*, and the headless CLI approval path (`pkg/app/internal/run/run.go`) drives the same enum. The three-button UI never shows a Cancel button and Escape/overlay/X all resolve to `deny` — but `cancel` remains a valid, client-issued action value for the stuck-approval recovery path.

Session grants are **not shown anywhere** — no list, no chip, no revoke surface; they end with the chat. This is an explicit non-feature. Per-website network grants are future work, not built here.

### D5 — Delete the dead code

`pkg/security/execapproval.go` (`ExecApprovalManager` et al.) and its test file, deleted outright — zero production callers, answers a UI flow ADR-036 already deleted.

### D6 — Fix God Mode's code comment

`pkg/config/sandbox.go`'s `GodMode` comment is rewritten to state what remains true post-D1–D3: floors every agent's ceiling at `allow` (D3 `deny` still applies), forces sandbox off, forces egress open, makes Auto-approve moot rather than "off" (nothing is left at `ask` to apply it to), does not disable audit/injection-guard/rate-limiting. Documentation-accuracy fix only.

### D7 — Filesystem pre-flight for an `ask`-resolved call: one source of truth, additively extended

An `ask`-resolved `bash` call is evaluated, before it runs, against the same rules the kernel will enforce; a call needing more than the sandbox allows asks *before* it starts, never after — Auto-approve decides only whether an already-contained call also needs that prompt (D9). **The single source, extended, not forked:**

- `fspolicy.FSPolicy` gains one new field: **`PathGrants []PathGrant`**, `PathGrant{Path string; Access uint64}`, using the *same* `sandbox.AccessRead|AccessWrite|AccessExecute` bitmask `PathRule.Access` already uses — not a new vocabulary. Unlike `AllowedRoots` (a subtree **write** grant from workspace mounts), a `PathGrant` is exactly one path and exactly the access class the pre-flight verdict found missing.
- `sandbox.DeriveKernelPolicy` renders each `PathGrant` as one additional `PathRule{Path, Access}` — additive to the existing `WorkDir`/`AllowedRoots` rendering, not a parallel code path.
- `guardCommand`'s path scan (consumer 1) checks `PathGrants` the same way it already checks `AllowedRoots`: contained if within `WorkDir`, `AllowedRoots`, or a `PathGrant` covering the needed access.
- **Tool scope, bash-only:** `PathGrants` is **not** part of the ambient value every `ResolveTurnFSPolicy` caller reads identically. `ResolveTurnFSPolicy` gains an optional grant-overlay parameter that **only the bash pre-flight/exec call sites** populate from `ApprovalGrantStore`; the other callers (`edit.go`, `filesystem.go`, `grep.go`, `send_file.go`, `web_serve.go`, `request_mount.go`, the browser tools) pass none and are unaffected by a bash-approved widening — see D9 for what those callers do instead.
- **Secret set is never widenable:** an escalation naming a path in `CarveOuts`/the secret set is refused outright — never prompted, never grantable, in every tool-policy state including God Mode.

**Consequence:** the next identical command in the session resolves the widened policy directly (no re-prompt); the widening does not leak past session close; a delegate inherits it via the same `InheritFrom` mechanism as command grants.

**Honest gap, corrected claim:** a pre-flight check cannot see symlink resolution at access time, a runtime-constructed path, or a re-exec under another identity. When the kernel denies something pre-flight missed, **the command fails with the child's own OS error** (e.g. a bare permission denial); Omnipus does not attempt to diagnose it as specifically a sandbox denial — Landlock's denial is not a structured, observable event to the gateway. It is never silently allowed and never silently retried unconstrained.

**No kernel sandbox** (Windows, app-level fallback, Landlock-degraded): `kernel_sandbox_active` is false, so D9's classification can never positively clear anything — every `ask` call prompts, Auto-approve on or off (D9).

**Anti-drift lock test:** a generated `{path, operation}` matrix, evaluated against a fixed `FSPolicy` including a non-empty `PathGrants`, asserts the pre-flight verdict and `DeriveKernelPolicy`'s actual rendering agree; a deliberately mismatched pair must fail the test. Pure Go, every CI OS; a second, Linux-only leg spawns a real Landlock-confined child.

### D8 — `bash`'s rendered network policy denies outbound by default whenever it resolves to `ask`

D2 deletes `git push`, `ssh …@`, `curl/wget … | sh`, `apt/yum/dnf/npm/pip install`, `docker run`/`exec` along with the rest of the block list — every one of these is a **network** operation, and D7's filesystem pre-flight does not cover any of them. **This is their compensating control**, mirroring what Claude Code and Codex actually ship: both deny network by default in their most-permissive sandboxed mode and escalate to a prompt on first need; neither uses a command-name deny list for this.

**Mechanism, per platform, honestly scoped:**

- **Linux, Landlock ABI v4+:** the kernel process-wide boot policy already seeds every child's `ConnectPortRules` with `DefaultConnectPorts = {53, 80, 443}` unconditionally (`sandbox.go::DefaultPolicy`). **For `bash`'s own rendered per-turn policy whenever the tool resolves to `ask`** — not gated on Auto-approve, which only decides whether a call inside this boundary still needs a click (D9) — `ConnectPortRules`/`BindPortRules` render **empty** instead: on ABI≥4, `handledAccessNet` is installed unconditionally, so an empty list is a true kernel-enforced deny-all for that child's `connect(2)`, not "no restriction." A network-need classifier — a sibling to D7's pre-flight, reusing D3's resolved-binary step — flags a command via (a) a curated, operator-extendable set of network-capable binaries (`git`, `curl`, `wget`, `ssh`, `scp`, `rsync`, `npm`/`pnpm`/`yarn`, `pip`, `apt`/`yum`/`dnf`, `docker`, `gh`, cloud CLIs) or (b) a literal `http(s)://` token. A flagged command escalates before spawn, exactly like D7's prompt; approving widens the session's rendered `ConnectPortRules` to `DefaultConnectPorts` (port-level, not domain-level — Landlock `NET_CONNECT_TCP` cannot filter by host) via a new `network` grant kind in `ApprovalGrantStore`, same session/delegate/clear-on-close lifetime as D7's path grants.
- **macOS:** the Seatbelt profile already renders `ConnectPortRules` identically (`seatbelt_profile.go`); same mechanism applies to the bash child.
- **Windows:** no kernel network control exists. No kernel sandbox means `ask` always prompts regardless of Auto-approve (D9) — D8 adds nothing there and takes nothing away.

**Honest gap, symmetric to D7's:** a command the classifier misses but that opens a raw socket is denied by the kernel at `connect()` time on Linux/macOS — not silently allowed. CIDR/host-level filtering for traffic Omnipus's own HTTP clients make remains the existing `SSRFChecker`/`ExecProxy` (`pkg/security/execproxy.go`), unchanged; a bash-spawned binary that ignores its `HTTP_PROXY`/`HTTPS_PROXY` env vars bypasses `ExecProxy` entirely — pre-existing, not new here; D8's port-level kernel deny is the actual containment for that case.

**What D8 does not cover, stated once:** `shutdown`/`kill`/the fork bomb/`sudo`/`chmod`/`eval` are not network operations; D8 is silent on them by design, same as D2.

### D9 — What "safe" means: staying inside the sandbox, judged per call, not per tool [founder decision, 2026-09-23]

**Auto-approve auto-clears a call if, and only if, it stays within what the kernel sandbox already permits for that turn — the agent's workspace files and anything else the effective policy already allows.** Everything else prompts: anything outside the workspace, any network access at all, secrets or credential files, and any settings change. This is evaluated **per call**, not per tool — the same tool can be auto-cleared on one call and prompted on the next, depending on what that specific call touches. `bash`'s pre-flight (D7 filesystem, D8 network) is this classification's kernel-backed implementation: a call the pre-flight can fully contain within the current per-turn rendering is eligible for Auto-approve; a call that needs a widening grant always prompts, whether or not Auto-approve is on — Auto-approve only ever decides whether an *already-contained* call also gets a click, never whether a *widening* does.

**Consequence 1 — the security claim is honestly weaker for tools that never spawn a kernel-confined child.** `web_fetch.go` (`WebFetchTool`), the browser tools (`pkg/tools/browser/tools.go`, `tools_interact.go`), and `send_file.go` (`SendFileTool`) run **in-process** — verified: none of the three calls `os/exec`, unlike `pkg/tools/shell.go`/`shell_bg.go`/`shell_process_unix.go`/`shell_process_windows.go` and `environment_setup_runner.go`, which do. There is no kernel enforcing what these calls touch. For the filesystem-touching ones among them, the same judgement is applied by evaluating the call against the same effective policy the kernel ruleset is derived from — `pkg/tools/resolvepath.go::ResolveTurnFSPolicy` → `pkg/sandbox/derive_from_fspolicy.go::DeriveKernelPolicy` (D7's single source of truth): `send_file.go:116`, `browser/tools.go:805`, and `browser/tools_interact.go:789` all call `ResolveTurnFSPolicy` directly and evaluate the result in-process, without ever reaching `DeriveKernelPolicy` or a spawned child. `web_fetch.go` touches no filesystem policy at all — its own app-layer guard is `SSRFChecker` (`webFetchParseArgs`/`webFetchDialContext`, `pkg/tools/web_fetch.go`), a different mechanism for a different resource (network, not filesystem), and it carries no pre-flight-escalation or grant-consultation step today. **This is an app-layer judgement, not a kernel one, and the ADR does not blur the two:** an in-process tool's Auto-approve classification is only as trustworthy as the code path that evaluates it; a `bash` call's is backed by a kernel that will refuse the syscall even if every layer of app logic above it is wrong. Any in-process tool an operator tightens to `ask` inherits D9's classification (workspace-contained filesystem access may auto-clear; network access never does) through this app-layer path, not a kernel one — stated here so a future reviewer does not read "Auto-approve" as uniformly kernel-backed across every tool.

**Consequence 2 — no kernel sandbox means nothing can be positively cleared.** `kernel_sandbox_active` (`SandboxStatus.yaml`, D1's platform predicate) false means D9's classifier has no confinement to compare a call against, so it can never certify a call as "stays inside" — every `ask`-resolved call prompts, Auto-approve on or off. This is the "Auto → Ask" badge state (`SandboxStatus.auto_approve_effective=true`, `kernel_sandbox_active=false`) and is not a bug: it is what "nothing to positively clear against" means on Windows and on a Linux/macOS host degraded to the app-level fallback.

**Consequence 3 — `guardCommand`'s path-containment disposition turns on whether prompt machinery is even available, not on a named mode.** `ask`-resolved (Auto-approve on or off) → a violation surfaces as the D7 pre-flight escalation, offered as a prompt with a widening choice, because `ask` is exactly the state where prompt machinery exists. `allow`-resolved or God Mode (no prompt machinery active in either — D1) → a violation is a hard denial with nothing to escalate to, because there is no dialog to escalate through. This replaces the first draft's three-named-mode framing of the same guard with the two-way split D1 already implies.

## Consequences

### Security
Removes a bypassable text layer; D8/D9 are its network-shaped compensating control; closes issue #83's live "Additional" claim via D3's resolve-and-verify; makes #83's headline claim moot by deleting the dead code (D5). D9 makes explicit what "safe" means and where that claim is kernel-backed versus app-layer only — a precision the first draft did not state. Accepted, precisely-scoped residual risk: Windows, God Mode, and the non-filesystem/non-network categories D2/D8 both leave untouched.

### Audit
Four new events — Auto-approve/mode change, pre-flight escalation (filesystem or network), grant recorded (scope: exact/prefix/path-widening/network-widening), approval decision — written via `ExecTool.emitAudit`'s `Details` map, not `logDecision`.

### UX
One tool-policy value (`ask`) plus one setting (Auto-approve) replaces six mechanisms and a three-named-mode selector. Fewer prompts when Auto-approve is on; every prompt that fires means the sandbox genuinely could not confine the action, or Auto-approve is off. Prefix grants close a real friction gap `ApprovalGrantStore`'s exact-fingerprint today cannot. **Accepted trade:** no grants list/revoke UI (D4). Headless turns under `ask` with Auto-approve off stall to the existing `ToolApprovalTimeout`, unchanged.

### Migration
**Greenfield, no upgrade path.** Retired keys are dropped on load (unknown-field tolerance, file half); the agent REST write path is strict — a stale client `PUT`ting `shell_policy` now gets a hard 400 from `rest_agents_update.go`'s extended raw-body sniff.

### Interaction with ADR-077
The two-layer ceiling/override merge is untouched; `bash` resolves through it like any tool. What changes is the *shipped default* (`allow` → `ask`, D1) and that a genuinely new field exists at global (`cfg.Sandbox.AutoApprove`) and per-agent (`AgentConfig.AutoApproveDisabled`) scope — the first draft's attempt to avoid new storage by overloading the existing `allow` value is abandoned; the contracts already carry the real fields. God Mode floors the ceiling at `allow` exactly as before; D3 `deny` rules and an agent's own stricter per-agent override both continue to survive it under strictest-wins.

## Alternatives considered

**Keep Auto as a third tool-policy value.** Rejected — Hard Constraint #6 defines exactly three values for the whole builtin catalog and forbids a fourth fallback; a fourth value would also need its own ceiling/override semantics duplicated from `ask`'s, for no behavioural gain over a setting layered on `ask`.

**Keep the block list as an off-by-default layer.** Rejected — reintroduces the false-coverage problem; every vendor surveyed rejected this shape.

**Auto-migrate deny patterns into D3 rules.** Rejected under greenfield — a regex and a resolved-binary rule are not equivalent; a 1:1 translation would misrepresent coverage.

**Runtime-catch the kernel's actual denial, filesystem and network alike.** Considered, then rejected for D7 (a Landlock/Seatbelt denial is not a structured event the gateway can observe; a command may have real side effects before hitting it) — and rejected for the identical reason for D8: a network denial has the same unobservability problem, so D8 uses the same pre-flight-classifier shape as D7 rather than a second, differently-designed detection mechanism.
