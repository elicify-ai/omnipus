## 1. Executive summary

ADR-068's central storage decision (D16) rests on a statement about ADR-067 that is false in the
code and false in ADR-067 itself, and it silently reverses an alternative ADR-067 explicitly
rejected. Separately, the ADR omits — with no acknowledgement — five controls that ADR-067's own
adversarial review forced into that ADR as blocking findings: workspace isolation, query cost
bounds, per-decision acceptance criteria, audit, and an upgrade migration for tool policy. The
record-identity mechanism that every relation joins on is unspecified and self-contradictory on
its own field name.

**Findings: 7 critical, 25 major, 13 minor, 5 observations.**

**Verdict: BLOCK.**

| **M-23** | Ambiguity / Incorrectness | D3.2 | **Absent-inclusive negation inverts the semantics every LLM has internalised, with no statement of the interaction with `required`.** The choice is defensible and well-argued for the checkbox case, but `status is not churned` returning records with no status will surprise every agent trained on SQL and on Notion. Two independently-sequenced plans over one code path will collide. | Add ADR-067 stage dependencies to D20's table, and reconcile W4 with ADR-067 stage 3 so one writer is built, not two. |
| **M-25** | Ambiguity / Incompleteness | D1 | **The scope of "the operator's own vault" is never defined.** Is a record any `.md` file with a `type:` key anywhere a workspace can see, or only inside a folder ADR-067's detector recognises as a KB (`.omnipus-vault/` or `.obsidian/`, `pkg/knowledge/marker.go`)? This determines what is indexed, what `vault.query` can reach, whether D18's postures are sufficient, and whether C-2's isolation question is even answerable. | State it: records exist only inside a detected knowledge base, scoped to the calling agent's workspace mounts. |

## 4. Test coverage assessment

- **Testability of requirements.** Most decisions are testable in principle; almost none is testable *as written*, because no acceptance criteria exist (M-16). D14's single criterion is the only falsifiable statement in the ADR and it is satisfiable by an implementation that handles one case (M-9).
- **Negative scenarios.** The ADR is unusually good on *reporting* negatives (D13) and unusually silent on *testing* them. Required and absent: cross-workspace read returns zero (C-2, ADR-067 AC-7.1's shape); out-of-set enum rejected (D4); list written to a scalar rejected (D3.1); ID collision detected (C-4); stale version token refused (C-5); relation to a non-existent record reported not silently dropped (D5).
- **Boundary conditions.** Undefined for every type: empty enum set, zero-length text, `many: true` with zero entries versus absent (D3.2's distinction is stated for scalars and never resolved for lists), a relation to itself, a sub-record list of one, a temporal interval with `from == to`.
- **Concurrency.** No test shape stated. ADR-067 D14 inherited `pkg/entity`'s **real cross-process** test pattern explicitly (*"citing another package's tests does not transfer the guarantee"*). ADR-068 inherits nothing and the ID allocator (C-4) is the sharpest concurrency risk in the design.
- **Regression risk.** Not addressed. ADR-067 has a §4.4 regression table naming memory-room recall, chat markdown links, `web_serve` previews and existing installs' tool access. ADR-068 touches `pkg/knowledge` (a landed, tested package), `pkg/config/defaults.go`, `pkg/coreagent/core.go` and the contracts, and names no regression risk at all.
- **False-green exposure.** D16 cites `docs/internal/false-green-patterns.md` approvingly, then specifies a verification surface with no failing case: a coverage validator that returns nothing when the registry is empty (the trap ADR-067 AC-17.2 was rewritten to catch), a splice criterion satisfiable by the easy path, and a universal-negative exit criterion.

## 7. Verdict

**BLOCK** — 7 critical, 25 major.

C-1 alone is disqualifying: the ADR's storage decision describes a system that does not exist and
reverses a recorded decision of the ADR it claims to extend. C-2, C-3 and C-5 are each a
regression against a finding that ADR-067's own adversarial review classified as blocking and
that ADR-067 had to answer before it could reach revision 2 — isolation, cost bounds, and audit.
An ADR in the same series, on the same branch, over the same files should not have to relearn
them.

Three findings share one shape worth naming, because it is the shape this ADR was written to
attack: **C-1, M-8 and C-7 are each a confident statement about existing code that the code
contradicts** — ADR-067 stores in SQLite (it stores in bleve), no Go code does byte-preserving
frontmatter writes (this branch does), a coverage gap aborts boot (it is repaired to `deny` with
one WARN). Every one is exactly the failure mode §1.3 catalogues: a plausible answer, confidently
narrated, with nothing in the system positioned to contradict it. Verifying claims about the tree
against the tree should be a step in the next revision, not only in its review.

The document's diagnostic half (§1, and the failure taxonomy that produces D3.1, D3.2, D4, D5,
D9 and D13) is genuinely strong and worth preserving intact. The gap is between that analysis
and the decisions built on top of it.
