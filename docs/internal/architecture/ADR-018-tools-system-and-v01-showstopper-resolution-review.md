# ADR-018 Review — Adversarial Red-Team

**Input:** `docs/internal/architecture/ADR-018-tools-system-and-v01-showstopper-resolution.md`
**Mode:** generic-markdown (ADR-review)
**Reviewer stance:** read-only, assume-the-worst. Every `[FACT]` verified against the live tree on `main`/working copy.
**Date:** 2026-06-03

## Executive Summary

13 findings: **3 CRITICAL, 5 MAJOR, 3 MINOR, 2 OBSERVATION**.

The ADR is well-grounded — most `[FACT]` tags verify correctly against the code, and clawhub.ai is live with a response shape that matches `ClawHubRegistry`. But the **single most load-bearing decision, D-A1, contains an architectural conflation that the "Confidence: High" rating does not survive**: general builtins (`exec`, `install_skill`, …) are not stateless — they are instantiated *per-agent with that agent's `Workspace` baked in*. A literal "one central registry holds the tool" reading of D-A1 Option A breaks per-agent workspace isolation. The ADR must split "central registry as the SSOT for UI/policy/metadata" (achievable, already half-built) from "central registry as the execution source" (not achievable without per-agent instancing). Two more CRITICALs concern the `dangerous`-rail completeness (D-A3/A5) being unverifiable as specified, and the D-B2 restart-key change colliding with `hot_reload` defaulting to **off**.

**Verdict: REVISE.**

## Findings

| ID | Severity | Lens | Decision | Description | Recommended fix |
|----|----------|------|----------|-------------|-----------------|
| F-01 | CRITICAL | Incorrectness / Infeasibility | D-A1 | "Move general builtins into ONE central registry" conflates SSOT-for-UI with execution-source. `exec` (`loop.go:1020 NewExecToolWithDeps(agent.Workspace, …)`) and `install_skill` (`loop.go:1378 NewInstallSkillTool(registryMgr, agent.Workspace)`) are instantiated **per-agent with that agent's workspace**. A single shared instance cannot serve agents with different workspaces → cross-agent workspace leakage / sandbox bypass. | Split D-A1 explicitly: the central `BuiltinRegistry` holds **metadata/templates** (name, description, category, dangerous, config-schema — exactly what the current `systools.AllTools(nil,nil)` boot population already does) and is the SSOT for `/api/v1/tools`, policy, and the UI. **Per-agent execution instances remain per-agent**, bound to `agent.Workspace`. State this metadata-vs-instance separation as a hard invariant in the spec. |
| F-02 | CRITICAL | Insecurity | D-A3 / D-A5 | The security rail depends on a *complete and correct* `dangerous` flag, but the only pre-existing classification signal — `RequiresAdminAsk()` — is **uniformly `true` for all 41 system tools** (`pkg/sysagent/tools/admin_ask.go`), including pure read-only ones (`AgentListTool`, `ConfigGetTool`, `PinListTool`, `ProjectListTool`, `SkillListTool`, `TaskListTool`, `CostQueryTool`, `ModelsListTool`). So `dangerous` **cannot be derived from `RequiresAdminAsk`**, and there is no existing per-tool danger signal for the ~20–26 general builtins at all (`exec` does NOT override `RequiresAdminAsk` — `base.go` default false). Completeness is therefore a manual hand-tagging of ~65 tools with no test that proves a new tool is tagged. | (a) Mandate that `Dangerous()` is hand-set per tool, NOT derived from `RequiresAdminAsk`. (b) Add a **registry-completeness test** that fails CI if any registered tool lacks an explicit `Dangerous()` decision (e.g. require a sentinel/registration-time assertion, not a silent `false` default — a silent default is exactly how the rail leaks). (c) Specify the canonical list of dangerous tools (at minimum: `exec`, all `agent-management`, `configuration`/`config.set`, `mcp.add`, `channel.enable/configure`, `skill.install`, `web_serve`) in the spec so plan-spec has an audit baseline. |
| F-03 | CRITICAL | Inconsistency / Inoperability | D-B2 ↔ D-B8 | D-B2's root cause is stated as "onboarding writes to `gateway.users` are counted as pending-restart." But the live code (`rest_pending_restart.go:36`) already lists `config.GatewayUsers` in `RestartGatedKeys` **and** already strips rotating fields via `normalizeUsersForDiff`. More importantly, `hot_reload` defaults to **`false`** (`config/defaults.go:363`) and *gates the entire reload watcher* (`gateway.go:779 if cfg.Gateway.HotReload`). When hot-reload is off, NO key applies without restart, yet the banner only surfaces `RestartGatedKeys` — so the banner is already inconsistent with reality. D-B8 forcing `hot_reload` on flips the operative model; the ADR never connects these. | In the spec: (1) State that forcing `hot_reload=on` (D-B8) is a **precondition** for the D-B2 restart-key model to be coherent. (2) Decide and document whether removing `gateway.users` from `RestartGatedKeys` is safe — verify user-management changes (`gateway.users`) genuinely take effect without restart (they may not, if auth state is cached at boot; that is why it was gated). (3) Re-baseline the `appliedConfig` snapshot **after** onboarding, per the ADR, but note `appliedConfig` is currently captured once at boot (`rest.go:84-90`, `gateway.go:1284`) — re-baselining requires a new code path the ADR doesn't scope. |
| F-04 | MAJOR | Incompleteness / Infeasibility | D-A6 | The dynamic typed-schema-over-the-wire is declared but the **contract shape is unspecified and in tension with Hard Constraint #8**. The existing `ToolRegistryEntry.yaml` has no `config_schema`/`config`/`dangerous` fields, and its `category` is a free-form prefix string, not the typed purpose enum D-A4 wants. A "JSON-Schema-ish" dynamic schema cannot be expressed as a fixed generated Go/TS type without either (a) a closed discriminated union of field-kinds, or (b) an `additionalProperties`/`x-`-style escape hatch that defeats the generated-type guarantee. | Spec must pick (a): define a **closed enum of field kinds** (`provider-select`, `credential-ref`, `number`, `text`, `string-list`, `model-select`, `toggle`, `path-list` per §3) as a discriminated `ToolConfigField` schema in `contracts/components/schemas/`, so the wire type stays generated and Zod-validatable. Forbid free-form JSON-Schema passthrough. Enumerate which of the 6 scattered configs (Brave/Tavily/Exec/Browser/Voice/SearchCache) are global-only vs per-field-overridable — the ADR leaves this open and it is load-bearing for the persistence model. |
| F-05 | MAJOR | Inconsistency | D-A4 / contract | D-A4 says "retire `core`/`system` as user-facing categories," but `ToolRegistryEntry.yaml` has a **separate `scope` field** whose enum is still `system`/`core`/`general` (lines 24-28), and `Tool.Scope()` drives it. The ADR addresses `category` but never mentions `scope`. Retiring `system`/`core` from `category` while leaving them in `scope` produces a UI that still shows "system/core" scope badges — the bug the owner wants gone may resurface via `scope`. | Spec must explicitly decide the fate of the `scope` field: keep it as an internal discriminator (not rendered), or fold it into the new category model. If kept, document that `scope` is non-user-facing and the SPA must not render it as a grouping axis. |
| F-06 | MAJOR | Incorrectness | §1-A / D-A1 | The reproduced bug ("`/api/v1/tools` returns only the 41 system tools") is real but the stated mechanism is **already partially fixed in code and the ADR doesn't acknowledge the half-built state it's correcting**. `HandleToolsRegistry` (`rest_tool_registry.go:122`) already reads `a.builtinRegistry.All()` — but `builtinRegistry` is populated only from `systools.AllTools` (`gateway.go:614`), so it returns system-only by construction. Worse: `gateway.go:689` **re-creates** `centralBuiltinReg` with live deps *after* it was already passed by value into `setupAndStartServices` (line 630) and stored on the restAPI — so the re-populated registry is **dropped on the floor**; `restAPI.builtinRegistry` keeps the nil-deps copy. | Spec must (a) state that the registry is populated system-only today and the fix is to *also register general-builtin metadata*; (b) flag the dead re-population at `gateway.go:689` as a bug to fix (pass a pointer or re-set the field), or the live-deps registry never reaches the handler. | F-07 | MAJOR | Insecurity / Incorrectness | D-A3 | "dangerous→Ask (not Deny)" weakens the *current* posture for general builtins. Switching the default to flat-allow + `dangerous→Ask` means: if an `exec`-class tool is mis-tagged `dangerous=false` (F-02), a fresh custom agent gets **silent flat-allow `exec`** — strictly worse than today. The ADR's own §7 says this, but D-A3 rates it "Medium-High" and defers the Ask-vs-Deny question to grill-spec. | Grill-spec decision: for the **global default of dangerous tools**, choose **Deny**, not Ask, for the agent-management/exec/config-write cluster, with Ask reserved for medium-danger (browser, web_serve). ## Structural / Narrative Assessment (generic-markdown mode)

- **Scope clarity:** Weak. Three problem clusters of wildly different risk are ratified as one shipping unit (F-08). Boundaries are "recommended," not enforced.
- **Actors:** Adequate. Agents, admin vs non-admin approvers, MCP servers, registry providers all identified.
- **Success criteria:** Mostly present per-decision via confidence blocks, but the security-critical success criterion — *"dangerous tagging is complete"* — has **no measurable definition** (F-02). "Completeness of the dangerous tagging is security-critical" is stated as a risk, never as a verifiable exit condition.
- **Failure modes:** Good on the registry-move blast radius (§7) and the dangerous-rail leak; silent on the per-agent-workspace failure mode (F-01) and the `hot_reload`-off interaction (F-03).
- **Implementation detail:** Sufficient for Part B and D-C1; insufficient for D-A6 (contract shape) and D-A1 (metadata-vs-instance split).
- **`[FACT]` accuracy:** High. Every spot-checked FACT verified true: `/tools` system-only, `registerSharedTools` per-agent, `FilterToolsByPolicy` contract, `Category()/RequiresAdminAsk()` on `base.go`, `/providers` Connected hardcode, `--user-font-size` inert, McpServerModal=Dialog, ClawHub 501 stubs, backend RegistryManager exists. The ADR did not overclaim grounding.

## STRIDE Summary (tools system)

| Component | Threat | Status in ADR |
|-----------|--------|---------------|
| Central builtin registry (D-A1) | Tampering / Info-disclosure: shared per-agent tool instance leaks one agent's workspace to another | **Not addressed** (F-01) |
| `dangerous` rail (D-A3/A5) | Elevation of privilege: mis-tagged/forgotten tool → fresh custom agent gets silent `exec` | Named as risk, **no verifiable control** (F-02, F-07) |
| Per-tool config (D-A6) | Info-disclosure: credential fields in config form | Addressed — `credential-ref` (vault), never plaintext. OK. |
| Tool-approval endpoint | EoP: non-admin approves dangerous tool | Already enforced (`isAdminRole`, `rest_tool_registry.go:388`) — preserved. OK. |
| MCP registration | Spoofing reserved prefix | Already enforced (`ValidateMCPName` rejects `system.`) — preserved. OK. |

## Unasked Questions

1. When two agents each need `exec` bound to their own workspace, what single object lives in the "one central registry"? (F-01 — the ADR has no answer.)
2. What CI gate proves a newly-added tool was given a `dangerous` decision rather than silently defaulting to `false`? (F-02)
3. Does `gateway.users` actually take effect without a restart today, or was it gated for a real reason? (F-03)
4. With `hot_reload` forced on (D-B8), what is the authoritative restart-key set, and is `appliedConfig` re-baselined post-onboarding given it's currently a once-at-boot snapshot? (F-03)
5. What is the closed field-kind enum for `ToolConfigField`, and which configs are per-field-overridable vs global-only? (F-04)
6. What happens to the `scope` field (`system/core/general`) when `category` retires `core`/`system`? (F-05)
7. Where does the 2–3 min token expiry actually originate? (F-11)

---

## Verdict

**REVISE** — 3 CRITICAL findings. D-A1 needs the metadata-vs-instance split before it is safe to plan-spec; D-A3/A5 need a verifiable `dangerous`-completeness control; D-B2/B8 need their `hot_reload` interaction resolved. Once F-01/F-02/F-03 are addressed in the ADR (and F-04–F-08 folded into the plan-spec boundaries), hand off to `/plan-spec` as three sequenced specs.
