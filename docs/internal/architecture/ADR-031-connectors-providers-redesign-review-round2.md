## Executive Summary

Re-grilling the R1-revised ADR-031. Most R1 fixes hold up against source (verified: `knownProtocols` = 61 entries; `AVAILABLE_PROVIDERS` = 30 variants / 15 companies; `_app.tsx` onboarding-before-auth ordering; ProvidersSection baseline; `/providers` = `withOptionalAuth`; `contract_test.go` exists; ADR-029 still `Proposed`). R1 did real work.

But the re-grill surfaces **one CRITICAL contradiction between a load-bearing FACT-derivation rule and the code it cites** (the `endpointHost` rule is wrong for 3 of the 5 providers it names), plus **4 MAJOR** issues — the most serious being that the F-07 refinement's entire justification (frontend-side localization) rests on an i18n system that **does not exist in the codebase**, making a headline "recommended refinement" speculative future-proofing rather than a grounded improvement.

- **Findings:** 1 CRITICAL, 4 MAJOR, 5 MINOR, 2 OBSERVATION.
- **Verdict: REVISE.** The `endpointHost` contradiction must be corrected before `/plan-spec` (an implementer will code the rule as written and it will diverge from `GetDefaultAPIBase`). The F-07 localizability basis must be re-grounded or the refinement re-justified on other grounds.

## Structural Integrity (generic-markdown mode — narrative)

- **Scope clarity:** Strong. In-scope (Channels + Providers + onboarding ModelKeyStep + login) and out-of-scope (routing/probe behavior, ADR-029 binding semantics) are explicit (§7 scope-creep note).
- **Actors:** Covered (operators/admins, onboarding flow, Settings screens). No system-actor gap.
- **Success criteria:** FR-10/FR-11/FR-12 now carry testable acceptance criteria (R1 win, verified). But **FR-1..FR-5 and FR-7 have no acceptance criteria** — they're asserted as `[FACT: user decision]` without a "done when" check. For a spec headed to `/plan-spec` that's tolerable (plan-spec adds BDD), but the ADR should not imply they're verifiable as-is.
- **Failure modes:** Partially addressed — R2-06 (state-fetch failure), R2-05 (rollback), R2-01 (endpoint derivation edge) are gaps.
- **Dependencies:** ADR-029 dependency is well-identified (F-10). The i18n dependency behind F-07 (R2-02) is **not** identified — the ADR assumes a capability it lacks.
- **Cross-references:** Internally consistent except R2-08 (§8 vs §6 contradiction on "derived/structural").

## Test-Coverage / Testability Assessment

- FR-11 (unknown-slug → lettermark) and FR-12 (SVG token check) have concrete, cheap unit tests. Good.
- The drift-guard (§6 G-2 pt 2) is testable but its *classification* input is hand-authored (R2-07) — the test can't validate the taxonomy, only membership.
- The NFR-1 "consistency test" (§9: both surfaces render identical terminology + logos) is well-motivated but under-specified: with G-3=C (duplicated pickers), the test can only assert *word/logo* parity, not *interaction* parity (the ADR concedes this in F-15). Plan-spec should scope the consistency test to exactly what G-2=B guarantees (terminology + logo), not imply layout parity.
- **Missing:** no test named for R2-01's `endpointHost` correctness (the highest-risk derivation). Plan-spec must add a table-test asserting `endpointHost(id)` for every catalog id against `GetDefaultAPIBase`, *including* the empty-for-deployment-configured cases.

## Unasked Questions

1. **Why "Standard API" and not "Pay-as-you-go API"?** (R2-04) The current label conveys the billing model the entire variant UX exists to disambiguate. What problem does the rename solve?
2. **Does the endpoint survive under B, or is a build-time embed the honest delivery of "one SoT"?** (R2-10) The operator chose "backend-owned" — did they choose "served over the wire at runtime," or is that an unexamined implementation assumption?
3. **What actually happens to the ollama/vllm/litellm row's endpoint display?** (R2-03) Today `endpointHint` shows `localhost:11434`; the new rule shows nothing. Intended?
4. **Is there any i18n on the roadmap?** (R2-02) If not, the F-07 split loses its headline justification and the operator's simpler "strings on the wire" stands.
5. **How is a mis-classified new protocol caught?** (R2-07) The drift-guard catches *unlisted* ids; it cannot catch an id wrongly tagged alias-vs-user-facing. Is human triage on every new protocol the accepted control?

None of these is a fundamental-direction defect — the ratified FR-1..FR-9 direction and the three fork decisions stand. These are precision defects in the R1-added contract-derivation detail, exactly the layer that must be exact before `/plan-spec` turns it into code.
