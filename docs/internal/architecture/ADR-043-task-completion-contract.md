# ADR-043 — Standardized Task Completion Contract (Fail-Closed on No Signal)

**Status:** Accepted (operator decision, 2026-07-13)
**Date:** 2026-07-13
**Deciders:** Daniel Piatkowski (product owner)
**Relates to:** [ADR-042 — Extend Task Execution to `subagent_3p` (External-CLI) Workers](./ADR-042-external-cli-task-execution.md) (§3's auto-complete false-success cascade, which this ADR supersedes); [ADR-032](./ADR-032-external-agent-workspace-execution.md), [ADR-036](./ADR-036-consolidate-shell-and-subagent-tools.md), [ADR-037](./ADR-037-remove-global-delegation-policy.md) (dispatch/identity/delegation machinery this ADR does not touch)
**Implementation:** `pkg/agent/task_completion_signal.go` (parser), `pkg/agent/task_executor.go` (`finishTaskRun`, `completeTaskWithResult`, `buildPrompt`)

---

## 1. Context

Before this ADR, `TaskExecutor.finishTaskRun` (`pkg/agent/task_executor.go`) auto-completed any task whose agent did not call `task_update` to a terminal status: it patched the task to `StatusDone`, used the run's raw response text as `Result` (or the literal string `"Task completed"` when the response was empty), and — via `onTaskComplete` — auto-advanced any `blocked_by` dependent whose only remaining blocker had just gone `Done`.

This was always a real gap, but ADR-042 §3 made it structural rather than incidental: extending task execution to `subagent_3p` (external-CLI) workers meant a dispatch kind with **no `task_update` tool at all** now reaches this branch on *every single run*, not just the rare "native agent forgot to call the tool" case. ADR-042 §3 named the consequence directly:

> An external CLI that exits cleanly after prose like "I could not complete this" (no crash, no fatal driver event) is auto-completed to `StatusDone` exactly the same as a genuine success, because there is no structured signal to distinguish the two... a single unverified "success" can silently unblock and dispatch downstream dependents that assumed real work was done.

ADR-042's shipped mitigation was a `slog.Warn` on the external-CLI auto-complete path — visibility only, not a fix. ADR-042 §3 explicitly deferred the real fix as "a stricter completion contract for `subagent_3p` executors... out of scope for this ADR." This ADR is that follow-up, and the operator's ruling on it is unambiguous: **defaulting to success when the agent gives no signal is forbidden, full stop** — not just for external-CLI workers, but uniformly, since a native agent that emits a plain response and forgets `task_update` is exactly the same "no signal" situation the external-CLI case merely made unavoidable.

## 2. Decision

**Replace the auto-complete-to-Done default with a standardized, machine-parseable completion marker that the agent's final output must carry when it did not call `task_update` — and fail the task closed (`StatusFailed`) when no such marker is found.** This is uniform across every agent type and dispatch kind (native + `subagent_3p`/external-CLI); there is no code path left where "the agent said nothing conclusive" resolves to success.

### 2.1 Precedence: explicit `task_update` still wins outright

`finishTaskRun`'s existing re-read-and-check-`task.IsTerminal` gate (`task_executor.go:299-309`, unchanged) still runs first. A native agent that calls `task_update` to a terminal status mid-run is unaffected by anything in this ADR — the marker contract only engages when that check finds the task still non-terminal, i.e. no explicit tool call happened.

### 2.2 The marker format

Implemented in `parseTaskCompletionSignal` (`pkg/agent/task_completion_signal.go`), covered by unit tests in `task_completion_signal_test.go` with no `AgentLoop`/dispatch dependency — several cases (markdown-wrapping variants, trailing-content tolerance, its negatives) are genuinely table-driven (`t.Run` subtests over a `[]struct{...}` case table); the rest (fence-awareness, last-occurrence-wins, CRLF, the two result-size caps) are individually named tests, not one large table. "Covered by unit tests" is the accurate framing; treat "table-driven" as describing a subset, not the whole file.

**Revised 2026-07-13** (post-implementation review — see the Implementation Review Changelog at the end of this ADR) to add fence-awareness, trailing-content tolerance, and the two result-size caps on top of the format originally decided:

- A line containing `TASK_STATUS: success` or `TASK_STATUS: failure` — case-insensitive, tolerant of markdown emphasis wrapping the whole line, just the label, just the colon, or just the value (`**TASK_STATUS: success**`, `` `TASK_STATUS: failure` ``, `TASK_STATUS: **success**`, `**TASK_STATUS:** success`, `**TASK_STATUS**: success`, ...), AND of trailing punctuation or short trailing prose after the value (`TASK_STATUS: success.`, `TASK_STATUS: success — all tests pass`). The captured value is always the FIRST `success`/`failure` token immediately after the label+colon+wrapper, so trailing prose that happens to mention the other status word never changes it, and a `\b` word-boundary guard stops a value like `successful` from being misread as `success`. A line whose value is neither `success` nor `failure` (e.g. a hedge like `TASK_STATUS: maybe`) simply does not match — it is not a recognized signal.
- **Lines inside (or forming) a ` ``` `/`~~~` fenced code block are ignored for BOTH the status and summary matches.** Closes a false-success gap found post-implementation: a model explaining the expected format by quoting the marker inside a fenced example (e.g. "I'll report like this: `` ```TASK_STATUS: success``` `` " while the surrounding prose says it is still mid-task) no longer counts as a real signal — it fails closed instead, exactly as no marker at all would. **A fence's closing delimiter must match its opener's type** (` ``` ` closes only ` ``` `, `~~~` closes only `~~~`, per CommonMark) — `computeFencedLines` tracks which delimiter opened the current fence and only a line of that same type closes it; a line of the *other* delimiter type while already fenced is just fenced content, not a boundary (hardening review finding H1, 2026-07-13 — see the second changelog entry below; the originally-shipped version toggled a single bool on either delimiter, so a `~~~` line could wrongly close a ` ``` `-opened fence early).
- **A line is also never treated as a marker line — independent of fencing — when it is markdown-indented as a code block, or when it is bullet/numbered-list-prefixed** (hardening review findings H2/H3, 2026-07-13): a leading tab, or 4-or-more leading spaces, reads as an indented code block (markdown's own threshold; a 1-3 space indent — `buildPrompt`'s own instruction lines use 2 — still matches normally); a leading `* `, `- `, `+ `, or `1. `-style numbered prefix reads as a model paraphrasing the instruction as a list item, not emitting it. Bold emphasis (`**TASK_STATUS**: success`) is deliberately NOT treated as a bullet — the distinguisher is whitespace immediately after the marker character (`* ` = bullet) versus another `*` (`**` = bold, no whitespace) — so it still matches. Implemented as a small pre-check (`isExcludedMarkerLine`) run before the regex match, not folded into the regex itself.
- An optional following `TASK_SUMMARY: <text>` line. When present, the summary text **plus every subsequent line to the end of the output** (CRLF-normalized — no embedded `\r`) becomes the task's `Result`, replacing the raw response (so an agent's scratch reasoning ahead of the marker never leaks into the persisted `Result`). When absent, the **full raw output** remains `Result` — unchanged, marker line included. Either way, `Result` is bounded to `maxFoundSignalResultChars` (8000 runes, rune-safe truncation) so a runaway response can't bloat the task store even on a genuine completion — this cap did not exist in the originally-shipped version, which left the no-`TASK_SUMMARY` path unbounded.
- **Last non-fenced, non-excluded occurrence wins.** The parser scans every non-fenced, non-indented, non-bullet-prefixed line and keeps overwriting its match on `TASK_STATUS`, so if a model echoes the instruction earlier in its own reasoning (a real, observed LLM behavior) and then emits the real signal at the end, the trailing one governs. See §3's accepted-limitation note on what this means for a marker whose own `TASK_SUMMARY` body quotes an unfenced standalone `TASK_STATUS` line.
- Empty or whitespace-only output, or output with no parseable `TASK_STATUS` line anywhere, yields "not found" — there is no partial-credit or best-effort inference attempted.

### 2.3 Fail-closed on no signal

`finishTaskRun` (`task_executor.go:250`), once the explicit-`task_update` check has been ruled out, calls `parseTaskCompletionSignal(resp)`:

- **Found, success** → `completeTaskWithResult(t, taskSessionID, task.StatusDone, signal.Result)` (`task_executor.go:360`).
- **Found, failure** → same call with `task.StatusFailed`. `Result` is the agent's own reported words (the `TASK_SUMMARY` text, or the full output if no summary) — this is *not* framed as a missing-signal failure; the agent did report an outcome, and its words are kept verbatim.
- **Not found** (includes the empty-output case) → `task.StatusFailed`, with a `Result` that explicitly explains the situation to a human: *"agent finished without a completion signal (TASK_STATUS line) — review the run transcript and re-run; raw output follows: ..."*, embedding the raw output (bounded to `maxFailClosedOutputChars` = 2000 chars via `truncateTaskOutput`, noting truncation when it applies; a placeholder `"(agent produced no output)"` when the output was genuinely empty). A `slog`-backed `logger.WarnCF` fires here — and *only* here; the two signal-found branches above are ordinary, expected completions and log nothing extra. This directly replaces the old external-CLI-specific auto-complete `WARN` (ADR-042 §3's mitigation): a signal-based completion needs no warning at all now; a fail-closed one still does, because it is the situation an operator needs to notice and investigate.

`completeTaskWithResult` is a new shared helper factoring out the store update + session-archive + `onTaskComplete` + `notifySourceChannel` sequence that used to be inlined in the auto-complete block, used by all three of the above outcomes. It is deliberately **not** used by the pre-existing hard-error branch above it in `finishTaskRun` (a Go `error` from the dispatch itself, e.g. an LLM provider error or a fatal external-CLI event) — that branch keeps calling `failTask` exactly as before, including its narrower behavior (no parent-follow-up notification). That asymmetry predates this ADR and is out of scope for it.

### 2.4 Prompt side: instruct every dispatch kind, keep `task_update` preferred where it exists

`TaskExecutor.buildPrompt` (`task_executor.go`) now always appends the marker instruction (a few lines: the `TASK_STATUS`/`TASK_SUMMARY` shape, both success and failure forms) regardless of dispatch kind. The existing `dispatchesExternalCLI` gate (`task_executor.go`, unchanged) still decides one thing only: whether the *additional* `task_update` tool-call instruction is appended afterward. Native agents get both instructions (`update_task` called out as taking priority since it is a structured, unambiguous signal — the instruction text previously misnamed this tool `task_update`, fixed alongside the revision below); `subagent_3p` (external-CLI) agents — which have no `update_task` tool wired to Omnipus at all — get the marker instruction only, since it is their only possible completion signal.

**Echo-safety (revised 2026-07-13):** with §2.2's trailing-content tolerance, the ORIGINAL single-line instruction ("`TASK_STATUS: success` (or `TASK_STATUS: failure` if unsuccessful)") would itself parse as a `success` signal if a model echoed the instruction text verbatim as its own final message without ever emitting a real signal — a false success from the *instruction*, not from anything the agent reported. `buildPrompt` now lists the two `TASK_STATUS` lines as separate, clean lines with the **failure variant deliberately last**:

```
When you are done, end your final message with ONE of the two status lines below (never both), plus an optional one-line summary:
  TASK_STATUS: success
  TASK_STATUS: failure
  TASK_SUMMARY: <one-paragraph summary of the outcome>
```

Because `parseTaskCompletionSignal` takes the LAST non-fenced occurrence, a raw echo of this block (with no real signal following it) resolves to `verdictFailure` — the safe direction — never `verdictSuccess`. This invariant is pinned by `TestBuildPrompt_InstructionEchoNeverResolvesToSuccess` (`task_completion_contract_test.go`) for both dispatch kinds; do not reorder the two lines without re-verifying the invariant still holds.

### 2.5 Scope: uniform, not dispatch-specific

This is not an external-CLI-only fix. A native agent that finishes without calling `task_update` is the *same* "no explicit signal" situation as an external-CLI run — before this ADR both silently defaulted to `Done`; after it, both are governed by the identical `parseTaskCompletionSignal` call inside `finishTaskRun`, with no branch distinguishing dispatch kind in the completion-resolution logic itself (only `buildPrompt`'s *prompt wording* differs, per §2.4).

### 2.6 The instruction surviving context eviction (native task runs)

The marker instruction lives only in the task's first user turn (`buildPrompt`'s output, sent as the initial prompt). A long, tool-heavy native task run can trip `windowTrim` (ADR-028's sliding-window eviction) and evict that turn from the live context entirely, silently dropping the instruction for the remainder of the run — a gap identified post-implementation, since ADR-028 predates this ADR and the two were never checked against each other until this review.

**Fix: piggyback on the breadcrumb mechanism, not a second injection path.** `processOptions.IsTaskRun` (`pkg/agent/loop.go`) marks a native task-dispatch turn (set by `processTaskDirect`'s `runAgentLoop` call; the external-CLI dispatch never reaches this code at all, since it does not use the native turn loop or `windowTrim`). `assembleMessages` (`pkg/agent/loop.go`) checks it: whenever the evicted-context breadcrumb block is non-empty (i.e. an eviction has actually happened — the exact condition under which the marker instruction is at risk) AND the turn is a task run, a terse one-line reminder is appended to the SAME breadcrumb block: `` Reminder (task run): end your final message with `TASK_STATUS: success` or `TASK_STATUS: failure` (ADR-043). `` This re-surfaces the instruction precisely when (and only when) it risks having been evicted, at near-zero token cost, and requires no new injection mechanism — it rides the delivery path (`buildBreadcrumb` → `assembleMessages` → `BuildMessages`) that ADR-028 already proved survives eviction.

This does not help the external-CLI dispatch path (`processTaskDirectExternalCLI`), which does not run through `assembleMessages`/`windowTrim` at all — an external CLI manages its own context independently of Omnipus's turn loop, so ADR-028 eviction does not apply to it in the first place.

## 3. Consequences

### Positive

- Closes the exact gap ADR-042 §3 flagged and deferred: a task can no longer silently reach `Done` — and silently unblock downstream `blocked_by` dependents — on prose alone with no structured signal, for any agent type.
- Uniform contract: one parser, one fail-closed branch, covering native forgetfulness and every `subagent_3p` run identically. No new per-dispatch-kind special-casing was introduced in the completion-resolution path.
- `task_update` remains the preferred, unambiguous signal for native agents — this ADR only closes the gap for when it *isn't* called, it does not discourage or replace it.
- A fail-closed result is actionable: it carries the raw agent output (truncated sanely) and an explicit human-readable explanation, not just a bare status flip.

### Negative / accepted

- **A native agent that does real, correct work but forgets both `task_update` and the marker now fails a task that arguably "succeeded."** This is the deliberate trade-off the operator ruled on: false-negative-by-omission (an operator has to notice and re-run) is preferred over false-positive-by-default (a silently wrong `Done` cascading into dependent tasks). The prompt instruction (§2.4) is the mitigation — every dispatch kind is told to emit the marker, and §2.6 mitigates the long-task-eviction case specifically — but a model that ignores its own instructions can still trigger the fail-closed path. This is a known, accepted shift in failure mode, not a new bug.
- **No mid-run, structured progress signal still exists for external-CLI workers** — unchanged from ADR-042 §2's own accepted trade-off; this ADR only changes what happens once the run *returns*, not the run's own observability while in flight.
- **The marker parser is intentionally conservative.** It does not attempt any fuzzy inference of intent from prose that lacks the literal `TASK_STATUS:` marker — an agent that clearly describes success in plain English without the marker still fails closed. This is intentional (a heuristic "does this sound like success" classifier would reintroduce exactly the kind of unverifiable, model-dependent judgment call this ADR exists to remove) but is worth stating plainly so it isn't mistaken for an oversight.
- **A genuine marker whose own `TASK_SUMMARY` body later quotes an unfenced, standalone `TASK_STATUS` line has its verdict flipped by that later line** (`parseTaskCompletionSignal`'s "last non-fenced occurrence wins" rule, §2.2). Fencing (` ``` `/`~~~`) the common "quoting the format as an example" case is handled (§2.2), but a genuinely bare marker line embedded in prose — e.g. a summary that says `The old status was TASK_STATUS: failure before I fixed it` — still flips the result. Accepted as simple-and-predictable over a more complex heuristic (e.g. "only the first marker after the summary label counts"); pinned by `TestParseTaskCompletionSignal_UnfencedLaterMarkerFlipsVerdict_KnownLimitation`. Mitigation is operator/prompt-level: don't embed bare `TASK_STATUS:` lines in summary prose; fence them if you must quote the format.
- **`completeTaskWithResult`'s store-write failure leaves the task stuck `in_progress`, logged but not retried or forced.** If `te.store.Update` fails when writing the terminal status/result (disk full, permissions, corruption), the task is left exactly as it was before the call — no second write is attempted, and no synthetic failure status is forced. This is deliberate: a persistent store failure would likely fail an immediate retry identically, and forcing a follow-up write risks compounding a partially-written task file rather than recovering it. An operator must notice the `ERROR` log (`"Completion update failed"`) and resolve the stuck task manually.
- **`notifySourceChannel`'s 500-character truncation is independent of, and smaller than, the two parser-level result caps** (`maxFailClosedOutputChars` = 2000, `maxFoundSignalResultChars` = 8000). The task's persisted `Result` can legitimately be up to 8000 runes; only the compact channel notification message truncates further, to 500 characters (`task_executor.go`'s `notifySourceChannel`). This is intentional (a channel message is a notification, not the durable record — the full `Result` remains readable via the task itself) but is worth stating so a future reader doesn't assume the two truncation points share one constant or one purpose.
- **An unbalanced opening fence with no matching close anywhere in the output swallows every line after it, including a genuine trailing marker, and fails the task closed** (`computeFencedLines`' documented conservative choice: an unterminated fence fences everything through the end of the output). Accepted-safe direction, unchanged by the 2026-07-13 hardening pass — pinned by `TestParseTaskCompletionSignal_UnclosedFence_FailsClosed_KnownLimitation`. A model that opens a fenced example and never closes it loses its own trailing signal; this is preferred over guessing where an unterminated fence "should" have closed.
- **A blockquote-prefixed marker line (`> TASK_STATUS: success`) does not match and fails closed** — `> ` is not part of the tolerated wrapper class (§2.2). Accepted, not an oversight; pinned by `TestParseTaskCompletionSignal_BlockquotePrefixed_NotAMarker`.

## 4. Alternatives considered

**(a) Keep auto-complete-to-Done but gate `blocked_by` auto-advance on a separate, stricter check.** Rejected — this only protects *downstream dependents*, not the task's own status/Result, which would still misreport an unverified prose failure as `Done`. The operator's ruling was about the default itself, not just its blast radius.

**(b) Require the marker only for `subagent_3p` (external-CLI) dispatch, leave native auto-complete-to-Done unchanged.** Rejected — a native agent forgetting `task_update` is the identical "no signal" situation; carving out an exception for it would reintroduce the exact default the operator ruled out, just scoped narrower. Uniformity was an explicit part of the decision, not an implementation convenience.

**(c) A heuristic/LLM-judged classifier over the raw response to infer success/failure when no marker is present.** Rejected — trades one unverifiable inference (silent auto-complete) for another (a second model's guess about the first model's prose), adds latency/cost, and is significantly harder to test deterministically than a literal marker line. The marker is cheap, explicit, and the same shape a model can reliably reproduce when instructed.

## 7. Implementation Review Changelog (2026-07-13)

A 7-reviewer gate on the initial implementation found and fixed the following before merge; this ADR's body above already reflects the revised behavior — this changelog is the record of what changed and why, for anyone diffing against an earlier reading of this document.

- **Parser grammar:** fence-awareness (§2.2) closed a false-success gap where a model quoting the marker inside a formatting example (fenced code block) counted as a real signal. Trailing-content tolerance (§2.2) fixed the opposite failure mode — genuine markers with trailing punctuation or short trailing prose (`TASK_STATUS: success.`, `**TASK_STATUS**: success`) were previously rejected outright, which would have fail-closed real successes. A CRLF bug (embedded `\r` bytes leaking into a folded multi-line `TASK_SUMMARY` result) was fixed. Two result-size caps were added (§2.2) — the found-signal path had no bound at all before this review. `truncateTaskOutput` was made rune-safe (previously a byte-index slice that could split a multi-byte UTF-8 rune mid-sequence).
- **Type design:** the `Found bool` / `Success bool` field pair (which allowed the meaningless `Found=false, Success=true` combination to be constructed) was collapsed into a tri-state `completionVerdict` with `Found()`/`Status()` methods.
- **Prompt echo-safety:** §2.4's instruction was redesigned so a verbatim echo of the instruction text can never resolve to `verdictSuccess` — the failure-variant line is deliberately last, exploiting the parser's own last-occurrence-wins rule in the safe direction. Pinned by a dedicated round-trip test.
- **Context-eviction interaction:** §2.6 closes a previously-undocumented gap where a long, tool-heavy native task run could have its marker instruction evicted from context by `windowTrim` (ADR-028) before the run ever finished.
- **Executor hardening:** `completeTaskWithResult`'s parameter was narrowed from `task.Status` to a plain `success bool` so writing a non-terminal status here is a compile-time error, not just a reviewable mistake. The store-write-failure comment (§3) was clarified to state its consequence plainly rather than leave it implicit.
- **Stale documentation:** `processTaskDirectExternalCLI`'s doc comment (`pkg/agent/loop.go`) still described the retired auto-complete-to-Done default and a "FIX 8" WARN reference; rewritten to describe the marker contract. ADR-042 §2.3 and its §3 "Positive" bullet were annotated with supersession pointers to this ADR.
- **New end-to-end coverage:** a blocked-dependent-stays-blocked test (the headline regression this ADR exists to close — a task blocked on a failed-not-done blocker must never advance), an explicit-`update_task`-call-wins-over-a-markerless-final-response precedence test, and a session-archival-on-completion test.

## 7.1 Hardening Review Changelog (2026-07-13, post-review-gate)

An adversarial verification pass over the already-merged §7 implementation found four further holes plus one note in the parser grammar; §2.2/§3 above already reflect the fixed behavior — this changelog is the record of what changed.

- **H1 — mixed fence delimiter types (fixed).** `computeFencedLines` toggled a single `inFence` bool on EITHER ` ``` ` or `~~~`, so a ` ``` `-opened fence could be wrongly closed early by a `~~~` line inside it (and vice versa) — CommonMark requires the closing delimiter to match the opener's type. Fixed by tracking which delimiter opened the current fence (`fenceDelim`); only a line of that same type closes it. Pinned by `TestComputeFencedLines_MixedDelimiterTypes` (direct unit coverage of the fenced-boolean output) and `TestParseTaskCompletionSignal_MixedFenceDelimiters_DoNotCrossClose`/`..._RealMarkerAfterProperCloseFound` (integration-level, both delimiter orderings, plus a positive case proving the fix doesn't over-fence past a properly-matched close).
- **H2 — bullet-list false success (fixed).** The wrapper class `[*`_\s]*` accepted a `* ` bullet prefix as just more whitespace, so a model paraphrasing the instruction as a bulleted list (e.g. `* \`TASK_STATUS: failure\` - otherwise` / `* \`TASK_STATUS: success\` - if all tests pass`, success last) parsed as a false SUCCESS. Fixed with a pre-regex gate (`isExcludedMarkerLine` + `bulletOrNumberedListPrefixRe`) that rejects a line whose first non-space content is a markdown bullet (`* `, `- `, `+ `) or numbered-list marker (`1. `), implemented as a separate predicate rather than grown into the marker regex itself for readability. Deliberately narrow so it does not misfire on markdown bold (`**TASK_STATUS**: success` — `*` immediately followed by another `*`, never whitespace) or italic (`*TASK_STATUS: success*` — no whitespace after the `*`), both of which still match. Pinned by `TestParseTaskCompletionSignal_BulletPrefixedLine_NotAMarker` (asterisk/hyphen/plus/numbered rejection, bulleted-both-variants-success-last false-success repro, bold-still-matches) and an extension of `TestBuildPrompt_InstructionEchoNeverResolvesToSuccess`'s `bulleted_paraphrase` subtest (a bulleted reformatting of `buildPrompt`'s own instruction lines must not resolve to `verdictSuccess`).
- **H3 — indented code blocks (fixed).** A marker inside a markdown indented code block (leading tab, or 4-or-more leading spaces) counted as a live signal, since the wrapper class swallows leading whitespace unconditionally.
