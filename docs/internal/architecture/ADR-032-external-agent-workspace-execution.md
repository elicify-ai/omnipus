## 1. Problem

`subagent_3p` (external-CLI delegation to `claude-code` / `codex` / `opencode`, dispatched via `pkg/agent/subturn.go` → `pkg/agent/external_dispatch.go`) had four compounding execution bugs, discovered when tracing an actual delegation:

1. **Wrong working directory.** The run executed inside a throwaway isolated dir (`$OMNIPUS_HOME/runner-runs/run-<id>`, a `git worktree` copy or — for a non-repo workspace — an **empty scratch temp dir**), never the agent's actual workspace. The external CLI saw none of the files the delegating conversation cared about.
2. **Wrong identity.** The dispatch-kind decision (native vs external-cli) and, for external-cli runs, the workspace/model/turn-cap/executor config all came from the **delegating PARENT's** `AgentInstance` (`baseAgent` in `spawnSubTurn`), never the **TARGET** worker named by `TargetAgentID`. A native parent delegating to an external-cli worker could silently dispatch natively (the parent had no `Subagents.Executor`); an external-cli run that did dispatch correctly still ran with the parent's workspace and model, not the target's.
3. **No model set.** The external CLI was never told which model to use (no `--model`/`-m` flag), so it fell back to its own CLI-level default regardless of what the agent was configured with.
4. **Per-tool flag defects.** Verified against the real installed `claude` (v2.1.198) and `opencode` (v1.16.0) CLIs, and against Codex CLI reference docs (codex not installed locally): `claude`'s `--output-format stream-json` emits nothing without `--verbose`; the driver appended `--resume <RunID>` where `RunID` is a freshly generated dispatch id, not a real prior session, which errors; `opencode`'s `run` subcommand has **no `--prompt` flag at all** (the driver was passing one that would fail on every real invocation — verified via `opencode run --help`), the message is a positional argument; `opencode`'s `-s/--session` resumes an *existing* session and errors on a fresh id; `codex`'s `-a/--ask-for-approval` is a **global** flag that errors when placed after the `exec` subcommand. None of the three drivers had a non-interactive, non-bypass approval posture, so a headless run had no way to proceed without stalling on an interactive prompt that never arrives.

## 2. Decisions

1. **Run in the workspace working directory.** `runExternalCLISubTurn` (`pkg/agent/external_dispatch.go`) now sets `RunOptions.WorkDir` to the resolved agent's own `Workspace` directory directly (`os.MkdirAll` to ensure it exists), not an isolated worktree/tempdir copy. **This intentionally relaxes the original Spec-4 FR-5.3 worktree-isolation boundary for external CLIs.** The external CLI's own sandbox remains the enforced security boundary — Omnipus adds no new confiner either way — for **codex** (Landlock/seccomp on Linux, engaged via `--sandbox workspace-write` per §2.4). **opencode is the exception, corrected here:** its CLI-level tool gating is the very mechanism `--dangerously-skip-permissions` (§2.4) turns OFF — for an opencode-backed run, that gating is disabled, not standing as "its own tool gating." See the compounded-risk discussion in §3. **claude is now the same exception, corrected 2026-07-05 (operator decision, issue #488):** its driver was originally narrowed to `--permission-mode acceptEdits` (below), but that flag is superseded — claude's driver now passes `--dangerously-skip-permissions` unconditionally, the same bypass mechanism opencode uses, so claude's own permission model is disabled too, not standing as "its own permission model." claude now carries the same zero-enforced-boundary characterization §3 gives opencode; **only codex** retains an enforced sandbox boundary of its own. No teardown step: the workspace is the agent's persistent tree, not a scratch dir. `pkg/agent/runner/worktree.go` (`PrepareWorkspace`/`RunWorkspace`/`Teardown`) is left in place (its own tests still pass) but is no longer called from the dispatch site; the boot-time reaper (`pkg/agent/runner/reaper.go`) still cleans up any pre-existing orphan dirs from before this change.
2. **Use the TARGET worker's own identity.** `spawnSubTurn` (`pkg/agent/subturn.go`) resolves the delegate named by `TargetAgentID` via `al.registry.GetAgent(...)`. The dispatch-kind decision (`runner.ResolveDispatch`) now reads the **resolved delegate's** `Subagents.Executor`, not the parent's. ~~When dispatch resolves to `external-cli` and a target was resolved, the child `AgentInstance`'s `Workspace`, `Model`, `MaxIterations`, and `Subagents` are sourced from the target, not the parent. Native dispatch is deliberately left byte-for-byte unchanged (still parent-sourced) to avoid a `Model`/`Candidates`/`Provider` consistency issue in the native LLM-call resolution path — rebuilding that pool per-delegate is a larger refactor out of this fix's scope.~~ — **superseded 2026-07-09 (operator decision): see the amendment above.** EVERY agent-level setting (identity, workspace, tools, tool policy, and now Model/Provider/Candidates/ProviderPool too) is sourced from the resolved target, for BOTH native and external-cli dispatch — a delegated sub-turn inherits nothing from the parent. An unresolvable target (deleted/renamed, or self-delegation with `TargetAgentID==""`) falls back to the parent's own config exactly as before — self-delegation trivially satisfies "inherit nothing from the parent" by being its own source.
3. **Auto-set the model.** `RunOptions` gained a `Model` field, populated from the resolved delegate's `Model`. Each driver's `buildArgs` sets the CLI's model flag when non-empty (`--model` for claude, `-m` for codex); opencode additionally guards on `provider/model` shape (its CLI-level `--model` flag requires that form) so a bare model name configured for a claude/codex agent is never passed to opencode as garbage.
4. **Non-interactive, workspace-write approval posture** (so headless runs never stall waiting on a TTY that will never answer):
   - **claude:** ~~`--permission-mode acceptEdits` (auto-approves file edits without the full `--dangerously-skip-permissions` bypass, which stays deliberately unused per FR-5.3/US-5)`~~ — **superseded 2026-07-05 (operator decision, issue #488):** the acceptEdits middle ground had no reachable approval UI in a headless run and stalled forever on any non-edit tool call, so the driver now passes `--dangerously-skip-permissions` unconditionally instead, matching codex/opencode's already-unconditional flags. claude no longer has a narrowed permission posture of its own — see the §2.1 and §3 corrections.
   - **codex:** `--ask-for-approval never` (placed **before** `exec` — a global flag, confirmed to error if placed after `exec`) plus `--sandbox workspace-write` (an exec-subcommand flag, placed after `exec`); `--dangerously-bypass-approvals-and-sandbox` stays deliberately unused.
   - **opencode:** `--dangerously-skip-permissions`. This CLI version exposes no middle-ground flag (only the interactive default or a full bypass); Omnipus's own consent routing for opencode is already best-effort/post-hoc regardless of this flag (a `tool.start` event is only observed after the call has begun either way — see `OpencodeDriver.Decide`'s POST-HOC note), so this does not regress Omnipus's own posture, only opencode's willingness to proceed headless. Flagged for operator reconsideration if a future opencode version adds a narrower auto-approve mode.
5. **Per-tool flag corrections**, verified where a real binary was available (see §1.4): claude gets `--verbose` and drops `--resume`; opencode's prompt moves from a nonexistent `--prompt` flag to the documented positional `[message..]` argument and drops `--session <RunID>` for fresh runs; codex's `--ask-for-approval` moves ahead of `exec`.

## 3. Consequences

- **Positive:** external-CLI delegation actually works end-to-end for the first time in the traced scenario — correct cwd, correct identity, correct model, non-stalling headless execution, and flags that match the real CLIs rather than an assumed/stale surface.
- **Negative / accepted risk:** the FR-5.3 worktree-isolation guarantee no longer applies to external CLIs — a misbehaving or compromised external CLI can now write anywhere in the agent's real workspace, not just a disposable copy. Accepted because the external CLI's own sandbox was already the actual security boundary (Omnipus added no confiner either way), and the isolated-copy behavior was actively harmful (CLIs saw no real files, defeating the point of delegation for anything beyond a stateless one-shot task). **This "the tool's own sandbox is the boundary" reasoning does not hold for opencode — see the compounded-risk item below.**
- **Compounded opencode risk — DECIDED (2026-07-02): accepted as an operator-trust boundary.** For an opencode-backed `subagent_3p`, three things now combine: (a) worktree isolation is removed by this ADR (decision 1) — opencode runs directly in the real workspace, not a disposable copy; (b) opencode is driven with `--dangerously-skip-permissions` (decision 4) — v1.16.0's *only* non-interactive option, since the interactive alternative hangs headless with no TTY ever available to answer it; and (c) per ADR-019 ("the CLI self-sandboxes"), Omnipus applies **no kernel confiner of its own** on the external-CLI path. Combined, an opencode child has **zero enforced boundary**: it can read `master.key`, `credentials.json`, or any other agent's workspace, and run arbitrary shell as the service user. Contrast **codex**, which retains a real boundary even under this ADR's own flags — its `--sandbox workspace-write` is an OS-level sandbox (Landlock/seccomp), not a permission prompt that gets waved through. *(This paragraph originally also contrasted claude here, on the strength of `--permission-mode acceptEdits` gating non-edit tools such as `Bash`; that contrast is now WRONG — see the 2026-07-05 correction below.)* **Operator decision (2026-07-02, Daniel Piatkowski): option (iii) — accept the risk as an operator-trust boundary, with NO change to the opencode posture and, at the operator's explicit direction, NO UI warning.** Rationale: configuring an opencode `subagent_3p` and wiring a delegation edge to it is itself a deliberate, privileged operator action, so opencode workers run under the operator's own trust. The alternatives — (i) apply an Omnipus Landlock/seccomp confiner to the opencode child (a scoped, opencode-only exception to ADR-019's "no new confiner" premise), or (ii) disable opencode as a `subagent_3p` executor until upstream ships a narrower non-interactive flag — were considered and NOT taken; either remains available if this is revisited. **Corrected 2026-07-05 (operator decision, issue #488): only codex retains its real boundary (above) and is unaffected.** claude no longer does — its driver now passes `--dangerously-skip-permissions` unconditionally (see §2.1/§2.4), so claude has joined opencode in the zero-enforced-boundary group this paragraph describes; it is no longer an exception to the risk analyzed here.
- **Concurrency: same-workspace race risk.** Removing per-run worktree isolation (decision 1) means two concurrent sub-turns that target the *same* delegate agent now execute in the *same* workspace directory at the same time, which can race on file writes or corrupt a git index if the workspace is a repo. Mitigation: the implementation adds a per-workspace-path serialization guard in this same change (concurrent runs against the same workspace path are queued, not parallelized); runs against *different* workspace paths remain fully concurrent, unaffected.
- **Codex sandbox boundary is doc-verified only.** Unlike claude and opencode (both verified against a real installed binary, §1 point 4), the `codex --sandbox workspace-write` boundary relied on in decisions 2 and 4 is verified only against Codex CLI reference documentation — codex is not installed in this environment. Its actual enforced semantics (in particular, whether writes outside the workspace are truly denied, and whether network egress is blocked as documented) should be live-verified against a real `codex` binary before this boundary is relied on as codex's primary security guarantee.
- **`--dangerously-skip-permissions` on opencode** is the one posture choice most likely to need revisiting — it is a strictly more permissive flag than the claude/codex equivalents chosen here, adopted only because this opencode CLI version (v1.16.0) has no narrower option. **Per the operator decision above (option iii), it is accepted as-is for now** — revisit if/when opencode ships an `acceptEdits`-equivalent. (See the compounded-risk item above for the full blast-radius discussion behind that decision.)
