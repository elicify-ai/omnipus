# ADR-042 — Extend Task Execution to `subagent_3p` (External-CLI) Workers

**Status:** Accepted (operator decision, 2026-07-13)
**Date:** 2026-07-13
**Deciders:** Daniel Piatkowski (product owner); architect (ratified)
**Relates to:** [ADR-032 — External-Agent (subagent_3p) Workspace Execution & Identity](./ADR-032-external-agent-workspace-execution.md) (the dispatch/identity machinery this ADR routes task runs through), [ADR-036 — Consolidate Shell and Subagent Tools](./ADR-036-consolidate-shell-and-subagent-tools.md) (`delegate` tool, `EdgeModeCategory` mode collapse), [ADR-037 — Remove the Global Per-Agent Delegation Policy](./ADR-037-remove-global-delegation-policy.md) (workspace-scoped trust as the sole delegation authority; unaffected by this ADR)

Line-number citations to `pkg/agent/loop.go`, `pkg/agent/runner/dispatch.go`, and `pkg/agent/task_executor.go` in this document have been re-verified against the tree as of that fix pass (all other citations retain their original "as read at decision time" caveat).

## 1. Context

Task execution (`AgentLoop.processTaskDirect`, `pkg/agent/loop.go:3871`) has always run every task on the **native** Omnipus engine, unconditionally — `processTaskDirect` resolves the assigned agent from the registry and calls `al.runAgentLoop(...)` directly, with no branch on the agent's executor kind. This is a different, parallel code path from agent-to-agent delegation (`spawnSubTurn` → `pkg/agent/subturn.go`), which **does** branch: it calls `runner.ResolveDispatch(executorConfigOf(target))` (`pkg/agent/runner/dispatch.go:92`) and, when the target's `SubagentsConfig.Executor.Kind == "external-cli"`, routes through `runExternalCLISubTurn` (`pkg/agent/external_dispatch.go:107`, the ADR-032 machinery: workspace/CoreTeam `work/`-dir resolution, per-workspace serialization lock, env scrubbing, driver dispatch, non-interactive approval posture).

Because the task-run path had no equivalent branch, assigning a task to a `subagent_3p` agent would have silently executed it on the native engine, under the native engine's own tool access, using the external-CLI agent's identity only nominally — a real security and correctness gap (mis-executing an agent's work under the wrong engine, with the wrong tool surface). Five call sites were built specifically to fail closed against this gap rather than let it happen silently:

1. `pkg/gateway/rest_tasks.go`'s `validateTaskAgentID` (`:367-386`) — the REST/SPA task-assignment gate. Its own doc comment (`:346-356`) states the exact limitation this ADR resolves: *"there is no ResolveDispatch/executor-kind branch on the task-run path ... Assigning a task to a subagent_3p today would silently run it on the NATIVE Omnipus engine instead of the configured external CLI, defeating the whole point of the agent."*
2. `pkg/sysagent/tools/task.go`'s `TaskCreateTool.Execute` (`:179-184`) and the cross-workspace `TaskUpdateTool.Execute` (`:314-327`) — the privileged Orchestrator/cross-workspace tool path, gated on `t.deps.GetCfg().IsExternalCLIWorkerID(...)`.
3. `pkg/tools/task.go`'s plain `create_task`/`update_task` tools — an `externalCLIWorkerCheck func(agentID string) bool` field (`:103-129`) installed via `SetExternalCLIWorkerChecker`, wired at `pkg/agent/loop.go:1564` (`taskCreate`) and `:1600` (`taskUpdate`) to `cfg.IsExternalCLIWorkerID`.

All five guards exist purely because the execution engine could not honor a `subagent_3p` assignment — not because task assignment to an external-CLI worker is conceptually wrong. UAT case **X-07** in `docs/internal/uat/uat-matrix-delegation-subagent-tasks-2026-07-13.md` ("Task-mode to external": *"create_task assignee=3p ... Allowed if edge+modes; pickup path defined"*) explicitly expects this to work once the engine gap is closed — a REST-vs-tool-path seam the operator wants reconciled by making the capability real, not by tightening the tool path to match the REST path's current fail-closed behavior.

## 2. Decision

**Add a `runner.ResolveDispatch` executor-kind branch to the task-run path, and remove the five fail-closed guards that existed only because that branch was missing.**

### 2.1 Dispatch branch in `processTaskDirect`

`processTaskDirect` (`pkg/agent/loop.go:3871`) already resolves the assigned agent (`ag, ok := registry.GetAgent(agentID)`, `:3880`) before dispatching. After that resolution, it calls `runner.ResolveDispatch(executorConfigOf(ag))` — the same call `spawnSubTurn` makes for agent-to-agent delegation — and branches:

- `DispatchKindNative` (nil/`""`/`"native"` executor kind, the status quo for every native agent): unchanged — `al.runAgentLoop(taskCtx, ag, processOptions{...})` exactly as today.
- `DispatchKindExternalCLI`: routes through the **existing** `runExternalCLISubTurn` machinery (ADR-032) instead of `runAgentLoop`, so a task run and a `delegate`-driven sub-turn share one execution path for external CLIs — no new driver dispatch, consent routing, workspace-dir resolution, or serialization logic is written for tasks specifically.

### 2.2 Ephemeral turnState, not the parent-delegation turnState

`runExternalCLISubTurn` takes a `*turnState` (`childTS`) and reads two things off it: `childTS.agent` (the delegate's identity — workspace, model, executor config) and `childTS.opts.WorkspaceID` (used by `workspace.FindForAgentPreferring` to decide whether the CoreTeam `workspaces/<id>/work/` override applies, ahead of falling back to `agent.Workspace`). A task run has no delegating parent turn to inherit from — there is no parent identity to *not* inherit, unlike the `spawnSubTurn` case ADR-032's identity rule addresses. The task-run branch therefore constructs a **minimal, ephemeral `turnState`** (via `newTurnState`, `pkg/agent/turn.go:264`) scoped to the single external-CLI run, rather than reusing `spawnSubTurn`'s parent-delegation construction path:

- `agent`: the resolved `ag` (the task's assignee — already fetched in `processTaskDirect`).
- `opts.WorkspaceID`: the task's `WorkspaceID`. `processTaskDirect`'s `taskCtx` already carries this — `TaskExecutor.runTask` (`pkg/agent/task_executor.go:217-218`) calls `tools.WithWorkspaceID(taskCtx, t.WorkspaceID)` before invoking `processTaskDirect` — so the branch reads it back via `tools.ToolWorkspaceID(ctx)` (`pkg/tools/base.go:227`) rather than adding a new parameter, the same convention `processTaskDirect` already uses for `tools.ToolDelegationDepth(ctx)` (`:3903`). This is what lets ADR-032's CoreTeam `work/`-dir override apply correctly to a workspace-assigned task, instead of silently falling back to the agent's own private workspace directory.
- Transcript: wired to the task's own `session.SessionTypeTask` session (`taskSessionID`, already created by `TaskExecutor.runTask` before calling `processTaskDirect` — `task_executor.go:182-214`) via `childTS.transcriptSessionID`/`transcriptStore`, exactly as the native path already does (`processTaskDirect`'s `TranscriptSessionID`/`TranscriptStore` fields on `processOptions`, `:3918-3919`).
- `turnID`: a fresh ID (mirrors `runExternalCLISubTurn`'s own fallback, `external_dispatch.go:123-126`, for when `childTS.turnID` is empty).

No `parentTurnState`, `parentSpawnCallID`, or delegation-depth bookkeeping is populated — a task run is a root execution, not a hop in a delegation chain.

### 2.3 Result handling: auto-complete, no mid-run `task_update`

`runExternalCLISubTurn` returns a `*tools.ToolResult` (`ForLLM`/`ForUser` carrying aggregated output, `Err` on failure) — not a `(string, error)` like `runAgentLoop`. The task-run branch adapts this to `processTaskDirect`'s existing `(string, error)` return so `TaskExecutor.finishTaskRun` (`task_executor.go:248`) needs no changes: success maps to `(result.ForUser, nil)`, failure to `("", result.Err)` (or the returned `error` when `runExternalCLISubTurn` itself errors before producing a `ToolResult`, e.g. missing executor config).

This matters because external CLIs have no `task_update` tool call available to them — they are driven through the ADR-032 driver/consent loop, not the Omnipus tool-call surface. `finishTaskRun`'s existing auto-complete logic (`task_executor.go:291-320`: re-read the task, and if its status is not already terminal — i.e., the agent never called `task_update` — patch it to `StatusDone` with the run's output as `Result`) already handles this for native agents that forget to call `task_update`; for external-CLI task runs it becomes the **only** completion path, since there is no mechanism by which the external CLI could have moved the task to a terminal status itself. A failed run reaches `finishTaskRun`'s error branch and calls `failTask` (`:613`) exactly as a native failure does today.

### 2.4 Timeout: reuse the sub-turn default, no new config key

The external-CLI run needs a timeout bound (`runExternalCLISubTurn`'s `timeout time.Duration` parameter). Rather than introduce a task-specific timeout config, the branch reuses `SubTurn.DefaultTimeoutMinutes` — `getSubTurnConfig` (`pkg/agent/subturn.go:47`) already resolves this to `defaultSubTurnTimeout` (5 minutes, `:31`) when unset (`:70-73`). **Accepted trade-off:** task assignments are conceptually longer-running work than a single `delegate` call, and a 5-minute default is a tight ceiling for that use case. An operator running long external-CLI tasks needs to raise `SubTurn.DefaultTimeoutMinutes` globally (it is not currently overridable per-task or per-agent) — this is a known limitation, not silently accepted risk: it is written here so the first "my external-CLI task timed out" report is diagnosed against this ADR, not treated as a new bug.

### 2.5 Guards removed

The five call sites in §1 are no longer needed once the engine gap they exist to prevent is closed, and are removed:

1. `pkg/gateway/rest_tasks.go`'s `validateTaskAgentID` — **only** the `cfg.IsExternalCLIWorkerID(agentID)` branch (`:381-386`) is removed. The function's remaining checks — agent existence (`:378-380`), and, critically, the **workspace `TeamSet` membership check** (`:387-399`, `workspaceTeamSet(ws)[agentID]` — CoreTeam ∪ delegation-edge endpoints) — are **unchanged** and remain the authorization gate for REST/SPA task assignment. A `subagent_3p` agent must still be on the target workspace's team (core team or a delegation edge) to be assignable; this ADR only removes the categorical "external-CLI workers can never be assigned, full stop" rejection, not workspace authorization.
2. `pkg/sysagent/tools/task.go`'s `TaskCreateTool.Execute` (`:179-184`) and `TaskUpdateTool.Execute` (`:314-327`) `IsExternalCLIWorkerID` checks — removed; the `DelegationDeny`/`delegationDenied` trust-set + mode + depth gate immediately adjacent to each (`:185-189`, `:281-293`) is unchanged and remains the authorization gate for this path.
3. `pkg/tools/task.go`'s `externalCLIWorkerCheck` field, `SetExternalCLIWorkerChecker` method, and the `TaskCreateTool`/`TaskUpdateTool` call sites that invoke it — removed. The `pkg/agent/loop.go:1564` (`taskCreate.SetExternalCLIWorkerChecker(cfg.IsExternalCLIWorkerID)`) and `:1600` (`taskUpdate.SetExternalCLIWorkerChecker(...)`) wiring calls are removed accordingly. The `delegationDeny` gate on this path (`SetDelegationDenyChecker`, `:1543` / `:1590`, unaffected by ADR-037) remains the authorization gate.

`externalCLIWorkerDenialMessage` (duplicated in `pkg/sysagent/tools/task.go` and `pkg/tools/task.go`, by the existing packages' own documented non-coupling convention) becomes dead code at all three of its call sites and is removed alongside them.

### 2.6 What stays unchanged

- **Workspace `TeamSet` membership** (REST path) and the **trust-set + mode(`task`) + depth delegation-deny gate** (tool path, `EdgeModeCategory`, `pkg/agent/loop.go:2031`, mapping the tool's 3-value `config.DelegationMode` down to the trust edge's 2-value `workspace.DelegationMode` category) are the authorization gates for task assignment, exactly as they are for native agents today. This ADR adds an execution capability; it does not touch who is allowed to assign a task to whom.
- **Per-workspace external-run serialization** (`workspaceRunLocks`, `external_dispatch.go:62-93`) — task runs against a workspace already being used by a concurrent `delegate`-driven external-CLI run (or another task run) to the same agent/workspace serialize exactly as two `delegate` calls would, with no task-specific change.
- **Env scrubbing, egress proxy, and the driver's non-interactive approval posture** (ADR-032 §2.1/§2.4) — identical for a task-driven run as for a `delegate`-driven one, since both now go through the same `runExternalCLISubTurn`.
- **`MaxTurns`/`MaxIterations` cap** — unchanged, sourced the same way `runExternalCLISubTurn` already sources it for delegation.
- **Usage-stats exclusion for `subagent_3p`** — `pkg/gateway/rest_stats.go:109` and `pkg/sysagent/tools/diag.go:231` both exclude `cfg.IsExternalCLIWorkerID(agentID)` agents from token-usage aggregation (`session.AggregateUsage`'s `Exclude` predicate) because external-CLI runs are not instrumented for Omnipus-side token accounting. This ADR does not change that: an external-CLI task run's token usage remains untracked in `/usage` and `get_usage`, exactly as an external-CLI `delegate` run's usage is untracked today. Not a new gap introduced here — flagged so it isn't mistaken for a regression once task assignment starts producing real external-CLI runs at higher volume.
- **Delegation-edge mode gates on the agent-tool path** — `ModeTask`-category edges (`EdgeModeCategory`, `loop.go:2031`) still gate `create_task`/`update_task` exactly as before; this ADR does not relax or extend which edges authorize task-mode assignment, only which assignee **types** the engine can actually execute once authorized.

### 2.7 Authorization model: human-initiated vs agent-initiated assignment (intended, asymmetric by design)

The two task-assignment surfaces are authorized by **deliberately different** rules, and this asymmetry is intentional — not a coarseness to be reconciled:

- **Human-initiated assignment (REST/SPA path)** is authorized by **workspace `TeamSet` membership only**. A human assigning or reassigning a task through the SPA does not have their choice constrained by delegation-edge modes: if the assignee is on the workspace's team (`workspaceTeamSet(ws)[agentID]` — CoreTeam ∪ delegation-edge endpoints), the assignment is authorized, regardless of whether any edge carries the `task` mode category. This is the full and correct authorization for a human operator — delegation-edge modes govern which agents may hand work to which *other agents*, a constraint on autonomous agent behavior, not on the operator directing their own workspace. Enforced in `validateTaskAgentID` (`pkg/gateway/rest_tasks.go`), whose surviving `TeamSet` check (§2.5.1) is exactly this rule.
- **Agent-initiated creation/reassignment (tool path)** goes through the full delegation gate: a delegation **edge** must exist from the calling agent to the target, that edge's `Modes` must admit the **`task`** category, and the per-edge/global **depth** cap must not be exceeded. An agent assigning work to another agent *is* delegation and is gated as such.

Verified (2026-07-13) that all four agent-tool surfaces enforce the task-mode edge category when an agent assigns/reassigns to another agent:

| Surface | Gate consulted (file) | Wiring | Fails |
|---|---|---|---|
| plain `create_task` | `pkg/tools/task.go` `TaskCreateTool.Execute` — `t.delegationDeny(ctx, agentID)` | `loop.go:1543` `SetDelegationDenyChecker(buildDelegationDenyCheckerForTaskReassignment(..., config.DelegationModeTask))` | **closed** if unwired |
| plain `update_task` | `pkg/tools/task.go` `TaskUpdateTool.Execute` — reassignment branch `t.delegationDeny(ctx, agentID)` | `loop.go:1590` same builder, `config.DelegationModeTask` | **closed** if unwired |
| sysagent `create_task_in_workspace` | `pkg/sysagent/tools/task.go` `TaskCreateTool.Execute` — `t.deps.DelegationDeny(ctx, caller, tk.AgentID)` | `pkg/gateway/gateway.go:1306` `DelegationDeny: agentLoop.NewSysagentDelegationDeny()` → `buildDelegationDenyCheckerForTaskReassignment(..., config.DelegationModeTask)` (`loop.go:2399`) | open if unwired (wired in production) |
| sysagent `update_task_in_workspace` | `pkg/sysagent/tools/task.go` `TaskUpdateTool.Execute` — ownership + reassignment branches via `t.deps.delegationDenied(ctx, caller, ...)` | same `gateway.go:1306` wiring | open if unwired (wired in production) |

All four resolve through one core chain: `buildDelegationDenyChecker` (`loop.go:2219`) → targeted → `findDelegationEdge(..., mode)` (`loop.go:1958`, requires an edge from caller to target) → `enforceEdgeModeAndDepth(edge, ..., mode, globalDepthCap)` (`loop.go:2060`) → `EdgeModeCategory(config.DelegationModeTask) = workspace.ModeTask` (`loop.go:2031`), which requires the edge's `Modes` to admit the `task` category (an edge with empty `Modes` admits all). This is the mode enforcement the human path deliberately does not apply.

### 2.8 Post-decision corrections (7-reviewer gate, 2026-07-13)

§§2.2–2.3 above describe the design as originally decided. A review pass on the landed implementation found the built `processTaskDirectExternalCLI` diverged from that design in three ways that are corrected now, not deferred:

- **Persona/soul composition was missing.** §2.2 says the ephemeral `turnState`'s `agent` field carries "the delegate's identity" — but the run's actual *input* originally passed `runExternalCLISubTurn` the bare task prompt, unlike `spawnSubTurn`'s agent-to-agent delegation path, which composes the target's soul/persona ahead of the task via `composeDelegateInput(al, task, actualSystem, targetAgentID)` (`pkg/agent/subturn.go:307`, producing a `"## System\n\n<soul>\n\n## Task\n\n<task>"` string, or the bare task when the target has no soul — the worker case). A task run now routes through the identical `composeDelegateInput` call (`processTaskDirectExternalCLI`, `pkg/agent/loop.go`) so an external-CLI worker's own configured persona travels with a task assignment exactly as it already did for a `delegate` call — the assignee's identity was resolved correctly (agent, workspace, model) but its *voice* was silently dropped for the task-run path specifically.
- **The dispatch's `AgentInstance` snapshot needed to be race-safe.** `processTaskDirect` resolves `ag` from the LIVE registry (`registry.GetAgent(agentID)`, §2.1); `AgentInstance.Model`/`Provider`/`Candidates`/`ThinkingLevel` (+ its provider pool) are protected by `AgentInstance.mu` because `SwitchModel`/`ApplyAgentModel` can rewrite them concurrently with an in-flight turn (`pkg/agent/instance.go:28-30`). `runExternalCLISubTurn` reads `agent.Model` unlocked for transcript attribution and `RunOptions.Model`. The fix (`AgentInstance.snapshotForExternalDispatch`, `pkg/agent/instance.go`) takes a single `RLock`, copies the whole mutex-protected quad together into a private, unshared `AgentInstance` value, and `processTaskDirectExternalCLI` uses that snapshot for the entire dispatch — mirroring `spawnSubTurn`'s existing `execSource`-snapshot pattern (`pkg/agent/subturn.go` ~603-662), which the agent-to-agent delegation path already relied on for the identical reason.
- **The ephemeral turnState was never registered as an active turn.** §2.2 builds the ephemeral `turnState` but the implementation never stored it in `al.activeTurnStates` the way native `runTurn` and `spawnSubTurn`'s own child `turnState` both do. Consequence: an in-flight external-CLI task run was invisible to `GetActiveTurn`/`GetActiveAgentIDs`, and missed the FR-048 graceful-shutdown transcript marker (`writeTurnCancelledRestartForActiveTurns`) — a gateway restart mid-run left no trace explaining the gap on next load. Fixed by registering/clearing the turnState around the dispatch (mirroring the existing `registerActiveTurn`/`clearActiveTurn` pair) and setting the `al` back-reference `spawnSubTurn` also sets on its child. A `RequestCancel` against this session can now reach and claim the turn; it safely no-ops the escalation timers (`cancelFunc`/`providerCancel` are intentionally left nil — there is no native LLM call or child delegation turn on this path to cancel) rather than actually stopping the dispatched CLI process, the same best-effort, observability-only posture already documented for external-CLI consent (`pkg/agent/runner/consent.go`).
- **No Go-level timeout bound existed for the task-run dispatch (surfaced while adding test coverage for this ADR, not originally decided or omitted on purpose).** `runExternalCLISubTurn` only forwards `rtCfg.defaultTimeout` to the driver as a `RunOptions.TimeoutSeconds` hint each real driver applies internally — it never bounded its own `ctx` with a deadline. `spawnSubTurn`'s agent-to-agent path already has its own safety-net `context.WithTimeout` for exactly this reason (`pkg/agent/subturn.go` ~458-473); the task-run path had no equivalent, so a hung/never-ending external CLI process (one that never emits an end or error event) would have blocked a dispatch-semaphore slot forever. `processTaskDirectExternalCLI` now wraps its dispatch `ctx` in `context.WithTimeout(ctx, rtCfg.defaultTimeout)` — derived from the incoming ctx (not `context.Background()`, unlike `spawnSubTurn`'s deliberately-independent child context) so a `TaskExecutor`-level cancel still takes effect immediately in addition to the deadline. §3's "5-minute default timeout is a real mismatch for task-shaped work" accepted trade-off now also covers this: the timeout is a genuine Go-level ceiling, not merely an unenforced hint to the driver.
- **The cancel-finish callback never fired (final-gate audit-trail gap, fixed 2026-07-13).** The bullet above ("A `RequestCancel` against this session can now reach and claim the turn...") described the turnState as reachable for cancel purposes once registered, but a later gate found the registration alone was not sufficient: `processTaskDirectExternalCLI` registered the turnState (previous bullet) yet never called `ts.Finish` on any exit path. `Finish` is the ONLY place that invokes the `onCancelFinish` callback `RequestCancel` installs via `SetOnCancelFinish` (`pkg/agent/cancel.go`) — the callback that appends the `turn_canceled` transcript entry, calls `MarkLastEntryTruncated`, and emits `audit.EventTurnCancelled`. Without it, a cancel against an in-flight external-CLI task run returned `CancelOutcome{Fired: true}` but left zero transcript or audit trace — silently contradicting the previous bullet's own description. Fixed by adding `defer ts.Finish(false)` (`pkg/agent/loop.go`), ordered — via Go's LIFO defer semantics — to run AFTER `clearActiveTurn`, mirroring native `runTurn`'s own `defer ts.Finish(false)` / `defer al.clearActiveTurn(ts)` pair and its documented rationale (a cancel racing the tail of a finished dispatch must not find a still-map-resident turnState and register a callback that can never fire). `Finish(false)` is safe on this ephemeral turnState: `cancelFunc`/`providerCancel` are nil (nil-checked internally), the hard-abort child-cascade branch is unreachable (`isHardAbort` is always `false` here), and `closeOnce.Do` plus the swap-then-nil-check around `onCancelFinish` make a second `Finish` call (e.g. a concurrent `InterruptSessionHard` calling `Finish(true)` on the same turnState) idempotent — the same guarantee `runTurn` already relies on.

## 3. Consequences

### Positive

- Closes a real engine-capability gap: `subagent_3p` agents can now actually do the work a task assigns them, through the same identity/workspace/consent machinery ADR-032 already proved out for `delegate`.
- Resolves the REST-vs-tool-path seam UAT case X-07 was written against — the agent-tool path's expectation ("assign a task to a 3p worker should work when the edge/mode allows it") and the REST path's prior hard rejection converge on one real capability instead of one being aspirational.
- No new execution machinery: the change is a dispatch branch plus an ephemeral `turnState` constructor; consent routing, sandboxing posture, serialization, and env scrubbing are 100% reused from ADR-032, not reimplemented or forked for tasks.
- `finishTaskRun`'s existing "auto-complete if the agent never called `task_update`" logic (already present for native agents that forget to call it) becomes the correct, sufficient completion path for external CLIs with zero new code in `task_executor.go` — a case of existing tolerance for one failure mode turning out to already cover a different, structural limitation.
- Five call sites of duplicated fail-closed logic (REST guard, two sysagent-tool guards, one shared-tool-plumbing field, two wiring call sites) are deleted rather than left to rot now that their premise no longer holds.

### Negative / accepted

- **5-minute default timeout is a real mismatch for task-shaped work.** Tasks are the product's "assign it and come back later" primitive; a `SubTurn.DefaultTimeoutMinutes`-sourced bound (5m default) is tuned for a `delegate` call, not a task. Accepted per §2.4 — operators running long external-CLI tasks must raise the global `SubTurn.DefaultTimeoutMinutes`, since there is no per-task or per-agent override today. A follow-up to give tasks (or `subagent_3p` executor config) their own timeout knob is reasonable but out of scope here.
- **No mid-run task visibility/update from the external CLI itself.** A native agent can call `task_update` mid-run (e.g., to record partial progress or fail itself with a specific reason); an external-CLI task run cannot, by construction — it only ever reaches a terminal state via `finishTaskRun`'s post-hoc auto-complete/fail-task logic after the whole run returns. This is consistent with how `delegate`-driven external-CLI sub-turns already behave (they don't have Omnipus tool access either), so it is not a new asymmetry this ADR introduces, but it is more visible for tasks, where "check in on long-running work" is a more natural expectation than for a single `delegate` call.
- **3p task-run token usage remains invisible in usage stats** (§2.6) — accepted as pre-existing, but likely to be noticed more once task assignment to external CLIs is a real, used capability rather than a rejected one.
- **Auto-complete false-success cascades to dependent tasks (7-reviewer-gate finding, added post-decision).** §2.3's "auto-complete if the agent never called `task_update`" completion path is not merely a fallback for external-CLI runs — it is the *only* path, unconditionally, on every run (see §2.8 below). An external CLI that exits cleanly after prose like "I could not complete this" (no crash, no fatal driver event) is auto-completed to `StatusDone` exactly the same as a genuine success, because there is no structured signal to distinguish the two. Since `finishTaskRun`'s `onTaskComplete` auto-advances any task whose `blocked_by` dependency just went `Done` (`advanceBlockedTasks`), a single unverified "success" can silently unblock and dispatch downstream dependents that assumed real work was done. **Mitigation shipped now:** `finishTaskRun`'s auto-complete branch emits a `slog.Warn` specifically identifying external-CLI (`subagent_3p`) dispatch (task ID + agent ID) so this is at least visible to an operator scanning logs, distinguishable from the rare native "agent forgot to call `task_update`" case that also reaches this branch. **Deferred as a product decision:** requiring an explicit, structured success signal before a 3p-assigned task's dependents auto-advance (e.g., a stricter completion contract for `subagent_3p` executors, or gating auto-advance on a human/agent confirmation step) is out of scope for this ADR — the auto-advance semantics are unchanged for now, WARN-log visibility is the only mitigation shipped.

> The human (REST/SPA) vs agent (tool) authorization asymmetry is **not** listed here as an accepted risk — it is an explicit, intended design decision. Human-initiated task assignment is authorized by workspace `TeamSet` membership alone and is deliberately **not** constrained by delegation-edge modes; only agent-initiated creation/reassignment goes through the edge + `task`-mode + depth gate. See §2.7 for the rule and the verified enforcement locations. `validateTaskAgentID` should **not** be given a task-mode edge check — that would wrongly constrain human operators and is explicitly not wanted.

## 4. Alternatives considered

**(a) Keep the fail-closed guards; add a disabled-with-tooltip UI treatment for `subagent_3p` assignees instead.** Rejected — the operator wants the actual capability delivered (task execution genuinely working for external-CLI workers), not a clearer explanation of why it doesn't work.

**(b) Route task runs through `spawnSubTurn` with a synthetic parent turn.** Rejected — `spawnSubTurn`'s entire design (ADR-032, 2026-07-09 amendment) is built around sourcing every agent-level field from a resolved **delegate**, driven by a real **parent** turn's identity/authorization context (`TargetAgentID`, the delegation-graph gate, etc.). A task run has no parent turn and no delegation-graph edge to walk — inventing a synthetic parent turn just to satisfy `spawnSubTurn`'s shape would reintroduce exactly the "does this field come from the parent or the target" ambiguity ADR-032 spent real effort eliminating, for no benefit over a small, purpose-built ephemeral `turnState`.

**(c) Build a new, task-specific external-CLI runner.** Rejected — this would duplicate the ADR-032 machinery (workspace/CoreTeam dir resolution, per-workspace serialization, driver dispatch, consent routing, env scrubbing) a second time for no behavioral difference from what `runExternalCLISubTurn` already does. The only genuinely task-specific concerns (result plumbing back into `(string, error)`, auto-complete-on-return) are handled at the call site in `processTaskDirect`/`finishTaskRun`, not by forking the runner itself.
