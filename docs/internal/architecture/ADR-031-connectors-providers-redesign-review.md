# Grill Report — ADR-031: Connectors & Providers UI/UX Redesign

- **Spec reviewed:** `docs/internal/architecture/ADR-031-connectors-providers-redesign.md`
- **Review date:** 2026-07-02
- **Reviewer:** grill-spec (adversarial, read-only)
- **Input mode:** `structured-spec` (ADR with FR-x / NFR-x / G-x identifiers; not a plan-spec)

---

## 1. Executive Summary

This ADR ratifies a Channels/Providers UI redesign and decides three open forks (G-1 real-logos-everywhere, G-2 backend/contract catalog, G-3 shared-catalog-only). The direction is coherent and prototype-backed, but the spec is **riddled with stale and incorrect `[FACT]` citations** — the very thing an ADR's evidence level is supposed to guarantee. Two of the load-bearing counts ("47 variants / 14 companies", "z-ai ×6 / qwen ×5") are wrong; the claim that `ProvidersSection.tsx` has "no empty state, no variant UI" is **false against the current code**; a file with the exact name the G-2 rejected-option proposes (`src/lib/agents/providerCatalog.ts`) **already exists**; and the G-2 drift-guard as written is **infeasible** because `knownProtocols` (61 entries, including CLI/alias/infra ids) cannot map 1:1 to a user-facing catalog. The G-1 legal decision is recorded honestly but the mitigation ("swappable SVGs", disclaimer) is asserted, not specified.

**Findings by severity:** 3 CRITICAL · 7 MAJOR · 6 MINOR · 3 OBSERVATION

**Verdict: REVISE** (no data-loss/security CRITICALs, but three CRITICALs that will send the downstream `/plan-spec` off a cliff — a wrong drift-guard contract, a false current-state baseline, and an undefined core wire field).

## 4. Test Coverage Assessment

The ADR is not a plan-spec, so no TDD plan is expected — but §9.3 does enumerate what `/plan-spec` must test, and that list has gaps:

- **Drift-guard test (§9.3) is the spec's headline safeguard and it's mis-specified** — see F-01. As written the test either fails permanently (61 ids, no catalog rows for CLI/alias/infra) or passes vacuously. This is the single most important test in the ADR and it can't be written as stated.
- **No negative/failure tests enumerated:** unknown provider id → catalog lookup (F-16); missing/removed `logoSlug` → fallback (F-09); catalog endpoint unavailable → onboarding still functions.
- **The login-removal regression test (§7, FR-9) is the one well-specified test** ("a not-onboarded user still reaches `/onboarding` via `_app` beforeLoad after the button is gone") — and it's correct; `_app.tsx` beforeLoad ordering was verified (onboarding check precedes auth). Good.
- **No a11y test** for NFR-4/5 (F-14).
- **No consistency test** proving onboarding and Settings render identical terminology/logos — the whole NFR-1 driver has no verification bullet.

## 5. STRIDE Threat Summary

| Component / flow | Threats identified |
|------------------|--------------------|
| `GET /api/v1/providers/catalog` (new) | **Information disclosure** (low): enumerates all provider protocols pre-auth if `withOptionalAuth`; a fingerprinting surface. **DoS** (low): no rate-limit specified. **Auth** unspecified (F-08). No spoofing/tampering concern — read-only static metadata, no secrets. |
| Vendored brand SVGs (go:embed) | **Tampering** (negligible): compiled-in, CSP-clean, no runtime fetch — good. **Legal (non-STRIDE but flagged):** recolored strict-TM marks (F-09, F-17). No injection risk if SVGs are static assets (confirm no inline `<script>` in vendored SVGs — a real XSS vector for SVGs rendered inline). |
| `ProviderCatalogEntry` wire type | **Information disclosure:** ships English display strings + logo slugs (presentation) over the contract (F-07) — not a security leak, but a design smell. No PII/credentials. |
| Onboarding model step (rebuilt) | **Elevation/Spoofing:** unchanged — key entry + probe path is explicitly out of scope (§7). Confirm the redesign doesn't accidentally weaken the probe/validation gate. |

**One concrete security add:** the spec must require that vendored SVGs are sanitized (no `<script>`, no `on*` handlers, no external `xlink:href`) before embedding, since `<BrandIcon>` implies inline SVG rendering (`currentColor` theming requires inline, not `<img>`). This is the only genuine new attack surface and it's unmentioned.

## 6. Unasked Questions (for the author to resolve before `/plan-spec`)

1. **What is the catalog's id-set?** All 61 `knownProtocols`, or the ~30 user-facing subset? This single answer determines whether the drift-guard (F-01), the migration (F-16), and the 61-vs-30 reconciliation (F-06) are solvable. Everything downstream hinges on it.
2. **What is `wire`'s exact enum and derivation rule?** (F-02) You cannot generate a contract type for a field you haven't defined.
3. **What happens to the existing `src/lib/agents/providerCatalog.ts`?** (F-04) Fold its `live/manual` logic into the new catalog, or leave it and accept two "providerCatalog" concepts?
4. **What are the exact disclaimer copy and render locations, and what makes a logo "swappable in one line"?** (F-09) The legal posture is load-bearing per your own §7 — it needs acceptance criteria.
5. **Is ADR-029 a hard prerequisite?** (F-10) Binding-first rows and workspace-first create depend on a still-Proposed ADR. Can ADR-031 ship without it, or does it block?
6. **Does `label`/`subtitle`/`logoSlug` truly need to be on the wire?** (F-07) Or can the contract carry facts and the frontend derive presentation, honoring your own NFR-2 exemption and preserving localizability?
7. **Should `Token Plan` ship now?** (F-12/G-5) You admit no provider uses it. Reserved, or removed until needed?
8. **Is the catalog endpoint pre-auth?** (F-08) It probably must be (onboarding needs it) — confirm and confirm it leaks nothing.

## 7. Verdict

**REVISE.**

No CRITICAL will cause data loss or a security incident, so this is not a BLOCK. But three CRITICALs (F-01 infeasible drift-guard, F-02 undefined-yet-contracted `wire`/`endpointHost`, F-03 false current-state baseline) will each derail `/plan-spec`: you would generate a contract for an undefined field, write a drift-guard that can't pass, and re-implement a `ProvidersSection` empty-state/variant UI that already exists. Fix those three plus the seven MAJORs (especially F-06's 61-vs-30 reconciliation, which is the real hard problem G-2=B introduces) and the spec is ready.
