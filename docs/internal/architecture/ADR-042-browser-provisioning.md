# ADR-042 — Browser provisioning: managed download-on-boot, not bundled

- **Status:** Accepted (build authorized 2026-07-14, commit `41c70b5d`)
- **Deciders:** Daniel Piatkowski (operator), lead engineering
- **Extends:** [[ADR-038]] (live browser), [[ADR-041]] (browser tabs/multi-target). Same `pkg/tools/browser` subsystem; the `BrowserManager` created per agent by `pkg/agent/loop.go::registerSharedTools`.
- **Motivation:** Operator directive — *"omnipus must install the browser on installation or bundle it in."* The managed Chrome-for-Testing download (`installer.go::EnsureChromium`) already existed, but it fired **lazily at first tool use**. Three real failures came from that: (1) a fresh install's first `browser_navigate` blocked ~30–60 s on a 130 MB download before doing anything; (2) `resolveExecPath` trusted any `exec.LookPath` hit, so an Ubuntu `chromium-browser` **snap stub** (present but unusable on hosts without snapd — every Fly.io machine, most minimal containers) was committed to and the managed fallback never ran, failing every browser tool at first use; (3) a CDP port squatter (observed live: an orphaned Chrome from an unrelated run on the fixed port 9223) surfaced as an opaque chromedp "websocket url timeout" with nothing naming the cause. Separately, the documented `tools.browser.exec_path` override was dead end-to-end (`BrowserToolConfig` never had the field; `loop.go` never copied it).

## Decisions

### D1 — Managed download-on-boot, NOT bundled (the core choice)
Chromium is **not** compiled/`go:embed`-ed into the binary. A managed `chrome-headless-shell` (Chrome for Testing, Stable channel) is **downloaded at gateway boot** via a new `BrowserManager.Preprovision(ctx)` and cached under `<ProfileDir>/../chromium/<version>/` (deduped on disk across restarts by `findInstalledBinary`, and in-process by the exec-path cache). Boot provisioning is non-blocking and non-fatal (D3), so the directive's intent ("available without operator action") is met for the normal gateway install path **without** bloating the binary.

**Why not bundle:** the chrome-for-testing headless-shell for linux64 is ~130 MB. Embedding it would (a) blow up the single-binary distribution — Hard Constraint #1 ("single Go binary … minimal footprint … no new runtime deps") is a load-bearing project tenet, and (b) pin every install to one Chromium version regardless of host. Downloading decouples the Chromium version from the binary and keeps the binary lean. *Note:* this is a Constraint-#1 (binary/distribution footprint) argument, NOT Constraint #3 — #3 is the <10 MB resident-RAM-overhead budget, which a downloaded Chromium also does not count against (Chrome's RAM is runtime working set, not "security-feature overhead"; one Chrome is already well over 10 MB and that was accepted when ADR-038 shipped).

### D2 — Validated discovery (probe before trust)
`resolveExecPath` no longer returns the first `exec.LookPath` hit. Each PATH candidate (`google-chrome`, `google-chrome-stable`, `chromium`, `chromium-browser`) is **probed with `--version`** (`probeChromiumBinary`, 5 s timeout each) before being accepted; a candidate that fails to run (the snap-stub case, a dead symlink, a missing shared lib) is logged at WARN and skipped, falling through to the next candidate and finally to the managed install. Resolution order is unchanged in shape — `cfg.ExecPath` (operator override, now stat+dir+exec-bit validated, D5) → in-process cache → `OMNIPUS_BROWSER_FORCE_MANAGED` → validated PATH → managed install — only the PATH step gained the probe. The successful path is memoized in an in-process cache (stat-validated on hit so a later-deleted binary re-resolves); a **failed** resolution is negative-cached for 60 s so a dead host bounds per-call cost (~20 s probe + ~30 s manifest timeout once per minute, not on every retry) and avoids a WARN storm.

### D3 — Non-blocking, non-fatal, gracefully degrading
`Preprovision` runs as one detached goroutine **per agent's `BrowserManager`** from `pkg/gateway/gateway.go` right after `NewAgentLoop` returns (the earliest point with both the shutdown-aware `ctx` and the fully-populated manager set), mirroring the existing `BootstrapRecapPass(ctx)` detached-boot idiom. On any failure it logs a WARN (through `logger` → `gateway.log`, not `slog` → `gateway_panic.log`) and retries **lazily at first real browser tool use** — the pre-existing behavior — so boot never fails and the directive degrades coherently where provisioning can't run: CLI-only usage (`omnipus <agent>` one-shot, no gateway) resolves lazily; Termux/Android (`cftPlatform` errors) falls back to a probed system chromium then lazy retry; the `lite` build is unaffected (browser tools are not lite-gated). N boot goroutines are safe: they only resolve/download (no Chrome launch, no port bind), and `EnsureChromium`'s package-level `installMu` serializes the one download.

### D4 — CDP port preflight (diagnosability, port still pinned)
`checkDebugPortAvailable` does a loopback `net.Listen`+`Close` on `127.0.0.1:9223` immediately before launch, turning a port squatter into a clear *"CDP debug port 9223 is already in use by another process — close it or stop the other instance"* error instead of chromedp's opaque timeout. **The port stays pinned at 9223** — `pkg/gateway/sandbox_apply.go` adds exactly this port to the Landlock `NET_CONNECT_TCP` allow-list, and randomizing it would re-break the sandboxed gateway ("dial tcp … connect: permission denied"). The probe is IPv4-only **by design**: Chrome binds `127.0.0.1` by default (no `--remote-debugging-address` is set in the allocator opts), chromedp dials `ws://127.0.0.1:<port>`, so a `[::1]`-only squatter cannot conflict with our launch — probing v6 would solve a non-problem and could false-positive on a legitimate v6 listener. A documented sub-ms TOCTOU window remains (probe-close → real bind); this is a diagnostics aid, not a guarantee.

### D5 — `tools.browser.exec_path` wired + validated (dead config fixed)
`BrowserToolConfig` gains `ExecPath` (`json:"exec_path"`, env tag documentation-only per the field convention); `registerSharedTools` copies it into `BrowserConfig.ExecPath`. The override is validated as a file that exists, is not a directory, and is executable-bit set (POSIX; the exec-bit check is skipped on Windows where `os.FileMode` carries no Unix exec bits) — surfacing a clear `configured exec_path %s is …` error instead of a generic chromedp launch failure. (Per the resolution-order doc, an operator override is *not* `--version`-probed: an explicit choice gets a loud, debuggable failure rather than the package silently substituting a different binary.)

## Consequences
**Positive:** a fresh install has Chromium downloading in the background from first boot, before any agent needs it; the first browser tool call no longer eats the download latency; broken PATH binaries no longer brick the browser; port squatters are named, not opaque; the `exec_path` override actually works. Memory/CPU: unchanged at steady state (one Chrome per the pre-existing model); boot provisioning adds only the download goroutines, which are idle once a binary resolves. Single binary preserved (Constraint #1); pure Go, no new deps (`go.mod` untouched).

**Risks / accepted limitations:**
- **Port-9223 / one-managed-Chrome-at-a-time limit** — pre-existing (ADR-038/041 era), NOT introduced here: every per-agent manager pins port 9223, so only the first agent to use the browser actually launches a managed Chrome; others fail to launch. Boot provisioning does **not** worsen this (goroutines only download). This needs its own ADR — investigated separately; tracked as the next follow-up.
- **Boot phones Google by default** (`googlechromelabs.github.io` + `storage.googleapis.com`, only when no working browser is present). Not telemetry (no usage data exfiltrated; SEC-24 governs *tool* egress, not the gateway's own fetch), but it can surprise airgapped/privacy-conscious operators. An opt-out (`tools.browser.preprovision`) is deferred — tracked issue.
- **CLI-only usage isn't boot-provisioned** (no gateway = no Preprovision); it resolves lazily. An `omnipus browser install` CLI was considered and deferred (operator decision 2026-07-14).
- **`Session()` takes no context** (pre-existing), so a browser tool call that wins the race against an in-flight boot download blocks for the download's duration regardless of the caller's deadline. Latency concern, not correctness; deferred.
- **Partial-download cleanup** is handled (`.part-*` temp removed on error; `EnsureChromium` removes the renamed zip on download failure; `findInstalledBinary` skips incomplete version dirs). A narrow `extractZip` mid-extract failure is the one theoretical poisoned-cache path (predates this ADR).

## Deferred (tracked)
Port-9223 multi-agent limit (own ADR); `tools.browser.preprovision` opt-out (issue); `omnipus browser install` CLI; `Session(ctx)` cancellation.
