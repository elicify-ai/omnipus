## 1. Executive summary

Forty-four findings: **7 CRITICAL, 18 MAJOR, 16 MINOR, 3 OBSERVATION.**

The direction changed twice and the document changed only forwards. Round 1's
findings were answered by *appending* — a corrections log, a D1.0a, a D1.1a–d,
a superseding D1.2 — while the sections those additions falsify were left
standing. The result is that the ADR's header, its reconciliation section
(D1.0), its comparison table, its Consequences section and its Alternatives
section all still describe the design as it stood two direction changes ago.
Three of the seven rows in the ADR's own §8 corrections log are still asserted
as true elsewhere in the same file, including one on **line 11**.

The pool — the largest-blast-radius change in the document — has **zero
acceptance criteria**, two of its own five "must decide" items undecided, a
sizing formula with three undefined terms whose headline number is derived from
an admitted placeholder, and a memory-pressure gate that does not exist on
macOS. Its own implementation spec, written the same day in the same worktree
and marked "Draft for implementation… all design questions are decided",
specifies the **opposite** cap policy: hard refusal plus a REST endpoint and a
close button, where D1.1c rules LRU eviction with "no error surface and no UI"
and says that REST path and button "are withdrawn".

And the ADR's own headline defect can still recur. Criterion 3b requires a
policy-denied agent to say "I am not permitted to see the browser" rather than
"there are no tabs". D1.5 puts that third state inside `ListTabs`.
`FilterToolsByPolicy` (`pkg/tools/compositor.go:436-439`) drops every
deny-verdict tool from the definitions sent to the model, so a denied agent
never calls `ListTabs` at all.

**Verdict: BLOCK.**

## 4. Test coverage assessment

§3 is the test plan, and after the direction change it covers roughly half the design.

**Untestable or wrongly placed as written**
- Criterion 3b (C205) — no change to `ListTabs` can satisfy it.
- Criterion 16 (M216) — asserts the absence of an error, not the presence of progress; it passes when nothing happens.
- Criteria 17 and 18 are D1 requirements under the D2 heading (m204).
- The ≤150 ms budget is not a criterion (m205).

**Missing entirely — the pool**
1. Cap reached, an evictable instance exists → whichever of eviction or refusal C204 settles on, plus the observable it produces.
2. Cap reached, **every** instance watched and busy → the ADR's soft overshoot fires exactly once and logs a WARN naming the cap and the workspace (M207 says the current wording permits unbounded growth; the test is what pins it).
3. Evicted workspace reopened → **still signed in** from its on-disk profile. This is the load-bearing claim that makes eviction acceptable and nothing tests it.
4. Thrash detection → k evict/reopen cycles in the window produce exactly one WARN naming the cap and the contending workspaces.
5. `kill -9` the gateway → next boot leaves zero orphan Chromes and zero stale markers (the D1 spec has this as its criterion 22; the ADR does not carry it).
6. **Second live gateway on the same `$OMNIPUS_HOME`** → the first gateway's Chromes survive (M213). This is the test that distinguishes "reconcile orphans" from "kill the neighbour".
7. Workspace deleted → its profile directory is gone from disk (D1.1d) and no other workspace's profile is touched.
8. Two cross-site tabs in one workspace occupy **distinct renderer processes** at the shipped `--renderer-process-limit` (C206).
9. G-2 itself: `chrome.tabCapture` succeeds against a second Chrome's default context, run with a receipt that cannot be satisfied by a skip (M204).

**Missing — D1/D2 interactions**
10. Boot with N workspaces and the warm defaults on → the ADR must first decide what should happen (M208), then assert it.
11. Upgrade from an install with the existing global profile → assert what the ADR decides in M215, whichever it is.
12. A delegated `Worker` turn calling `browser_upload_file` with no human attached → denied, not hung (M217).
13. An audit event that actually renders in Settings → Security → Audit Log with a non-dotted event name (M210).

**Regression surface the ADR still does not name.** Round 1 flagged that `d2_spike_test.go`, `stress_5agents_test.go`, `tab_adoption_e2e_test.go`, `shared_control_test.go` and `tools_control_test.go` encode the per-agent model. ## 6. Unasked questions

1. **Which document is authoritative — this ADR or `browser-workspace-ownership-spec.md`?** They specify opposite cap behaviour (C204), a different gate list (two vs three-or-four), a different metric for the sizing measurement (RSS vs PSS, M218), and a different set of operator-facing surfaces. The ADR does not say the spec exists; the spec says it folds the ADR in. Someone has to decide which one moved and record it.
2. **What is a workspace's browser profile path, and who owns the disk?** N profiles at `~/.omnipus/browser/profiles/<?>/` with browser caches inside them is unbounded disk growth on a pod whose root volume this project has already filled twice. No quota, no reaping of a deleted-then-recreated workspace's leftovers, no statement of the path scheme.
3. **What happens to an agent on two workspaces?** Round 1 asked this and it is still unanswered — and it is now sharper, because the answer selects a Chrome process, not just a context. The gateway resolves the panel by `agent_id` (M214), which for a two-workspace agent names two browsers.
4. **Does the pool's cap count instances or does it count the memory the formula budgets?** D1.1c counts instances ("cap of three"); D1.1b budgets bytes. A workspace with 4 heavy renderers and one with a blank tab are one instance each and differ by ~1 GB. If the cap is really a memory guard, counting instances is the wrong unit — the same mistake D1.1b spends two pages establishing about tabs.
5. **Who closes a browser when a workspace goes quiet?** Item 3 of "the pool must decide" (M203). Without it the cap fills with idle instances and eviction becomes the normal path rather than the exception, which changes every latency claim in D1.1c.
6. **Is the capture session per workspace or per viewer?** M209. It determines the renderer budget, whether two operators watching one workspace share a stream, and what `browser_attach` means after the re-key.
7. **What does the operator see when the pool is at capacity?** D1.1c rules "no error surface, no UI"; the spec ships a REST endpoint and a close button. Before C204 is resolved, nobody can say whether this product has a capacity concept the operator can perceive at all.
8. **What is the cap's default on a fresh install?** "No hardcoded default ships" (D1.1b) is not a default. Every install needs a number on first boot, before any measurement has been taken on that host.
9. **Does the ADR intend `browser_evaluate` to reach the shared workspace browser?** Jim holds it and Ray does not (`core.go:909-921` vs `:1052-1064`). Under D1.2, Jim's `browser_evaluate` now runs against a browser carrying the operator's logins for every site the workspace has visited. The ADR never revisits that grant against the new sharing model.
