# Grill-Spec Review — ADR-029 (Round 4)

**Reviewed document:** `docs/internal/architecture/ADR-029-channel-instance-workspace-binding.md`
**Review mode:** `structured-spec` (formal FR/NFR IDs, decision criteria, option analysis, confidence blocks — but not `plan-spec` BDD/traceability format)
**Reviewer stance:** Adversarial, read-only. Assumes the worst interpretation.
**Prior rounds:** R1 (3 CRITICAL + 8 MAJOR), R2 (1 CRITICAL + 4 MAJOR), R3 (0 CRITICAL + 6 MAJOR). This is R4.

---

## 1. Executive Summary

ADR-029 is a mature, unusually well-grounded architecture decision. Its `[FACT]` citations were spot-checked against source and **verify accurately** (factory count, `ChannelId` enum size 16 vs. `validChannelIDs` 14, `normalizeChannelMap` drop behaviour, `RouteInput`/`ResolvedRoute` shapes, `resolveMessageRoute` precedence, `channelCredKey` format, `Session.workspace_id` already present, UI `__none__`/`SmartSelect` idiom). The chosen direction (Option A) is sound and the drift-enforcement mechanism (NEW-1) is now concrete.

That said, this round found **1 CRITICAL** (a latent routing-correctness hole in the drift mechanism itself — the *disabled-workspace* / *unbound-mid-flight* case that neither of the two guarded sites covers), plus several MAJOR gaps concentrated in areas the ADR defers to plan-spec but which contain load-bearing decisions that will cause rework if wrong. There is also a **self-inflicted internal inconsistency**: the factory count, the entire subject of R3's MAJ-001 correction to "13", is still stated as "11" and "19" in three later sections.

**Findings by severity:** 1 CRITICAL · 7 MAJOR · 6 MINOR · 4 OBSERVATION.

**Verdict: REVISE.**

The CRITICAL is a genuine gap in the routing-correctness invariant that is the ADR's headline promise ("a bound instance provably cannot reach P7/global-default"). It is closable with a scoping clarification, not an architecture change — Option A still holds. The MAJORs are mostly "this deferral hides a decision" and internal-consistency defects.

| F-01 | **CRITICAL** | Incompleteness / Incorrectness | §6 D3 drift mechanism; §7 | **The "provably cannot reach global-default" invariant has an uncovered third escape path: a bound instance whose *workspace* is deleted/archived, or whose binding is *cleared* while messages are in flight.** The mechanism (D3) fires `Drop` only when the P0 identity agent is "deleted, disabled, or a worker." But if the workspace is deleted (MAJ-005 says workspace-delete "disables + unbinds" its instances) there is a window — and a config-desync path — where the instance still has a live `Identity.ID` pointing at a *still-valid* agent, yet the operator's intent ("this instance is no longer bound") is gone. In that state `BoundInstance` is computed from `WorkspaceID != "" && Identity.kind==agent`; if unbind clears `WorkspaceID` but leaves `Identity` (or vice versa — the ADR stores them "independently", O-1/§5), the two-field derivation of `BoundInstance` becomes **ambiguous** and can either (a) mis-classify a bound instance as unbound → silently reaches global-default (violates FR-6a), or (b) mis-classify an unbound instance as bound → drops legitimate traffic (violates NFR-1). The ADR never specifies the atomicity/ordering of clearing `WorkspaceID` vs. `Identity` on unbind/workspace-delete, nor which field is authoritative for `BoundInstance`. | Specify: (1) `BoundInstance` is derived from **one** authoritative field (`WorkspaceID != ""`), not the conjunction — `Identity` is the *mechanism*, `WorkspaceID` is the *intent*; (2) unbind and workspace-delete MUST clear `WorkspaceID` **and** `Identity` **atomically** (single `safeUpdateConfigJSON` transaction); (3) add a BDD scenario "workspace deleted while instance bound → instance disabled, `WorkspaceID` and `Identity` both cleared, subsequent inbound hits the unbound (default) path, not a drop and not a stale-bound misroute." Without this the headline invariant is unprovable. |

## 4. Test Coverage Assessment

The §9-step-3 BDD list is above-average for an ADR and covers the precedence matrix (explicit `agent_id` wins, handoff pin wins, P0 ordinary inbound, drift→reject, membership 422, unknown-workspace 404, empty-CoreTeam disabled-save, per-instance distinct sessions/creds/stores).

**Gaps (must be added before / during plan-spec):**
- **Negative security test** for InstanceID spoofing via the `instance_id` metadata fallback (F-06). This is the single highest-value missing test.
- **Workspace-lifecycle test**: workspace deleted while an instance is bound → clean unbind, no drop, no stale misroute (F-01).
- **Partial-cascade-failure test**: instance delete where store-dir removal fails after cred removal → idempotent re-run completes; no orphan (F-05).
- **Pre-existing-binding-shadow test**: instance with per-peer bindings becomes bound → shadowed bindings warned/rejected, not silently dead (F-03).
- **Concurrency test**: concurrent workspace-delete + instance-reconfigure (F-05) — the file-based store has no cross-file transaction.

The ADR correctly identifies the O-2 "config-read-only spike gives a false green" trap — this is the most important test-methodology insight in the doc and should be preserved verbatim into plan-spec.

## 6. Unasked Questions

1. **On unbind and workspace-delete, are `WorkspaceID` and `Identity` cleared atomically, and which one is authoritative for `BoundInstance`?** (Drives F-01 — the CRITICAL.)
2. **What happens to pre-existing per-peer/guild/team bindings when an instance becomes workspace-bound?** Silently shadowed by P0, or detected/warned/rejected? (F-03)
3. **What exactly does "disabled" mean in the drift trigger, and is the check gated so unbound channels are unaffected?** (F-04)
4. **If the enum-open or key-grammar decision is wrong post-ship, what is the containment?** (F-07 — the one-way doors have no described rollback.)
5. **Is the multi-step delete cascade (config + creds + store) idempotent and ordered, given no cross-file transactionality?** (F-05)
6. **Does adding `InstanceID` to the session key change the key shape for ALL existing single-instance channel sessions, or only multi-instance ones?** (F-12)
7. **Is the `instance_id` metadata fallback in `inboundInstanceID` a permanent spoofing surface, or is it removed once struct-field stamping lands?** (F-06)
8. **Which is the real WS-B lane size — 11, 13, or 19 factories?** (F-02 — the doc says all three.)

## Verdict

**REVISE**

One CRITICAL (F-01: the "cannot reach global-default" invariant has an uncovered workspace-delete/unbind-desync escape path, rooted in the two-field `BoundInstance` derivation) and seven MAJORs (internal factory-count contradiction, pre-existing-binding shadowing, "disabled" trigger ambiguity, cascade atomicity, InstanceID-spoofing enforcement gap, one-way-door rollback, fan-out over-partitioning). None require abandoning Option A — the architecture holds. They require tightening the drift-classification to a single authoritative field, resolving the numeric/API-code contradictions, and pulling three deferred decisions (binding-shadow, cascade atomicity, spoofing enforcement) from "plan-spec will handle it" into stated ADR positions, since each is a decision that causes rework if made wrong.
