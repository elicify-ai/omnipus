# Wave 0 Review — Round 1 — Silent Failure Hunter

**Scope:** `f6eccbcd..08690ff9` (`sendfile-fix`, Slice A / FR-031 — Contracts foundation)
**Reviewer role:** `silent-failure-hunter` (pr-review-toolkit)
**Review focus:** silent failures in error handling, inadequate fallback behavior, catch blocks that swallow errors, fallback logic that could mask real problems. Verify the generator's prior silent-failure shape (anonymous inline payload instead of pointer to named schema) is repaired and the catch is not masking OTHER silent failures. Verify the `llm-error.ts` refactor does not silently fall through to an undefined default.

## Findings

| ID | Severity | File:line | One-line | Fix |
|---|---|---|---|---|
| SFH-01 | **MAJOR** | `scripts/gen-asyncapi-go/main.go:419-438` (`matchingNamedInlineGoType`) | The matcher is greedy on a naming-convention heuristic: any property of a frame whose inline shape HAPPENS to match a sibling named schema `<OwnerWithoutFrame><PascalCase(propName)>` will be coerced to a pointer to the named type even if the spec author's intent was an inline-different-from-named duplicate. The only guard is `sameSchemaShape` — which is checked, but the heuristic silently fails to communicate the assumption to the spec author. | Add a comment AND a runtime check that the inline property is deliberately a "mirror of components.schemas.X" (e.g., a heuristic-detected guard fence: log a warning if `matchingNamedInlineGoType` matches and the schema author has not explicitly flagged the inline property as `x-mirror-of: <Name>`); OR explicit-list the (frame, propName, namedSchema) tuples the matcher is allowed to bridge, and require the rest to be inline. The current "any-shape-match" behavior is the new silent-failure shape. |
| SFH-02 | **MAJOR** | `scripts/gen-asyncapi-go/main.go:440-477` (`sameSchemaShape`) | The matcher does not compare `description`, `title`, or `default` values. Two schemas with identical structural shape but divergent `description` text are reported as matching — so a future spec author who updates the description in `ErrorPayload` but forgets the inline mirror will receive a *silent* GO-struct-generation success while the SPA-side Zod codegen (which reads the inline mirror) still uses the stale description in error messages. The generator can't surface this drift. | Either (a) extend `sameSchemaShape` to compare `description` and `title` strings and fail the match on divergence, or (b) add a CI lint step that requires `description`/`title` text parity between each inline mirror and its named source. |
| SFH-03 | **MAJOR** | `scripts/gen-asyncapi-go/main.go:100, 161-162` (`schema.additionalProps`) + `main.go:447` (compared in `sameSchemaShape`) | `additionalProperties` is stored as a `bool` (only the JSON-schema-true form is captured). Two schemas with `additionalProperties: { type: "string" }` vs `additionalProperties: { type: "integer" }` BOTH store `additionalProps: true` and `sameSchemaShape` returns **true** — silently collapsing a real wire-type divergence into a single pointer. The current `contracts/asyncapi.yaml` and `contracts/components/schemas/MediaLibraryEntry.yaml`/`MediaAttachmentRequest.yaml` use `additionalProperties: false` (so unaffected), but the new Slice A schemas are the ONLY ones with this attribute; the failure mode is dormant, not absent. | Extend `schema` to capture the `additionalProperties` schema (or `false`/`true` sentinel) and recursively compare it in `sameSchemaShape`. Add a regression test for two structurally-similar schemas whose `additionalProperties` schemas differ. |
| SFH-04 | **MAJOR** | `contracts/asyncapi.yaml:1416-1430` (inline `ErrorPayload` mirror) + `:1880-1894` (inline `ReplayErrorPayload` mirror) | The repair only fixes the Go-side emission (`*ErrorPayload`). The SPA-side inline mirror is what the Zod codegen reads, and the spec author must keep TWO copies of each payload shape in sync (one in `components.schemas.ErrorPayload`, one inlined in `ErrorFrame.payload`). If the author updates `ErrorPayload` and forgets the inline mirror, the Go side reads the new schema, the SPA Zod validator reads the stale inline mirror, and a wire frame that passes Zod validation then fails its server-side decoder (or vice versa). The generator emits no warning when the inline mirror MIGHT be a mirror — the existence of a same-shaped named schema is the only signal. | Add a YAML anchor or `$ref` fallback for the inline mirror (the existing comment claims "Zod TDZ prohibits `$ref`", but a generator step that inlines the named schema's shape at codegen time would eliminate the entire class of drift). OR add a `scripts/check-asyncapi-mirrors.sh` CI step that asserts the inline-mirror shape equals the named-schema shape byte-for-byte. |
| SFH-05 | **MAJOR** | `src/lib/llm-error.ts:101-115` (`readLLMErrorFromFrame`) | The function returns the narrowed `LLMError` shape on a successful shape test, but the new `LLMError` type alias points at `GeneratedLLMError` which after `LLMError['code']` becomes a string literal union. If a future backend emits a NEW code (e.g., `provider_error`), the `code: le.code as LLMErrorCode` cast silently widens it to the existing union — the runtime SPA shows the FALLBACK copy (`codeToDisplay.unknown`) instead of surfacing "the backend emitted a code the SPA build doesn't know" as a *labeled* condition. The `codeToMessage` fallback is correct, but the SPA has no signal that an unrecognized code arrived (no telemetry, no toast, no metric). The hand-written `LLMErrorCode` enum (deleted in this refactor) used to be a *literal* in `codeToDisplay`'s `Record<LLMErrorCode, string>` — adding a new code would have failed TS compile. The new type alias preserves the compile-time check via `Record`, but the runtime fallback path is silent. | Add a `if (code && !(code in codeToDisplay))` metric / `console.warn` / `verboseDetail` byte in the `codeToMessage` fallback path so an unrecognized code is observable. The fallback-to-`unknown` is correct (never throw, never blank — that invariant is preserved), but the "what code did the backend actually send?" information is currently lost. |
| SFH-06 | **MINOR** | `src/lib/llm-error.ts:147` (`\ No newline at end of file`) | The refactor dropped the trailing newline. POSIX text-file convention requires one; some lint configs warn. Not a silent failure, but a tool-friction regression. | Add trailing newline. |
| SFH-07 | **MINOR** | `src/lib/llm-error.ts:6-8` (Removed aliases) | The removed header JSDoc documented the critical invariant: "if the spec adds a new code, regenerate the contract and add it here in the same PR." The new file deletes that comment. The TypeScript `Record<LLMErrorCode, string>` type still enforces the rule at compile time, but the human-readable WHY is gone. A future maintainer might wonder why `LLMErrorCode` is a `Generated*` alias and not a hand-maintained union. | Restore the comment (or rewrite it to point at the `Record<LLMErrorCode, string>` compile-time gate). |
| SFH-08 | **MINOR** | `src/lib/api/generated/asyncapi-types.ts:151-158` (SPA-side `ErrorFrame.payload`) | The SPA-side `ErrorFrame.payload` is an inline type `{ llm_error: LLMError; }` while the generated `ErrorPayload` interface (line 525) exists alongside it. The Go side uses `*ErrorPayload`. The SPA COULD use the named `ErrorPayload` for symmetry; the omission is a documentation drift hazard (a future maintainer adds a field to `LLMError` and updates `ErrorPayload` but forgets the inline mirror in `ErrorFrame`). The error is caught at compile by the `tsc` invariant `payload?: { llm_error: LLMError }` must equal `ErrorPayload`, but the lint doesn't enforce that. | Replace the inline `payload?: { llm_error: LLMError; }` with `payload?: ErrorPayload` (and `payload?: ReplayErrorPayload` for the replay frame). The Zod codegen has the TDZ constraint at the AsyncAPI level, but the TS-side type alias is free. |
| SFH-09 | **MINOR** | `scripts/gen-asyncapi-go/main_test.go:47-78` (only positive test) | The new test only covers the happy-path: ErrorFrame + ErrorPayload where the shapes match. There is no negative test: (a) what happens when the inline payload has a field the named schema lacks? (b) when the named schema has a field the inline lacks? (c) when the `required` map differs? (d) when the inline has `additionalProperties: true` and the named has `additionalProperties: false`? The current `sameSchemaShape` would correctly reject most of these, but the contract is untested. A future maintainer "simplifies" `sameSchemaShape` and breaks one of the rejection paths without a test catching it. | Add 4-5 negative tests covering the rejection cases the spec relies on. |
| SFH-10 | **OBS** | `scripts/gen-asyncapi-go/main.go:419` (no symmetric "always-inline" guard) | The matcher is `matchingNamedInlineGoType` (positive). There is no `matchingNamedInlineReject` log when a near-miss is detected (e.g., inline has extra field `x` the named lacks). A spec author who almost-mirrors a named schema will get a silently-emitted inline struct instead of a warning that they're 1 field away from a collision. | Add a `// TODO: log near-miss` or a debug-mode warning in production for maintainability. (Low priority — the silent inline fallback is the *correct* behavior, but observable drift is preferable to silent drift.) |

## Rejected candidates

- **The `sameSchemaShape` schema-doctrine of "structural equality, not semantic"** is the correct call for type generation; checking `description`/`title` would be over-reach. The drift risk is logged in SFH-02 as a CI-level concern, not a generator-level one.
- **The `codeToMessage` fallback to `codeToDisplay.unknown` on unrecognized codes** is the correct forward-compat behavior (never throw, never blank). The OBS-level concern in SFH-05 is that the "what code did the backend send?" information is lost — not that the fallback is wrong.
- **`generate`'s `format.Source` failure path** (line 73-79) writes the unformatted source to disk for debugging and exits nonzero. Not silent — preserves the failure.
- **`scripts/gen-contracts.sh` step 5** copies `contracts/components/schemas/*.yaml` to `pkg/gateway/inboundschemas/`. If the canonical source diverges the second copy gets stale, but the script is idempotent and re-runs cleanly on every CI build — not a silent failure.
- **`pkg/api/generated/contract_test.go::TestErrorFrame_PayloadOmitEmpty` and `TestReplayErrorFrame_PayloadOmitEmpty`** correctly catch the regression the repair is fixing. The test failure mode is loud (assert.NotContains on a literal substring), not silent.
- **`src/lib/llm-error.ts::isTypedLLMError`** (line 89) is a permissive shape guard (object + string `code` + string `message` + boolean `retryable`). It does NOT validate the full `LLMError` Zod schema, but the module-level comment (line 86-87) explicitly notes: "Zod already did that at the WS boundary." Not a silent failure — the comma is documented.
- **`getLLMErrorDisplay`'s omission of `detail` when `verboseChatEnabled` is false** is the documented cross-cutting ADR-051 §RD4-7 contract, not a swallowed error.

## Verdict

**REVISE — 0 CRIT / 5 MAJOR / 3 MINOR / 2 OBS.**

The generator repair is technically correct (the new `matchingNamedInlineGoType` produces the right `*ErrorPayload` pointer for the current `contracts/asyncapi.yaml`) and the contract tests will catch the regression. But the new matcher's safety depends on a silent invariant ("the inline mirror is the same as the named schema") that no CI gate enforces and no human-actionable warning surfaces. The `llm-error.ts` refactor is a quality improvement but loses two pieces of safety: the human-readable WHY (JSDoc) and the runtime observability of unrecognized codes (no metric / warn on the fallback path).

The 5 MAJORs are addressable in Wave 1 review round 1:
- SFH-01 (heuristic greed), SFH-02 (description drift), SFH-03 (additionalProps schema), SFH-04 (inline-mirror drift) belong to the generator/spec-authoring concern.
- SFH-05 (unrecognized-code observability) belongs to the SPA side and is independent of the generator.

The 3 MINORs (SFH-06..08) and 2 OBS (SFH-09..10) are stylistic / test-coverage tightenings that improve robustness but do not block Slice A from proceeding.
