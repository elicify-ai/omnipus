How an agent's mind is assembled · grounded in code

Context — what the model actually sees

Every turn, Omnipus builds the agent's system prompt by stacking a fixed sequence of layers — some universal (every agent gets them), some per-agent (its soul, files, skills, memory). Then, at send time, it wraps that prompt with the message array and a compact tool manifest. This page shows every element, where it comes from, and how it differs by agent type.

The whole picture · one diagram

Two assemblies: the system prompt, then the request

First the system prompt is assembled from layers (left). Then, at request time, that prompt becomes message [0], a tool manifest is injected at [1], and history + the user turn follow — alongside the always-callable tool defs (right).

Left: the system prompt is stacked from layers (blue = universal, gold = per-agent). Right: at send time it becomes msg[0], a manifest note is injected at msg[1], history + user follow, and the tools[] param carries the Full tier always + the loader.
The split that trips people up: visibility ≠ callability. The manifest note (msg[1]) makes ~60 lazy tools discoverable as names; only the 13 Full tools + the `tools` loader are callable defs from turn one. A lazy tool must be loaded (by name or search) before the model can invoke it — that is why an agent sometimes says it "can't" do something it is in fact permitted to do.

Drill-down · what's literally inside layers 1 & 2

Inside the universal layers — a table of contents draft proposal

The two layers every agent shares, expanded to the exact headings the code emits. Layer 1 is the environment preamble (envcontext.render); Layer 2 is identity + workspace + the general rules (getWorkspaceAndRules). They're byte-identical for every agent — only resolved values (paths, sandbox mode, agent name) differ.

Draft thesis (proposed change, not yet built). The environment preamble is the natural home for everything about the harness — it's the one block that's the same for every agent, every turn. Today it explains only paths · sandbox · network. The memory model and the tool system are equally universal harness facts, yet they're scattered (memory across 3 places, tool-loading only in an ephemeral turn-time note + a stale rule citing retired tools). The draft below folds Memory and Tools into ## Environment so an agent reads "how this harness works" once, coherently. Items tagged draft are proposed additions.

① ## Environment preamble universal

pkg/agent/envcontext/render.go · "new-office onboarding" — tells the agent where it can and cannot work. Redacted, capped at 2000 runes; emitted only when a provider is wired; fully suppressed when OMNIPUS_PENTEST_HIDE_SANDBOX=1.

  • ## Environment — intro: "You are running inside the Omnipus agent harness…"
  • ### Paths you can use
    • Workspace (your working directory): <path>
    • Omnipus home (framework data; read-only): <path>
  • ### Paths you cannot use
    • Everything outside the workspace — denied unless allow-listed
    • /dev/tty & other TTY devices — blocked
    • System paths (/etc · /usr · /root · $HOME outside ws) — denied
  • ### Sandbox & network
    • Sandbox: enforce | permissive | off | <unknown>
    • Network: outbound-allowed | outbound-denied
  • ### Memory draft · folded in
    • You have durable cross-turn memory (markdown on disk) — separate from this chat's history
    • Two rooms: Private (agent-only, follows you across workspaces) · Shared (workspace-wide, read in a workspace session)
    • Relevant memories are pre-loaded into your prompt; recall_memory(query[, room]) to search for more
    • Persist with remember(content, category[, room]); record reviewed lessons with run_retrospective(…)
    • Never write_file a memory file — always use remember
  • ### Tools draft · folded in
    • A few core tools are always callable; everything else loads on demand via the tools loader
    • tools{query:"what you need"} to search · tools{names:["exact_name"]} to load by name — then call the tool
    • This is also how you find connected MCP servers' tools — they're discovered and loaded the same way
    • If you don't see a tool you need, load it first — don't refuse or ask for approval just because it isn't visible
  • ### Active warnings — only if any are live (degraded boot, missing key…)

Read top-to-bottom this is the agent's orientation: where am I (env paths + sandbox) → who am I (identity) → what's around me (workspace, memory rooms, skills) → how must I behave (the 5 rules). Only after all of that does its individual SOUL (layer 3) begin.

The word "workspace" is now overloaded

v0.3 makes Workspace a top-level container (My Workspace + named workspaces — holds agents, tasks, memory, channels). But the prompt already used "workspace" to mean the agent's own directory. Two meanings, one word — and they appear three lines apart. The code keeps them as separate trees; only the prompt vocabulary lags.

Where it differs · by agent type

Same skeleton, different layer 3–6

Layers 1–2 are byte-identical for everyone. The personality, files, skills and memory (layers 3–6) are where a core base agent, a user's custom agent, and a delegation-only sub-agent diverge.

🏛️ Core base agent Mia · Jim · Ray · Ava

  • SOUL: compiled-in prompt via GetPrompt(id) — invisible, no SOUL.md on disk
  • Uses workspace-only identity (the compiled SOUL carries the persona)
  • Deny-default, least-privilege policy seeded per role
  • Per-agent skill allowlist; full memory rooms
  • A chat target with heartbeat & durable memory

🧑‍🎨 Custom agent user-made (Main)

  • SOUL: SOUL.md on disk (+ AGENT.md / USER.md / IDENTITY.md)
  • If a SOUL.md exists → workspace-only identity; if not → the full default identity block
  • Tools & skills per the policy you set in the Agents screen
  • Own workspace, own memory rooms, a chat target

⚙️ Sub-agent / Worker delegation-only

  • SOUL: compiled (Planner · Explorer · Researcher) or templated worker
  • Not a chat target — spawned only via delegation
  • Narrower toolset; no heartbeat, no own channel
  • Memory/recall surface trimmed to the delegated task
Same BuildSystemPrompt code path for all three — the branch is just "is there a compiled prompt for this id?" (core) → "is there a SOUL.md on disk?" (custom) → else default identity. Everything else (resources, skills, memory) is wired the same way and simply resolves to per-agent data.
The fourth input · tools, not prompt

Tools arrive on a separate channel — in three tiers

Tool definitions are not part of the system-prompt text; they ride the API tools[] parameter. To keep that payload small, the manifest optimisation (pkg/tools/manifest.go) splits every allowed tool into three tiers.

Full 13 · always sent

Sent as callable defs every turn — the high-frequency core:

read_file · write_file · edit_file · list_directory · exec · search_web · fetch_url · send_message · hand_off · return_to_default · remember · recall_memory · set_todos

Infra the loader

A single always-callable tool — tools — that drives the manifest. The agent calls tools{names:[…]} or tools{query:"…"} to unlock lazy tools for the next turn. Never appears in the manifest list itself.

Lazy ~60 · on demand

Every other allowed tool. Listed by name in the "# More tools (load before use)" note at msg[1], but not callable until loaded. This is the progressive-disclosure surface that keeps the prompt cheap.

The load gate is real. If a capability (e.g. create_workspace, spawn) is policy-allowed but sits in the Lazy tier, the model must load it first. A weaker model can confabulate "I need approval / I don't have that tool" instead of loading — a prompt/indirection issue, not a permission denial. Verify against the audit log, not the agent's narration.
Performance · why edits show up

Built once, cached, mtime-invalidated

The assembled prompt is cached per agent. It rebuilds automatically when any tracked source changes — a cheap stat() mtime check on SOUL.md / AGENT.md / USER.md / the memories dir / last-session.md / skill roots. Edit a SOUL.md and the next turn rebuilds; nothing else does.

✅ Triggers a rebuild

  • Editing SOUL.md / AGENT.md / USER.md / IDENTITY.md
  • A new memory written (memories dir mtime bumps)
  • A new / changed skill in any skill root
  • A new last-session.md

♻️ Stays cached

  • Same files, same mtimes → served from cache (read-lock fast path)
  • Concurrent turns double-check under write-lock — no duplicate builds
  • Compiled core prompts never change at runtime → always cache-hit
