The base roster · four agents in the box

Four base agents ship by default — plus a Worker tier and three seeded specialists

There's one user: you. The roster (see blueprint / delegation) is base agents (Main) vs a sub-agent layer. Four base agents ship in the box as chat targets with their own heartbeat and durable memory. The sub-agent layer has two parts: a general-purpose Worker tier + three specialist subagents (Planner · Explorer · Researcher) that ship compiled-in in 0.1.0. Max is retired from base: automation is now a platform surface; optionally available as a marketplace pack. Further specialists and the Maker/creative set arrive via marketplace agent packs once the v0.2 installer is live.

⭐ Mia · the Assistant

Default. Your memory-rich personal front door — bound to My Workspace, runs your tasks · email · calendar, knows you across workspaces. owner = you.

🧭 Jim · the Orchestrator

Planner / PM. Supervises work across the tasks · blocked_by DAG and the delegation graph — Max-parallel fan-out, worktrees.

🔭 Ray · Scout

Research & summarize. Fans out reads, distils findings; the canonical delegation target for "go find out".

🛠️ Ava · the Builder

Agent & skill authoring (unchanged). Shapes new custom agents and skills from templates.

Beyond the base four: the sub-agent layer — the Worker tier (general-purpose execution) and the Planner · Explorer · Researcher specialist subagents (compiled-in defaults) — do the labour. Further specialists and the Maker/creative set arrive via marketplace agent packs (v0.2+). The split is base Main agents vs sub-agent workers/specialists; there is no fixed "5 cores".
Mia · your Assistant

The Assistant is yours — auto-provisioned, the ⭐ default

Mia is a base agent auto-provisioned for you at onboarding ("meet your Assistant" in My Workspace), seeded from a built-in template, then named and shaped by you. She's the ⭐ default chat target.

🤝 Yours, by ownership

  • A base agent you own (owner = you, attribution) — auto-provisioned at onboarding
  • Seeded from a built-in Assistant template, then fully yours — name · tone · model · tools
  • The ⭐ default agent on a fresh install

🏠 Bound to My Workspace

  • Bound to your My Workspace; runs your email · calendar · tasks
  • The assistant binding = this agent owns your My Workspace (a pre-seeded workspace)
  • Wired to your delegated connections

🧠 Cross-workspace recall

  • Its agent-global private room spans your workspaces — it knows you for free
  • It also reads the shared rooms of the workspaces it works in
  • No special store: the two-room spec already gives this
The sub-agent layer · workers + specialists

Below the base agents: Worker tier + three seeded specialists

Sub-agents do the labour. They're not chat targets (the test-run button is the exception) — they're spawned by delegation. Two kinds: the general-purpose Worker (Subagent wire type) and the three compiled-in specialist subagents.

⚙️ Subagent characteristics (all sub-agents)

  • No heartbeat · no own connection · not chat targets (test-run button excepted)
  • Runs only via delegation — immediate (await/background) when invoked; no autonomous backlog
  • Narrow recall: the current workspace's shared room (+ its own private room)
  • Bounded delegation allowed: a specialist subagent may carry a depth ≥ 1 trust-set policy, letting it delegate further. The general-purpose Worker defaults to depth 0 (leaf).
  • Soul is optional. Effective prompt = soul.md (if any) + the task prompt from the caller.

🔌 Executor kind

  • native — runs in-process on the Omnipus agent loop (Subagent wire type)
  • external-cli — Claude Code · opencode · Codex as a child process (subagent_3p wire type); the CLI manages its own tools/skills/sandbox
  • future: remote-a2a — a remote agent over agent-to-agent
Three seeded specialists · compiled-in by default

🗂️ Planner

Deep decomposition. Produces the task DAG / workflow plan. Delegates to Explorer + Researcher (depth ≥ 1, trust-set policy) to gather context before planning. Invoked by Jim (Orchestrator).

🔎 Explorer

Internal-context exploration — files, memory. Depth-0 leaf. Delegated-to by Planner for local information gathering.

🌐 Researcher

External-source research. Depth-0 leaf. Delegated-to by Planner for web/external research. Ray (Scout) is the chat-facing research colleague; Researcher is the subagent Ray delegates to — no duplication.

Specialists ship compiled-in for 0.1.0 (no installer available yet). They become a marketplace pack once the v0.2 plugin installer exists, and the preinstalled copies graduate to that pack distribution. My Workspace is pre-seeded with the default team (4 base + Worker + Planner/Explorer/Researcher) plus default delegation edges.
Deferred to v0.2.0 — observable sub-agent sessions. A delegated sub-agent run should be a first-class, inspectable entry in the session history, with delegation lineage (parent_id · depth · owner) so the call-tree renders — including external-CLI child runs as their own session rather than text merged into the caller's transcript. In v0.1.0 a sub-agent run is folded into its caller's session (only task_create yields a discrete session); first-class sub-agent session visibility + lineage lands in v0.2.0.

Agents area · library + Workspace Teams

Agent personas are global — the Agents area is a reusable library

Agents are defined once and reused everywhere. The Agents area (sidebar global library) has two views:

📚 Agents (library)

  • All agent definitions — core + custom Main + Worker + specialists
  • Filter: [All | by workspace] to see which agents are members of a given workspace team
  • The two sidebar sections: BUILT-IN ROSTER (Mia · Jim · Ray · Ava — adaptive expand: visible when no custom Main agents exist; collapses once you have custom ones) and MAIN AGENTS (custom). Empty state: "No custom Main agents yet. Create one, or use a built-in below."

🏢 Workspace Teams

  • An index of every per-workspace team
  • Click a team → that workspace's delegation graph (same data as the workspace Team tab — one source of truth)
  • Add/remove agents from a team; drag to connect delegation edges
Editing an agent is global. The existing AgentProfile slide-over is reused everywhere you see an agent (library · Workspace Teams · workspace Team tab). Edits apply to the one global definition and take effect everywhere the agent is used. A cue reminds you: "Editing Mia — applies everywhere she's used." Per-workspace agent overrides are out for 0.1.0 (revisit later if needed).

Only participation is per-workspace — team membership, delegation edges, memory room, session tags. The persona (soul, model, tools, skills) is global.
Agent form · unified create/edit

Main ≈ Subagent — one unified form with per-type differences

The create/edit form is the same structure for Main and Subagent — not separate wizards. subagent_3p (external CLI) is the most distinct.

Main (core + custom)

  • Full form: name · description (required) · soul · model+provider · fallback models · tools · skills · sandbox profile
  • Heartbeat — on/off · interval · HEARTBEAT.md (Main-only; implemented as a recurring-trigger task with surface: heartbeat; shown in agent profile, hidden from board/calendar)
  • Voice field — reserved, disabled in v0.1.0 (TTS → v0.2)
  • No inherit toggles — Main sets everything explicitly

Subagent (native)

  • Same form as Main, MINUS heartbeat + voice
  • PLUS inherit toggles on: model · fallback models · tools · skills · sandbox — each facet is either "Inherit from caller" (default) or set explicitly
  • Inherit vs explicit is set at creation time (by a user or by Ava); at runtime "inherit" resolves from the calling agent
  • description is required (for routing/disambiguation)
  • Bounded delegation: specialists carry a depth ≥ 1 + trust-set policy; Workers default to depth 0

subagent_3p (external CLI)

  • HIDES: tools · skills · sandbox — the external CLI manages its own isolation
  • ADDS: CLI executor config — cli (claude-code · codex · opencode) · cli_path · env_overrides · cli_args
  • model = the CLI's own (free-text; no provider picker)
  • No heartbeat · no voice
  • description required
The inherit facets for Subagents are: model · fallback models · tools · skills · sandbox. Inherit is the safe default — a subagent can't run less-confined than its caller unless explicitly configured. subagent_3p hides the sandbox entirely; the CLI process provides its own isolation.
Model · two fields

{model, provider} — explicit, consistent, unambiguous

The primary model is a two-field pair (model + provider) consistent with fallback models — no more single combined slug that can't resolve against the catalog.

Why two fields

  • Single slug (openrouter/google/gemini-2.5-flash) can't match the catalog entry (google/gemini-2.5-flash) → false "UNRESOLVED" warning
  • Explicit provider = unambiguous resolution at routing time; validation is simple
  • Consistent with fallback_models which already use {model, provider} — one shape everywhere

Model selector

  • Provider-headed sections even with a single provider
  • Models sorted within each group; groups in stable order
  • Warning only when the model genuinely isn't in the chosen provider's catalog — softer wording; no "calls will fail" copy
Heartbeat · the autonomous work loop

Per-agent heartbeat — Main agents only

A heartbeat is a recurring-trigger task in the unified task model, with surface: heartbeat — it uses the same trigger engine as all other scheduled work and is hidden from the board/calendar. Subagents have no heartbeat (they run only on delegation).

🔁 How it works

  • Each Main agent (core + custom) has its own on/off + interval + HEARTBEAT.md
  • On fire: the agent runs its HEARTBEAT.md as its task prompt — checks its backlog, decides what to pull
  • A task delegated to a Main agent lands in that agent's backlog (inbox) — it does NOT auto-start. The agent picks it up when heartbeat fires, per instructions in its HEARTBEAT.md
  • The seeded default HEARTBEAT.md for Main agents includes the backlog-check guidance

📋 Agent profile

  • Heartbeat on/off + interval shown in the agent profile (Main agents only)
  • The heartbeat task (surface: heartbeat) is shown in the agent profile — it renders as a compact schedule item, not a board card
  • Subagents: heartbeat controls are hidden entirely from their form
  • Heartbeat = the agent's autonomous work loop (pairs with the on_agent_idle trigger in v0.3)

Safety

High blast-radius — handled by existing gates

Delegated access

An agent acting with the user's Google creds is powerful. Calendar/email write actions sit behind the existing allow / ask / deny per-agent policy; reads (free/busy, triage) are low-risk.

Untrusted inbound

Inbound email is a command surface → sender allowlist + DMARC/SPF (not raw From). Same Rule-2 ownership gating already in place.

Isolation

The present gate is owner ownership — canAccess (#406, rest_projects.go:75) — so an agent only reaches data in workspaces it owns. Per-workspace kernel isolation is the target (the sandbox-redesign design, unimplemented); today isolation is per-agent-workspace, not per-workspace.
