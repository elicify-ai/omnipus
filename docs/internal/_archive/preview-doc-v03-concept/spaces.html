Overview / Workspaces
The structural foundation

Workspaces

A Workspace is a project — everything to deliver it lives inside: tasks, team, memory, sessions, settings. One pre-seeded default (My Workspace), named workspaces for real work. The sidebar switcher picks the active workspace; chat is its front view, not a global front door. No abstract "spaces", no mode switcher. (Channels & Connections have their own page →)

Workspace = project, not instance

One workspace, one project — everything inside it

A Workspace is a project container — not an active "instance" or a scope filter. Everything needed to deliver the project lives inside it: its tasks, its team of agents, its shared memory room, its sessions. Picking a workspace in the sidebar sets the entire context (chat, tasks, memory, team). You never pick a separate "scope" — context is simply which workspace you've selected.

Pick a workspace in the sidebar → you enter it on the Chat tab. The workspace is the project; its team, tasks, memory, and sessions are all scoped to it.

What stays per-workspace

  • Team — which agents are on this project (their membership, not their definition)
  • Delegation graph — the edges (who can delegate to whom, with what modes/depth) within the team
  • Workspace memory room — the shared room all team agents read/write here
  • Tasks — the board, list, graph, and calendar views; every task carries a workspace_id
  • Sessions — tagged with this workspace; "this project's conversations" is a filtered view

What stays global (reusable library)

  • Agent personas — Mia, Jim, Ray, Ava, and every custom agent live in the global Agents library; editing an agent applies everywhere it is used
  • Connectors — channels and connections (Telegram, email, …) are globally managed
  • Skills & Tools — globally installed, available to all agents
  • Settings — gateway, security, and credentials are global
Naming goes all the way down: we rename project → workspace across code, contracts and storage too — today's project_id → workspace_id, rest_projects.go → rest_workspaces.go, Project.yaml → Workspace.yaml, users/<user>/projects/ → /workspaces/, and the memory "project room" → "workspace room". A v0.1.0 migration (contract-affecting, Constraint #8), done up front so nothing downstream carries the old name. (Pages cite today's project_* names as the current code.)
Tenancy, precisely: Omnipus is a single-user self-hosted app — one user (name set at onboarding), one password. No multi-user, no RBAC roles, no tenancy. Sensitive settings (model/billing keys, channel setup, security, deletes) are protected by re-typing the same password — a sudo-style confirm, not a second credential or admin account. owner=username survives only as attribution ("you" vs which agent created something), never an access gate. Workspaces, agents, memory and tasks are simply yours — nothing is hidden or access-gated.
The workspace detail screen

Seven tabs — Chat is the default

Entering a workspace opens its Chat tab — chat-first, always. The other tabs give you the task views and the team graph. Every tab is scoped entirely to this workspace; there is no global task board or global team graph.

Entering a workspace always lands on Chat. Chat is not a global front door — it is the front view of the active workspace.

Chat default tab

The front view of the workspace. Agent picker shows only this workspace's team. Sessions are tagged with the workspace; the history panel is filtered to this workspace's conversations.

Board · List · Graph · Calendar task views

  • Board — kanban by the 7-state lifecycle (Inbox → Next → Planning → In Progress → Blocked → Done → Failed)
  • List — flat, filterable
  • Graph — the task DAG: tasks as nodes, blocked_by as dependency edges
  • Calendar — scheduled/recurring tasks by fire time

Team delegation graph

The per-workspace delegation graph. Nodes = agents on this project. [+ Add agent] / remove = add/remove a node = team membership. Edges = delegation (drag to connect; click edge → modes/depth). Managing the team and managing delegation are the same action in one view.

Two distinct graphs in a workspace — same visual idea, different contents: the Task DAG (tasks as nodes, dependencies as edges — the Graph tab) and the Team graph (agents as nodes, delegation as edges — the Team tab). They are separate views with separate data.

Settings workspace tab

Workspace properties — name, description, repository link, owner attribution, archive. Distinct from global Settings (gateway, security, credentials).

Sidebar reorganization

Workspaces are primary nav; libraries are global

The mental model: the sidebar = "switch project, or go to a global library." Per-workspace work (chat, tasks, team) lives inside the workspace. Global reusable assets (agent personas, connectors, skills, settings) stay in the sidebar.

The sidebar is reorganized: Workspaces is the primary nav list (My Workspace ⭐ + named + Archive). Global libraries (Agents, Connectors, Skills & Tools, Settings) stay below.

What moved

  • Chat → workspace Chat tab (no longer a top-level sidebar item)
  • Tasks / Board / Calendar → workspace Board / List / Graph / Calendar tabs
  • Automations → REMOVED (scheduling is now tasks with triggers; no separate screen)
  • Workspaces → promoted to the primary nav section at the top
  • Team → new workspace Team tab (delegation graph)

What stays global

  • Agents — the persona library + Workspace Teams index (see below)
  • Connectors — channels and connections
  • Skills & Tools — globally installed
  • Settings — gateway, security, credentials
Team tab — per-workspace delegation

The Team tab = the delegation graph

A workspace's Team tab is its delegation graph. Nodes are the agents on this project; edges are the delegation rules between them. Adding or removing an agent IS adding or removing a team member — and drawing or deleting an edge IS editing the delegation policy. You manage the team and the delegation in one view.

Team membership

  • [+ Add agent] pulls from the global Agents library and adds that agent to this workspace's team (adds a node to the graph)
  • Remove — removes the agent from this workspace's team (removes the node + its edges)
  • The agent's global persona is unchanged — only participation in this workspace changes
  • My Workspace is pre-seeded: Mia · Jim · Ray · Ava + Planner / Explorer / Researcher specialist subagents + default delegation edges

Delegation edges

  • Drag between two agent nodes → create a delegation edge
  • Click an edge → set modes (await / background / task) and depth
  • Delegation is per-workspace — the same agent can have different delegation rules in different workspaces
  • The delegation graph is owned by the workspace; the workspace Team tab and the Agents → "Workspace Teams" view show the same data (one source of truth)
Agent personas stay global. Adding Mia to a workspace does not copy her definition — it adds her as a member. Editing her profile (from the library, the Workspace Teams view, or the Team tab) applies everywhere she is used. A small cue clarifies this: "Editing Mia — applies everywhere she's used." Per-workspace agent overrides are out of scope for 0.1.0.

Agents area — two views

  • Agents (library) — all agent persona definitions; filter [All | by workspace] to see membership
  • Workspace Teams — an index of every per-workspace team; clicking a team opens that workspace's delegation graph — the same graph as the workspace Team tab

Editing an agent is available from everywhere you see one (library · Workspace Teams · workspace Team tab) and reuses the existing AgentProfile slide-over panel — no new component.

Memory model

Sessions are tagged, not partitioned

Sessions are stored per-agent and tagged with a workspace_id — they are not moved or copied into the workspace. "This project's conversations" is a filtered view, not a separate store. A session can carry more than one workspace tag if a conversation spans projects.

Sessions

  • Stored per-agent (agents/<id>/sessions/) + tagged with workspace_id
  • SessionMeta.WorkspaceID already exists in the codebase — no re-keying needed
  • The chat history panel in a workspace filters by the active workspace tag
  • Per-project continuity: resuming a workspace picks the last session tagged with that workspace (so an agent resumes "where I left off on this project")
  • A session can carry >1 workspace tag if a conversation genuinely spans projects; the task Jim creates goes to its own workspace_id independent of the chat

Memory rooms

  • Workspace memory room — the shared room all team agents read/write (scoped to this workspace; lives at workspaces/<id>/.omnipus/)
  • Agent's private cross-workspace bank — memories saved with remember(scope=private) go to agents/<id>/.omnipus/ and are read in every workspace
  • Recall = current workspace room + agent's private bank. Mia additionally wide-reads all owned workspace rooms
  • Agent personas stay global; only the workspace room (shared) and the private bank (agent-wide) carry per-workspace memory
Filesystem · sandbox · prompt engine

An agent works inside the Workspace draft to-be · needs ADR

Today (v0.1.0) the concept and the code disagree: an agent's files, exec cwd and sandbox root all live in its own agents/<id>/ dir (FUNC-11), and the Workspace only owns tasks + shared memory. The Workspaces concept says the opposite — an agent always works in a Workspace. This draft realigns the folder structure, the sandbox root, and the prompt engine to the concept. Behavioural change — not just naming; gated behind an ADR.

The contradiction we're fixing. write_file · exec · edit_file are built with one fixed base dir = agents/<id>/ (instance.go). The per-turn workspace_id is threaded only into tasks / todos / shared-memory — never into the file tools. So an agent never actually cds into the Workspace it's acting in. The word "workspace" in the prompt today means the agent's own dir — the legacy meaning, which collides with the container.

Folder structure — as-is → to-be

AS-IS (v0.1.0) — agent works in its own dir
$OMNIPUS_HOME/ ├─ agents/<id>/ ← agent works HERE │ ├─ files · exec cwd · scratch │ ├─ skills/ │ ├─ sessions/ │ └─ .omnipus/memories/ private └─ workspaces/<ws_id>/ ← only bookkeeping ├─ <ws_id>.json record └─ .omnipus/memories/ shared
TO-BE — agent works in the Workspace
$OMNIPUS_HOME/ ├─ agents/<id>/ ← identity + private bank only │ ├─ SOUL.md persona (global ✓ stays) │ ├─ sessions/ (tagged by workspace_id) │ └─ .omnipus/memories/ private ✓ stays └─ workspaces/<ws_id>/ ← agent WORKS here ├─ <project files> write_file · exec cwd ├─ AGENT.md Project Instructions (Settings tab) ├─ tasks/ todos/ calendar └─ .omnipus/memories/ shared skills are NOT here — global registry (below): ~/.omnipus/skills/ global registry (+ ClawHub) <builtin>/skills/ shipped → per-agent allowlist (FR-9.4)

The agent's agents/<id>/ dir shrinks to what genuinely belongs to the agent across all Workspaces: its persona/config, its sessions (already tagged by workspace_id), and its private cross-workspace memory. Everything that is work moves into the Workspace.

Skills stay a global registry — not per-Workspace. Today skills load from three roots (skills/loader.go): builtin (<cwd>/skills/, shipped) + global (~/.omnipus/skills/, incl. ClawHub) + a per-agent overlay (agents/<id>/skills/). Access is governed by a per-agent allowlist (WithSkillAllowlist, FR-9.4, default-DENY) — the prompt's # Skills summary is filtered to just what each agent may use, exactly the selective-access model used for tools. So this redesign keeps skills global + allowlisted; it does not introduce a per-Workspace skill store. (Open option for the ADR: if the per-agent skills overlay re-points at the Workspace as a side effect of re-rooting, "skills available in this Workspace" could become an opt-in — but that's a deliberate choice, not today's behaviour.)

🛡️ Sandbox follows the Workspace

  • Writable root = the active Workspace — workspaces/<ws_id>/. Landlock/seccomp grant write there, not in a per-agent dir
  • The agent's private memory dir (agents/<id>/.omnipus/) is allow-listed as a second writable path — so private recall keeps working without widening the sandbox
  • Cross-workspace isolation — acting in Workspace A, the kernel denies reads/writes to Workspace B's tree. Switching Workspaces re-scopes the sandbox for the next turn
  • Sandbox is re-derived per turn from workspace_id (same signal that already routes tasks + shared memory)

🧩 Prompt engine — Workspace Project Instructions one field · Settings tab

  • A single Workspace-level instruction block (the Workspace's AGENT.md) — not per-agent. Like a project CLAUDE.md
  • Edited in the existing Workspace → Settings tab as "Workspace / Project Instructions" — one textarea, no new editor
  • Injected as a context layer for every agent acting in the Workspace; absent → nothing added (zero overhead)
  • The agent's persona (SOUL.md) stays global; the Workspace adds "how we work on this project" on top. See the Context Builder layer model

Net effect. "An agent works in a Workspace" becomes literally true: its files, sandbox, shared memory, tasks and per-Workspace AGENT.md are all the Workspace it's in; only its persona (SOUL) and private memory follow the agent across Workspaces. The prompt can then honestly say "You are working in Workspace <name>" — no collision left. Scope/ordering: this is a structural change (folder move + sandbox re-rooting + relocating AGENT.md) — it belongs to the Workspaces redesign and needs its own ADR + migration, not the v0.1.0 stabilization line.
Why this is the simple version. Because the Workspace instruction is one block for the whole Workspace (not a per-agent override), the hard questions vanish: no per-agent keying, no per-field merge policy. It's additive — appended as a context layer like a project CLAUDE.md, on top of each agent's global persona. An agent in a Workspace with no instructions behaves exactly as today. Agents stay global; only the Workspace gains a setting.
Impact assessment · code-grounded

What this change actually touches

Mapped against the live code (feat/0.1.0-uat-fixes). Verdict: feasible, but a structural multi-layer change with one hard kernel constraint and a new frontend axis. Not a v0.1.0 item — its own ADR + phased migration.

The crux — one sentence. Today everything is bound once, at agent construction, to a fixed root: the file/exec tools, the sandbox policy, the ContextBuilder + its prompt cache. The proposal needs them per-turn, following workspace_id. Exactly one thing in the codebase already does that correctly — memory's SetWorkspaceID swaps the shared room per turn under a lock. That is the template every other layer has to copy.

LayerKey touchpoints (today)What has to changeEffort / risk
Filesystem resolveAgentWorkspace · agents/<id>/ tree Move working files → workspaces/<ws_id>/; keep sessions + private memory in agents/<id>/; one-time migration (no framework for this today) medium
Backend engine instance.go:149-162 (6 file/exec tools) · loop.go wireExecToolDeps Tools store the root as an immutable field — must resolve workspace at Execute-time from context (the WithWorkspaceID signal already exists, just unused by file tools) high
Sandbox loop.go:~1089 SandboxPolicy · Landlock backend Landlock is one-shot & process-global — can't re-root per turn at the kernel. See blocker ① critical
Context engine context.go (fixed cb.workspace + per-agent cache) · definition.go (single-root loader) Inject one Workspace instruction block per turn + a per-(agent, workspace) cache key. No merge policy (single additive block). See blocker ② medium
Frontend AgentProfile · WorkspaceTeamTab · api.ts · Agent.yaml One new instructions field on the Workspace type + a textarea in the existing Settings tab. No per-agent editor, no new endpoint. See below low
① Critical blocker — Landlock can't re-root per turn. The production sandbox calls landlock_restrict_self() once per process; the ruleset is immutable afterward. A per-turn writable root cannot be kernel-enforced. Options: (a) exec children stay pinned to a static root (weakens the "works in the Workspace" promise for exec); (b) spawn a fresh sandboxed child process per workspace-scoped exec; (c) per-turn enforcement only in the app-level fallback backend (degraded security). This is the one genuinely hard problem.
② Critical blocker — the prompt cache goes incoherent. One ContextBuilder per agent holds a fixed workspace + one cached prompt, shared across turns and sub-turns. Same agent in ws1 then ws2 returns the stale ws1 prompt — invalidation only watches agents/<id>/, never the active Workspace. Fix: key the cache per-(agent, workspace) and thread the active workspace through ~8 cb.workspace sites.
Frontend · the simple path

Edited in the Workspace → Settings tab that already exists

No per-agent override, no dual-mode editor. The Workspace detail already has a Settings tab (workspaces.$workspaceId.settings.tsx), and the Workspace record already carries name · description · core_team · repository. The per-Workspace instruction is just a new "Workspace / Project Instructions" textarea there — one field, one place, applied to every agent in the Workspace. Agents stay global.

✅ One textarea in Settings

  • Add a Project Instructions field to the existing Settings tab
  • Saved via the existing Workspace PUT — no new editor, no per-agent UI
  • The global Agents screen is untouched — AgentProfile stays exactly as is

📜 One new wire field

  • Add instructions to Workspace.yaml — the record is already the right home
  • Contract-first (#8): schema → regen Go + TS + Zod
  • No new endpoint — the Workspace GET/PUT already exist

🎯 What it deletes from the plan

  • No WorkspaceAgentOverride type · no per-agent endpoints
  • No dual-mode AgentProfile · no Team-tab routing change
  • Frontend effort: high → low
The simplification. Treating the per-Workspace instruction as a Workspace setting (not a per-agent AGENT.md override) removes the entire "global base vs workspace override" problem from the frontend AND the merge policy from the backend. The UI change is one field in a tab that already exists. The only hard work left is the backend re-rooting (blocker ①) and the workspace-aware prompt cache (blocker ②) — both independent of how the instruction is edited.

Suggested phasing

1

Per-turn root

Resolve file/exec workspace at Execute-time from workspace_id; sessions + private memory stay agent-scoped. Fallback backend first.

2

Context + cache

Inject the Workspace instruction as a context layer; per-(agent,workspace) cache key. Copy the SetWorkspaceID pattern. No merge policy.

3

Sandbox decision

ADR picks (a) static exec root, (b) per-exec child, or (c) fallback-only. The gating call.

4

Settings field

One instructions field on Workspace.yaml + a textarea in the existing Settings tab. Low effort, no new endpoint.

Bottom line. With the instruction simplified to a Workspace setting, the frontend is cheap and the AGENT.md merge policy disappears. What remains is genuinely backend: re-rooting file/exec per Workspace (blocker ① — the Landlock ceiling) and a workspace-aware prompt cache (blocker ②). Recommend an ADR that locks just the sandbox decision — everything else is now mechanical, and the existing per-turn workspace_id plumbing (memory/tasks/todos already ride it) means the signal is already there.
The pre-seeded default

My Workspace ⭐

My Workspace is the one pre-seeded, delete-protected default. It is the Assistant's home and the app default front door (My Workspace → Chat → Mia). It comes with a pre-seeded team and default delegation edges.

Pre-seeded team

  • Mia (Assistant ⭐) — your primary chat colleague; bound to My Workspace; can recall across all your workspace rooms
  • Jim (Orchestrator) · Ray (Scout) · Ava (Builder) — the other three base agents
  • Planner · Explorer · Researcher — specialist subagents, seeded by default; Planner delegates to Explorer + Researcher; Jim delegates to Planner
  • Default delegation edges are seeded from each agent's role; new workspaces seed edges on agent add

Special properties

  • The only workspace that cannot be deleted
  • The Assistant's email account (if configured) lives here; email is a tool operated in My Workspace
  • Mia can additionally wide-read all your workspace memory rooms (cross-workspace recall); other agents are scoped to their current workspace
  • Named workspaces for real projects ("Acme", "Q3 Launch") work exactly the same way — My Workspace is just the default, not structurally special
